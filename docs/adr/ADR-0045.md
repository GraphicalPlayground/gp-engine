# ADR-0045: Intrusive Reference-Counted Smart Pointers and Bit-Packed Atomic RHI Lifecycle State

> Establishes `gp::RefCountedPtr<T, Policy>` as an 8-byte, zero-control-block intrusive smart
> pointer paired with `IntrusiveRefCounted<Derived, ThreadSafety>` and a 32-bit bit-packed atomic
> lifecycle counter (`AtomicRefStateCounter`: 30-bit reference count + `MarkedForDelete` and
> `Deleting` state flags). This architecture eliminates external control-block heap allocations,
> guarantees single-register passing across dynamic RHI module boundaries, prevents ABA resurrection
> races during multi-threaded deferred GPU resource deletion, and supports custom policy binding for
> native COM interfaces (`ID3D12Resource`, `IDXGISwapChain`).

![Accepted][badge-accepted]

## Context

In a multi-threaded Rendering Hardware Interface (`gp::rhi`, [ADR-0002](./ADR-0002.md)), GPU
resources—including buffers (`RHIBuffer`), textures (`RHITexture`), shader views
(`RHIShaderResourceView`), and pipeline states (`RHIGraphicsPipelineState`)—are shared concurrently
across the Game Thread, Render Thread, async asset streaming jobs, and RHI command compilation
workers.

Using a non-intrusive control-block smart pointer (such as `std::shared_ptr<T>` or `gp::SharedPtr<T>`)
to manage RHI and low-level engine resources introduces four severe architectural failure modes:

### 1. Fat-Pointer Register Pressure and Control-Block Heap Churn

A non-intrusive shared pointer stores two 64-bit pointers (`{ T* m_ptr, ControlBlock* m_control }` =
16 bytes), doubling the memory footprint of every descriptor table, draw packet, and resource array
while spilling across register pairs on x86-64 and ARM64 calling conventions. Worse, constructing a
shared pointer from a raw pointer allocates a separate heap control block, fragmenting memory and
placing the reference counter on a distant cache line from the resource's virtual table and
metadata.

### 2. Unsafe Raw-Pointer Round-Tripping Across Dynamic Module Boundaries

Because `gp::rhi` loads backend implementations (`d3d12`, `vulkan`, `metal`) as dynamic shared
libraries ([ADR-0002](./ADR-0002.md)), internal command contexts and low-level C APIs frequently
pass raw `RHIResource*` pointers for zero-cost binding. Re-wrapping a raw pointer into a
control-block smart pointer without `enable_shared_from_this` creates a second independent control
block, guaranteeing a double-free crash.

### 3. Deferred GPU Deletion and Multi-Threaded ABA Resurrection Races

When the last CPU reference to an `RHIBuffer` or `RHITexture` is released (`refCount: 1 -> 0`) on
the Game or Render Thread, the resource **cannot** be immediately destroyed (`delete this`) if an
in-flight GPU command list is still reading its VRAM allocation. Instead, the resource must
intercept the zero-reference transition and enqueue itself into a frame-fenced RHI **Deferred
Deletion Queue**.

If the intrusive counter is a naive integer (`Atomic<UInt32>`), a hazardous multi-threaded race
emerges while the resource sits in the pending-delete queue awaiting GPU fence completion:

- **Double-Enqueue Corruption:** If a transient cache or lookup table briefly increments and
  decrements the resource (`0 -> 1 -> 0`) while it is already queued for deferred deletion, the
  resource is pushed into the deletion queue a **second time**, causing a double-free when the GPU
  fence retires.
- **Unprotected Destruction Tearing:** Once the RHI deletion queue begins executing the resource's
  physical destructor, any concurrent lookup attempting to resurrect the pointer causes a
  use-after-free crash unless the counter word itself atomically encodes a terminal `Deleting`
  state.

### 4. Redundant Smart Pointer Wrappers for Platform COM Objects

In the Direct3D 12 and DXGI backends (`ID3D12Device`, `ID3D12Resource`, `IDXGISwapChain4`), native
OS interfaces already embed an intrusive reference count via `IUnknown::AddRef()` and
`IUnknown::Release()`. Hardcoding `RefCountedPtr<T>` to a single base class forces backend code to
pull in Windows-specific `Microsoft::WRL::ComPtr` headers instead of using a unified engine pointer.

## Decision

We decompose the intrusive reference-counting subsystem into granular, role-specific headers under
`source/runtime/core/public/memory/pointers/`, governed by C++23 concepts (`IsRefCountPolicy`,
`IsRefCounted`) and backed by `gp::thread::Atomic<gp::UInt32>` ([ADR-0024](./ADR-0024.md)).

### 1. Bit-Packed Atomic Lifecycle State Word (`AtomicRefStateCounter`)

Inspired by Unreal Engine 5's `FRHIResource::FAtomicFlags` and Frostbite/Decima deferred resource
retirement queues, `AtomicRefStateCounter` packs both the reference count and two lifecycle state
bits into a single 32-bit lock-free `gp::thread::Atomic<gp::UInt32>` word:

<!-- markdownlint-disable MD013 -->
```text
 31         30         29                                                  0
+----------+----------+-----------------------------------------------------+
| Deleting | Marked   |                  Reference Count                    |
|  (1 bit) | ForDelete|                     (30 bits)                       |
|  0x8000  |  (1 bit) |            Max: 1,073,741,823 references            |
|   0000   |  0x4000  |                    Mask: 0x3FFFFFFF                 |
|          |   0000   |                                                     |
+----------+----------+-----------------------------------------------------+
```
<!-- markdownlint-enable MD013 -->

- **Bits `[0..29]` (`kRefCountMask = 0x3FFFFFFFu`):** Unsigned 30-bit reference count supporting up
  to $1,073,741,823$ simultaneous references.
- **Bit `30` (`RefStateFlags::MarkedForDelete = 1u << 30u`):** Atomically latched when a resource
  transitions to 0 references and is enqueued into an RHI deferred deletion queue.
- **Bit `31` (`RefStateFlags::Deleting = 1u << 31u`):** Atomically latched when final physical
  destruction begins. Any attempt to `addRef()` while `Deleting` is set triggers an immediate
  assertion (`GP_ASSERT`), catching use-after-free resurrection bugs deterministically.

### 2. Memory-Ordering Protocol (`Relaxed` Increment, `Release` Decrement + Conditional `Acquire` Fence)

To minimize interconnect bus traffic on x86-64 and avoid redundant `ldaddal` / `dmb ish` barriers
on ARM64:

1. **`addRef()` Uses `MemoryOrder::Relaxed`:** Incrementing an existing reference counter requires
   no memory barrier because the caller already holds a valid reference to the object; no new payload
   mutations are published to other threads by creating an additional alias.
2. **`release()` Uses `MemoryOrder::Release` + Conditional `Acquire` Fence:** Non-final decrements
   (`N -> N - 1` where `N > 1`) only require `MemoryOrder::Release` so all prior reads and writes
   made through the released alias become visible to the eventual destroying thread. Only the final
   decrement (`1 -> 0`) executes `gp::thread::atomicThreadFence(MemoryOrder::Acquire)` prior to
   invoking the destructor or `onZeroReferences()`.
3. **Safe Cache Promotion (`tryAddRefIfNotDeleting()` and `tryAddRefIfLive()`):** RHI descriptor and
   PSO caches holding non-owning raw pointers can atomically promote them via compare-and-swap
   without racing against `tryBeginDeleting()`.

### 3. Explicit Ownership Tags (`AdoptRefTag` vs. `RetainRefTag`)

Raw pointer construction is a classic source of reference-count leaks when some objects initialize
their embedded counter to `0` and others initialize to `1` (or COM `Create*` functions return a
pre-incremented pointer). `gp-engine` eliminates this ambiguity with explicit tag dispatch:

- **Default Raw-Pointer Constructor & `gp::retainRef(T*)`:** Increments the reference count via
  `Policy::addRef(ptr)` (`RetainRefTag` / `gp::kRetainRef`).
- **`gp::adoptRef(T*)` (`AdoptRefTag` / `gp::kAdoptRef`):** Takes ownership of an already-referenced
  raw pointer **without** calling `Policy::addRef(ptr)`.
- **`IntrusiveRefCounted` Initial Count = `0`:** Newly constructed `IntrusiveRefCounted` objects
  initialize their counter to `0` at compile time (`constexpr`), and `makeRefCounted<T>(args...)`
  immediately increments or adopts the initial reference cleanly.

### 4. Policy-Based Customization (`DefaultRefCountPolicy<T>`) and `onZeroReferences()` Hook

`RefCountedPtr<T, Policy = DefaultRefCountPolicy<T>>` delegates reference operations to `Policy`:

```cpp
template <typename T>
struct DefaultRefCountPolicy
{
    static constexpr void addRef(T* ptr) noexcept { ptr->addRef(); }
    static constexpr void release(T* ptr) noexcept { ptr->release(); }
    static constexpr gp::UInt32 getRefCount(const T* ptr) noexcept { return ptr->getRefCount(); }
};
```

Inside `IntrusiveRefCounted<Derived, ThreadSafety>`, when `release()` decrements the reference count
from `1 -> 0`:

- If `Derived` defines a custom `onZeroReferences()` method (detected at compile time via a
  `requires` expression), `IntrusiveRefCounted` invokes `static_cast<Derived*>(this)->onZeroReferences()`.
  This allows `RHIResource` to call `markForDelete()` and push `this` into a GPU fence deletion
  queue or return the block to a `PoolAllocator` ([ADR-0042](./ADR-0042.md)) with **zero virtual
  call overhead**.
- Otherwise, `IntrusiveRefCounted` defaults to `delete static_cast<const Derived*>(this)`.

### Architectural Invariants

1. **Strict 8-Byte Pointer Footprint:** `static_assert(sizeof(RefCountedPtr<T, Policy>) == sizeof(T*))`
   and `static_assert(alignof(RefCountedPtr<T, Policy>) == alignof(T*))` must hold for all
   instantiations so `RefCountedPtr<T>` passes in a single CPU register.
2. **Self-Assignment and Aliasing Safety:** Copy assignment (`operator=`) and `reset(T*)` must
   always increment the incoming pointer's reference count (`addRef`) **before** decrementing the
   outgoing pointer's reference count (`release`), or guard against `m_ptr == rhs`, preventing
   premature self-destruction during aliased assignments.
3. **Move-Before-Delete Reentrancy Discipline:** Destructors, move assignments, and `reset()` must
   nullify or swap `m_ptr` into a local stack variable **before** invoking `Policy::release(oldPtr)`
   so any reentrant observer inspecting the smart pointer during destruction sees a clean state.
4. **Concept-Constrained Policies:** Every `RefCountedPtr<T, Policy>` method that manipulates the
   reference count is constrained by `gp::concepts::IsRefCounted<T, Policy>`, while allowing
   forward-declared incomplete types `T` in class member declarations (`RefCountedPtr<RHITexture> m_tex;`).
5. **Lock-Free Bit-Packed State Transitions:** `AtomicRefStateCounter` must never use software locks;
   all reference count and `MarkedForDelete` / `Deleting` transitions execute via lock-free
   `gp::thread::Atomic<gp::UInt32>` primitives.

## Alternatives Considered

### Option A: Use Non-Intrusive `gp::SharedPtr<T>` Across the RHI

Use a standard 16-byte external control-block shared pointer for `RHIResource` handles.

**Why rejected:** Doubles the size of every RHI resource handle from 8 bytes to 16 bytes, incurs an
extra heap allocation or control-block lookup per resource, breaks raw-pointer round-tripping across
dynamic RHI backend plugins, and cannot cleanly intercept `refCount == 0` inside the resource to
route live objects to a frame-fenced GPU deferred deletion queue.

### Option B: Plain Integer Intrusive Counter Without Lifecycle State Bits

Implement `IntrusiveRefCounted` with a plain 32-bit integer counter (`Atomic<UInt32>`) and no
bit-packed `MarkedForDelete` / `Deleting` flags.

**Why rejected:** While sufficient for immediate `delete this` destruction, a plain integer counter
cannot atomically distinguish between a newly constructed resource (`refCount == 0`), a resource
sitting in an RHI deferred deletion queue (`refCount == 0` + `MarkedForDelete`), and a resource
actively executing its physical destructor (`Deleting`). Packing the two lifecycle flags into the
top bits of the existing 32-bit atomic word costs zero additional bytes and eliminates multi-threaded
double-enqueue and resurrection races.

### Option C: Intrusive Dual-Counter Base (`StrongCount` + `WeakCount` in `T`)

Embed both a strong reference count and a weak tombstone counter inside every `IntrusiveRefCounted`
object, deferring `operator delete` until `WeakCount == 0`.

**Why rejected:** Adds 4 to 8 bytes to every RHI object, forces manual separation of destructor
execution (`~T()`) from memory deallocation, and leaves "zombie" memory blocks of `sizeof(T)`
allocated whenever a weak handle lingers. In AAA RHI architectures (Unreal, Frostbite, Decima),
hot-swappable resource indirection is handled via explicit RHI reference resources
(`RHITextureReference`) rather than weak pointers.

## Consequences

### Positive

- **Zero heap overhead and single-register ABI.** `RefCountedPtr<T>` has the exact size and
  alignment of a raw `T*` (8 bytes), fitting in a single CPU register and keeping the reference
  counter hot in the first cache line of `T`.
- **First-class RHI deferred deletion safety.** `AtomicRefStateCounter` and the CRTP
  `onZeroReferences()` hook allow `RHIResource` subclasses to atomically latch `MarkedForDelete`,
  enqueue themselves onto GPU fence queues, and optionally unmark/resurrect before physical
  destruction (`tryMarkForDelete()`, `unmarkForDelete()`, `beginDeleting()`).
- **Seamless COM and custom backend interoperability.** `RefCountedPtr<T, Policy>` wraps D3D12/DXGI
  interfaces (`ID3D12Resource`, `IDXGIAdapter4`) via a lightweight policy struct without pulling
  `<wrl/client.h>` into headers.
- **Deterministic thread-safety granularity.** Subsystems confined to a single thread can specify
  `RefCountThreadSafety::SingleThreaded` to use plain integer increments/decrements, while
  cross-thread RHI and asset objects default to `RefCountThreadSafety::ThreadSafe`.

### Negative

- **Intrusive inheritance requirement.** Types managed by `RefCountedPtr<T>` with the default policy
  must inherit from `IntrusiveRefCounted<T>` (or provide compatible `addRef()` / `release()` /
  `getRefCount()` methods). Third-party value types that cannot be modified and lack intrusive
  counters must use `UniquePtr<T>` or `SharedPtr<T>`.
- **30-bit reference count ceiling in `AtomicRefStateCounter`.** Reserving 2 bits for
  `MarkedForDelete` and `Deleting` caps the maximum simultaneous reference count of a single object
  at $1,073,741,823$ ($2^{30} - 1$), which is still orders of magnitude beyond any realistic engine
  workload and is guarded by debug assertions.
