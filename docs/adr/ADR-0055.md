# ADR-0055: Allocator-Aware Contiguous Dynamic Array (`gp::Vector`) and Trivial Relocatability

> Establishes `gp::container::Vector<T, Allocator>` (`gp::Vector`, `gp::InlineVector`,
> `gp::FixedVector`, `gp::ScratchVector`, `gp::PolymorphicVector`, `gp::AlignedVector`) as a
> 24-byte contiguous dynamic array integrating sized `gp::concepts::IsAllocator` arenas
> ([ADR-0042](./ADR-0042.md)), bitwise relocation (`gp::concepts::IsRelocatable`),
> uninitialized/defaulted construction fast-paths, and $O(1)$ unordered swap-erase semantics.

![Proposed][badge-proposed]

## Context

Contiguous dynamic arrays are the primary data structure in a data-oriented game engine. Almost
every frame-critical workload (frustum culling output, draw-call packet lists, physics contact
manifolds, skeletal pose palettes, and asset streaming buffers) depends on flat, cache-friendly
contiguous storage.

Implementing `gp::Vector<T, Allocator>` in `gp-engine` must resolve four concrete architectural
problems that make standard `std::vector` and legacy policy wrappers unsuitable for AAA runtime
systems:

### 1. ABI Instability, Hidden Heap Allocations, and the `resize()` Zero-Initialization Tax

Standard library `std::vector` implementations vary in layout and debug iterator machinery across
MSVC, Clang, and GCC, breaking ABI across dynamic RHI and plugin DLL boundaries
([ADR-0021](./ADR-0021.md)). Furthermore, `std::vector<T>::resize(n)` mandates value-initialization
(`memset` to zero for trivial types) before the caller can write into the buffer. When an I/O
thread reads a 64 MiB compressed pak chunk or a compute pass writes 100,000 skinned vertices into a
destination array, mandatory zero-initialization wastes memory bandwidth by writing every cache
line twice.

### 2. Element-by-Element Move Loops vs. Bitwise Relocatability and In-Place Arena Growth

When a C++ standard container outgrows its capacity, it allocates a new buffer and executes an
$O(N)$ loop invoking the move constructor on each new element and the destructor on each old
element. However, in a game engine, almost all runtime types (including math vectors, matrices,
handles, `gp::Name` ([ADR-0047](./ADR-0047.md)), `gp::RefCountedPtr` ([ADR-0045](./ADR-0045.md)),
and 24-byte SSO `gp::String` ([ADR-0046](./ADR-0046.md))) are bitwise relocatable
(`gp::concepts::IsRelocatable<T>`). Moving them via `reallocate` or a single `memmove` eliminates
per-element loop overhead and allows `LinearAllocator` ([ADR-0042](./ADR-0042.md)) to expand the
active top-of-bumper array in $O(1)$ time with zero bytes copied.

### 3. $O(N)$ Element Shifting During Unordered Removal

Erasing an element from the middle of a standard array shifts all subsequent elements left by one
slot, costing $O(N)$ memory writes. In many gameplay and rendering collections (active particle
lists, broadphase proxy arrays, pending async request tables), element order does not matter.
Forcing an $O(N)$ shift when an $O(1)$ tail-swap (`removeAtSwap` / `eraseSwap`) suffices wastes
frame budget when culling hundreds of items per tick.

### 4. Self-Aliasing Mutation Hazards

Callers frequently append or insert elements that reference the vector's own live storage, such as
`vec.pushBack(vec[0])`, `vec.insert(0, vec.back())`, or `vec.append(vec.view())`. If `pushBack` or
`insert` reallocates the backing buffer or shifts elements in place before reading the source
reference, the source pointer dangles or reads overwritten memory, causing silent corruption.

## Decision

We introduce `gp::container::Vector<T, Allocator>` in
`source/runtime/core/public/containers/arrays/Vector.hpp` and expose ergonomic engine aliases in
`namespace gp`.

```text
source/runtime/core/
  public/
    containers/
      ContainerForward.hpp       <-- Forward declarations for Vector, VectorView, StridedView,
                                     and gp::InlineVector / ScratchVector / FixedVector aliases
      arrays/
        Vector.hpp               <-- 24-byte gp::container::Vector<T, Allocator> implementation
  tests/
    containers/
      arrays/
        Vector.tests.cpp         <-- Comprehensive GoogleTest suite (lifecycle, arenas, SBO,
                                     relocatability, self-aliasing, swap-erase, and constexpr)
```

### 1. 24-Byte Direct-Pointer Layout and Engine Type Aliases

`gp::container::Vector<T, Allocator>` stores three 8-byte fields alongside a
`GP_NO_UNIQUE_ADDRESS` allocator instance:

```text
+-----------------------+-----------------------+-----------------------+
| T* m_data (8B)        | USize m_size (8B)     | USize m_capacity (8B) |
+-----------------------+-----------------------+-----------------------+
+ GP_NO_UNIQUE_ADDRESS Allocator m_allocator (0B for stateless allocators)
```

| Alias | Allocator (`ADR-0042`) | x64 Size | Primary Role |
| :--- | :--- | :--- | :--- |
| `gp::Vector<T>` | `DefaultAllocator` | `24 B` | General dynamic array |
| `gp::AlignedVector<T, A>` | `AlignedHeapAllocator<A>` | `24 B` | SIMD / cache-line array |
| `gp::ScratchVector<T>` | `ThreadScratchAllocator` | `24 B` | Per-thread scratch array |
| `gp::PolymorphicVector<T>` | `PolymorphicAllocator` | `32 B` | Runtime `IAllocator*` array |
| `gp::InlineVector<T, N>` | `InlineAllocator` | `24B+SBO` | Stack SBO + heap fallback |
| `gp::FixedVector<T, N>` | `FixedBufferAllocator` | `24B+SBO` | Stack SBO, no heap fallback |

Because `m_data` always points directly to the active buffer (whether on the heap, inside a
`LinearAllocator` slab, or inside an `InlineAllocator`'s embedded byte array), `operator[]`,
`data()`, and `begin()` execute with zero branch instructions.

### 2. Sized `IsAllocator` Reallocation and `IsRelocatable` Fast-Path

When `Vector` changes capacity from `m_capacity` to `newCapacity`, it computes
`oldBytes = m_capacity * sizeof(T)` and `newBytes = newCapacity * sizeof(T)` with alignment
`kAllocAlignment = max(alignof(T), kMinimumAlignment)`:

1. **Bitwise Relocatable Fast-Path (`gp::concepts::IsRelocatable<T>`):**
   Calls `m_allocator.reallocate(m_data, oldBytes, newBytes, kAllocAlignment)`.
   - For `LinearAllocator` and `ThreadScratchAllocator`, if `m_data` sits at the top of the bump
     cursor, the arena bumps `m_offset` in place in $O(1)$ time with zero memory copied.
   - For `InlineAllocator`, if `newBytes` fits within the inline buffer, it returns the inline
     pointer; if transitioning from inline to fallback heap, `InlineAllocator::reallocate`
     allocates from the fallback heap and copies `oldBytes` automatically.
2. **Non-Relocatable Path (`!gp::concepts::IsRelocatable<T>`):**
   Allocates `newData = m_allocator.allocate(newBytes, kAllocAlignment)`, moves and destroys the
   live `[0, m_size)` elements via `gp::memory::relocateConstructItems(newData, m_data, m_size)`,
   and frees the old block via `m_allocator.deallocate(m_data, oldBytes, kAllocAlignment)`.

### 3. Construction Modes and $O(1)$ Swap-Erase Ergonomics

To eliminate unnecessary CPU work in hot loops, `Vector` separates construction semantics and
removal ordering into explicit methods:

- **Resizing & Appending Modes:**
  - `resize(count)` / `resize(count, value)`: Value-initializes (`zeroMemory` for trivial types) or
    copy-constructs new elements.
  - `resizeDefaulted(count)` / `pushBackDefaulted()` / `addDefaulted(count)`: Uses
    `gp::memory::defaultConstructItems`. Invokes default constructors for non-trivial types and
    compiles to a zero-cost no-op for trivially constructible types.
  - `resizeUninitialized(count)` / `pushBackUninitialized()` / `addUninitialized(count)`: Advances
    `m_size` without constructing elements, leaving raw memory ready for immediate I/O or SIMD
    writes.
  - `addZeroed(count)`: Explicitly zeroes newly added raw storage via `gp::memory::zeroMemory`
    followed by default construction for non-trivial types.
- **Ordered ($O(N)$) vs. Unordered Swap ($O(1)$) Removal:**
  - **Ordered:** `erase`, `removeAt(index, count)`, `removeFirst(value)`, `removeAll(value)`, and
    `removeAllIf(predicate)` preserve relative element order by shifting trailing elements left.
  - **Unordered ($O(1)$ Swap-Erase):** `eraseSwap`, `removeAtSwap(index, count)`,
    `removeFirstSwap(value)`, `removeAllSwap(value)`, and `removeAllIfSwap(predicate)` destruct the
    target element(s) and relocate replacement element(s) from the tail of the vector in $O(1)$
    time.

### 4. Architectural Invariants

1. **Zero Allocation on Default Construction:** Default-constructing `gp::Vector` initializes
   `{ nullptr, 0, 0 }` and performs zero allocator calls.
2. **Sized Deallocation Contract:** Every `reallocate` and `deallocate` call passes exact
   `m_capacity * sizeof(T)` byte counts to satisfy `gp::concepts::IsAllocator`
   ([ADR-0042](./ADR-0042.md)).
3. **Self-Aliasing Safety:** `pushBack`, `insert`, and `append` detect when a source reference or
   range aliases `[m_data, m_data + m_size)` and preserve or adjust the source offset across
   reallocation and element shifts.
4. **Unified `gp::USize` Indexing:** `SizeType` is `gp::USize` and `DifferenceType` is `gp::ISize`,
   matching `gp::Array`, `gp::String`, `gp::StringView`, `gp::VectorView`, and `gp::StridedView`.
5. **Strict Bounds Checking:** All index and iterator accessors validate preconditions via
   `GP_ASSERT` in debug and development builds.

## Alternatives Considered

### Option A: 16-Byte Header with 32-Bit Size and Capacity (RAGE `atArray` / id Tech `idList` Model)

Store `T* m_data` (8 bytes) alongside 32-bit `UInt32 m_size` and `UInt32 m_capacity` to fit the
vector header in 16 bytes.

**Why rejected:** `gp::Array`, `gp::String`, `gp::StringView`, and `gp::memory::IsAllocator` all
standardize on 64-bit `gp::USize`. Using 32-bit counters in `gp::Vector` introduces narrowing casts
at every container boundary, requires maintaining duplicate `Vector` and `Vector64` classes, and
risks silent 32-bit overflow when loading multi-gigabyte asset blobs or voxel buffers.

### Option B: Container-Owned Storage Policies (Unreal Engine `TArray` `ForElementType` Model)

Embed `m_data` inside an allocator policy (`Allocator::ForElementType<T>`) rather than storing
`T* m_data` in `Vector`.

**Why rejected:** Rejected in [ADR-0042](./ADR-0042.md). Inverting ownership into container storage
policies prevents allocators from being instantiated as standalone arenas (`LinearAllocator`,
`StackAllocator`, `PoolAllocator`) and obscures the container's physical layout behind nested
template wrappers.

### Option C: Always-On Union Small Buffer Optimization (LLVM `SmallVector` / Folly Hybrid)

Use a 24-byte tagged union inside `gp::Vector<T>` to store elements inline when the total byte size
is $\le 22$ bytes, mirroring `BasicString`.

**Why rejected:** Unlike characters (`sizeof(char) == 1`), engine array elements (`Vector4f`,
`Matrix4x4f`, `Vertex`, `Transform`, `String`) usually have `sizeof(T) >= 16` or `alignof(T) >= 16`.
A 23-byte union fits zero or one such element while forcing a branch on every `data()` and
`operator[]` access. Providing `gp::InlineVector<T, N>` via `InlineAllocator` achieves explicit
stack capacity for any `T` and `N` while keeping `m_data` branchless.

## Consequences

### Positive

- **Branchless element access across all storage tiers.** `m_data[index]` compiles to a direct
  pointer load whether the vector is backed by the global heap, a `LinearAllocator`, or an
  `InlineVector<T, N>` stack buffer.
- **Unlocks $O(1)$ in-place resizing on linear arenas.** Combining `IsRelocatable<T>` with sized
  `m_allocator.reallocate(m_data, oldBytes, newBytes, align)` allows `LinearAllocator` and
  `ThreadScratchAllocator` to grow the active array without copying memory.
- **Eliminates redundant initialization in I/O and SIMD pipelines.** `resizeDefaulted` and
  `resizeUninitialized` avoid the `memset` double-write penalty of `std::vector::resize`.
- **Provides $O(1)$ unordered removal.** `eraseSwap`, `removeAtSwap`, and `removeAllIfSwap` let
  gameplay and rendering loops cull elements without $O(N)$ array shifts.

### Negative

- **24-byte base footprint on 64-bit targets.** Using 64-bit `gp::USize` for `m_size` and
  `m_capacity` costs 8 bytes more per `Vector` header than a 32-bit counter layout.
- **Caller responsibility for `resizeUninitialized`.** Elements added via `resizeUninitialized` or
  `pushBackUninitialized` contain indeterminate bytes until explicitly written by the caller.
