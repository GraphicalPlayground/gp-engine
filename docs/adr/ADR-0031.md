# ADR-0031: Dual Hardware Counters and Per-Thread High-Resolution Kernel Waitable Timers

> Calling Win32 `Sleep(1)` defaults to a 15.625ms OS scheduler quantum, while globally forcing
> `timeBeginPeriod(1)` degrades system-wide power efficiency and battery life across all running
> processes. Furthermore, OS monotonic clocks (`QueryPerformanceCounter`) have higher read latency
> (~15–25ns) than raw CPU cycle counters (`__rdtsc` ~1–3ns). `gp::platform::Time` abstracts both
> an invariant monotonic nanosecond clock (with a 1-cycle multiply fast-path when QPC runs at
> 10 MHz) and a raw CPU cycle counter (`cpuCycles()`) for micro-profiling, while implementing
> sub-millisecond thread sleep via thread-local `CREATE_WAITABLE_TIMER_HIGH_RESOLUTION` kernel
> objects on Windows and `clock_nanosleep` on POSIX.

![Proposed][badge-proposed]

## Context

Real-time interactive engines require deterministic frame timing, low-latency performance
counters, and predictable thread suspension. Pacing a game loop to 60 FPS, 120 FPS, or 144 FPS
requires releasing remaining frame budget to the operating system without oversleeping past
display v-blanks. On Windows platforms, standard timekeeping and thread synchronization APIs
present three major hardware and architectural challenges.

### The OS Scheduler Quantum Crisis

Standard Win32 `Sleep(1)` does not guarantee a 1-millisecond sleep duration. The default Windows
scheduler quantum operates on a timer interrupt interval of 15.625 milliseconds (64 ticks per
second). When a thread calls `Sleep(1)`, the kernel deschedules the thread until the next timer
tick occurs. Depending on when the call happens within the current quantum, the thread can
remain descheduled for any duration up to 15.625 milliseconds.

In a 60 FPS loop with a 16.66-millisecond budget, or a 144 FPS loop with a 6.94-millisecond
budget, an unexpected 15.6-millisecond suspension misses the presentation deadline entirely.
This descheduling causes visible dropped frames, stutter, and swapchain starvation.

### The Global timeBeginPeriod Antipattern

Historically, Windows game titles addressed this limitation by invoking `timeBeginPeriod(1)`.
This multimedia API requests a global kernel timer resolution of 1 millisecond. While this makes
`Sleep(1)` wake up near the 1-millisecond mark, the setting applies globally across all running
processes on the system.

Microsoft explicitly discourages `timeBeginPeriod(1)` in modern Windows environments. Forcing
the kernel interrupt to fire every millisecond prevents CPU cores from entering deep power-saving
C-states (such as C6 and C7). The constant interrupt handling forces processor packages to remain
in high-power states, accelerating battery drain on mobile devices and increasing system thermal
output. On handheld gaming PCs and laptops, this elevated power consumption induces thermal
throttling during long play sessions. Additionally, starting with Windows 10 version 2004, the OS
ignores `timeBeginPeriod` for background processes, leaving background threads subject to the
default 15.625-millisecond quantum.

### OS Clock Read Latency vs Micro-Profiling

Simulation clocks require monotonic time to compute frame deltas and schedule events. On Windows,
`QueryPerformanceCounter` (QPC) is the canonical monotonic source. Querying QPC incurs roughly
15 to 25 nanoseconds of overhead per call. This overhead stems from software dispatch layers,
synchronization barriers, or register read delays across external timer hardware such as the High
Precision Event Timer (HPET) or platform ACPI power management timers.

While 20 nanoseconds is negligible when sampled once per frame, it perturbs high-frequency
micro-profiling. Low-level engine primitives, including lock-free queue operations, job-stealing
schedulers, memory allocators, and ECS component queries, often execute in 15 to 50 nanoseconds.
Invoking QPC to profile these tight scopes multiplies measured durations and skews profiling data.

Hardware architectures offer raw cycle counters with 1 to 3 nanoseconds of read latency. On
x86 and x64 processors, the `__rdtsc` intrinsic queries the Time Stamp Counter directly from CPU
registers without a kernel transition. On ARM64 platforms, the virtual counter register
(`CNTVCT_EL0`, queried via `_ReadStatusReg`) provides similar register-level read performance.
Micro-profiling needs direct access to these cycle counters, while frame simulation needs
calibrated nanoseconds.

## Decision

We introduce `gp::platform::windows::Time` and expose it through `gp::platform::Time`,
implementing a dual-counter architecture with fast-path frequency scaling and thread-local
high-resolution waitable timers.

### Dual Hardware Counter Architecture

To address both frame-level simulation and fine-grained micro-profiling, the platform time
subsystem separates wall-clock monotonic timekeeping from processor cycle measurements:

1. **Monotonic Nanoseconds (`nowNanoseconds`):** Provides a continuous 64-bit nanosecond clock
   backed by `QueryPerformanceCounter`. Used for game clock simulation, frame pacing, duration
   arithmetic, and system timeouts.
2. **Raw CPU Cycles (`cpuCycles`):** Directly reads hardware counters (`__rdtsc` on x86/x64,
   `_ReadStatusReg(ARM64_CNTVCT)` on ARM64). Consumes only 1 to 3 nanoseconds per query,
   allowing lightweight profiling of short-lived algorithms without kernel overhead.

```cpp
namespace gp::platform::windows {

class GP_CORE_API Time : public gp::platform::generic::Time
{
public:
    Time() = delete;

    [[nodiscard]] static gp::UInt64 nowNanoseconds() noexcept;
    [[nodiscard]] static gp::UInt64 rawPerformanceCounter() noexcept;
    [[nodiscard]] static gp::UInt64 performanceFrequency() noexcept;
    [[nodiscard]] static gp::UInt64 cpuCycles() noexcept;
    [[nodiscard]] static gp::UInt64 utcTimestampMicroseconds() noexcept;
    [[nodiscard]] static DateTime localDateTime() noexcept;
    [[nodiscard]] static DateTime utcDateTime() noexcept;
    static void sleepNanoseconds(gp::UInt64 nanoseconds) noexcept;
};

} // namespace gp::platform::windows
```

### Invariant 10 MHz QPC Fast Path

Converting raw QPC ticks to nanoseconds typically requires 64-bit integer division:

$$\text{nanoseconds} = \frac{\text{ticks} \times 10^9}{\text{frequency}}$$

Because 64-bit integer division (`DIV` on x86-64) consumes 20 to 40 CPU cycles and naive
multiplication can overflow `UInt64` after 18.4 seconds of uptime, the engine applies an
optimized calculation strategy:

1. **10 MHz Fast Path:** On modern Windows 10 and Windows 11 hardware, the QPC frequency is
   fixed to the invariant TSC frequency of exactly 10 MHz ($10,000,000\text{ Hz}$), where each tick
   equals 100 nanoseconds. When `performanceFrequency() == 10'000'000ULL`, `nowNanoseconds()`
   computes `ticks * 100ULL`. This calculation executes as a single-cycle integer multiplication
   with no division.
2. **Overflow-Safe Fallback:** If running on legacy platforms or virtualized environments with an
   arbitrary frequency, the calculation decomposes into whole seconds and fractional remainder:

   <!-- markdownlint-disable MD013 -->
   $$\text{ns} = \left(\frac{\text{ticks}}{\text{freq}} \times 10^9\right) + \frac{(\text{ticks} \pmod{\text{freq}}) \times 10^9}{\text{freq}}$$
   <!-- markdownlint-enable MD013 -->

   This split prevents intermediate multiplication overflow for over 584 years of continuous
   uptime while preserving nanosecond accuracy.

```cpp
gp::UInt64 Time::nowNanoseconds() noexcept
{
    const gp::UInt64 ticks = rawPerformanceCounter();
    const gp::UInt64 freq = performanceFrequency();

    // Fast path: 10 MHz invariant timer on modern Windows (1 tick = 100ns)
    if (freq == detail::kStandardWin32QpcFrequency) [[likely]]
    {
        return ticks * 100ULL;
    }

    // Overflow-safe split multiplication for arbitrary frequencies
    const gp::UInt64 wholeSeconds = ticks / freq;
    const gp::UInt64 remainderTicks = ticks % freq;
    return (wholeSeconds * detail::kNanosecondsPerSecond) +
           ((remainderTicks * detail::kNanosecondsPerSecond) / freq);
}
```

### Per-Thread High-Resolution Waitable Timers

To achieve sub-millisecond sleeping without mutating global OS scheduler state, `sleepNanoseconds`
allocates a Windows waitable timer configured with `CREATE_WAITABLE_TIMER_HIGH_RESOLUTION`:

```cpp
struct ThreadLocalHighResTimer
{
    HANDLE timerHandle{ nullptr };

    ThreadLocalHighResTimer() noexcept
    {
        timerHandle = ::CreateWaitableTimerExW(
            nullptr, nullptr, CREATE_WAITABLE_TIMER_HIGH_RESOLUTION, TIMER_ALL_ACCESS);

        if (timerHandle == nullptr)
        {
            timerHandle = ::CreateWaitableTimerExW(nullptr, nullptr, 0, TIMER_ALL_ACCESS);
        }
    }

    ~ThreadLocalHighResTimer() noexcept
    {
        if (timerHandle != nullptr)
        {
            ::CloseHandle(timerHandle);
            timerHandle = nullptr;
        }
    }
};
```

These high-resolution waitable timers deliver approximately 0.5-millisecond precision on supported
hardware. To eliminate kernel object creation overhead during active frame loops, the timer handle
is stored in thread-local storage (`static thread_local`). The handle is allocated once per
thread on its first sleep invocation and closed automatically when the thread terminates.

```cpp
void Time::sleepNanoseconds(gp::UInt64 nanoseconds) noexcept
{
    if (nanoseconds == 0ULL) [[unlikely]]
    {
        return;
    }

    const gp::UInt64 intervals100Ns = nanoseconds / 100ULL;
    if (intervals100Ns == 0ULL)
    {
        return;
    }

    static thread_local detail::ThreadLocalHighResTimer s_tlsTimer{};
    if (s_tlsTimer.timerHandle != nullptr) [[likely]]
    {
        LARGE_INTEGER dueTime{};
        dueTime.QuadPart = -static_cast<LONGLONG>(intervals100Ns);

        if (::SetWaitableTimerEx(
                s_tlsTimer.timerHandle, &dueTime, 0, nullptr, nullptr, nullptr, 0) != FALSE)
        {
            (void)::WaitForSingleObject(s_tlsTimer.timerHandle, INFINITE);
            return;
        }
    }

    const DWORD sleepMs = static_cast<DWORD>(nanoseconds / 1'000'000ULL);
    if (sleepMs > 0u)
    {
        ::Sleep(sleepMs);
    }
}
```

### Pacing Mechanism Comparison

| Pacing Mechanism | Resolution | CPU Core Power | System-Wide Impact | Battery Impact | Wakeup Jitter |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Standard `Sleep(1)`** | ~15.625 ms | Low (sleeps core) | None | High efficiency | Extreme (up to 15.6 ms) |

| **Thread-Local High-Res Timer** | ~0.5 ms | Low (yields core) | None (per-thread object) | Preserves power states | Low (~0.1 to 0.5 ms) |

### Architectural Invariants

1. **Dual-Counter Specialization:** `nowNanoseconds()` serves simulation timing, frame pacing,
   and timeout evaluation. `cpuCycles()` is reserved for relative micro-benchmarks. Because raw
   cycle counters can diverge across CPU sockets or shift during dynamic voltage and frequency
   scaling (DVFS), cycle counts are never converted to absolute wall-clock timestamps.
2. **Invariant 10 MHz Fast Path with Safe Fallback:** `nowNanoseconds()` tests the cached QPC
   frequency against $10,000,000\text{ Hz}$. When matched, it performs a 1-cycle integer
   multiplication (`ticks * 100ULL`). For non-standard frequencies, it computes split quotient
   and remainder values to guarantee freedom from 64-bit overflow for over 584 years.
3. **Thread-Local Kernel Object Reuse:** Waitable timer handles are stored in thread-local
   storage via `ThreadLocalHighResTimer`. This guarantees zero kernel handle allocation or
   destruction overhead during active frame execution, while RAII cleans up the handle upon thread
   exit.
4. **Isolated Thread Pacing Without Global System Mutation:** Thread pacing relies on per-thread
   waitable timer handles and `WaitForSingleObject`. The engine strictly forbids calls to global
   state modifiers such as `timeBeginPeriod` or `timeEndPeriod`.

## Alternatives Considered

### Option A: Global `timeBeginPeriod(1)` with Win32 `Sleep(1)`

Invoke `timeBeginPeriod(1)` at startup to increase global timer interrupt frequency to 1 kHz,
followed by standard `Sleep(1)` calls during frame pacing.

**Why rejected:** This approach alters the timer resolution of the entire operating system,
preventing idle CPU cores across all applications from entering deep C-states. On portable
devices such as laptops and handheld gaming PCs, this practice depletes battery life and elevates
temperatures, triggering thermal throttling under continuous load. Furthermore, modern Windows
versions ignore `timeBeginPeriod` for background processes.

### Option B: Pure CPU Busy-Spinning (`_mm_pause` in a while-loop)

Achieve precise frame pacing by keeping the CPU core in a continuous loop executing `_mm_pause`
instructions until the target timestamp arrives.

**Why rejected:** Busy-spinning consumes 100% of an execution core, burning maximum power and
generating excessive heat on portable devices. It also starves lower-priority worker threads and
OS background tasks of CPU execution time, degrading overall system responsiveness.

### Option C: Windows Multimedia Timers (`timeSetEvent`)

Use legacy multimedia timer callbacks (`timeSetEvent` and `timeKillEvent`) to signal
synchronization events at 1-millisecond intervals.

**Why rejected:** The multimedia timer API is deprecated by Microsoft. It relies on internal
hidden worker threads spawned by `winmm.dll`, introducing thread synchronization overhead,
uncontrolled memory allocation, and unpredictable callback latency.

## Consequences

### Positive

- **Sub-millisecond frame pacing without global side effects.** Per-thread waitable timers
  provide roughly 0.5-millisecond sleep precision without altering the operating system
  interrupt period for background tasks or concurrent applications.
- **Single-cycle monotonic timestamp conversion.** The 10 MHz invariant QPC fast path replaces
  64-bit integer division with a single multiplication by 100 on modern Windows platforms.
- **Low-overhead micro-profiling.** Hardware cycle counters read processor registers in 1 to 3
  nanoseconds via `__rdtsc` and `CNTVCT_EL0`, allowing instrumentation of hot loops without
  kernel transition overhead.
- **Zero steady-state kernel handle allocations.** Storing waitable timer handles in
  thread-local storage reuses existing handles across frames and cleans up resources
  automatically on thread termination.

### Negative

- **Platform-dependent timer resolution.** High-resolution waitable timers require Windows 10
  version 1803 or newer. On legacy Windows builds, the implementation falls back to standard
  waitable timers with coarser resolution.
- **Kernel transition overhead on small delays.** Suspending a thread via `WaitForSingleObject`
  incurs context switch overhead of several microseconds, making waitable timers unsuitable for
  delays shorter than 100 microseconds.
- **Cycle counter drift across CPU cores.** Hardware cycle counters reflect core-local ticks
  rather than calibrated wall-clock time, requiring developers to restrict `cpuCycles()` to
  relative micro-benchmarks rather than cross-thread timestamping.
