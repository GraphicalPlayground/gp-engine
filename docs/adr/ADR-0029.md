# ADR-0029: Centralized Display Topology, Spatial Resolution, and Headless Virtual Display Fallback

> Scattering display enumeration, multi-monitor spatial math, and hotplug table management across
> individual OS backends duplicates complex geometry logic and causes nullptr crashes when the
> engine runs on headless CI runners or dedicated servers without a physical display. To guarantee
> a uniform contract, `gp::hal::generic::ApplicationBackend` centralizes the active display
> pointer table (`kMaxDisplays = 16`), implements deterministic spatial resolution
> (`getDisplayForPoint` via nearest clamped boundary distance and `getDisplayForRect` via maximum
> overlapping pixel area), and automatically provisions a synthetic `1920x1080 @ 60Hz` virtual
> primary display whenever zero physical monitors are detected.

![Proposed][badge-proposed]

## Context

Desktop environments commonly span multiple monitors arranged in non-uniform configurations.
These multi-display desktop layouts introduce two distinct architectural challenges:
discontinuous virtual desktop coordinates and missing hardware in headless execution environments.

### Multi-Monitor Coordinate Topology Challenges

On modern operating systems, multi-monitor setups form a discontinuous 2D coordinate space.
Displays differ in resolution, physical aspect ratio, refresh rate, orientation, and DPI
scaling. Furthermore, secondary monitors are often arranged with negative coordinate offsets
(for example, placing a screen to the left of or above the primary monitor).

Staggered monitor arrangements create dead zones, which are regions within the combined desktop
bounding box that contain no active pixel surface. Determining which monitor owns a given
window rectangle or cursor coordinate requires geometric calculations:

1. **Dead-Zone Ambiguity:** When the mouse pointer moves across the corner boundary of
   staggered displays, its coordinate can momentarily exist in an unmapped dead zone. The engine
   must resolve this coordinate to a valid display without returning null or snapping to an
   arbitrary default.
2. **Multi-Monitor Window Spanning:** When a window straddles the boundary between two displays,
   the engine must identify the monitor that contains the majority of the window's visible
   surface area to apply appropriate DPI scaling and refresh rate synchronization.
3. **Backend Logic Divergence:** If individual platform backends (Win32, SDL3, Cocoa, Wayland)
   implement spatial queries independently, subtle differences in coordinate rounding,
   boundary clamping, and tie-breaking produce inconsistent window placement across operating
   systems.

### The Headless Execution Null Pointer Hazard

Dedicated multiplayer game servers, continuous integration test runners (such as GitHub Actions
or GitLab CI), Docker containers, and cloud render workers frequently execute without an
attached physical monitor:

- On Linux, the `DISPLAY` and `WAYLAND_DISPLAY` environment variables are typically unset.
- On Windows Server, service processes run in Session 0, which lacks an interactive desktop.
- Cloud virtual machines often run without physical GPU display adapters or EDID emulators.

In these environments, operating system display enumeration queries (such as
`SDL_GetNumVideoDisplays` or Win32 `EnumDisplayDevices`) return zero connected displays. Engine
subsystems responsible for camera initialization, swapchain setup, UI layout, and default
window placement routinely query `backend->getPrimaryDisplay()` or assert that
`backend->getDisplayCount() > 0`.

If the platform backend returns `nullptr` or reports zero displays, calling code either crashes
with a null pointer dereference or requires conditional branches across the entire engine.
Requiring every subsystem to guard against a null primary display adds defensive boilerplate and
causes sporadic failures during automated test runs.

## Decision

We centralize display topology tracking, spatial geometry resolution, and headless virtual
display fallback within `gp::hal::generic::ApplicationBackend`. Concrete platform backends
(such as `SDL3ApplicationBackend`) populate backend-owned display structures, while the shared
generic layer maintains the active display pointer table and executes all spatial queries.

### Active Display Pointer Table

`GenericApplicationBackend` maintains a fixed-capacity pointer table referencing active
displays:

```cpp
gp::hal::generic::Display* m_displayTable[kMaxDisplays]{};
gp::UInt32 m_displayCount{ 0u };
DisplayId m_primaryDisplayId{ kInvalidDisplayId };
```

The maximum display capacity is capped at `kMaxDisplays = 16u`. When monitors are connected or
disconnected, derived backends register or unregister pointers through protected methods.
Unregistering a display shifts subsequent entries to the left, preserving contiguous array
packing without dynamic memory allocation.

### Deterministic Spatial Resolution Algorithms

The generic backend provides two deterministic geometric algorithms to resolve screen-space
coordinates across multi-monitor layouts:

#### 1. Point Resolution (`getDisplayForPoint`)

Given a virtual desktop coordinate `point`:

1. **Fast Path (Containment):** Iterate through connected displays. If
   `disp->getBounds().contains(point)` evaluates to true, return that display immediately.
2. **Dead-Zone Fallback (Clamped Euclidean Distance):** If the coordinate falls into a dead zone
   outside all monitors, compute the squared Euclidean distance to each display's bounding box.
   The point coordinates are clamped to the monitor bounds:
   $$x_{clamped} = \max(x_{min}, \min(point.x, x_{max}))$$
   $$y_{clamped} = \max(y_{min}, \min(point.y, y_{max}))$$
   The distance is evaluated as:
   $$d^2 = (point.x - x_{clamped})^2 + (point.y - y_{clamped})^2$$
   The backend selects the display with the minimum $d^2$. Ties preserve the current primary
   display or the lowest index entry.

#### 2. Rectangle Resolution (`getDisplayForRect`)

Given a virtual desktop window rectangle `rect`:

1. **Overlapping Area Calculation:** For each connected display, evaluate the overlapping pixel
   area between `rect` and the display bounds:
   $$A_{overlap} = \max(0, \min(x_2) - \max(x_1)) \times \max(0, \min(y_2) - \max(y_1))$$
2. **Maximum Overlap Selection:** Return the display that yields the highest $A_{overlap} > 0$.
3. **Off-Screen Fallback:** If the rectangle is located entirely off-screen ($A_{overlap} = 0$ for
   all monitors), resolve ownership using the rectangle's geometric center coordinate via
   `getDisplayForPoint(rect.center())`.

### Synthetic Headless Virtual Display Fallback

When the platform backend initializes on a system with zero physical monitors,
`activateHeadlessFallbackIfEmpty()` configures an internal synthetic display:

- **Display ID:** `kHeadlessDisplayId = 0xFFFFFFFFu`.
- **Display Name:** `"GP Virtual Headless Display"`.
- **Bounds and Work Area:** Origin `(0, 0)`, Extent `1920 x 1080`.
- **Refresh Rate:** 60.0 Hz (rational 60/1).
- **Pixel Format:** `DisplayPixelFormat::RGBA8888`.
- **DPI and Content Scale:** 1.0f (corresponding to baseline 96 DPI).
- **Luminance:** Standard Dynamic Range (80.0 nits paper white, 250.0 nits max, 0.005 nits min).
- **Flags:** `DisplayFlags::Primary | DisplayFlags::Connected`.

The fallback display occupies slot 0 of `m_displayTable`, ensuring `m_displayCount == 1`. When a
physical monitor is subsequently registered, the synthetic display is evicted. If all physical
monitors are later unplugged, the backend reinstates the synthetic display automatically.

### Architectural Invariants

1. **Zero-Null Display Contract:** `getDisplayCount()` always returns $\ge 1$, and
   `getPrimaryDisplay()` never returns `nullptr` under any runtime condition, including headless
   servers and automated test containers.
2. **Deterministic Spatial Resolution:** Cursor positions in multi-monitor dead zones resolve via
   minimum squared Euclidean distance to clamped monitor edges. Window rectangles resolve by
   maximum overlapping pixel area, falling back to center point resolution when off-screen.
3. **Bounded Static Topology Table:** The display pointer table is fixed at `kMaxDisplays = 16`
   entries without dynamic memory allocations. Registering and unregistering displays modifies
   pointers in place with contiguous compaction.
4. **Transparent Headless Virtual Display:** When physical monitor count is zero, the backend
   provisions a synthetic $1920 \times 1080$ display at 60 Hz. Registering a physical monitor
   evicts the virtual fallback, while disconnecting all physical monitors restores it.

## Alternatives Considered

### Option A: Backend-Specific Spatial Resolution

Each platform backend (Win32, SDL3, Cocoa, Wayland) implements display enumeration and spatial
geometry independently using native platform APIs (such as Win32 `MonitorFromPoint` and
`MonitorFromRect`).

**Why rejected:** Duplicates geometric resolution algorithms across every platform backend.
Platform-specific APIs handle coordinate clamping and edge dead zones differently, leading to
inconsistent cross-platform window placement. Centralizing the geometry in the generic layer
ensures identical spatial behavior across all supported operating systems.

### Option B: Returning Nullptr for Headless Displays

When no physical monitors are connected, `getDisplayCount()` returns 0 and `getPrimaryDisplay()`
returns `nullptr`.

**Why rejected:** Forces every consumer subsystem (viewports, cameras, UI frameworks, swapchain
initializers) to implement null checks and defensive fallback paths. A single missing branch
causes fatal crashes on automated CI runners and dedicated multiplayer game servers. Providing a
synthetic virtual display establishes a reliable non-null contract engine-wide.

### Option C: Dynamic Heap Allocation for Active Display Lists

Store registered display pointers in a dynamically resizable array (`gp::Vector<IDisplay*>`)
that resizes as monitors are connected and disconnected.

**Why rejected:** Violates the engine's zero-allocation invariant for runtime hardware
management. Dynamic allocations during monitor hotplug events introduce heap fragmentation and
create failure conditions during low-memory execution. A fixed table of 16 displays comfortably
exceeds typical workstation configurations without runtime memory allocations.

## Consequences

### Positive

- **Guaranteed non-null display queries.** Engine systems safely call `getPrimaryDisplay()`
  without branching or defensive fallback checks.
- **Deterministic multi-monitor geometry.** Dead-zone handling and cross-monitor window
  ownership behave identically across Windows, Linux, and macOS.
- **Stable headless continuous integration.** Automated test runners and dedicated servers
  initialize windowing and viewport systems without requiring physical monitors or virtual
  framebuffers.
- **Zero runtime allocations during topology updates.** The fixed pointer table manages monitor
  hotplug events without dynamic heap allocations.

### Negative

- **Fixed monitor capacity limit.** Systems with more than 16 physical monitors cannot register
  additional displays without recompiling with a larger `kMaxDisplays` value.
- **Synthetic metrics during headless testing.** Automated graphics tests execute against a
  default $1920 \times 1080$ layout, which does not exercise multi-monitor configurations or
  non-standard DPI scales unless explicitly overridden.
