# ADR-0037: Vector4 as a General-Purpose Four-Dimensional Vector with Homogeneous Coordinate Support

> Defines `gp::math::Vector4<T>` as a general-purpose four-dimensional vector whose mathematical
> operations consistently account for all four components, while preserving its compatibility with
> homogeneous 3D coordinates (`w = 0` for directions, `w = 1` for points). This separates general
> 4D mathematics from affine point/direction semantics, preventing context-dependent behavior in
> fundamental vector operations.

![Accepted][badge-accepted]

## Context

The engine needs a vector type suitable for the broad range of operations found in a
production-quality game engine: four-dimensional mathematical calculations, colors, planes,
SIMD-friendly data, and values passed through matrix transformations. `Vector4` is also useful
for carrying homogeneous 3D coordinates, where `w = 0` conventionally represents a direction
and `w = 1` represents a point.

These uses overlap in storage but do not have identical mathematical rules. A homogeneous
coordinate is not a separate affine type merely because its fourth component is used as a
point-or-direction marker. Treating every `Vector4` operation as affine geometry would make
ordinary four-dimensional operations ambiguous:

- A four-dimensional dot product includes `w`.
- A four-dimensional length includes `w`.
- A four-dimensional normalization scales all four components.
- Component-wise arithmetic operates on all four components.

The engine must therefore define whether `Vector4` is fundamentally a point type or a general
vector type, while still supporting its use in homogeneous matrix calculations.

## Decision

`gp::math::Vector4<T>` is a general-purpose four-dimensional vector. All general vector
operations operate on `x`, `y`, `z`, and `w`:

- `dot` is the four-dimensional dot product.
- `length` and normalization include all four components.
- Component-wise arithmetic operates on all four components.
- The default constructor and scalar constructor preserve their explicitly documented component
  initialization behavior.

`Vector4` also supports homogeneous 3D coordinates when used with transformation matrices. In
that context, the conventional interpretation is:

- `w = 0` for a direction;
- `w = 1` for a point.

The homogeneous interpretation is established by the caller or by the relevant conversion and
matrix APIs; it does not change the mathematical meaning of the general `Vector4` operations.

The `Vector4` cross product is the ordinary 3D cross product applied to `x`, `y`, and `z`, with
the result's `w` set to zero. This preserves the direction semantics of the result and the
anti-commutativity invariant:

```cpp
a.cross(b) == -b.cross(a)
```

Code that requires strictly affine point/vector semantics should use explicit point and direction
APIs or dedicated types rather than silently changing the meaning of general `Vector4`
operations.

## Alternatives Considered

### Option A: Make Vector4 a point-oriented homogeneous type

Treat `w = 1` as the default point representation and make operations interpret `w` according to
affine point/vector rules.

**Why rejected:** This conflates homogeneous-coordinate transport with the general four-dimensional
mathematics required by the engine. It makes dot products, lengths, normalization, scalar
operations, and component-wise operations context-dependent. It also makes `Vector4` unsuitable
for non-geometric four-component values.

### Option B: Make Vector4 only a strict mathematical four-dimensional vector

Remove or discourage homogeneous-coordinate use and require a separate representation for matrix
points and directions.

**Why rejected:** This would make matrix and shader-facing code more verbose and would discard the
standard and efficient `w = 0/1` representation used throughout real-time graphics.

### Option C: Encode point and direction semantics in a runtime mode

Store or pass an additional mode indicating whether each `Vector4` is a point, direction, or
generic four-dimensional value.

**Why rejected:** This adds state and branching to a fundamental value type without providing
strong compile-time safety. It also complicates copying, SIMD operations, serialization, and API
interoperability.

## Consequences

### Positive

- `Vector4` has one stable and unsurprising mathematical contract.
- Four-dimensional operations remain usable for all engine subsystems.
- Homogeneous matrix transformations retain the conventional and efficient `w = 0/1`
  representation.
- The cross product has a valid direction result with `w = 0`.
- Callers can distinguish general 4D calculations from affine point/direction operations at the
  API boundary.

### Negative

- Callers must understand whether a `Vector4` is being used as a generic 4D value or as a
  homogeneous coordinate.
- A `Vector4` does not enforce point-versus-direction semantics at compile time.
- Code requiring a spatial dot product or spatial length must use `Vector3` or an explicitly
  named XYZ-only operation.
- Dedicated point and direction types may still be desirable for APIs where stronger type safety
  is required.
