# ADR-0027: Event-Driven Window Shadow State for Lock-Free Game Thread Queries

> Native OS windowing APIs (Win32, Cocoa, Wayland, SDL3) restrict window property queries
> (`GetWindowRect`, `SDL_GetWindowSize`) to the main OS thread; invoking them from the Game or
> Render threads causes race conditions, kernel syscall overhead, and mid-frame state tearing. To
> guarantee thread safety and zero-cost queries, `gp::hal::generic::Window` maintains a local
> "Shadow State" (cached dimensions, framebuffer pixel extent, position, DPI scale, focus, and
> visibility flags). This shadow state is mutated exclusively on the Game Thread when draining
> `WindowEvent` packets from the lock-free `SPSCByteRingBuffer`, turning all IWindow getters into
> deterministic, `constexpr` L1-cache reads.

![Proposed][badge-proposed]

## Context

Operating system windowing APIs impose strict thread affinity on native window objects. On
Microsoft Windows, an `HWND` is owned by the specific OS thread that registered its window
class and called `CreateWindowEx`. Apple macOS requires all `NSWindow` and view interactions to
run on the main Cocoa dispatch thread. Linux Wayland compositors bind surface event dispatching
and buffer commit requests to the thread running `wl_display_dispatch`. Platform abstraction
layers such as SDL3 mirror these underlying requirements by mandating that window inspection
and message polling execute on the platform thread.

Secondary engine threads (such as the Game Thread, Task Worker Threads, and Render Thread)
frequently query window geometry, display scale, and visibility state. Invoking platform
windowing APIs directly across thread boundaries introduces severe engineering failure modes:

- **Cross-thread syscall race conditions and deadlocks.** Querying Win32 APIs such as
  `GetClientRect` or `GetWindowRect` from a non-owner thread forces the OS kernel to marshal
  the request through internal `SendMessage` calls to the thread that owns the `HWND`. If the
  OS message pump thread is currently waiting on an engine synchronization primitive or
  swapchain fence held by the calling thread, the application enters an unrecoverable
  deadlock.
- **Mid-frame state tearing.** Desktop window managers and compositors operate asynchronously
  relative to the game frame loop. A user or window manager can resize, reposition, minimize,
  or scale a window at any point during frame execution. If disparate engine subsystems query
  window geometry directly from the OS at different points in the same frame tick, they
  observe contradictory values. UI layout algorithms compute positions against pre-resize
  extents (such as 1920x1080), camera projection matrices update against post-resize extents
  (such as 2560x1440), and render target binding fails or causes stretched viewports during
  presentation.
- **Performance stalls and cache pollution.** Direct OS window queries require user-to-kernel
  mode transitions (`syscall`) and message queue scans. Each invocation costs hundreds to
  thousands of CPU cycles. Subsystems query window properties dozens of times per frame for
  mouse coordinate normalization, UI layout passes, camera frustum updates, and backbuffer
  configuration. Issuing synchronous OS calls across these passes degrades CPU budgets and
  evicts hot instructions from cache.

The engine requires an architecture that guarantees thread safety, eliminates cross-thread
syscall stalls, and ensures that all subsystems observe an identical, invariant window state
throughout each frame tick.

## Decision

We introduce an Event-Driven Window Shadow State inside `gp::hal::generic::Window`. The shadow
state caches all public window properties in local engine memory. Property getters read directly
from these cached fields without issuing operating system system calls or acquiring thread
synchronization locks.

### Shadow State Data Layout

Window properties are grouped into local value fields inside `gp::hal::generic::Window`:

```cpp
struct WindowShadowState
{
    math::Extent2D clientExtent{};
    math::Extent2D framebufferExtent{};
    math::Point2D position{};
    Float32 dpiScale = 1.0f;
    WindowFlags flags = WindowFlags::None;
};
```

These fields record:

- `clientExtent`: Logical window dimensions in density-independent points, used for UI layout,
  clipping rects, and mouse hit-testing.
- `framebufferExtent`: Physical backbuffer pixel resolution, used for swapchain configuration,
  render target allocation, and graphics viewports.
- `position`: Signed screen coordinate location of the top-left window corner on the desktop.
- `dpiScale`: Display content scaling factor for rasterizing text and high-DPI user interfaces.
- `flags`: Bitfield or boolean indicators for input focus, cursor hovering, HDR output, and
  close requests.

### Thread Ownership and Mutation Protocol

The lifecycle and mutation of the shadow state follow a strict two-stage synchronization
protocol:

1. **Producer Phase (OS Thread / Platform Backend):** The platform message pump thread executes
   inside `IApplicationBackend::pumpEvents()`. When the native message loop receives an OS
   mutation event (`WM_SIZE`, `WM_MOVE`, `WM_DPICHANGED`, or SDL3 equivalents), the backend
   serializes the event into a 16-byte Plain Old Data (POD) `WindowEvent` packet. This packet
   is pushed into the lock-free Single-Producer Single-Consumer ring buffer
   (`SPSCByteRingBuffer`). The platform thread never writes directly to the window's shadow
   state variables.
2. **Consumer Phase (Game Thread):** At the beginning of each frame tick, during Phase 4 of
   `Application::tick()`, the Game Thread invokes `drainEventStream()`. When dequeuing an event
   with category `EventCategory::Window`, the engine routes the packet to the target window via
   `IWindow::onWindowEvent(ev)`. The window updates its local shadow fields in place.
3. **Zero-Cost Inline Getters:** All public state query methods on `IWindow` (`getSize()`,
   `getFramebufferSize()`, `getPosition()`, `getDpiScale()`, `isFocused()`) are implemented in
   `GenericWindow` as inline const accessors. They compile to direct memory loads from local
   cache lines without mutex locks, atomic fences, or system calls.
4. **Frame Invariance:** Once event drainage finishes in Phase 4, the window shadow state
   remains strictly invariant for the remainder of the frame. UI layout, gameplay simulation,
   camera updates, and render submission all read the exact same window geometry throughout
   the current frame. Subsequent OS resizing events queued by the desktop window manager
   remain in the ring buffer until Phase 4 of the next frame.

### Architectural Invariants

1. **Single-Writer Thread Discipline:** Window shadow state fields are mutated strictly on
   the Game Thread during the event drainage phase of `Application::tick()`. The platform
   message pump thread never writes directly to shadow state variables.
2. **Immutable Frame Horizon:** After event drainage completes, shadow state values remain
   invariant across all subsequent game frame phases (fixed update, variable update, render
   dispatch). Mid-frame window resizes from the OS are queued and applied at the start of
   the next frame.
3. **Zero-Syscall Public Getters:** `IWindow` state accessors (`getSize()`, `getPosition()`,
   `isFocused()`) never invoke OS APIs, acquire synchronization primitives, or issue atomic
   fences. They execute as direct reads from L1/L2 cache.
4. **Decoupled Backend Execution:** Backend implementations (such as `SDL3Window`) forward OS
   mutations exclusively through POD `WindowEvent` packets written to the event ring buffer.
   Backends never expose raw OS window pointers to gameplay or rendering code.

### Architectural Strategy Matrix

The following matrix contrasts the Event-Driven Shadow State pattern against alternative
approaches:

<!-- markdownlint-disable MD013 -->
| Strategy | Thread Safety | Query Latency | Mid-Frame Tearing Protection | Deadlock Risk |
| :--- | :--- | :--- | :--- | :--- |
| **Direct OS Queries** (`GetClientRect`) | Unsafe (thread-affinity violation) | High (~500-2500 ns syscall) | None (tears whenever compositor updates) | High (cross-thread message deadlocks) |
| **Mutex-Protected State** (`std::mutex`) | Safe (mutual exclusion) | Medium (~25-60 ns uncontended) | Partial (consistent per call, tears mid-frame) | Medium (priority inversion with OS loop) |
| **Atomic Properties** (`Atomic<Extent2D>`) | Safe (atomic memory operations) | Low (~5-15 ns per fence) | None (separate fields tear independently) | None (lock-free) |
| **Event-Driven Shadow State** (`GenericWindow`) | Safe (single-writer Game Thread) | Zero (~1-2 ns L1 cache read) | Guaranteed (frozen frame horizon) | None (wait-free queries) |

## Alternatives Considered

### Option A: Direct OS API Queries on Demand (`GetClientRect` / `SDL_GetWindowSize`)

Subsystems query the underlying platform API or SDL3 window functions directly whenever they
need window geometry or focus status.

**Why rejected:** Violates OS thread-affinity rules when invoked from worker or render
threads. Triggers expensive user-to-kernel mode switches and instruction cache invalidations.
Causes mid-frame state tearing when the OS compositor modifies window geometry while frame
systems execute. Introduces deadlock risks on Windows due to synchronous `SendMessage` calls
when the OS thread is blocked on engine locks.

### Option B: Mutex-Guarded Window Properties

Window properties reside behind a mutual exclusion lock (`gp::Mutex`). The platform message
pump acquires the lock to write updates, and the Game Thread acquires the lock to read getters.

**Why rejected:** Serializes the platform thread against the Game Thread, introducing lock
contention and unpredictable latency spikes. Causes priority inversion if the Game Thread holds
the lock during heavy update work while the OS message pump needs to process input. Fails to
prevent mid-frame state tearing because properties can still update between the UI layout pass
and the camera matrix pass within the same frame tick.

### Option C: Individual Atomic Fields (`Atomic<Extent2D>`, `Atomic<Point2D>`)

Store width, height, position, and window flags inside independent atomic variables updated by
the platform thread and read by engine threads.

**Why rejected:** Cannot provide compound atomic updates across multiple properties. Updating
width and height, or client extent and framebuffer pixel extent, involves two separate atomic
stores. The Game Thread can observe an updated width with an old height, resulting in
inconsistent aspect ratios. Atomic fields also fail to provide frame invariance, as properties
can change between consecutive lines of game logic.

## Consequences

### Positive

- **Zero-cost inline queries.** State getters read directly from local member variables,
  compiling to direct register loads without thread synchronization or system calls.
- **Deterministic frame invariance.** All subsystems observe identical window geometry and
  state throughout the frame, eliminating aspect ratio mismatches, UI clipping errors, and
  swapchain presentation glitches.
- **Elimination of cross-thread deadlocks.** The Game Thread executes without blocking on the
  OS message loop, and the platform thread pushes updates without waiting on game subsystems.
- **Clean architectural decoupling.** Hardware and platform details remain encapsulated behind
  the backend boundary. Interface consumers interact only with value types and generic window
  contracts.

### Negative

- **Single-frame latency on OS resize reflections.** External window modifications initiated
  by the desktop window manager reflect in engine state on the subsequent frame tick after event
  drainage.
- **Duplicated state storage.** The engine retains an extra copy of window geometry, metrics,
  and visibility flags in application memory alongside the operating system native window
  structures.
