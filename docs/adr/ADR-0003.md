# ADR-0003: CMake as Build Generator with GPBT as Declarative Orchestration Layer

> Adopts CMake as the build generator paired with a declarative orchestration layer (GPBT) to
> enable discovery-order independence and enforce module visibility.

![Accepted][badge-accepted]

## Context

The GP Engine is a multi-platform C++ monorepo spanning dozens of modules with strict visibility
rules ([ADR-0001](./ADR-0001.md)), runtime-loaded backends ([ADR-0002](./ADR-0002.md)), and
lifecycle-separated source directories ([ADR-0004](./ADR-0004.md)). Our build system must satisfy
five requirements:

1. **Declarative module descriptions.** A module's build description must say *what* the module is
   (its sources, its dependencies, its visibility) without encoding *how* CMake should configure it.
2. **Mechanical enforcement of `public/private` boundaries.** The build system must set include
   paths so a consumer of module `M` cannot access `M/private/` or `M/internal/`, even if the paths
   exist on disk.
3. **Dependency-order-independent discovery.** In a large tree, the order in which CMake discovers
   modules must not matter. A module declared before its dependency must still build.
4. **C++-ecosystem standard.** The build system must be familiar to a C++ engineer from any studio
   background, without requiring a proprietary scripting language.
5. **Educational transparency.** A student reading a module's build description must understand the
   full dependency story of that module in under 30 lines.

Raw CMake fails requirements 1-3 without heavy scaffolding. Alternatives like UnrealBuildTool,
Premake, and Bazel each fail at least one of 1-5.

## Decision

We adopt CMake as the build generator (satisfying requirement 4) and build a thin orchestration
layer on top of it, the Graphical Playground Build Tool (GPBT), to satisfy requirements 1-3.

GPBT is a pure CMake include library: a set of `.cmake` files that define macros. No external
language runtime (C#, Python, Ruby) is required. Anyone who can read CMake can read GPBT.

### The three-phase build

Standard CMake processes `CMakeLists.txt` files in discovery order. If module B depends on module A
but B is discovered first, the build breaks. GPBT solves this with a two-pass system (similar to
UnrealBuildTool's Rules compilation, implemented in CMake):

1. **Registration.** GPBT recursively scans the source tree and executes each `CMakeLists.txt` in
   a lightweight registration mode. Each target records its name, type, source glob roots, and
   dependency list. No real CMake targets are created.
2. **Configuration.** GPBT topologically sorts all registered targets and re-processes each
   `CMakeLists.txt` in dependency order, creating the real CMake targets with include paths,
   compile definitions, and link libraries.
3. **Generation.** Standard CMake generation to the chosen backend (Ninja, Makefile, MSBuild,
   Xcode).

### The four dependency visibility levels

GPBT introduces four dependency kinds that map to the three coupling levels described in
[ADR-0002](./ADR-0002.md):

| GPBT macro | Compile | Link | Runtime | Propagated to consumer? |
| --- | --- | --- | --- | --- |
| `gpAddDependency(PUBLIC B)` | Yes (B's `public/`) | Yes | - | Yes |
| `gpAddDependency(PRIVATE B)` | Yes (B's `public/`) | Yes | - | No |
| `gpAddDependency(INTERNAL B)` | Yes (B's `public/`) | Yes | - | No (semantically internal) |
| `gpAddDependency(DYNAMIC B)` | - | - | Yes (build-order only) | - |

`DYNAMIC` creates a build-order edge so the shared library builds before the engine binary, with no
link-time dependency.

### GPBT macro surface

A complete module declaration looks like:

```cmake
include(gp-build-tool)

gpStartModule(audio)
  gpAddDependency(PUBLIC  core)
  gpAddDependency(PRIVATE gp::thirdparty::sdl3)
  gpTargetSetTestsEnabled(TRUE)
  gpTargetSetBenchmarksEnabled(TRUE)
gpEndModule()
```

GPBT automatically globs `private/**/*.cpp` as private sources, adds `public/` to the PUBLIC
include path (propagated to consumers), adds `private/` and `internal/` to the PRIVATE include
path, and creates test and benchmark executables when opted in.

### Filesystem analogy

<!-- markdownlint-disable MD013 -->
| GPBT macro | Filesystem analogue |
| --- | --- |
| `gpStartModule(name) ... gpEndModule()` | A folder with a `CMakeLists.txt` |
| Auto-glob `private/**/*.cpp` | The `private/` folder |
| Auto-PUBLIC `public/` include path | The `public/` folder |
| Auto-PRIVATE `internal/` include path | The `internal/` folder |
| `gpAddDependency(PUBLIC B)` | "B's `public/` is part of my API surface" |
| `gpAddDependency(PRIVATE B)` | "B is an implementation detail; consumers don't see it" |
| `gpAddDependency(DYNAMIC B)` | "B is a runtime plugin; no link edge" |
| `gpStartPlugin(name) ... gpEndPlugin()` | A folder under `source/plugins/` |
| `gpStartExecutable(name) ...` | A folder under `source/launch/` or `source/programs/` |

## Alternatives Considered

### Option A: Raw CMake (no orchestration layer)

Write standard `CMakeLists.txt` files using `add_library`, `target_include_directories`, and
`target_link_libraries` directly.

**Why rejected:** Raw CMake does not enforce discovery-order independence. Public/private path
discipline must be repeated in every module, and there is no mechanical enforcement of `public/`
exposure. Macros would be copy-pasted and drift within a release cycle.

### Option B: UnrealBuildTool (C# rules files)

Adopt UE's module descriptor format (`*.Build.cs` + `*.Target.cs`) and write a C# tool to
process them.

**Why rejected:** Introduces a C# runtime and an out-of-band tool into a pure C++ project.
Engineers arriving from Godot, O3DE, or other CMake-based studios would have to learn a bespoke
build language. We take the semantics of UBT's
`PublicDependencyModuleNames`/`PrivateDependencyModuleNames` and express them in CMake instead.

### Option C: Bazel / Buck2

Use a hermetic, content-addressed build system.

**Why rejected:** While reproducible at Google/Meta scale, it requires non-trivial `BUILD` file
authorship and a learning curve outside the standard C++ CMake ecosystem. Our educational focus
requires CMake.

### Option D: Premake

Use Premake's Lua-based build description language.

**Why rejected:** Premake generates project files without managing dependency propagation or
include-path visibility. We would still need a custom layer on top, and Lua is less familiar to C++
engineers than CMake.

### Option E: Meson

Use the Meson build system.

**Why rejected:** Strong cross-platform support, but no native mechanism for runtime-plugin
dependency edges (`DYNAMIC` in GPBT). It would require custom wrappers like GPBT in a less
familiar ecosystem.

## Consequences

### Positive

- **CMake familiarity is widely available.** Any C++ engineer who has worked on an open-source
  project can read GPBT after a brief ramp-up.
- **GPBT is transparent.** It lives as plain `.cmake` files under `cmake/`. Engineers debugging the
  build can read the implementation directly.
- **The `public/private` boundary is mechanically enforced.** A developer cannot accidentally
  expose `private/` headers to consumers.
- **Discovery-order independence removes a class of build bugs.**
- **`DYNAMIC` dependencies model runtime plug-ins.** The build system expresses a distinction that
  raw `target_link_libraries` cannot.

### Negative

- **GPBT is a custom tool that must be learned.** Despite being written in CMake, its macro API is
  GP-specific.
- **The two-pass system adds configure-time overhead.** The double traversal adds seconds to
  `cmake ..` on large source trees. This cost occurs once at configure time.
- **GPBT diverges from vanilla CMake.** A developer who adds a module with raw CMake instead of
  GPBT macros will produce a target that bypasses the visibility rules.
