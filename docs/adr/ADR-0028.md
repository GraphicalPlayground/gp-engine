# ADR-0028: Zero-Allocation Cached Display Topology and Shadow Mode Tables

> Querying OS display managers (`EnumDisplaySettings`, `SDL_GetFullscreenDisplayModes`) at runtime
> triggers synchronous EDID/driver calls and heap allocations that stall the calling thread. To
> eliminate runtime allocations and OS stalls, `gp::hal::generic::Display` caches monitor bounds,
> work areas, HDR luminance metadata, and deduplicated `DisplayMode` tables inside fixed-capacity
> inline storage (`kMaxCachedModes = 64`). The topology is populated once on startup and
> incrementally synchronized via `DisplayEvent` packets from the lock-free `SPSCByteRingBuffer`.

![Proposed][badge-proposed]

## Context

Configuring display output (resolution, refresh rate, display orientation, and HDR
luminance) is a standard requirement for real-time video games. Players expect responsive
settings menus that list available screen resolutions and switch video modes without
causing hitches. Querying display hardware through operating system APIs, however, presents
three distinct performance problems:

1. **Synchronous Driver Stalls:** Querying display hardware through platform APIs (such as
   Win32 `EnumDisplaySettingsEx`, X11 `XRandR`, macOS `CGDisplayCopyAllDisplayModes`, or SDL3
   `SDL_GetFullscreenDisplayModes`) invokes synchronous graphics driver routines. Each call
   routes through user-mode drivers (UMD) and kernel-mode drivers (KMD/WDDM) to read Extended
   Display Identification Data (EDID) and DisplayID blocks across the DDC/CI bus. These calls
   block the calling thread for 5ms to 50ms per attached display. Executing these queries
   on the Game Thread during active gameplay or menu navigation drops frames and stalls
   simulation updates.
2. **Dynamic Heap Allocations:** Operating system interfaces and wrapper libraries rely on
   dynamic heap allocations to return variable-length mode arrays. For example, SDL3's
   `SDL_GetFullscreenDisplayModes` allocates a mode pointer array (`SDL_DisplayMode**`) via
   `SDL_malloc` on every call. Repeated display queries violate the engine rule requiring
   zero heap allocations on runtime execution paths, introducing allocator lock contention
   and memory fragmentation.
3. **Duplicate Mode Bloat:** Raw operating system mode enumerations return numerous duplicate
   or obsolete entries. Drivers report separate entries for fractional refresh rates (59.94 Hz
   versus 60.00 Hz, 23.976 Hz versus 24.00 Hz), deprecated color formats, and legacy
   interlaced modes (1080i). Passing these unscrubbed lists directly to user interfaces
   clutters resolution pickers with redundant choices that confuse users.

To keep user interface menus responsive and protect frame budgets, the display subsystem
must eliminate runtime driver calls and heap allocations, serving filtered video mode
tables from pre-allocated, cache-resident memory.

## Decision

We introduce `gp::hal::generic::Display`, an implementation of `gp::hal::IDisplay` that
stores display metrics, geometry, and video modes in fixed-capacity inline storage.

### Fixed-capacity inline storage

Each display instance maintains monitor bounds, usable work areas, content scaling, HDR
luminance metadata, and an inline array of display modes:

<!-- markdownlint-disable MD013 -->
```cpp
namespace gp::hal::generic
{

class Display : public gp::hal::IDisplay
{
public:
    static constexpr gp::USize kMaxDisplayNameBytes = 128u;
    static constexpr gp::UInt32 kMaxCachedModes = 64u;

protected:
    DisplayDesc m_desc{};
    DisplayMode m_supportedModes[kMaxCachedModes]{};
    gp::UInt32 m_supportedModeCount{ 0u };
    char m_nameBuffer[kMaxDisplayNameBytes]{ "Generic Display" };

public:
    // Zero-allocation accessors reading directly from inline storage
    [[nodiscard]] constexpr DisplayId getId() const noexcept override;
    [[nodiscard]] constexpr StringView getName() const noexcept override;
    [[nodiscard]] constexpr DisplayRect getBounds() const noexcept override;
    [[nodiscard]] constexpr DisplayRect getWorkArea() const noexcept override;
    [[nodiscard]] constexpr Float32 getContentScale() const noexcept override;
    [[nodiscard]] constexpr const DisplayHDRMetadata& getHDRMetadata() const noexcept override;
    [[nodiscard]] constexpr const DisplayMode& getCurrentMode() const noexcept override;
    [[nodiscard]] constexpr const DisplayMode& getDesktopMode() const noexcept override;
    [[nodiscard]] constexpr gp::UInt32 getSupportedModeCount() const noexcept override;
    [[nodiscard]] constexpr const DisplayMode* getSupportedMode(gp::UInt32 index) const noexcept override;
    [[nodiscard]] constexpr bool findClosestMode(
        const Extent2D& targetResolution, Float32 targetRefreshRate, DisplayMode& outMode
    ) const noexcept override;
};

}   // namespace gp::hal::generic
```

### Mode deduplication and sanitization

The engine enumerates display modes once during platform initialization on the OS thread
(`SDL3Display::refresh()`). The initial scan filters raw driver modes before caching them:

- **Fractional Refresh Rate Deduplication:** Modes with fractional differences (such as
  59.94 Hz and 60.00 Hz) are merged into a single entry, retaining the primary timing
  frequency supported by the display.
- **Interlaced Mode Rejection:** Deprecated interlaced video modes (such as 1080i) are
  discarded so the renderer receives only progressive scan targets.
- **Ordered Insertion:** Modes are sorted in descending order by pixel area (width multiplied
  by height) and refresh rate. This sorting allows linear search routines to locate optimal
  resolutions efficiently.
- **Fixed Storage Limit:** Deduplication restricts the cache size to `kMaxCachedModes = 64`.
  Because modern displays report between 8 and 30 distinct progressive modes, 64 slots
  support high-refresh panels and ultra-wide aspect ratios without dynamic allocations.

### Zero-allocation runtime queries

All runtime display queries read directly from inline struct members:

- Accessors (`getBounds()`, `getWorkArea()`, `getContentScale()`, `getHDRMetadata()`) return
  plain-old-data structs or const references to member fields.
- Mode accessors (`getSupportedModeCount()`, `getSupportedMode()`) return integers or pointers
  into `m_supportedModes` without heap allocations or operating system calls.
- Mode matching in `findClosestMode` iterates through the inline array to minimize squared
  resolution distance and refresh rate differences, operating with zero heap allocations.

### Asynchronous hotplug and incremental topology sync

When a user connects, disconnects, or adjusts a monitor, the display subsystem synchronizes
state across threads using the engine's event system:

1. **OS Thread Event Capture:** The platform backend processes monitor messages on the main
   OS thread. When a display change occurs (connect, disconnect, move, resize, orientation
   change, or HDR toggle), the backend pushes a `DisplayEvent` into the wait-free
   `gp::container::SPSCByteRingBuffer`.
2. **Game Thread Topology Draining:** At the beginning of each tick, the Game Thread drains
   the ring buffer and forwards each `DisplayEvent` to the appropriate `Display` instance
   via `onDisplayEvent(ev)`.
3. **In-Place State Mutation:** The display instance updates its internal `DisplayDesc`
   fields in place. The Game Thread never queries OS drivers or blocks on platform
   synchronization primitives, maintaining consistent frame pacing.

### Architectural invariants

1. **Contiguous Inline Storage:** Each `Display` instance stores video modes in an inline array
   of size `kMaxCachedModes = 64`. Mode tables must never allocate dynamic heap memory.
2. **Zero Driver Calls on Frame Loops:** The Game Thread and Render Thread must never call
   synchronous OS display queries (`EnumDisplaySettings`, `SDL_GetFullscreenDisplayModes`).
   All queries read from local shadow state.
3. **Unidirectional Event Synchronization:** Display topology changes propagate from the OS
   thread to the Game Thread strictly through `DisplayEvent` packets in the lock-free
   `SPSCByteRingBuffer`.
4. **Deterministic Mode Resolution:** The `findClosestMode` function matches modes by
   evaluating squared resolution distance first, followed by refresh rate delta, ensuring
   consistent mode selection across all supported platforms.

### Display query architecture comparison

<!-- markdownlint-disable MD013 -->
| Metric / Characteristic | Dynamic OS Query (`SDL3` / Win32) | Dynamic Heap Wrapper (`std::vector`) | Fixed Inline Cache (`GenericDisplay`) |
| :--- | :--- | :--- | :--- |
| **Allocation Count** | 1 to 3 dynamic allocations per query (`SDL_malloc`) | Allocations on initial fill and vector growth | Exactly 0 runtime allocations |
| **Query Latency** | 5ms to 50ms (synchronous driver kernel I/O) | 20ns to 100ns (heap pointer indirection) | < 5ns (L1 cache inline member access) |
| **Driver Stall Risk** | High; blocks calling thread on graphics UMD/KMD | None during read; present during sync | None; queries never invoke driver APIs |
| **UI Menu Responsiveness** | Stutters whenever resolution menus open | Smooth, but risks heap fragmentation | Perfectly smooth with zero frame drops |
| **Memory Locality** | Dispersed pointers across OS runtime heap | Separate heap allocation block | Inline contiguous storage inside Display |

## Alternatives Considered

### Option A: Querying the OS on demand

Call platform APIs directly (`SDL_GetFullscreenDisplayModes`, Win32 `EnumDisplaySettingsEx`)
whenever code requests display modes or resolution settings.

**Why rejected:** Querying display hardware triggers synchronous driver calls to read monitor
EDID data, taking between 5ms and 50ms per display. These stalls cause frame stutters when
opening video settings menus. Operating system APIs also allocate heap memory on each call,
violating engine memory constraints.

### Option B: Dynamically resized heap arrays

Store mode lists in dynamically allocated arrays (`std::vector<DisplayMode>` or custom heap
buffers) populated during startup.

**Why rejected:** Dynamic arrays require heap allocations during initialization and hotplug
events, causing heap fragmentation. Resizing containers introduces pointer invalidation risks
if other threads read mode data during an update. Fixed inline arrays provide predictable
memory usage and stable memory addresses.

### Option C: Global static shared mode table

Maintain a single shared list of standard video modes (such as 1080p, 1440p, 4K at 60Hz and
144Hz) across all attached displays.

**Why rejected:** A global table fails to reflect hardware differences between monitors.
In multi-display configurations, one monitor may support 5120x1440 at 240Hz while another
supports only 1920x1080 at 60Hz. A static shared table would either present invalid modes
for secondary displays or hide supported modes for high-end displays.

## Consequences

### Positive

- **Zero-allocation runtime queries.** Display accessors read directly from contiguous inline
  storage, avoiding dynamic memory allocators and preventing heap fragmentation.
- **Elimination of driver stalls.** Querying display geometry or supported modes never triggers
  synchronous kernel driver calls, preventing frame drops during gameplay and menu navigation.
- **Clean video mode lists.** Automated filtering removes interlaced modes and merges fractional
  refresh rates, presenting organized lists for user interface menus.
- **Thread-safe event updates.** Display changes synchronize through lock-free ring buffer
  packets, allowing the Game Thread to update state without mutex locks.

### Negative

- **Fixed capacity overhead.** Allocating storage for 64 modes per display consumes inline
  memory regardless of how many modes a given monitor supports.
- **Mode table truncation.** Rare display setups that report more than 64 distinct video modes
  will have surplus modes truncated by the fixed array boundary.
- **Initial startup probe latency.** Initializing the display topology on the OS thread still
  incurs the initial hardware query cost before gameplay starts.
