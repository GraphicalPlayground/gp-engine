# ADR-0021: STL-Free Concurrency Primitives and Platform Abstraction

> Rejects `<thread>`, `<mutex>`, and `<atomic>` in favor of custom engine-native primitives
> (`gp::thread::Atomic`, `gp::thread::Thread`, `gp::container::SPSCByteRingBuffer`) placed in the
> core module, ensuring strict memory control and ABI stability across module boundaries.

![Proposed][badge-proposed]

## Context

Standard C++ concurrency facilities (`<thread>`, `<mutex>`, `<atomic>`, `<condition_variable>`)
target desktop software with unconstrained allocation budgets. Game engines execute on
deterministic frame cycles with strict execution budgets. Standard concurrency abstractions
introduce several architectural hazards within this environment:

- **Uncontrolled Dynamic Heap Allocations:** Spawning a `std::thread` dynamically allocates an
  internal control block and an invocation context via global `malloc` or `operator new`. In
  real-time systems, heap allocations trigger lock contention on global memory allocators and
  cause heap fragmentation. Furthermore, `std::thread` does not allow configuring hardware
  stack reservation size or CPU core affinity at creation time.
- **ABI Instability Across Dynamic Modules:** Primitives like `std::mutex` and `std::atomic`
  rely on compiler-specific, opaque layouts. On Windows, MSVC implements `std::mutex` via
  `SRWLOCK` or `CRITICAL_SECTION` with specific padding. On Linux, glibc provides
  `pthread_mutex_t`. When passing synchronization objects across dynamic library boundaries
  (DLL, SO, dylib), differing compiler flags, runtime library versions, or toolchain releases
  cause memory offset mismatches, leading to crashes or lock corruption.
- **Silent Fallback to Software Locks:** Under ISO C++, `std::atomic<T>::is_lock_free()`
  operates as a runtime query. The standard does not provide a compile-time guarantee that
  operations compile to hardware instructions. When `T` exceeds the platform register size
  (such as 16-byte structures on 64-bit platforms) or lacks required natural alignment,
  compilers route atomic operations through global OS spinlocks or helper routines in
  `libatomic`. This removes the lock-free guarantee without compiler diagnostic warnings.
- **Missing Diagnostic and Profiling Integration:** Modern game development relies on low-level
  profiling tools (such as Tracy, Visual Studio, PIX, and RenderDoc). Standard threads do not
  support setting OS thread names (such as Win32 `SetThreadDescription` or Linux
  `pthread_setname_np`) or assigning thread priority levels directly during initialization.
- **Header File Pollution and Compilation Latency:** Including `<thread>`, `<mutex>`, or
  `<atomic>` pulls extensive template definitions, `<type_traits>`, and system headers into
  translation units. This bloats preprocessed file sizes, lengthens incremental compilation
  times, and leaks macro definitions into game module scopes.

To support deterministic execution and strict platform isolation, the engine requires native
concurrency primitives designed around explicit memory layouts, zero heap allocations,
concept-constrained lock-free guarantees, and complete header isolation.

## Decision

We introduce engine-native threading and concurrency primitives under `gp::thread`,
`gp::platform`, and `gp::container`, housed in `source/runtime/core/`:

1. `gp::thread::Atomic<T>`: Constrained by the `AtomicValue` concept. Requires trivial
   copyability, exact cv-unqualified types, and physical sizes of 1, 2, 4, or 8 bytes. Maps
   directly to CPU lock-free instructions (`LOCK CMPXCHG`, `LOCK XADD`) or compiler intrinsics,
   with `kIsAlwaysLockFree = true` guaranteed at compile time.
2. `gp::platform::Thread`: Wraps native operating system primitives (`_beginthreadex` on
   Windows, `pthread_create` on POSIX) with zero dynamic allocation. Passes configuration
   parameters via a stack-allocated handoff payload, supporting custom stack sizing, CPU
   affinity masks, priority tiers, and debugger thread descriptions.
3. `gp::container::SPSCByteRingBuffer`: A wait-free Single-Producer Single-Consumer ring
   buffer (`SPSCRingBuffer<gp::UInt8>`) providing cross-thread event queues with three-tier
   64-byte cache-line isolation (Read-Only, Producer, Consumer) and shadow index caching.
4. `gp::memory::MemoryOrder`: An engine-scoped enumeration defining explicit memory ordering
   semantics (`Relaxed`, `Consume`, `Acquire`, `Release`, `AcqRel`, `SeqCst`) without
   requiring `<atomic>`.

### Physical Directory Layout

The core module hosts threading primitives, platform abstractions, and lock-free containers
according to module directory discipline:

```text
    platforms/

          WindowsThread.cpp     <-- Stack-allocated handoff and _beginthreadex logic
```

### Architectural Invariants

1. **Zero Heap Allocations on Thread Paths:** Thread instantiation, execution trampolines,
   and atomic synchronization must never invoke dynamic memory allocators (`malloc`, `new`).
   Thread creation parameters pass via stack-allocated synchronization blocks.
2. **Compile-Time Lock-Free Validation:** Types wrapped by `gp::thread::Atomic<T>` must
   satisfy the `AtomicValue` concept. Instantiating types requiring runtime software locks
   or `libatomic` routines fails at compile time.
3. **Platform Header Isolation:** Operating system headers (`<windows.h>`, `<process.h>`,
   `<pthread.h>`) are confined strictly to `private/platforms/<os>/` source files. Public
   headers expose opaque handles (`void* NativeHandle`) and fixed-width integral types.
4. **Hardware Cache-Line Isolation:** Shared cross-thread data structures must align and pad
   internal state variables to 64-byte boundaries, preventing false sharing across CPU cores.
5. **Deterministic Thread Configuration:** Thread spawning requires a `ThreadDesc` structure
   specifying entry function, user context, stack reservation, affinity mask, scheduling
   priority, and debugger description before execution starts.

### Standard Concurrency vs. Engine Native Primitives

<!-- markdownlint-disable MD013 -->
| Architectural Dimension | Standard Library (`std::`) | GP Engine Implementation (`gp::`) |
| :--- | :--- | :--- |
| **Allocation Model** | Allocates heap control blocks and invocation tuples via global `malloc`/`new`. | Zero dynamic allocations; uses stack-allocated handoff blocks and bounded structures. |
| **ABI Stability** | Unstable across dynamic libraries due to compiler-opaque struct layouts and padding. | Stable C-compatible layouts, fixed-width types, and opaque native handle wrappers. |
| **Lock-Free Guarantees** | Runtime evaluation via `is_lock_free()`; silent fallback to library spinlocks. | Concept-enforced compile-time guarantee (`AtomicValue`); fails compilation if not lock-free. |
| **Platform Integration** | No native support for thread naming, CPU core affinity, or stack sizing. | Explicit `ThreadDesc` with debugger naming (`SetThreadDescription`), affinity, and stack control. |
| **Header Overhead** | Heavy headers (`<thread>`, `<atomic>`) pulling system headers and template bloat. | Minimal, fine-grained headers adhering to IWYU with zero OS header leakage. |

## Alternatives Considered

### Option A: Standard Library `<thread>`, `<mutex>`, `<atomic>`

Rely on the ISO C++ Standard Library concurrency implementations across all platforms.

**Why rejected:** Standard library concurrency triggers dynamic heap allocations during
thread creation, violating deterministic frame memory budgets. Struct padding and internal
layouts differ between MSVC, libc++, and libstdc++, creating ABI hazards across dynamic
module boundaries. Additionally, `std::atomic` permits types that silently fall back to
software locks, thread creation offers no standard mechanism for setting CPU core affinity
or debugger names, and including `<thread>` causes header pollution.

### Option B: External Concurrency Library (Boost.Thread, Intel TBB)

Adopt a third-party concurrency framework to handle multi-threading, task scheduling,
and atomics across platforms.

**Why rejected:** Third-party concurrency frameworks introduce external dependencies and
heavy compilation overhead. These libraries implement their own memory allocators and task
schedulers that conflict with the engine linear and pool allocator architecture. Using an
external dependency also obscures the low-level mechanics of OS thread scheduling and hardware
atomic intrinsics, conflicting with the educational goals of the codebase.

### Option C: Direct OS API Inlining via Macros

Inline Win32 and POSIX function calls (`CreateThread`, `pthread_create`) directly across
engine systems via conditional compilation macros.

**Why rejected:** Inlining OS calls directly into subsystem headers leaks platform headers
like `<windows.h>` across the codebase. `<windows.h>` introduces macros (such as `min`, `max`,
and `CreateWindow`) that collide with engine identifiers and inflate compile times. Direct
calls also prevent clean unit testing via platform mock interfaces.

## Consequences

### Positive

- **Deterministic memory usage without allocation overhead.** Thread instantiation and atomic
  operations avoid the general-purpose heap, preventing lock contention and heap fragmentation
  during engine runtime.
- **Compile-time validation of lock-free invariants.** The `AtomicValue` concept prevents
  subsystems from using atomics that fall back to OS spinlocks, guaranteeing hardware
  instruction mapping.
- **Consistent ABI stability across dynamic modules.** Fixed-width integers and opaque handle
  abstractions ensure binary compatibility across shared library boundaries.
- **Fast compilation and zero macro pollution.** Isolating platform headers inside private
  implementation files prevents macro namespace pollution and shortens build times.
- **Integrated platform profiling and diagnostic visibility.** Explicit thread naming and
  affinity configuration integrate directly with system debuggers and external profilers like
  Tracy.

### Negative

- **Platform implementation maintenance.** Supporting multiple operating systems requires
  maintaining independent implementations and test suites for Windows, Linux, and macOS.
- **Restricted atomic value types.** Enforcing lock-free hardware mapping restricts atomic
  values to 1, 2, 4, or 8 bytes, requiring composite structures to use alternative lock-free
  approaches.
- **Explicit lifecycle management.** Developers must manage thread lifetimes explicitly
  through join or detach calls, as automatic scoping wrappers like `std::jthread` are
  deliberately omitted.
