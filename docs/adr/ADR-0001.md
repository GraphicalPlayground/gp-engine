# ADR-0001: Adoption of Public/Private/Internal Directory Discipline for Modules

> Establishes a three-tier directory structure (`public/`, `private/`, `internal/`) enforced by
> the build system to isolate module internals and prevent uncontrolled dependencies.

![Accepted][badge-accepted]

## Context

As a C++ game engine grows, header dependencies multiply. Without physical boundaries, subsystems
couple tightly, compile times climb, circular dependencies appear, and isolated refactors break
unrelated modules. The source tree needs hard architectural constraints so developers know what is
safe to include and cannot cross module boundaries by accident.

Putting all headers flat at the module root gives no signal about intended exposure. The compiler
sees every header, so a developer reaching across a private boundary gets no warning. A folder
named `private/` is a contract: nothing outside the module may include from it.

## Decision

Every module in the GP Engine uses a three-tier visibility layout modeled on Unreal Engine 5's
`Public/Private/Internal` split and enforced by our build tool ([ADR-0003](./ADR-0003.md)):

<!-- markdownlint-disable MD013 -->
| Tier | Directory | Include scope | Propagated to consumers? |
| --- | --- | --- | --- |
| Public API | `public/` | Any module with a dependency | Yes, in consumer include path |
| Private implementation | `private/` | This module only | No |
| Internal contract | `internal/` (optional) | Allowlisted friend modules | No, must be granted |
<!-- markdownlint-enable MD013 -->

Concretely, when GPBT configures a module `M`, the compiler sees:

```cmake
# For M itself during compilation:
-I .../M/public    (PUBLIC: propagated)
-I .../M/private   (PRIVATE: this build only)
-I .../M/internal  (PRIVATE: this build only, but shared with explicit friends)

# For any module that declares a dependency on M:
-I .../M/public    (only: never private or internal)
```

The `internal/` tier handles headers shared between two closely related modules (such as the
binary contract between `core` and `engine` for memory-budget reporting) that do not belong in the
public SDK. Any module not listed as an internal friend cannot include from `internal/`.

## Alternatives Considered

### Option A: Flat header directory at the module root (no `public/private` split)

All headers sit at the module root; the compiler and linker do not distinguish public from private.
Quake, Doom 3, Cocos2d-x, and Godot all use this approach (flat with prefixes or subsystem dirs).

**Why rejected:** There is no mechanical enforcement. Including `../../audio/FooInternal.hpp` from
a renderer module compiles without error, so violations wait for code review. Over hundreds of
modules, architectural debt accumulates faster than review can catch it.

### Option B: Two-tier split (`include/` + `src/`), standard C++ project convention

The conventional C++ layout uses `include/<module>/` for public headers and `src/` for everything
else, as in most CMake-based open-source projects.

**Why rejected:** It has no native `internal/` tier. Encoding the internal/public split in a flat
`include/` tree requires naming conventions like `_internal.hpp`, which have the same enforcement
gap as Option A. A shared root `include/` folder also breaks our invariant that every module is
self-contained with its own `CMakeLists.txt`.

### Option C: Unreal Engine's exact `Public/Private/Internal` (PascalCase)

Adopt UE's exact convention, including PascalCase directory names.

**Why rejected:** We use `lower-kebab-case` for all directories ([ADR-0005](./ADR-0005.md)). We
adopt the semantics of UE's three-tier split and use our own capitalization.

## Consequences

### Positive

- **Enforces encapsulation at the filesystem level.** A boundary violation fails the build
  immediately instead of waiting for code review.
- **Reduces header-inclusion cascades.** A change inside `private/` never triggers recompilation
  in consumers, keeping incremental builds fast.
- **Makes dependency intent explicit.** Reading a module's `CMakeLists.txt` shows which headers
  it exposes and to whom in under 30 lines.
- **Clarity for new readers.** Anyone opening a module sees the three zones right away and knows
  where the API ends and the implementation begins.
- **Enables `internal/` for trusted sub-graphs.** Without the third tier, closely related modules
  must either pollute `public/` or duplicate code.

### Negative

- **Navigation overhead.** Developers must descend one more level to reach source files.
- **Judgment still required.** The build system enforces visibility, while developers still decide
  what belongs in `public/`. Tooling cannot stop a module from leaking implementation types
  through `public/`.
- **`internal/` allowlist maintenance.** Granting internal access to a new module requires updating
  the allowlist during refactors.

## Rationale and Cross-References

Every subsequent layout decision builds on this three-tier split:

- [ADR-0003](./ADR-0003.md): GPBT enforces this at build time via
  `gpAddDependency(PUBLIC|PRIVATE|INTERNAL ...)`.
- [ADR-0004](./ADR-0004.md): Lifecycle directories apply the same separation at the top-level
  `source/` tree.
- [ADR-0006](./ADR-0006.md): Co-located `tests/` and `benchmarks/` directories are siblings of
  `public/` and `private/`.

**Canonical reference:** Unreal Engine 5 Source Tree,
`Engine/Source/Runtime/Core/{Public,Private,Internal}/`.
