# ADR-0034: Sub-Frame Edge Latching and Two-Phase Frame Transition Snapshots

> Naive double-buffered input state arrays (`current[k] && !previous[k]`) silently drop rapid
> sub-frame "micro-clicks" whenever both a `KeyState::Pressed` and `KeyState::Released` event for
> the same button are queued into the `SPSCByteRingBuffer` during a single frame tick. To guarantee
> zero dropped inputs regardless of frame rate or CPU hitches, `gp::hal::input::InputSystem`
> separates continuous hold state (`Held`) from edge-latched transition flags (`PressedThisFrame`,
> `ReleasedThisFrame`, `RepeatedThisFrame`). `beginFrame()` clears the previous frame's edge
> latches and zeroes relative motion deltas prior to pumping OS events, while event ingestion
> latches all intra-frame edges before gameplay `onUpdate()` executes.

![Proposed][badge-proposed]

## Context

Interactive real-time game engines must process peripheral signals arriving from asynchronous
hardware interrupts while running a synchronous, frame-budgeted simulation loop. Bridging
these two domains requires preserving transient input events without introducing
unpredictable execution timing or thread stalls.

### 1. The Sub-Frame Micro-Click Problem

Modern gaming hardware features low-travel optical switches, high-speed controller
triggers, and mechanical keyboard switches designed for rapid actuation. Highly skilled
players in fast-paced genres (competitive first-person shooters, fighting games, and rhythm
titles) tap buttons and click mouse switches in short bursts lasting 5 to 15 milliseconds.

Concurrently, game engine display loops target standard frame intervals:

- 16.6 milliseconds per frame at 60 FPS
- 33.3 milliseconds per frame at 30 FPS
- 50 milliseconds or longer during transient CPU hitches (garbage collection pauses, asset
  streaming spikes, shader pipeline creation, or OS thread scheduling preemption)

When the duration of a button press and release cycle is shorter than the engine's
frame interval, the operating system event pump collects both a press notification and a
release notification within that single frame window. In a multi-threaded architecture with
lock-free communication channels (as described in ADR-0013 and ADR-0026), the OS pump pushes
both `KeyState::Pressed` and `KeyState::Released` event packets into the Game Thread's
`SPSCByteRingBuffer` before the gameplay update tick (`onUpdate()`) begins.

### 2. Failure Mode of Naive Double-Buffered Input Arrays

Traditional game engines often track digital button state using two parallel boolean arrays:
a current state buffer and a previous state buffer:

```cpp
bool m_currentState[kMaxButtons];
bool m_previousState[kMaxButtons];
```

Under this pattern, transition queries evaluate the difference between the two arrays:

```cpp
bool isDown = m_currentState[k];
bool wasJustPressed = m_currentState[k] && !m_previousState[k];
bool wasJustReleased = !m_currentState[k] && m_previousState[k];
```

When events are drained from the cross-thread queue in a single batch at the start of a frame,
the following execution sequence unfolds:

1. **Prior frame state:** Button `k` was unpressed, so `m_previousState[k] == false` and
   `m_currentState[k] == false`.
2. **Press event arrival:** The batch drain pops `KeyState::Pressed` for button `k`:
   `m_currentState[k] = true;`
3. **Release event arrival:** Within the same batch drain, the corresponding
   `KeyState::Released` packet arrives:
   `m_currentState[k] = false;`
4. **Gameplay update execution:** Batch event draining completes. The simulation tick runs
   `onUpdate()`. Gameplay code checks if the player initiated an action by calling
   `wasJustPressed(k)`.
5. **Silent failure:** The query evaluates `m_currentState[k] && !m_previousState[k]`, which
   resolves to `false && !false == false`.

The button actuation is silently discarded. The player pressed and released the button, the
hardware registered the electrical contact, and the operating system delivered the packet.
However, because both edges resolved within a single frame interval, the boolean assignment
overwrote the transition. Discrete player actions (jumping, firing a semi-automatic weapon,
or executing a parry) fail to trigger, creating the impression of unresponsive controls.

```text

OS Queue   Push(Pressed)        Push(Released)
Engine                                              Drain: state = true -> state = false
Query                                               wasJustPressed() == false (DROPPED)
```

Double buffering functions acceptably for continuous inputs (holding a key to run), but
breaks down when handling discrete pulses that occur faster than the frame rate.

## Decision

We standardize on bitflag sub-frame edge latching across all input implementations in
`gp-engine`, specifically within `GenericKeyboard`, `GenericMouse`, `GenericGamepad`, and
`GenericInputSystem`.

### 1. Bitflag Representation: Separating Hold State from Transition Edges

Instead of storing boolean flags, each scancode, keycode, mouse button, and controller button
maintains an 8-bit bitmask defined by `ButtonStateFlags` in
`source/runtime/hal/base/public/input/InputTypes.hpp`:

```cpp
enum class ButtonStateFlags : gp::UInt8
{
    None              = 0,
    Held              = 1 << 0,
    PressedThisFrame  = 1 << 1,
    ReleasedThisFrame = 1 << 2,
    RepeatedThisFrame = 1 << 3
};
```

The bit fields maintain strict semantic separation:

- `Held`: Reflects the physical continuous state of the button at the conclusion of event
  ingestion. If the button is currently held down, the bit is `1`; if released, the bit is `0`.
- `PressedThisFrame`: A sticky edge latch indicating that the button transitioned from up to
  down at least once during this frame interval.
- `ReleasedThisFrame`: A sticky edge latch indicating that the button transitioned from down to
  up at least once during this frame interval.
- `RepeatedThisFrame`: Indicates an operating system key auto-repeat event for text editing or
  repeat handling.

### 2. Transition Logic via `applyTransition`

State transitions are processed through `applyTransition()`, ensuring that intra-frame
releases never erase the activation latch:

```cpp
GP_FORCEINLINE_HINT static constexpr void
applyTransition(ButtonStateFlags& flags, KeyState state, bool isRepeat) noexcept
{
    if (state == KeyState::Pressed)
    {
        if (isRepeat)
        {
            flags |= ButtonStateFlags::Held | ButtonStateFlags::RepeatedThisFrame;
        }
        else if ((flags & ButtonStateFlags::Held) == ButtonStateFlags::None)
        {
            flags |= ButtonStateFlags::Held | ButtonStateFlags::PressedThisFrame;
        }
    }
    else
    {
        if ((flags & ButtonStateFlags::Held) != ButtonStateFlags::None)
        {
            flags = (flags & ~ButtonStateFlags::Held) | ButtonStateFlags::ReleasedThisFrame;
        }
    }
}
```

Under this logic, a sub-frame micro-click preserves all relevant state transitions:

1. **Initial state:** `flags == ButtonStateFlags::None` (`0b0000`).
2. **Press event arrives:** `flags |= Held | PressedThisFrame` results in `flags == 0b0011`.
3. **Release event arrives in same batch:** `flags = (flags & ~Held) | ReleasedThisFrame`.
   The `Held` bit is cleared, but `PressedThisFrame` is untouched. The resulting state is
   `ButtonStateFlags::PressedThisFrame | ButtonStateFlags::ReleasedThisFrame` (`0b0110`).
4. **Gameplay evaluation:**
   - `isKeyDown(k)` queries `(flags & Held) != None` -> returns `false`.
   - `wasKeyJustPressed(k)` queries `(flags & PressedThisFrame) != None` -> returns `true`.
   - `wasKeyJustReleased(k)` queries `(flags & ReleasedThisFrame) != None` -> returns `true`.

The activation edge is safely detected during the frame tick, even though the physical button
is no longer held down when simulation queries run.

### 3. Two-Phase Frame Snapshot Protocol

To maintain deterministic input state throughout the frame tick, `gp-engine` coordinates
per-frame lifecycle updates across two distinct phases:

<!-- markdownlint-disable MD013 -->
```text
Frame N-1 Simulation -> [ Phase 1: beginFrame() ] -> [ Phase 2: Ingestion ] -> Frame N Simulation
                        - Clear edge latches         - Drain SPSC queue        - onUpdate()
                        - Preserve Held bits         - Apply transitions       - Immutable queries
                        - Reset relative deltas      - Accumulate deltas
```
<!-- markdownlint-enable MD013 -->

#### Phase 1: Lifecycle Preparation (`beginFrame()`)

Before pumping operating system events or draining the event ring buffer,
`InputSystem::beginFrame()` invokes `beginFrame()` across all active devices (`Keyboard`,
`Mouse`, `Gamepad`). This step:

- Masks out transient edge flags from the preceding frame while preserving active hold states:

  ```cpp
  for (gp::UInt32 i = 0u; i < kMaxScancodes; ++i)
  {
      m_scancodes[i] &= ButtonStateFlags::Held;
  }
  ```

- Resets accumulated relative motion deltas and mouse wheel offsets to zero:

  ```cpp
  m_delta = Stick2D(0.0f, 0.0f);
  m_wheelDelta = Stick2D(0.0f, 0.0f);
  ```

#### Phase 2: Event Ingestion

The Game Thread drains input packets from the lock-free `SPSCByteRingBuffer`. Each packet
updates the corresponding device:

- Key events invoke `applyTransition()` on the scancode and keycode lookup tables.
- Mouse button events invoke `applyTransition()` on `m_buttons` and update `m_heldMask`.
- Mouse movement events update absolute position coordinates and accumulate relative
  displacements: `m_delta.x += ev.deltaX;` and `m_delta.y += ev.deltaY;`.
- Controller button events invoke `applyTransition()` on controller button arrays.

#### Gameplay Execution

When `onUpdate()` runs, simulation code observes a consistent snapshot. Polling calls
(`isKeyDown()`, `wasButtonJustPressed()`, `getDelta()`) perform direct L1-cache reads from flat
arrays without locking, heap allocations, or state mutation.

### 5. Architectural Invariants

1. **Strict Bitmask Edge Retention:** An intra-frame release transition clears the `Held` bit,
   but must never clear the `PressedThisFrame` latch bit. Edge latches remain sticky until the
   next frame lifecycle boundary.
2. **Deterministic Lifecycle Clearing in `beginFrame()`:** Transient edge flags
   (`PressedThisFrame`, `ReleasedThisFrame`, `RepeatedThisFrame`) and relative motion deltas
   (`deltaX`, `deltaY`, scroll offsets) must only be reset during `beginFrame()`,
   strictly prior to OS event queue drainage.
3. **Zero Dynamic Allocation:** Input state representation across all devices must rely solely
   on pre-allocated, fixed-capacity arrays of primitive bitmasks (`ButtonStateFlags`), avoiding
   heap allocations, pointer chasing, or dynamic collection overhead during event ingestion.
4. **Orthogonal Query Independence:** State getters must evaluate independent bitmask flags.
   Instantaneous hold state (`isKeyDown`), activation edges (`wasKeyJustPressed`), and release
   edges (`wasKeyJustReleased`) remain decoupled, enabling gameplay systems to detect both
   edges of a sub-frame pulse without contradiction.

### 6. Comparative Architectural Matrix

The following table evaluates the trade-offs across common engine input handling approaches:

<!-- markdownlint-disable MD013 -->
| Dimension | Naive Double-Buffered Arrays | Immediate Event Callbacks | Per-Key Event History Queues | Sub-Frame Edge Latching (`gp-engine`) |
| :--- | :--- | :--- | :--- | :--- |
| **Micro-Click Preservation** | Dropped when press and release occur in same frame | Preserved via immediate listener invocation | Preserved via timestamped event queue | Preserved via sticky bitmask edge latches |
| **Frame Hitch Tolerance** | Vulnerable; hitching increases drop probability | Moderate; queues grow, listener ordering degrades | High; queues retain full history | High; sticky flags preserve all transitions |
| **Zero-Allocation Guarantee** | Yes (static boolean arrays) | No (dynamic listener registries or lambda captures) | No (dynamic queue nodes or fixed circular buffers) | Yes (static fixed-capacity `UInt8` arrays) |
| **Query Ergonomics** | Simple polling (`current && !previous`) | Fragmented; requires state accumulation in listeners | Complex; requires iterating event sequences | Ergonomic polling (`wasKeyJustPressed`) |
| **Relative Delta Zeroing** | Requires explicit frame reset step | Inconsistent; depends on callback timing | Requires timestamp filtering | Deterministic reset in `beginFrame()` |
<!-- markdownlint-enable MD013 -->

## Alternatives Considered

### Option A: Naive Double-Buffered Boolean Arrays (`current[k] && !previous[k]`)

Maintain two boolean arrays per device (`m_currentState` and `m_previousState`). Copy
current to previous at the end of each frame, updating current directly as events arrive.

**Why rejected:** Silently drops sub-frame micro-clicks whenever a press and release
occur within the same frame interval. During frame rate drops (such as running at 30 FPS or
encountering CPU load spikes), fast button taps disappear completely.

### Option B: Immediate Event-Driven Callbacks / Lambdas

Dispatch immediate notifications or lambda delegates to registered gameplay listeners as each
event packet is popped from the input ring buffer.

**Why rejected:** Moves gameplay state mutation into arbitrary times during event
drainage. This breaks deterministic simulation order, complicates actor lifecycle
management, and requires heap allocations or dynamic listener registrations.

### Option C: Event History Queue per Key

Maintain a circular event history buffer or linked list of timestamped transitions for every
individual scancode, mouse button, and controller input.

**Why rejected:** Storing dedicated event queues across hundreds of keys and buttons
creates significant memory overhead and fragments data cache locality. Dynamically
allocating event nodes violates the engine's zero-allocation mandate, while fixed-size
circular buffers per key waste memory bandwidth and complicate standard polling queries.

## Consequences

### Positive

- **Guaranteed micro-click capture.** Fast button presses and switch releases occurring
  within a single frame interval are captured reliably, preventing dropped player inputs
  during frame rate dips or CPU load spikes.
- **Zero dynamic allocations.** State updates manipulate compact 8-bit bitmask fields in
  statically sized arrays, avoiding heap allocations or dynamic memory overhead during
  gameplay.
- **Cache-efficient memory layout.** Fixed-capacity arrays of `ButtonStateFlags` keep the
  memory footprint of input devices compact (under 1 KB for `GenericKeyboard`), maximizing
  L1 data cache residence during frame evaluation.
- **Ergonomic polling interfaces.** Gameplay code uses clean query methods (`isKeyDown`,
  `wasKeyJustPressed`, `wasKeyJustReleased`) without managing listener lifetimes or tracking
  manual state booleans.
- **Deterministic two-phase lifecycle.** Decoupling edge clearing in `beginFrame()` from
  event ingestion ensures that input states remain immutable and reliable throughout the
  entire gameplay tick.

### Negative

- **Loss of sub-frame event ordering.** When multiple buttons transition within the same
  frame interval, the bitmask indicates that both occurred, but does not preserve the
  chronological order between them. Systems requiring sub-millisecond sequence verification
  must inspect the raw event stream.
- **Multi-click count compression for keys.** If a keyboard key is pressed, released, and
  pressed again within a single frame interval, the bitmask indicates
  `PressedThisFrame | Held | ReleasedThisFrame`, compressing the two taps into a single
  transition pair. (Mouse devices address this for double clicks using a dedicated hardware
  click counter in `m_clicks`).
