# ADR-0013: Multi-Threaded Event Architecture via Lock-Free Queues and Immutable Frame State

> Mandates that OS events are pumped by a dedicated OS thread into a Single-Producer/Single-Consumer
> lock-free ring buffer, allowing the Game Thread to drain them at the start of a frame to guarantee
> a deterministic, lock-free, immutable input state.

![Proposed][badge-proposed]

## Context

A production AAA game engine is a discrete, real-time dynamical simulation operating under strict
microsecond deadlines at 60 Hz (16.67 ms), 120 Hz (8.33 ms), or 240 Hz (4.17 ms). Operating systems,
by contrast, are asynchronous, interrupt-driven platforms designed for desktop compositing and interactive
multitasking. Reconciling these diametrically opposed execution models represents one of the most
critical architectural challenges in engine engineering:

### 1. The Fundamental OS vs. Game Loop Impedance Mismatch

Operating systems push hardware peripheral and windowing events through asynchronous, platform-specific
message queues that mandate execution on dedicated system threads or re-entrant callbacks:

- **Win32 Message Pumps & Modal Traps:** Win32 ties window messages (`HWND`) to the OS thread that created
  them via thread-bound message queues (`PeekMessageW`, `GetMessageW`, `DispatchMessageW`). When a user
  clicks the window title bar, drags the window, resizes borders, or opens a system context menu, the Win32
  subsystem enters an internal, blocking modal loop inside `DefWindowProc` (`WM_ENTERSIZEMOVE`,
  `WM_SYSCOMMAND`). If the Game Thread executes this message pump directly, the entire engine simulation
  freezes indefinitely, halting physics, dropping network heartbeats, and stalling audio presentation.
- **macOS Cocoa Runloops:** Apple's Cocoa framework demands that `NSApplication`, `NSWindow`, and
  `[NSEvent nextEventMatchingMask:...]` execute strictly on the OS process main thread (`thread 0`).
  Offloading the Game Thread or running real-time simulation on thread 0 creates intractable thread-affinity
  conflicts with Cocoa's event dispatch model.
- **Linux Wayland Compositor Protocols:** Wayland relies on asynchronous, client-driven file descriptor
  polling (`wl_display_dispatch`, `epoll`) and explicit surface commit handshakes (`xdg_shell`). Dropping
  or delaying compositor events can cause the display server to declare the surface unresponsive and kill
  the process.

In contrast, game engines require **state immutability and temporal determinism**. Subsystems such as
character controllers, physics raycasters, camera view-matrix calculators, and user interface widget
trees assume that hardware input (mouse cursor coordinates, analog gamepad triggers, key press states)
remains stationary throughout the evaluation of a single frame tick.

### 2. Failure Modes of Naive Approaches

Naively coupling OS event polling with the real-time simulation leads to severe architectural and runtime
defects:

```text
Naive Synchronous Polling Failure Mode (Mid-Frame State Tearing):

  Frame Timeline [t0 -----------------------------------------------------> t0 + 16.6ms]
  
  Game Thread:  [ Physics Update ] ---------> [ Render Pass ] ------------> [ Presentation ]
                     |                             |
  Mouse Polling:  Query Mouse (X = 100)         Query Mouse (X = 142)  <-- TEARING!
                     |                             |
  Consequence:    Raycast shoots at (100)       Reticle drawn at (142)
                  Hit detection misses the visual target; camera matrix jitters.
```

- **Mid-Frame State Tearing:** Polling the operating system for hardware inputs on demand mid-frame
  causes state tearing. If a character physics step queries the mouse position at $t = 0\text{ ms}$
  ($X = 100$) and the graphics pass constructs the weapon aim matrix at $t = 8\text{ ms}$ ($X = 142$),
  the rendered view model desynchronizes from the simulated collision query. The player experiences
  aim-point jitter, misaligned weapon traces, and missed raycasts.
- **Mutex Contention and Priority Inversion:** Naively synchronizing an event queue using an OS mutex
  (`gp::Mutex`, `std::mutex`, or Win32 `CRITICAL_SECTION`) forces the OS message pump and the Game
  Thread to contend for the same lock. If the Game Thread is descheduled by the OS kernel while holding
  the mutex during an intensive scene graph traversal, the OS message pump stalls. Conversely, high-polling
  gaming peripherals (8,000 Hz esports mice, controller IMUs) flooding the queue with messages force
  repeated kernel context switches (~1–5 $\mu\text{s}$ per contested lock transition), burning CPU
  cycles and blowing the frame budget.
- **False Sharing and Cache-Line Ping-Ponging:** When independent producer and consumer threads write
  to adjacent memory locations on the same 64-byte CPU cache line (e.g., placing `head` and `tail` cursors
  side by side in a naive queue struct), the CPU hardware cache coherency protocol (MESI: Modified,
  Exclusive, Shared, Invalid) continuously invalidates the L1/L2 cache lines across cores. Every enqueue
  forces an interconnect bus transaction (e.g., AMD Infinity Fabric or Intel Ring Bus), degrading cross-core
  throughput.
- **Dynamic Heap Allocation Thrashing:** Constructing polymorphic event objects via `new` or `malloc`
  (e.g., `std::vector<std::unique_ptr<IEvent>>`) on the message pump thread invokes global heap locks,
  fragments virtual memory, and destroys data locality. Under sustained input bursts, memory allocation
  contention destroys the real-time guarantees of the engine.

We require an architectural boundary that isolates the OS event polling loop onto its own thread,
guarantees wait-free and lock-free cross-thread data transport, prevents false sharing at the hardware
cache-line level, and provides the Game Thread with a perfectly coherent, immutable input snapshot per tick.

## Decision

We mandate `gp::SPSCByteRingBuffer`, a bounded, cache-line-isolated Single-Producer Single-Consumer (SPSC)
lock-free byte ring buffer, as the exclusive communication conduit between the OS event pumping thread and
the engine Game Thread.

Events are serialized into a contiguous raw byte stream using Type-Length-Value (TLV) encoding
([ADR-0019](./ADR-0019.md)) containing strictly trivially copyable Plain Old Data (POD) structures
([ADR-0020](./ADR-0020.md)).

```text
+-------------------------------------------------------------------------------------------------+
|                               CROSS-THREAD EVENT PIPELINE ARCHITECTURE                           |
+-------------------------------------------------------------------------------------------------+

 [ Dedicated OS Message Thread ]                           [ Real-Time Game Engine Thread ]
               |                                                          |
  OS Message Pump (Win32 / Cocoa / SDL3)                                   |
               |                                                          |
  Translate native OS event to Engine POD                                 |
               |                                                          |
  Evaluate Backpressure (ADR-0026)                                        |
  [ Shed continuous motion if critical ]                                  |
               |                                                          |
  Write to SPSC Byte Ring Buffer (ADR-0013)                                |
  memory_order_release (m_head)                                           |
               |                                                          |
               +=====================[ 64-Byte Padded ]====================+
               |                  SPSCByteRingBuffer                      |
               |    [Read-Only]  |  [Producer]   |  [Consumer]            |
               |    Buffer Ptr   |  m_head       |  m_tail                |
               |    Capacity/Mask|  m_cachedTail |  m_cachedHead          |
               +==========================================================+
                                                                          |
                                                    Phase 4: Application::drainEventStream()
                                                    memory_order_acquire (m_head)
                                                                          |
                                                    Decode TLV Packets (Zero Heap Allocations)
                                                    |---> WindowEvent   -> Window Shadow State (ADR-0027)
                                                    |---> DisplayEvent  -> Display Topology (ADR-0028)
                                                    |---> Input Events  -> Input State Tables (ADR-0034)
                                                    |---> FocusLost     -> releaseAllInputs() (Anti-Stuck)
                                                                          |
                                                    +---------------------------------------------+
                                                    |  IMMUTABLE INPUT & WINDOW SNAPSHOT CREATED  |
                                                    +---------------------------------------------+
                                                                          |
                                                    Phase 5: Clock Tick & Timestep Accumulation
                                                                          |
                                                    Phase 6: Fixed Physics Simulation (Deterministic)
                                                                          |
                                                    Phase 7: Variable Gameplay Update (Immutable Input)
                                                                          |
                                                    Phase 8: Rendering Presentation (Interpolation α)
```

### 1. Producer Thread Responsibilities (`IApplicationBackend::pumpEvents`)

1. **Dedicated OS Thread Execution:** The operating system backend runs on a dedicated OS message thread
   (or the primary platform thread mandated by Cocoa/Win32) executing `IApplicationBackend::pumpEvents()`
   ([ADR-0010](./ADR-0010.md), [ADR-0011](./ADR-0011.md)).
2. **Translation to Engine PODs:** Raw platform messages (`MSG`, `NSEvent*`, `SDL_Event`) are immediately
   translated into standard-layout, trivially copyable engine POD structures (`WindowEvent`, `KeyboardEvent`,
   `MouseEvent`, `GamepadEvent`, `DisplayEvent`).
3. **TLV Packet Packing:** Each event is preceded by a 4-byte `EventHeader` (`EventCategory` [2 bytes] +
   `payloadSize` [2 bytes]). Variable-length data (such as UTF-8 text strings or file drag-and-drop paths)
   are packed contiguously into trailing payload bytes.
4. **Two-Tier Backpressure Enforcement:** To prevent high-frequency continuous motion packets (such as
   8,000 Hz mouse deltas or controller IMU updates) from exhausting buffer capacity during Game Thread
   hitches, the producer checks available space against `criticalReserveBytes` ([ADR-0026](./ADR-0026.md)).
   Continuous motion events are shed when capacity is constrained, preserving dedicated headroom for discrete
   lifecycle and button-state transitions (`KeyState::Released`, `WindowAction::CloseRequested`).
5. **Non-Blocking Write with Release Semantics:** Data is written into the circular storage using
   `SPSCByteRingBuffer::tryWritePacket()` and committed with an atomic `memory_order_release` store to
   `m_head`. The producer never executes an OS wait, never locks a mutex, and never allocates heap memory.

### 2. Consumer Thread Responsibilities (`Application::drainEventStream`)

1. **Strictly Sequenced Phase 4 Execution:** As defined in [ADR-0012](./ADR-0012.md), the Game Thread
   executes `Application::drainEventStream()` exclusively during **Phase 4** of the frame loop, immediately
   following transient input latch clearing (`beginFrame()`) and preceding clock accumulation and gameplay
   simulation.
2. **Lock-Free TLV Packet Decoding:** The consumer peeks packet headers from the ring buffer using
   `tryPeekAt()`. If a full packet is present, it copies the POD payload directly into stack-allocated
   structures via `gp::detail::consumeFixedPayload()`, advancing `m_tail` with an atomic
   `memory_order_release` store.
3. **Shadow State Synchronization:**
   - `WindowEvent` packets update the thread-safe local cache of `gp::hal::generic::Window`
     ([ADR-0027](./ADR-0027.md)), enabling lock-free L1-cache queries for window dimensions, DPI, and focus.
   - `DisplayEvent` packets synchronize display topology tables and HDR metadata in
     `gp::hal::generic::Display` ([ADR-0028](./ADR-0028.md), [ADR-0029](./ADR-0029.md)).
   - Input packets update edge-detection arrays and analog tables in `IInputSystem` ([ADR-0034](./ADR-0034.md)).
4. **Stuck-Key Sanitization:** If a window loses focus (`WindowAction::FocusLost`), minimizes, or hides,
   the consumer calls `m_inputSystem->releaseAllInputs()`, neutralizing orphaned key-down states caused
   by the OS swallowing key-up messages during window switching.
5. **Establishment of the Immutable Input Snapshot:** Once `drainEventStream()` drains the ring buffer,
   Phase 4 terminates. The entire state of hardware input, window geometry, and device topology is frozen.
   All subsequent simulation sub-steps (`onFixedUpdate()`), gameplay scripts (`onUpdate()`), and graphics
   command builders (`onRender()`) read this immutable snapshot without fear of mid-frame state mutation.

### 3. Memory Layout & MESI Cache-Line Isolation

To prevent hardware false sharing between the OS Producer Thread and the Game Consumer Thread,
`gp::SPSCByteRingBuffer` enforces a strict 3-tier, 64-byte aligned memory layout adhering to
[ADR-0025](./ADR-0025.md):

```text
+-------------------------------------------------------------------------------------------------+
|                         SPSCByteRingBuffer PHYSICAL CACHE-LINE LAYOUT                           |
+-------------------------------------------------------------------------------------------------+

 Cache Line 0 (Read-Only Zone): 64 Bytes [alignas(64)]
 +-----------------------------------+-------------------+-------------------+-------------------+
 | m_buffer (PointerType)            | m_capacity (USize)| m_mask (USize)    | m_allocator (Ptr) |
 | 8 Bytes                           | 8 Bytes           | 8 Bytes           | 8 Bytes           |
 +-----------------------------------+-------------------+-------------------+-------------------+
 | m_ownsMemory (bool)               | Padding to 64 Bytes                                       |
 | 1 Byte                            | 31 Bytes                                                  |
 +-----------------------------------+-----------------------------------------------------------+

 Cache Line 1 (Producer-Modified Zone): 64 Bytes [alignas(64)]
 +-------------------------------------------------------+---------------------------------------+
 | m_head (gp::Atomic<USize>)                            | m_cachedTail (USize)                  |
 | 8 Bytes (Written by Producer via Release)             | 8 Bytes (Local shadow copy of tail)   |
 +-------------------------------------------------------+---------------------------------------+
 | Padding to 64 Bytes                                                                           |
 | 48 Bytes                                                                                      |
 +-----------------------------------------------------------------------------------------------+

 Cache Line 2 (Consumer-Modified Zone): 64 Bytes [alignas(64)]
 +-------------------------------------------------------+---------------------------------------+
 | m_tail (gp::Atomic<USize>)                            | m_cachedHead (USize)                  |
 | 8 Bytes (Written by Consumer via Release)             | 8 Bytes (Local shadow copy of head)   |
 +-------------------------------------------------------+---------------------------------------+
 | Padding to 64 Bytes                                                                           |
 | 48 Bytes                                                                                      |
 +-----------------------------------------------------------------------------------------------+

 Static Size & Alignment Contract:
   static_assert(sizeof(SPSCByteRingBuffer) == 3u * 64u);
   static_assert(alignof(SPSCByteRingBuffer) == 64u);
```

- **Cache Line 0 (Read-Only Zone):** Initialized once during startup. Read concurrently by both threads
  without synchronization because immutable data cannot trigger cache invalidations under the MESI protocol
  (cores hold the line in the `Shared` state indefinitely).
- **Cache Line 1 (Producer-Modified Zone):** Contains `m_head` (the atomic write cursor modified exclusively
  by the OS thread) and `m_cachedTail` (a thread-local shadow copy of the consumer's read cursor). The OS
  core holds this line in the `Modified` or `Exclusive` state. The Game Thread never writes to this line.
- **Cache Line 2 (Consumer-Modified Zone):** Contains `m_tail` (the atomic read cursor modified exclusively
  by the Game Thread) and `m_cachedHead` (a thread-local shadow copy of the producer's write cursor). The
  Game Thread core holds this line in the `Modified` or `Exclusive` state. The OS thread never writes to
  this line.
- **Shadow Index Caching:** When the producer checks for free capacity (`canWrite()`), it compares `m_head`
  against its private `m_cachedTail`. It only incurs an atomic load with `memory_order_acquire` against the
  real `m_tail` when the cached calculation indicates that the buffer is full. Symmetrically, the consumer
  only reads `m_head` via `memory_order_acquire` when its local `m_cachedHead` indicates the buffer is empty.
  This reduces inter-core interconnect bus traffic by more than 99% during typical frame execution.

### 4. Architectural Invariants

Every subsystem interacting with cross-thread event routing must strictly uphold the following invariants:

1. **Power-of-Two Capacity & Bitmask Wrapping:** Backing memory capacity must be strictly $2^N$ bytes
   ($N \ge 1$). Circular array index wrapping is computed via bitwise masking (`index & m_mask`), replacing
   expensive integer division/modulo instructions (`idiv`, taking 15–40 CPU cycles) with a single-cycle
   bitwise AND (`and`, 1 CPU cycle).
2. **Strict Cache-Line Separation:** Producer and consumer state variables must reside on distinct 64-byte
   cache lines (`HardwareConstants::cacheLineSize`). Mixing read-only, producer, or consumer variables
   on the same cache line violates compile-time static assertions.
3. **Acquire-Release Synchronization with Zero Sequential Consistency Overhead:** All cross-thread
   visibility is achieved strictly via `memory_order_release` on cursor stores and `memory_order_acquire`
   on cursor loads. `memory_order_seq_cst` (which emits heavy `MFENCE` or `LOCK` prefixes on x86-64 and
   full memory barriers on ARM64) is strictly forbidden on the event routing hot path.
4. **Zero Mutex Locks and Zero Heap Allocations:** Steady-state event polling, translation, queuing,
   draining, and dispatching must never invoke OS mutexes, condition variables, `malloc`, `new`, or standard
   library allocators. All buffer memory is pre-allocated during application initialization.
5. **Immutable Input Snapshot Guarantee:** Intra-frame polling of raw OS events is strictly prohibited.
   Input state is modified exclusively during Phase 4 (`drainEventStream()`). Once Phase 4 concludes,
   input state is read-only for the remainder of the frame, guaranteeing identical input observations across
   all simulation and rendering sub-systems.
6. **Two-Tier Backpressure and Critical Headroom Reservation:** The producer must prioritize discrete
   lifecycle and button-release events over high-frequency continuous motion packets. When free space in
   the ring buffer drops below `criticalReserveBytes`, continuous motion packets must be shed immediately
   to prevent input desynchronization.

### 6. C++ Implementation Mechanics

#### Producer Side: Two-Tier Admission & Packet Packing (`SDL3ApplicationBackend.cpp`)

```cpp
template <typename PayloadT>
GP_FORCEINLINE_HINT void ApplicationBackend::commitFixedEvent(
    gp::SPSCByteRingBuffer& stream,
    gp::hal::event::EventCategory category,
    const PayloadT& payload,
    bool isContinuous,
    EventPumpStats& stats
) const noexcept
{
    constexpr gp::USize kTotalPacketBytes = sizeof(gp::hal::event::EventHeader) + sizeof(PayloadT);

    // Tier 1 Backpressure: Shed continuous motion if remaining capacity is within the critical reserve
    if (isContinuous && !stream.canWrite(kTotalPacketBytes + m_config.criticalReserveBytes)) [[unlikely]]
    {
        ++stats.shedContinuousCount;
        return;
    }

    const gp::hal::event::EventHeader header{
        .category = category,
        .payloadSize = static_cast<gp::UInt16>(sizeof(PayloadT))
    };

    // Atomic push with memory_order_release
    if (stream.tryWritePacket(header, &payload, sizeof(PayloadT))) [[likely]]
    {
        ++stats.pushedCount;
        stats.bytesWritten += kTotalPacketBytes;
    }
    else
    {
        ++stats.droppedCriticalCount;
    }
}
```

#### Consumer Side: Fixed Payload Consumption (`Application.cpp`)

```cpp
namespace gp::detail
{
template <typename PayloadT>
[[nodiscard]] GP_FORCEINLINE_HINT bool
consumeFixedPayload(gp::SPSCByteRingBuffer& stream, PayloadT& outPayload) noexcept
{
    // Peek payload bytes following the 4-byte EventHeader
    if (!stream.tryPeekAt(sizeof(hal::event::EventHeader), &outPayload, sizeof(PayloadT))) [[unlikely]]
    {
        return false;
    }
    // Commit consumption by advancing tail cursor with memory_order_release
    stream.advanceConsumer(sizeof(hal::event::EventHeader) + sizeof(PayloadT));
    return true;
}
} // namespace gp::detail

void Application::drainEventStream() noexcept
{
    while (!m_eventStream.isEmptyApprox())
    {
        hal::event::EventHeader header{};
        if (!m_eventStream.tryPeekAt(0u, &header, sizeof(hal::event::EventHeader))) [[unlikely]]
        {
            break;
        }

        const gp::USize totalPacketBytes = sizeof(hal::event::EventHeader) + header.payloadSize;
        if (!m_eventStream.canRead(totalPacketBytes)) [[unlikely]]
        {
            break;
        }

        switch (header.category)
        {
        case hal::event::EventCategory::Keyboard:
        {
            hal::event::KeyboardEvent ev{};
            if (gp::detail::consumeFixedPayload(m_eventStream, ev))
            {
                m_inputSystem->onKeyboardEvent(ev);
                onKeyboardEvent(ev);
            }
            break;
        }
        case hal::event::EventCategory::Window:
        {
            hal::event::WindowEvent ev{};
            if (gp::detail::consumeFixedPayload(m_eventStream, ev))
            {
                if (m_mainWindow.isValid() && m_mainWindow->getId() == ev.windowId)
                {
                    m_mainWindow->onWindowEvent(ev); // Updates L1 Window Shadow State
                }
                if (ev.action == hal::event::WindowAction::FocusLost)
                {
                    m_inputSystem->releaseAllInputs(); // Anti-stuck key sanitization
                }
                onWindowEvent(ev);
            }
            break;
        }
        // Additional TLV categories handled uniformly...
        default:
            m_eventStream.advanceConsumer(totalPacketBytes);
            break;
        }
    }
}
```

## Alternatives Considered

<!-- markdownlint-disable MD013 -->
| Architectural Option | Synchronization Mechanism | Thread Stall Risk | Cache Coherency Cost | Allocation Overhead | Verdict |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **SPSC Lock-Free Ring Buffer (Adopted)** | Acquire-Release Atomic Cursors | **Zero** (Completely Non-Blocking) | **Minimal** (64-byte isolated cache lines) | **Zero** (Pre-allocated steady state) | **Adopted** |
| **Mutex-Guarded Event Queue** | OS Mutex / Futex System Call | **High** (Priority inversion, OS stalls) | **Severe** (Cache ping-pong on lock word) | High if backing array resizes | **Rejected** |
| **Synchronous Game Thread Polling** | Single-Threaded Inline OS Dispatch | **Catastrophic** (Win32 modal drag freezes) | None (Single thread) | Moderate depending on OS backend | **Rejected** |
| **MPMC Lock-Free Queue** | Atomic CAS Loops / Atomic RMW | **Moderate** (Contention retry storms) | **High** (False sharing across many cores) | High (Requires linked nodes or hazard pointers) | **Rejected** |
<!-- markdownlint-enable MD013 -->

### Option A: Mutex-Guarded Event Queue (`gp::Mutex` + `gp::Vector<Event>`)

Protecting an event container with an operating system mutual exclusion primitive (e.g. `gp::Mutex`,
`std::mutex`, or Win32 `CRITICAL_SECTION`).

**Why rejected:**
1. **Priority Inversion and Thread Stalls:** If the Game Thread is preempted by the OS kernel scheduler
   while holding the mutex during an intensive frame calculation, the dedicated OS message thread is
   blocked from ingesting hardware messages. This causes OS message queue overflows, missed window
   lifecycle events, and dropped device notifications.
2. **Kernel Context Switch Overhead:** When contention occurs, OS mutexes transition from user-space
   atomic spinloops to kernel sleep states (e.g. `WaitOnAddress`, Linux `futex`). Entering the kernel
   incurs a $1,000\text{–}5,000\text{ ns}$ scheduling penalty per contention event, introducing frame-time
   spikes.
3. **Severe Scalability Limits under High-Polling Hardware:** Modern esports gaming mice poll at rates
   up to 8,000 Hz (one event every $125\text{ }\mu\text{s}$). Contending for a mutex at this frequency
   severely degrades overall CPU cache throughput and robs the Game Thread of its frame budget.

### Option B: Direct Synchronous Polling on Game Thread

Polling operating system messages directly from the Game Thread via synchronous platform calls (e.g.
`PeekMessageW` or `SDL_PollEvent`) inline within the game loop.

**Why rejected:**
1. **Win32 Modal Loop Trapping:** When a user resizes or drags a window, Win32 enters an internal
   blocking modal loop inside `DefWindowProc`. If the Game Thread runs the message pump, the entire engine
   freezes until the user releases the mouse button. Background tasks, audio streaming, and network
   simulation are completely suspended.
2. **Mid-Frame State Tearing:** Subsystems executing later in the frame (such as rendering command encoders)
   that query hardware input directly observe updated coordinates compared to subsystems executing earlier
   (such as physics integrators), causing camera stutter and visual misalignment.
3. **Platform Thread-Affinity Collisions:** On platforms such as macOS (Cocoa), windowing APIs must run
   on process thread 0. If the Game Thread is hosted on a worker thread or managed by a job system task
   graph, direct synchronous polling is fundamentally impossible without violating OS architectural rules.

### Option C: Multi-Producer Multi-Consumer (MPMC) Queue

Adopting a general-purpose Multi-Producer Multi-Consumer lock-free queue (such as Dmitry Vyukov's MPMC
bounded queue or MoodyCamel's ConcurrentQueue).

**Why rejected:**
1. **Unnecessary Atomic Contention:** MPMC queues rely on atomic Compare-And-Swap (`CAS`, `cmpxchg`) loops
   or ticketed sequence numbers to arbitrate among multiple concurrent writers and readers. Because the
   hardware-to-engine event stream is strictly **Single-Producer** (the OS thread) and **Single-Consumer**
   (the Game Thread), paying the hardware synchronization overhead of CAS retry loops is completely
   unjustified.
2. **False Sharing and Memory Traffic:** MPMC structures must synchronize sequence counters across all
   participating cores, triggering heavy inter-core interconnect bus transactions. In contrast, an SPSC
   queue requires only unidirectional head/tail synchronization, which can be further amortized using
   shadow index caching.
3. **Complexity & Pedagogical Value:** MPMC queues introduce substantial architectural complexity
   (handling ABA problems, memory reclamation, hazard pointers). Using an SPSC queue provides maximum
   runtime efficiency while maintaining perfect pedagogical transparency for students deconstructing
   engine concurrency.

## Consequences

### Positive

- **Strict intra-frame determinism and elimination of state tearing.** Draining all pending OS events
  in a single batch at Phase 4 freezes the input and window state for the entire frame tick, guaranteeing
  that physics simulation, gameplay updates, and render passes operate on a completely coherent, immutable
  snapshot.
- **Total elimination of OS thread blocking and mutex synchronization overhead.** The OS thread pushes
  events into the ring buffer via non-blocking, wait-free pointer increments with release semantics,
  preventing Game Thread hitches from stalling the platform message pump or triggering OS priority inversion.
- **Zero runtime heap allocations during steady-state input streaming.** Backing ring buffer storage
  is pre-allocated during engine initialization; event ingestion and draining operate entirely on stack-allocated
  POD structures and inline memory copies, completely eliminating runtime memory fragmentation and allocator
  contention.
- **Optimal hardware cache-line utilization and zero false sharing.** By explicitly padding and aligning
  `m_head` and `m_tail` to distinct 64-byte cache lines, the engine eliminates MESI cache ping-ponging
  between CPU cores, allowing both threads to execute at full memory interconnect bandwidth.
- **Resilience against OS modal drag loops and high-polling peripheral saturation.** Offloading OS message
  pumping to a dedicated thread prevents Win32 modal drag/resize loops from freezing the game loop, while
  two-tier backpressure shedding shields the buffer from being overwhelmed by 8,000 Hz gaming peripherals.

### Negative

- **Fixed bounded buffer capacity and potential packet shedding.** Because the ring buffer is statically
  sized to avoid runtime allocations, an extreme Game Thread stall combined with high input volume can
  fill the buffer, requiring the engine to shed continuous motion packets or drop events.
- **One-frame maximum input latency amortized across the frame budget.** Events queued by the OS thread
  immediately after Phase 4 has executed will not be consumed until Phase 4 of the subsequent frame tick,
  introducing an intrinsic latency bounded by the frame time ($\le 8.33\text{ ms}$ at 120 Hz).
- **Structural boilerplate and serialization discipline required for variable-length payloads.** Developers
  cannot pass arbitrary C++ objects with dynamic pointers across the boundary; all event structures must
  strictly adhere to Plain Old Data (POD) layouts, requiring explicit length tracking and stack packing
  for variable-length UTF-8 strings or dropped file paths.
