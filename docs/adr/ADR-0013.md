# ADR-0013: Multi-Threaded Event Architecture via Lock-Free Queues and Immutable Frame State

> Mandates that a dedicated OS thread pumps OS events into a Single-Producer/Single-Consumer
> lock-free ring buffer, letting the Game Thread drain them at frame start for an immutable input
> state.

![Proposed][badge-proposed]

## Context

A game engine runs a discrete simulation on microsecond budgets at 60 Hz (16.67 ms), 120 Hz
(8.33 ms), or 240 Hz (4.17 ms). Operating systems, by contrast, are asynchronous and
interrupt-driven, built for desktop compositing and multitasking. Reconciling these two models is
a central challenge in engine architecture.

### 1. OS vs. game loop impedance mismatch

Operating systems deliver peripheral and windowing events through asynchronous, platform-specific
queues that require dedicated threads or re-entrant callbacks:

- **Win32 message pumps and modal traps:** Win32 ties window messages (`HWND`) to the thread that
  created them via thread-bound queues (`PeekMessageW`, `GetMessageW`, `DispatchMessageW`). When a
  user drags a title bar, resizes borders, or opens a system menu, Win32 enters a blocking modal
  loop inside `DefWindowProc` (`WM_ENTERSIZEMOVE`, `WM_SYSCOMMAND`). Running this pump on the Game
  Thread freezes simulation, network heartbeats, and audio.
- **macOS Cocoa runloops:** Cocoa requires `NSApplication`, `NSWindow`, and
  `[NSEvent nextEventMatchingMask:...]` to run on the process main thread (`thread 0`). Running
  real-time simulation on thread 0 conflicts with Cocoa's event dispatch.
- **Linux Wayland compositor protocols:** Wayland uses asynchronous file descriptor polling
  (`wl_display_dispatch`, `epoll`) and surface commit handshakes (`xdg_shell`). Delaying compositor
  events can cause the display server to mark the surface unresponsive and kill the process.

Game engines, meanwhile, require state immutability and temporal determinism. Character controllers,
physics raycasters, camera matrices, and UI widget trees assume hardware input (mouse coordinates,
gamepad triggers, key states) stays constant across a single frame tick.

### 2. Failure modes of naive approaches

Coupling OS event polling directly to simulation causes four runtime defects:

```text
Naive Synchronous Polling Failure Mode (Mid-Frame State Tearing):

  Frame Timeline [t0 -----------------------------------------------------> t0 + 16.6ms]
  
  Game Thread:  [ Physics Update ] ---------> [ Render Pass ] ------------> [ Presentation ]
                     |                             |
  Mouse Polling:  Query Mouse (X = 100)         Query Mouse (X = 142)  <-- TEARING!
                     |                             |
  Consequence:    Raycast shoots at (100)       Reticle drawn at (142)
                  Hit detection misses the visual target; camera matrix jitters.
```

- **Mid-frame state tearing:** Polling hardware inputs on demand mid-frame tears state. If physics
  reads the mouse at $t = 0\text{ ms}$ ($X = 100$) and rendering builds the aim matrix at
  $t = 8\text{ ms}$ ($X = 142$), the view model desynchronizes from the collision query, causing
  aim jitter and missed raycasts.
- **Mutex contention and priority inversion:** Guarding an event queue with an OS mutex
  (`gp::Mutex`, `std::mutex`, or Win32 `CRITICAL_SECTION`) makes the OS message pump and Game
  Thread contend for the same lock. If the kernel deschedules the Game Thread while it holds the
  mutex, the OS message pump stalls. High-polling peripherals (8,000 Hz esports mice, controller
  IMUs) also trigger repeated kernel context switches (~1-5 $\mu\text{s}$ per contended lock),
  eating into the frame budget.
- **False sharing and cache-line ping-ponging:** When producer and consumer threads write to
  adjacent fields on the same 64-byte cache line (such as `head` and `tail` side by side in a
  queue struct), MESI cache coherency invalidates L1/L2 lines across cores on every write, forcing
  interconnect bus traffic (AMD Infinity Fabric or Intel Ring Bus).
- **Heap allocation thrashing:** Allocating polymorphic event objects with `new` or `malloc`
  (`std::vector<std::unique_ptr<IEvent>>`) on the pump thread hits global heap locks, fragments
  memory, and breaks data locality under input bursts.

We need a boundary that isolates OS event polling onto its own thread, transports data lock-free
without false sharing, and hands the Game Thread an immutable input snapshot each tick.

## Decision

We mandate `gp::SPSCByteRingBuffer`, a bounded, cache-line-isolated Single-Producer Single-Consumer
(SPSC) lock-free byte ring buffer, as the sole conduit between the OS event thread and the Game
Thread.

Events are serialized into a contiguous byte stream using Type-Length-Value (TLV) encoding
([ADR-0019](./ADR-0019.md)) with trivially copyable Plain Old Data (POD) structures
([ADR-0020](./ADR-0020.md)).

```text
+-------------------------------------------------------------------------------------------------+
|                               CROSS-THREAD EVENT PIPELINE ARCHITECTURE                          |
+-------------------------------------------------------------------------------------------------+

 [ Dedicated OS Message Thread ]                     [ Real-Time Game Engine Thread ]
               |                                                    |
  OS Message Pump (Win32 / Cocoa / SDL3)                            |
               |                                                    |
  Translate native OS event to Engine POD                           |
               |                                                    |
  Evaluate Backpressure (ADR-0026)                                  |
  [ Shed continuous motion if critical ]                            |
               |                                                    |
  Write to SPSC Byte Ring Buffer (ADR-0013)                         |
  memory_order_release (m_head)                                     |
               |                                                    |
               +=====================[ 64-Byte Padded ]====================+
               |                  SPSCByteRingBuffer                      |
               |    [Read-Only]  |  [Producer]   |  [Consumer]            |
               |    Buffer Ptr   |  m_head       |  m_tail                |
               |    Capacity/Mask|  m_cachedTail |  m_cachedHead          |
               +==========================================================+
                                                                    |
                                         Phase 4: Application::drainEventStream()
                                         memory_order_acquire (m_head)
                                                                    |
                                         Decode TLV Packets (Zero Heap Allocations)
                                         |---> WindowEvent  -> Window Shadow State (ADR-0027)
                                         |---> DisplayEvent -> Display Topology (ADR-0028)
                                         |---> Input Events -> Input State Tables (ADR-0034)
                                         |---> FocusLost    -> releaseAllInputs() (Anti-Stuck)
                                                                    |
                                         +---------------------------------------------+
                                         |  IMMUTABLE INPUT & WINDOW SNAPSHOT CREATED  |
                                         +---------------------------------------------+
                                                                    |
                                         Phase 5: Clock Tick & Timestep Accumulation
                                                                    |
                                         Phase 6: Fixed Physics Simulation (Deterministic)
                                                                    |
                                         Phase 7: Variable Gameplay Update (Immutable Input)
                                                                    |
                                         Phase 8: Rendering Presentation (Interpolation alpha)
```

### 1. Producer thread responsibilities (`IApplicationBackend::pumpEvents`)

1. **Dedicated OS thread execution:** The OS backend runs on a dedicated OS message thread (or the
   main thread mandated by Cocoa/Win32), calling `IApplicationBackend::pumpEvents()`
   ([ADR-0010](./ADR-0010.md), [ADR-0011](./ADR-0011.md)).
2. **Translation to engine PODs:** Native platform messages (`MSG`, `NSEvent*`, `SDL_Event`) are
   translated into standard-layout, trivially copyable POD structs (`WindowEvent`,
   `KeyboardEvent`, `MouseEvent`, `GamepadEvent`, `DisplayEvent`).
3. **TLV packet packing:** Each event starts with a 4-byte `EventHeader` (`EventCategory` [2 bytes]
   + `payloadSize` [2 bytes]). Variable-length data (UTF-8 strings or drag-and-drop file paths) is
   packed into trailing payload bytes.
4. **Two-tier backpressure:** To keep continuous motion packets (such as 8,000 Hz mouse deltas or
   IMU updates) from filling the buffer during Game Thread hitches, the producer checks free space
   against `criticalReserveBytes` ([ADR-0026](./ADR-0026.md)). Continuous motion events are dropped
   when space is tight, reserving headroom for discrete lifecycle and button-state transitions
   (`KeyState::Released`, `WindowAction::CloseRequested`).
5. **Non-blocking write with release semantics:** Data is written via
   `SPSCByteRingBuffer::tryWritePacket()` and committed with an atomic `memory_order_release` store
   to `m_head`. The producer never waits on the OS, locks a mutex, or allocates heap memory.

### 2. Consumer thread responsibilities (`Application::drainEventStream`)

1. **Phase 4 execution:** Per [ADR-0012](./ADR-0012.md), the Game Thread runs
   `Application::drainEventStream()` during Phase 4 of the frame loop, right after `beginFrame()`
   clears transient input latches and before clock accumulation and simulation.
2. **Lock-free TLV decoding:** The consumer peeks packet headers with `tryPeekAt()`. When a full
   packet is available, it copies the POD payload into stack-allocated structs via
   `gp::detail::consumeFixedPayload()`, advancing `m_tail` with `memory_order_release`.
3. **Shadow state synchronization:**
   - `WindowEvent` packets update the local cache in `gp::hal::generic::Window`
     ([ADR-0027](./ADR-0027.md)) for lock-free L1 queries of window dimensions, DPI, and focus.
   - `DisplayEvent` packets update display topology tables and HDR metadata in
     `gp::hal::generic::Display` ([ADR-0028](./ADR-0028.md), [ADR-0029](./ADR-0029.md)).
   - Input packets update edge-detection arrays and analog tables in `IInputSystem`
     ([ADR-0034](./ADR-0034.md)).
4. **Stuck-key sanitization:** If a window loses focus (`WindowAction::FocusLost`), minimizes, or
   hides, the consumer calls `m_inputSystem->releaseAllInputs()`, clearing orphaned key-down states
   left when the OS swallows key-up messages during window switching.
5. **Immutable input snapshot:** Once `drainEventStream()` finishes Phase 4, hardware input, window
   geometry, and device topology stay frozen for the rest of the frame. `onFixedUpdate()`,
   `onUpdate()`, and `onRender()` read this snapshot without mid-frame mutation.

### 3. Memory layout and MESI cache-line isolation

To prevent false sharing between the OS Producer Thread and the Game Consumer Thread,
`gp::SPSCByteRingBuffer` uses a 3-tier, 64-byte aligned memory layout per [ADR-0025](./ADR-0025.md):

```text
+-------------------------------------------------------------------------------------------------+
|                         SPSCByteRingBuffer PHYSICAL CACHE-LINE LAYOUT                           |
+-------------------------------------------------------------------------------------------------+

 Cache Line 0 (Read-Only Zone): 64 Bytes [alignas(64)]
 +-----------------------------------+-------------------+-------------------+-------------------+
 | m_buffer (PointerType)            | m_capacity (USize)| m_mask (USize)    | m_allocator (Ptr) |
 | 8 Bytes                           | 8 Bytes           | 8 Bytes           | 8 Bytes           |
 +-----------------------------------+-------------------+-------------------+-------------------+
 | m_ownsMemory (bool)               | Padding to 64 Bytes                                       |
 | 1 Byte                            | 31 Bytes                                                  |
 +-----------------------------------+-----------------------------------------------------------+

 Cache Line 1 (Producer-Modified Zone): 64 Bytes [alignas(64)]
 +-------------------------------------------------------+---------------------------------------+
 | m_head (gp::Atomic<USize>)                            | m_cachedTail (USize)                  |
 | 8 Bytes (Written by Producer via Release)             | 8 Bytes (Local shadow copy of tail)   |
 +-------------------------------------------------------+---------------------------------------+
 | Padding to 64 Bytes                                                                           |
 | 48 Bytes                                                                                      |
 +-----------------------------------------------------------------------------------------------+

 Cache Line 2 (Consumer-Modified Zone): 64 Bytes [alignas(64)]
 +-------------------------------------------------------+---------------------------------------+
 | m_tail (gp::Atomic<USize>)                            | m_cachedHead (USize)                  |
 | 8 Bytes (Written by Consumer via Release)             | 8 Bytes (Local shadow copy of head)   |
 +-------------------------------------------------------+---------------------------------------+
 | Padding to 64 Bytes                                                                           |
 | 48 Bytes                                                                                      |
 +-----------------------------------------------------------------------------------------------+

 Static Size & Alignment Contract:
   static_assert(sizeof(SPSCByteRingBuffer) == 3u * 64u);
   static_assert(alignof(SPSCByteRingBuffer) == 64u);
```

- **Cache Line 0 (Read-Only Zone):** Initialized once at startup. Both threads read it concurrently
  without synchronization because immutable data causes no MESI invalidations (cores hold the line
  in `Shared` state).
- **Cache Line 1 (Producer-Modified Zone):** Holds `m_head` (written only by the OS thread) and
  `m_cachedTail` (the producer's local shadow of `m_tail`). The OS core holds this line in
  `Modified` or `Exclusive` state; the Game Thread never writes to it.
- **Cache Line 2 (Consumer-Modified Zone):** Holds `m_tail` (written only by the Game Thread) and
  `m_cachedHead` (the consumer's local shadow of `m_head`). The Game Thread core holds this line in
  `Modified` or `Exclusive` state; the OS thread never writes to it.
- **Shadow index caching:** When checking free space (`canWrite()`), the producer compares `m_head`
  against `m_cachedTail`, and only performs an `acquire` load of `m_tail` when the cached check
  looks full. The consumer likewise loads `m_head` with `acquire` only when `m_cachedHead` looks
  empty. This cuts inter-core interconnect traffic by over 99% during normal frames.

### 4. Architectural invariants

Subsystems participating in cross-thread event routing must uphold six invariants:

1. **Power-of-two capacity and bitmask wrapping:** Buffer capacity must be $2^N$ bytes ($N \ge 1$).
   Index wrapping uses bitwise AND (`index & m_mask`, 1 cycle) instead of integer division/modulo
   (`idiv`, 15-40 cycles).
2. **Cache-line separation:** Producer and consumer variables must stay on separate 64-byte cache
   lines (`HardwareConstants::cacheLineSize`), checked by `static_assert`.
3. **Acquire-release synchronization:** Cross-thread visibility uses `memory_order_release` on
   cursor stores and `memory_order_acquire` on cursor loads. `memory_order_seq_cst` (which emits
   `MFENCE`/`LOCK` on x86-64 and full barriers on ARM64) is forbidden on the hot path.
4. **Zero mutexes and zero heap allocations:** Steady-state polling, translation, queuing, draining,
   and dispatching must never touch OS mutexes, condition variables, `malloc`, or `new`. All buffer
   storage is allocated at startup.
5. **Immutable input snapshot:** Intra-frame polling of raw OS events is forbidden. Input state
   updates only in Phase 4 (`drainEventStream()`), remaining read-only for the rest of the frame.
6. **Two-tier backpressure:** When free space falls below `criticalReserveBytes`, continuous motion
   packets must be dropped immediately to protect discrete lifecycle and button-release events.

### 6. C++ implementation mechanics

#### Producer side: two-tier admission and packet packing (`SDL3ApplicationBackend.cpp`)

```cpp
template <typename PayloadT>
GP_FORCEINLINE_HINT void ApplicationBackend::commitFixedEvent(
    gp::SPSCByteRingBuffer& stream,
    gp::hal::event::EventCategory category,
    const PayloadT& payload,
    bool isContinuous,
    EventPumpStats& stats
) const noexcept
{
    constexpr gp::USize kTotalPacketBytes =
        sizeof(gp::hal::event::EventHeader) + sizeof(PayloadT);

    // Tier 1 Backpressure: shed continuous motion inside critical reserve
    const gp::USize requiredBytes = kTotalPacketBytes + m_config.criticalReserveBytes;
    if (isContinuous && !stream.canWrite(requiredBytes)) [[unlikely]]
    {
        ++stats.shedContinuousCount;
        return;
    }

    const gp::hal::event::EventHeader header{
        .category = category,
        .payloadSize = static_cast<gp::UInt16>(sizeof(PayloadT))
    };

    // Atomic push with memory_order_release
    if (stream.tryWritePacket(header, &payload, sizeof(PayloadT))) [[likely]]
    {
        ++stats.pushedCount;
        stats.bytesWritten += kTotalPacketBytes;
    }
    else
    {
        ++stats.droppedCriticalCount;
    }
}
```

#### Consumer side: fixed payload consumption (`Application.cpp`)

```cpp
namespace gp::detail
{
template <typename PayloadT>
[[nodiscard]] GP_FORCEINLINE_HINT bool
consumeFixedPayload(gp::SPSCByteRingBuffer& stream, PayloadT& outPayload) noexcept
{
    // Peek payload bytes following the 4-byte EventHeader
    constexpr gp::USize kHeaderBytes = sizeof(hal::event::EventHeader);
    if (!stream.tryPeekAt(kHeaderBytes, &outPayload, sizeof(PayloadT))) [[unlikely]]
    {
        return false;
    }
    // Commit consumption by advancing tail cursor with memory_order_release
    stream.advanceConsumer(kHeaderBytes + sizeof(PayloadT));
    return true;
}
} // namespace gp::detail

void Application::drainEventStream() noexcept
{
    while (!m_eventStream.isEmptyApprox())
    {
        hal::event::EventHeader header{};
        if (!m_eventStream.tryPeekAt(0u, &header, sizeof(hal::event::EventHeader))) [[unlikely]]
        {
            break;
        }

        const gp::USize totalPacketBytes = sizeof(hal::event::EventHeader) + header.payloadSize;
        if (!m_eventStream.canRead(totalPacketBytes)) [[unlikely]]
        {
            break;
        }

        switch (header.category)
        {
        case hal::event::EventCategory::Keyboard:
        {
            hal::event::KeyboardEvent ev{};
            if (gp::detail::consumeFixedPayload(m_eventStream, ev))
            {
                m_inputSystem->onKeyboardEvent(ev);
                onKeyboardEvent(ev);
            }
            break;
        }
        case hal::event::EventCategory::Window:
        {
            hal::event::WindowEvent ev{};
            if (gp::detail::consumeFixedPayload(m_eventStream, ev))
            {
                if (m_mainWindow.isValid() && m_mainWindow->getId() == ev.windowId)
                {
                    m_mainWindow->onWindowEvent(ev); // Updates L1 Window Shadow State
                }
                if (ev.action == hal::event::WindowAction::FocusLost)
                {
                    m_inputSystem->releaseAllInputs(); // Anti-stuck key sanitization
                }
                onWindowEvent(ev);
            }
            break;
        }
        // Additional TLV categories handled uniformly...
        default:
            m_eventStream.advanceConsumer(totalPacketBytes);
            break;
        }
    }
}
```

## Alternatives Considered

<!-- markdownlint-disable MD013 -->
| Option | Sync | Stall risk | Cache cost | Allocations | Verdict |
| :--- | :--- | :--- | :--- | :--- | :--- |
| SPSC ring | Acquire-release | Zero | Minimal (64B lines) | Zero | Adopted |
| Mutex queue | OS mutex / futex | Priority inversion | Lock bounce | On resize | Rejected |
| Sync poll | Inline dispatch | Win32 modal freeze | None | OS-dependent | Rejected |
| MPMC queue | Atomic CAS loops | Contention retries | Multi-core | Hazard ptrs | Rejected |
<!-- markdownlint-enable MD013 -->

### Option A: Mutex-guarded event queue (`gp::Mutex` + `gp::Vector<Event>`)

Protect an event container with an OS mutual exclusion primitive (`gp::Mutex`, `std::mutex`, or
Win32 `CRITICAL_SECTION`).

**Why rejected:**

1. **Priority inversion and thread stalls:** If the kernel preempts the Game Thread while it holds
   the mutex, the OS message thread stalls, overflowing OS message queues and dropping window or
   device events.
2. **Kernel context switch overhead:** Contended mutexes drop from user-space spinloops into kernel
   waits (`WaitOnAddress`, Linux `futex`), adding 1,000-5,000 ns per contention event.
3. **Scaling under high-polling hardware:** 8,000 Hz gaming mice generate one event every 125
   $\mu\text{s}$. Mutex contention at that rate burns cache throughput and frame budget.

### Option B: Direct synchronous polling on Game Thread

Poll OS messages directly from the Game Thread via `PeekMessageW` or `SDL_PollEvent` inside the
game loop.

**Why rejected:**

1. **Win32 modal loop trapping:** Dragging or resizing a window enters a blocking modal loop inside
   `DefWindowProc`, freezing the engine, audio, and network simulation until the mouse button is
   released.
2. **Mid-frame state tearing:** Later subsystems (rendering) observe newer coordinates than earlier
   ones (physics), causing camera stutter and aim misalignment.
3. **Thread-affinity conflicts:** On macOS (Cocoa), windowing APIs must run on thread 0. If the
   Game Thread runs on a worker thread or job graph, direct polling violates OS rules.

### Option C: Multi-Producer Multi-Consumer (MPMC) queue

Use a general-purpose MPMC lock-free queue (such as Dmitry Vyukov's MPMC bounded queue or
MoodyCamel's ConcurrentQueue).

**Why rejected:**

1. **Unneeded atomic contention:** MPMC queues use Compare-And-Swap (`CAS`, `cmpxchg`) loops or
   sequence numbers to arbitrate multiple writers and readers. Because our stream has one producer
   (the OS thread) and one consumer (the Game Thread), CAS retry loops add cost for no benefit.
2. **Inter-core traffic:** MPMC structures synchronize sequence counters across cores, whereas an
   SPSC queue needs only unidirectional head/tail updates amortized by shadow index caching.
3. **Extra complexity:** MPMC queues bring ABA issues, memory reclamation, and hazard pointers. An
   SPSC queue is faster and easier to inspect.

## Consequences

### Positive

- **Intra-frame determinism.** Draining all pending OS events in Phase 4 freezes input and window
  state for the whole tick, so physics, gameplay, and rendering see the same snapshot.
- **No OS thread blocking or mutexes.** The OS thread writes with non-blocking pointer increments
  and release semantics, so Game Thread hitches never stall the message pump.
- **Zero steady-state heap allocations.** Buffer storage is allocated at startup; ingestion and
  draining use stack PODs and inline copies.
- **Cache-line isolation.** Padding `m_head` and `m_tail` to separate 64-byte cache lines prevents
  MESI cache ping-ponging between cores.
- **Resilience to modal drag loops and 8,000 Hz mice.** Offloading OS polling avoids Win32 modal
  freezes, and two-tier backpressure sheds continuous motion before discrete events drop.

### Negative

- **Bounded buffer capacity.** Under an extreme Game Thread stall combined with heavy input, the
  fixed buffer can fill and shed continuous motion packets or drop events.
- **Up to one frame of input latency.** Events pushed right after Phase 4 wait until Phase 4 of the
  next tick ($\le 8.33\text{ ms}$ at 120 Hz).
- **POD serialization discipline.** Cross-thread events cannot carry arbitrary C++ objects or raw
  pointers; variable-length UTF-8 strings or file paths require explicit length headers and inline
  packing.
