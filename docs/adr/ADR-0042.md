# ADR-0042: Lifetime-Scoped Arena Allocators, First-Class Allocator Contract, and Named Pool Telemetry

> Container-owned storage wrappers modeled after Unreal Engine (`SizedAllocatorBase`,
> `ForAnyElementType`, `ForElementType<T>`) invert memory ownership by embedding the container's
> data pointer inside the policy, cannot be instantiated as standalone memory allocators, and fail
> to express explicit physical memory lifetimes (per-frame linear scratchpads, LIFO stacks, and
> fixed-block node pools). `gp-engine` replaces container storage wrappers with a first-class,
> lifetime-scoped allocator library (`HeapAllocator`, `AlignedHeapAllocator`, `LinearAllocator`,
> `StackAllocator`, `PoolAllocator`, `FixedBufferAllocator`, `InlineAllocator`,
> `ThreadScratchAllocator`, `TaggedAllocator`, and `PolymorphicAllocator`) backed by
> `gp::memory::Malloc`. All allocators satisfy a unified C++23 sized allocation contract
> (`gp::concepts::IsAllocator`) that passes `oldSizeInBytes` on reallocation and deallocation to
> enable headerless $O(1)$ arena operations and named pool telemetry (`GP_MEM_ALLOC_N`,
> `GP_MEM_FREE_N`) in the Tracy profiler.

![Proposed][badge-proposed]

## Context

High-performance game engines manage memory across radically different lifetimes and access
patterns: persistent asset buffers, level-scoped scene graphs, fixed-size linked nodes (`List`,
sparse tables, spatial trees), small stack-resident strings/vectors, and transient per-frame or
per-job scratch arrays.

Our initial allocator scaffolding (`SizedAllocatorBase.hpp` and `SizedHeapAllocator.hpp`) copied
Unreal Engine's `TSizedAllocatorBase` container policy pattern. Evaluating this design against
production requirements and deconstructive pedagogy exposed four structural flaws:

### 1. Inverted Ownership in Unreal-Style Container Storage Policies

In Unreal Engine (`ContainerAllocationPolicies.h`), an allocator type (`TSizedHeapAllocator`) is
not a memory allocator; it is a container storage trait exposing two nested classes
(`ForAnyElementType` and `ForElementType<T>`) that own the container's raw `m_data` pointer and
compute array slack growth. This coupling creates major architectural friction:

- **Non-Standalone Abstraction:** You cannot instantiate `SizedHeapAllocator` to allocate a raw
  byte buffer, a job payload, or a single struct outside of a container.
- **Opaque Two-Phase Template Indirection:** Every container (`Vector`, `String`, `List`, `Set`,
  `Map`) must route pointer access through `Allocator::template ForElementType<T>` instead of
  directly managing its own data layout (`m_data`, `m_size`, `m_capacity`) and calling an
  allocator for memory blocks.
- **Conflation of Capacity Heuristics and Physical Memory:** Array growth math
  (`defaultCalculateSlackGrow`) is a container resize policy, not a property of physical memory
  arenas. Mixing the two forces every custom allocator to re-implement container slack methods.

### 2. General-Purpose Heap Churn and Fragmentation

Routing every dynamic container (`Vector`, `String`, `List`) and temporary buffer through the
global OS heap (`MallocAnsi`) causes severe runtime degradation during frame execution:

- **Virtual Page Fragmentation:** Interleaving short-lived frame allocations (culling results,
  UI layout vertices, narrowphase contact manifolds) with long-lived level allocations fragments
  the heap.
- **Synchronization Overhead:** General-purpose heap allocators require internal locks or complex
  per-thread bin caches to handle arbitrary-order frees across worker threads.
- **Pointer-Chasing Node Overhead:** Node-based containers (`List`, tree structures) that call
  general-purpose `Malloc` per node scatter elements across unrelated cache lines and pay
  per-allocation heap metadata overhead.

Engines such as **id Tech**, **Decima**, **Glacier 2**, and **Anvil** solve this by binding
allocations to explicit **lifetime-scoped arenas**: linear bump allocators for frame/scratch
lifetimes, LIFO stack allocators for scoped subtasks, and intrusive fixed-block free lists
(`PoolAllocator`) for node-based containers.

### 3. The Hidden Cost of Size-Blind `reallocate(ptr, newSize)` and `deallocate(ptr)`

Standard C `realloc(ptr, newSize)` and `free(ptr)` omit the existing allocation size. Because the
caller does not supply `oldSizeInBytes`, the allocator is forced into an expensive compromise:

1. **Prepending Hidden Metadata Headers:** Storing an 8- to 16-byte header immediately before the
   returned pointer wastes memory and destroys natural 16-, 32-, or 64-byte hardware alignment
   (requiring up to `alignment` extra padding bytes per allocation).
2. **OS Heap Queries:** Calling platform functions such as `_aligned_msize` (Windows) or
   `malloc_usable_size` (POSIX) fails when the original alignment is unknown (as seen in
   `MallocAnsi.cpp`) and is impossible inside headerless `LinearAllocator` bump arenas.

Crucially, engine containers (`Vector`, `String`, `List`, `Set`, `Map`) **always know the exact
byte size of their current allocation** (`m_capacity * sizeof(T)` or `sizeof(Node)`). Passing
`oldSizeInBytes` to `reallocate` and `deallocate` allows a `LinearAllocator` to resize the most
recent allocation at the top of its bump cursor **in-place in $O(1)$ time with zero memory copy**,
and allows non-top reallocations to copy `math::min(oldSizeInBytes, newSizeInBytes)` without
storing per-allocation size headers.

### 4. Monolithic Profiler Blindness

Currently, only `MallocAnsi` emits `GP_MEM_ALLOC_N(ptr, size, "MallocAnsi")`. When an arena
pre-allocates a 16 MB block from `MallocAnsi` once at startup and sub-allocates thousands of
objects from that block at runtime, the profiler sees a single flat 16 MB allocation and is
completely blind to internal arena utilization, peak high-water marks, and per-subsystem memory
leaks.

## Decision

We replace `SizedAllocatorBase` and `SizedHeapAllocator` with a first-class, lifetime-scoped
allocator library in `source/runtime/core/public/memory/allocators/`, backed by
`gp::memory::Malloc` and integrated with the Tracy profiler. Container growth and element
lifecycle utilities are decoupled into `source/runtime/core/public/memory/utils/`.

### 1. Unified Sized Allocator Contract (`IsAllocator` and `IAllocator`)

Every allocator in `gp-engine` implements a consistent, sized byte-allocation contract verified at
compile time by `gp::concepts::IsAllocator<T>`:

```cpp
template <typename T>
concept IsAllocator = requires(
    T& allocator,
    const T& constAllocator,
    void* ptr,
    const gp::USize sizeInBytes,
    const gp::USize oldSizeInBytes,
    const gp::USize newSizeInBytes,
    const gp::UInt32 alignment
)
{
    { allocator.allocate(sizeInBytes, alignment) } noexcept -> gp::concepts::IsSame<void*>;
    { allocator.reallocate(ptr, oldSizeInBytes, newSizeInBytes, alignment) } noexcept -> gp::concepts::IsSame<void*>;
    { allocator.deallocate(ptr, oldSizeInBytes, alignment) } noexcept -> gp::concepts::IsSame<void>;
    { constAllocator.getActualAllocationSize(sizeInBytes, alignment) } noexcept -> gp::concepts::IsSame<gp::USize>;
    { constAllocator.owns(ptr) } noexcept -> gp::concepts::IsSame<bool>;
};
```

For subsystems and containers that require runtime-injected arenas without templating the container
on the concrete arena type, `IAllocator` provides the virtual interface counterpart, and
`PolymorphicAllocator` wraps an `IAllocator*` (or `Malloc*`) as a copyable/movable value type
satisfying `IsAllocator`.

### 2. Zero-Overhead Container Binding via `[[no_unique_address]]`

Containers (`gp::Vector<T, Allocator>`, `gp::container::BasicString<CharT, Allocator>`,
`gp::List<T, Allocator>`, `gp::Set<T, KeyFuncs, Allocator>`, `gp::Map<K, V, SetAllocator, KeyFuncs>`)
store their allocator member using `[[no_unique_address]]`:

1. **Zero-Byte Default Footprint (`DefaultAllocator = HeapAllocator`):** Because `HeapAllocator`,
   `AlignedHeapAllocator<Alignment>`, and `ThreadScratchAllocator` are stateless empty structs
   (`std::is_empty_v<T>`), `[[no_unique_address]]` eliminates their storage overhead completely.
   A `gp::Vector<T>` using `DefaultAllocator` occupies strictly `sizeof(T*) + 2 * sizeof(SizeType)`
   (16 bytes with 32-bit `SizeType`, 24 bytes with 64-bit `SizeType`).
2. **Embedded Small-Buffer Optimization (`InlineAllocator<CapacityBytes, Alignment, Fallback>`):**
   When a container is instantiated with `InlineAllocator<256>`, the 256-byte aligned buffer lives
   inside the `[[no_unique_address]]` allocator member directly inside the container. Calls to
   `allocate()` and `reallocate()` up to 256 bytes return the inline buffer pointer; exceeding
   256 bytes seamlessly allocates from `Fallback` (defaulting to `HeapAllocator`) and copies
   `oldSizeInBytes` across.
3. **Runtime Arena Injection (`PolymorphicAllocator`):** When instantiated with
   `gp::Vector<T, gp::memory::PolymorphicAllocator>`, the container stores an 8-byte `IAllocator*`
   pointer, allowing callers to bind a `LinearAllocator`, `StackAllocator`, `PoolAllocator`, or
   `TaggedAllocator` at construction time (`gp::Vector<Entity, PolymorphicAllocator> list(&frameArena);`).

### 3. Lifetime-Scoped Arena Primitives

All arena allocators obtain their backing memory slab from `gp::memory::Malloc*` (defaulting to
`gp::memory::getInlineMalloc()` / `getGlobalMalloc()`) or operate over an externally provided
caller buffer (zero heap allocations):

1. **`LinearAllocator` (Bump / Frame Arena):**
   - Maintains `m_buffer`, `m_capacity`, `m_offset`, and `m_peakOffset`.
   - `allocate(size, alignment)` aligns `m_offset` upward and advances the cursor in $O(1)$ time.
   - `reallocate(ptr, oldSize, newSize, alignment)` checks whether `ptr` is the most recent
     allocation at the top of the bumper (`static_cast<UInt8*>(ptr) + oldSize == m_buffer + m_offset`).
     If true and aligned, it adjusts `m_offset` **in-place** without copying or stranding dead
     bytes. Otherwise, it bumps a new block and copies `math::min(oldSize, newSize)` bytes.
   - `deallocate(ptr, oldSize, alignment)` reclaims space if `ptr` is at the exact top of the
     bumper; otherwise it is a deterministic no-op.
   - Supports full `reset()` and RAII scope unwinding via `ScopedMemoryMark<LinearAllocator>`.
2. **`StackAllocator` (LIFO Arena):**
   - Prepends an 8-byte `Header { UInt32 previousOffset; UInt32 allocationSize; }` immediately
     prior to the aligned user pointer.
   - `deallocate(ptr, oldSize, alignment)` validates that `ptr` corresponds to the current stack
     top and restores `m_offset = header->previousOffset`.
   - Supports arbitrary multi-step unwinding via `ScopedMemoryMark<StackAllocator>`.
3. **`PoolAllocator` (Intrusive Fixed-Block Slab):**
   - Divides a contiguous backing buffer into `blockCount` aligned slots of `blockSize` bytes
     (`blockSize >= sizeof(FreeBlock)`).
   - Unallocated slots store an intrusive singly-linked `FreeBlock* next` pointer in their first
     8 bytes—incurring **0 bytes** of metadata overhead.
   - `allocate()` pops `m_freeListHead` in $O(1)$ time; `deallocate()` pushes the block back onto
     `m_freeListHead` in $O(1)$ time. Ideal for `List<T>` nodes, octree nodes, and fixed-size
     command packets.
4. **`ThreadScratchAllocator` (Thread-Local Scratchpad):**
   - Manages a thread-local (`thread_local`) `LinearAllocator` lazily backed by `GlobalMemory`.
   - Enables zero-contention, lock-free temporary container and buffer allocations on any worker
     or game thread, paired with `ScopedScratchMark` to rewind the thread's scratch cursor at
     scope exit.

### 4. Named Pool Telemetry and Tracy Profiler Integration

To prevent profiler blindness while avoiding duplicate physical heap counting in Tracy:

- **Physical Heap Layer (`MallocAnsi`):** Continues to report OS-level allocations to the
  `"MallocAnsi"` pool via `GP_MEM_ALLOC_N(ptr, size, "MallocAnsi")` and
  `GP_MEM_FREE_N(ptr, "MallocAnsi")`.
- **Logical Arena & Subsystem Layer (`TaggedAllocator`, `LinearAllocator`, `StackAllocator`, `PoolAllocator`):**
  - Every arena accepts an optional pool name (`const char* poolName`, e.g., `"Arena.Frame"`,
    `"Pool.SceneNodes"`). When `poolName != nullptr`, sub-allocations emit
    `GP_MEM_ALLOC_N(ptr, size, m_poolName)` and `GP_MEM_FREE_N(ptr, m_poolName)`. Because Tracy
    tracks named pools independently (`TracyAllocN` / `TracyFreeN`), logical arena sub-allocations
    and physical `"MallocAnsi"` backing slabs are visualized on separate tracks without colliding.
  - `TaggedAllocator<InnerAllocator>` wraps any allocator, attributing every container or
    subsystem allocation to a named Tracy pool and maintaining `AllocatorStats` (`allocatedBytes`,
    `peakAllocatedBytes`, `activeAllocations`, `totalAllocations`).

### Architectural Invariants

1. **First-Class Standalone Allocators:** Every allocator in `gp::memory` is a self-contained
   object capable of allocating raw memory blocks independently of any container class. Unreal-style
   `ForAnyElementType` / `ForElementType<T>` wrapper classes are forbidden.
2. **Mandatory Sized Reallocation and Deallocation:** All allocator `reallocate` and `deallocate`
   methods accept `oldSizeInBytes`. Containers must pass their current allocation byte size when
   resizing or freeing memory.
3. **Zero-Cost Stateless Defaults via `[[no_unique_address]]`:** Stateless allocators
   (`HeapAllocator`, `AlignedHeapAllocator`, `ThreadScratchAllocator`) must satisfy
   `gp::concepts::IsStatelessAllocator` (`sizeof(T) == 1` and `std::is_empty_v<T>`) so containers
   storing them with `[[no_unique_address]]` incur zero byte overhead.
4. **Decoupled Container Utilities (`memory/utils/`):** Slack growth math (`AllocatorUtilities.hpp`)
   and typed element construction/relocation (`MemoryOps.hpp`) are standalone utilities in
   `memory/utils/` and must never be embedded inside allocator interfaces.
5. **Named Pool Telemetry Separation:** Arena and tagged allocators must use `GP_MEM_ALLOC_N` and
   `GP_MEM_FREE_N` with an explicit pool name (never unnamed `GP_MEM_ALLOC`) so logical arena
   tracking never collides with physical OS heap tracking in Tracy.

## Alternatives Considered

### Option A: Retain Unreal Engine 5 Container Allocation Policies (`SizedAllocatorBase` / `SizedHeapAllocator`)

Complete the existing `SizedAllocatorBase` CRTP hierarchy where allocators expose nested
`ForAnyElementType` and `ForElementType<T>` classes that own the container's `m_data` pointer.

**Why rejected:** Conflates container pointer ownership and capacity slack heuristics with physical
memory allocation. Policies written in this style cannot be used outside containers to allocate
raw buffers or structs, obscure the container's actual memory layout behind two nested template
layers, and make lifetime-scoped arenas (`LinearAllocator`, `StackAllocator`, `PoolAllocator`)
awkward to express.

### Option B: Mandatory Polymorphic `IAllocator*` Pointer in Every Container (Pure EASTL / `std::pmr` Model)

Force every `Vector`, `String`, `Set`, and `Map` to store an 8-byte `IAllocator*` pointer directly
and remove template allocator parameters altogether.

**Why rejected:** Adds a permanent 8-byte size penalty (+50% on a 16-byte `Vector<T>`) and a
virtual function call to every container in the engine, even when 90% of persistent containers use
the default heap or compile-time `InlineAllocator<N>`. By templating containers on
`Allocator = DefaultAllocator` with `[[no_unique_address]]` and providing `PolymorphicAllocator`
as an opt-in allocator type, `gp-engine` achieves both 0-byte overhead by default and runtime
polymorphic arena injection when desired.

### Option C: Unsized `reallocate(ptr, newSize)` and `deallocate(ptr)` Contract

Match the C standard library signature by omitting `oldSizeInBytes` from `reallocate` and
`deallocate`.

**Why rejected:** Without `oldSizeInBytes`, `LinearAllocator` cannot determine whether `ptr` sits
at the top of the bump cursor to perform an in-place $O(1)$ expansion, nor can it know how many
bytes to copy when relocating to a larger block without prepending a hidden size header to every
allocation. Prepending headers wastes memory and breaks cache-line alignment. Since containers
already track their capacity, passing `oldSizeInBytes` is free at the call site and unlocks
headerless arena reallocation.

## Consequences

### Positive

- **Eliminates heap fragmentation for transient and node-based workloads.** `LinearAllocator`,
  `StackAllocator`, `PoolAllocator`, and `ThreadScratchAllocator` turn per-frame temporaries and
  linked-node allocations into $O(1)$ cache-local pointer operations with zero OS lock contention.
- **Preserves a 16-byte default container footprint.** Storing stateless allocators via
  `[[no_unique_address]]` guarantees that `Vector<T>` and `String` pay zero bytes for their
  default allocator while still supporting `InlineAllocator<N>` and `PolymorphicAllocator`.
- **Enables $O(1)$ in-place linear reallocation without metadata headers.** Passing
  `oldSizeInBytes` allows `LinearAllocator` and `FixedBufferAllocator` to expand the active top
  allocation in place when a `Vector` or `String` grows sequentially.
- **Provides granular subsystem and arena visibility in Tracy.** `TaggedAllocator` and named
  arena pools (`GP_MEM_ALLOC_N` / `GP_MEM_FREE_N`) surface live byte counts, high-water marks,
  and leak callstacks per arena without conflicting with `"MallocAnsi"` telemetry.
- **Maximizes deconstructive pedagogical clarity.** Separating `memory/backends/` (`Malloc`),
  `memory/allocators/` (`LinearAllocator`, `StackAllocator`, `PoolAllocator`, `HeapAllocator`),
  and `memory/utils/` (`MemoryOps`, `AllocatorUtilities`) teaches students the exact responsibility
  of each layer.

### Negative

- **Container type differentiation across static allocators.** `Vector<T, HeapAllocator>` and
  `Vector<T, InlineAllocator<128>>` are distinct C++ types; functions accepting read-only sequences
  should accept `VectorView<T>` / `StringView`, while functions mutating arena-backed containers
  across API boundaries should use `Vector<T, PolymorphicAllocator>`.
- **Strict lifetime discipline required for arena-backed containers.** If a container backed by a
  `LinearAllocator` or `ScopedScratchMark` outlives an arena `reset()` or mark rewind, its
  destructor or subsequent accesses will reference reclaimed memory.
- **Caller responsibility for accurate `oldSizeInBytes`.** Low-level callers invoking
  `reallocate` or `deallocate` directly on `LinearAllocator` or `InlineAllocator` must pass the
  same size that was requested during allocation.
