# ADR-0018: Capability-Based Device Abstraction (Input, Haptic, Spatial)

> Establishes a modular hierarchy for hardware devices, separating them by capability
> (e.g., `InputDevice` for buttons, `HapticDevice` for rumble/force-feedback, `SpatialDevice` for
> VR/Gyro tracking) rather than monolithically grouping them.

![Proposed][badge-proposed]

## Context

Gaming hardware exhibits wide variance in physical capabilities across peripherals:

- Keyboards expose discrete binary switches organized in row and column electrical matrices.
- Mice provide high-frequency 2D relative motion deltas, scroll wheels, and low-latency microswitch
  buttons.
- Standard gamepads supply analog potentiometer sticks, triggers, and digital face buttons.
- Modern controllers (such as the Sony DualSense, Nintendo Switch Pro Controller, or Xbox Wireless
  Controller) incorporate dual-motor rumble, trigger force feedback, programmable RGB lightbars, 3D
  inertial measurement units (accelerometer and gyroscope), and capacitive touch surfaces.
- Spatial peripherals (such as VR motion controllers and graphics digitizer tablets) introduce
  6-degree-of-freedom tracking, pen tip pressure, tilt angles, and tangential rotation.

### Failure Mode of Monolithic Inheritance Hierarchies

A common anti-pattern in hardware abstraction layers is grouping all peripheral features into a
single monolithic base class (`class Device` or `class IInputDevice`). Such an interface declares
virtual methods for every conceivable hardware feature:

```cpp
// Monolithic Anti-Pattern: Violates Interface Segregation Principle
class IDevice
{
public:
    virtual ~IDevice() = default;
    virtual void setRumble(float lowFreq, float highFreq) = 0;
    virtual void setTriggerRumble(float left, float right) = 0;
    virtual void setLEDColor(uint8_t r, uint8_t g, uint8_t b) = 0;
    virtual Vector3 getAccelerometer() const = 0;
    virtual Vector3 getGyroscope() const = 0;
    virtual uint32_t getTouchCount() const = 0;
    virtual float getPenPressure() const = 0;
};
```

This monolithic structure forces non-participating peripherals to implement dummy stubs. A keyboard
or mouse must provide empty implementations that return false, return zeroed readings, or throw
exceptions. This violates the Interface Segregation Principle (ISP). Client code cannot determine
whether calling `setRumble()` is valid without consulting documentation or performing runtime
defensive checks.

### Component-Based Versus Interface-Based Composition

An alternative design uses dynamic component attachment (`device.getComponent<Haptics>()`). While
common in gameplay entity systems, dynamic component lookup presents clear engineering liabilities
at the hardware abstraction boundary:

- Querying components at runtime requires hash table searches or linear scans across component
  arrays.
- Registering components dynamically allocates memory on the heap, conflicting with zero-allocation
  constraints during gameplay.
- Client code must handle null pointers returned when a component is missing, converting
  compile-time type verification into runtime branch checks.
- Fragmented component allocations across the heap degrade CPU cache locality during high-frequency
  input dispatch.

The engine requires a design that guarantees compile-time type safety, eliminates dummy interface
stubs, avoids dynamic heap allocations, and separates hardware actuation from hardware input
ingestion.

## Decision

We introduce granular capability interfaces located in `source/runtime/hal/base/public/input/`.
Hardware abstractions inherit only the capabilities supported by their underlying hardware.

### Granular Capability Contracts

The HAL decomposes peripheral capabilities into three primary interfaces:

1. `IInputDevice`: The base contract for all peripherals. It governs device identity
   (`getDeviceId()`, `getDeviceType()`, `getDeviceName()`), connection status (`isConnected()`),
   battery telemetry (`getBatteryPercent()`), and per-frame lifecycle operations (`beginFrame()`,
   `releaseAllInputs()`, `reset()`).
2. `IHapticDevice`: The actuation contract for hardware outputs. It encapsulates dual-motor
   vibration (`supportsRumble()`, `setRumble()`), trigger force feedback (`supportsTriggerRumble()`,
   `setTriggerRumble()`), emergency stop (`stopHaptics()`), and LED control (`supportsLEDColor()`,
   `setLEDColor()`, `setPlayerLED()`).
3. `ISpatialDevice`: The contract for 3D motion tracking, spatial sensing, multi-touch, and pen
   tablets. It encapsulates IMU motion queries (`hasSensor()`, `isSensorEnabled()`,
   `setSensorEnabled()`), continuous sensor readings (`getAccelerometerReading()`,
   `getGyroscopeReading()`), multi-touch contacts (`getActiveTouchCount()`, `getTouchContact()`),
   stylus state (`getPenState()`), and event ingestion hooks (`onSensorEvent()`, `onTouchEvent()`,
   `onPenEvent()`).

### Composition via Multiple Interface Inheritance

Concrete peripheral contracts compose these capabilities through multiple inheritance of pure
virtual interfaces:

- `IKeyboard` derives solely from `IInputDevice`.
- `IMouse` derives solely from `IInputDevice`.
- `IGamepad` derives from `IInputDevice`, `IHapticDevice`, and `ISpatialDevice`.


Subsystems throughout the engine consume these capability interfaces directly:

- A rumble or haptic feedback manager accepts `IHapticDevice&` without binding to button states or
  thumbsticks.
- A motion-aiming camera system accepts `ISpatialDevice&` without coupling to mouse or keyboard
  types.
- The input manager processes lifecycle operations uniformly across all peripherals using
  `IInputDevice&`.

### Architectural Invariants

1. No dummy capability stubs: Interfaces represent guaranteed capabilities. A class implementing an
   interface provides concrete functionality for that capability family. Peripherals do not declare
   or implement interfaces for unsupported features.
2. Zero-cost compile-time composition: Multiple inheritance of pure virtual interfaces incurs zero
   dynamic heap allocations. Function dispatch resolves through standard virtual method tables
   constructed by the compiler.
3. Separation of actuation from ingestion: Actuation (transmitting commands to hardware motors and
   LEDs) is isolated in `IHapticDevice`. Ingestion (reading input states and sensor feeds from
   hardware) is organized across `IInputDevice`, `ISpatialDevice`, and domain-specific state
   interfaces.
4. Unified lifecycle via `IInputDevice`: Device identification, frame-boundary transition clearing
   (`beginFrame`), and focus-loss input sanitization (`releaseAllInputs`) remain uniform across all
   peripherals by anchoring them in `IInputDevice`.

### Interface Definitions

The C++ definitions demonstrate the separation of concerns across capability contracts:

#### `IInputDevice.hpp`

```cpp
namespace gp::hal::input
{

class IInputDevice
{
public:
    [[nodiscard]] constexpr IInputDevice() noexcept = default;
    virtual ~IInputDevice() noexcept = default;

    IInputDevice(const IInputDevice&) = delete;
    IInputDevice& operator=(const IInputDevice&) = delete;
    IInputDevice(IInputDevice&&) = delete;
    IInputDevice& operator=(IInputDevice&&) = delete;

public:
    [[nodiscard]] virtual InputDeviceId getDeviceId() const noexcept = 0;
    [[nodiscard]] virtual InputDeviceType getDeviceType() const noexcept = 0;
    [[nodiscard]] virtual StringView getDeviceName() const noexcept = 0;
    [[nodiscard]] virtual bool isConnected() const noexcept = 0;
    [[nodiscard]] virtual gp::UInt8 getBatteryPercent() const noexcept = 0;

    virtual void beginFrame() noexcept = 0;
    virtual void releaseAllInputs() noexcept = 0;
    virtual void reset() noexcept = 0;
};

} // namespace gp::hal::input
```

## Alternatives Considered

### Option A: Monolithic Base Class (`class Device` with All Methods)

Define a single base class that declares every input, haptic, and sensor method across all
peripheral types.

**Why rejected:** This design violates the Interface Segregation Principle. When a peripheral class
like `Keyboard` or `Mouse` is forced to implement `setRumble()` or `getGyroscopeReading()`, it must
provide non-functional stub implementations. Client systems lose the ability to verify capabilities
at compile time; an audio system sending vibration commands to a keyboard receives a runtime failure
code rather than being prevented from compiling. Adding future hardware capabilities, such as eye
tracking or flight stick throttle axes, pollutes the interface for every peripheral in the engine.

### Option B: Dynamic Component Architecture (`device.getComponent<Haptics>()`)

Adopt an entity-component pattern where peripherals store capabilities as dynamically attached
components queried at runtime via templates or type IDs.

**Why rejected:** Dynamic component systems introduce runtime overhead that conflicts with the
engine's performance constraints. Storing components in hash tables or dynamic arrays requires heap
allocations during peripheral initialization. Component lookups require pointer indirection, hash
calculations, and branch checks on every frame. When client code queries an optional component, it
must check for null pointers, turning what could be compile-time interface enforcement into runtime
defensive code. Furthermore, scattering component memory across the heap reduces data cache locality
during input dispatch.

### Option C: Standalone Concrete Device Classes without Shared Capability Contracts

Implement isolated concrete classes (`Keyboard`, `Mouse`, `Gamepad`) without shared capability
interfaces for haptics or spatial sensing.

**Why rejected:** Without shared capability interfaces, subsystems cannot write generic code
targeting common hardware features. A haptic feedback manager would need explicit overloads for
every peripheral type that supports vibration (`triggerHaptic(Gamepad&)`,
`triggerHaptic(VRController&)`, `triggerHaptic(Wheel&)`). This duplication fragments actuation logic
and prevents virtual or composite devices from integrating into haptic or spatial processing
pipelines.

## Consequences

### Positive

- **Adherence to Interface Segregation Principle.** Peripherals implement only the capability
  contracts their hardware supports, eliminating empty stub methods and dummy return values across
  simple devices like keyboards and mice.
- **Compile-time type verification for client systems.** Gameplay and engine subsystems express
  dependencies on specific capability interfaces rather than concrete peripheral types, ensuring at
  compile time that targeted hardware supports the requested operations.
- **Zero dynamic heap allocation during composition.** Composing capabilities through C++ multiple
  interface inheritance uses compile-time virtual tables, avoiding the heap allocations, dictionary
  lookups, and pointer chasing inherent in dynamic component architectures.
- **Decoupled actuation and ingestion pathways.** Writing commands to hardware actuators (rumble
  motors, trigger resistance, RGB lightbars) is segregated from reading incoming sensor and button
  data, simplifying data flow across engine subsystems.
- **Uniform lifecycle management across devices.** Frame edge clearing (`beginFrame`), input reset
  upon window focus loss (`releaseAllInputs`), and connection state tracking remain centralized in
  `IInputDevice`, maintaining consistent operational behavior across all peripheral types.

### Negative

- **Virtual method table pointer overhead.** Composing multiple interfaces on a single class, such
  as `IGamepad`, introduces multiple vptr instances per object, increasing instance size by 8 to 16
  bytes on 64-bit architectures and adding pointer adjustment overhead during cross-interface casts.
- **Coarse capability granularity within interfaces.** Grouping features into broad capability
  contracts means that a controller with standard rumble and a controller with independent trigger
  rumble both implement `IHapticDevice`, requiring client code to query fine-grained capability
  flags such as `supportsTriggerRumble()`.
- **Interface maintenance across backend implementations.** Modifying or extending a capability
  interface requires updating all implementing classes across platform backends, increasing
  refactoring effort when new hardware capabilities are introduced.

## Rationale and Cross-References

memory allocations, compile-time contract enforcement, and clear decoupling of subsystems. The
design allows client code to interact with haptic and spatial hardware without depending on specific
peripheral classes, while keeping low-level lifecycle and edge-latching operations unified.
