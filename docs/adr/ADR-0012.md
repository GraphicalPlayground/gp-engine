# ADR-0012: Centralized Application Layer for Platform Lifecycle and Event Orchestration

> Defines `gp::application::Application` as the central host that owns the injected backend,
> tracks active windows, and orchestrates OS events and engine subsystems.

![Accepted][badge-accepted]

*Amended and extended by [ADR-0053][adr-0053]: Job System Lifecycle Integration, Double-Buffered
Frame Arenas, and Phased Frame Task Graphs in `gp::Application`.*

## Context

A game engine drives a real-time loop at 60, 120, or 240 Hz, coordinating asynchronous OS events
(window resizes, display DPI changes, hotplugged controllers, power suspensions) with synchronous
engine subsystems (clocks, fixed-frequency physics, gameplay updates, and rendering).

Common failure modes in this layer include:

- **Decentralized polling and state desynchronization:** Letting input, audio, physics, and the
  renderer poll the OS message queue independently causes race conditions and mid-frame state
  tearing. Processing a window resize midway through a render pass invalidates swapchains while
  command buffers are still recording, triggering GPU device-lost errors.
- **Monolithic god-class:** Early frameworks often collapsed windowing, OpenGL context creation,
  asset loading, scene graph ticking, and audio into one `Application` class, violating single
  responsibility and making unit testing impossible.
- **Inconsistent frame pacing and the spiral of death:** Feeding variable OS elapsed time directly
  into physics integrators breaks determinism. Unbounded physics sub-stepping during CPU hitches
  consumes more frame time each tick until the engine freezes.
- **Background CPU waste:** Loops that spin continuously when minimized or hidden burn 100% of a
  CPU core, draining laptop batteries and hitting thermal limits.
- **Stuck-key states:** Losing OS window focus (`FocusLost`) while a key is held causes the OS to
  swallow the key-up event, leaving the input system stuck unless cleared by the application host.

We need a centralized application host that separates platform plumbing from simulation, enforces a
deterministic frame lifecycle, routes OS events lock-free, and manages idle power usage.

## Decision

We establish `gp::Application` (in `source/runtime/application/`) as the engine's execution host
and subsystem orchestrator.

`Application` owns the injected platform abstraction layer ([ADR-0011](./ADR-0011.md)), manages the
primary window, provisions the lock-free Single-Producer Single-Consumer (SPSC) byte ring buffer
([ADR-0013](./ADR-0013.md)), coordinates the engine clock ([ADR-0030](./ADR-0030.md),
[ADR-0031](./ADR-0031.md), [ADR-0032](./ADR-0032.md)), and drives the frame loop.

```text
+-------------------------------------------------------------------------------------------------+
|                                     gp::Application Host Loop                                   |
+-------------------------------------------------------------------------------------------------+
                                                 |
  1. OS Power-Saving Wait:  If minimized/suspended, sleep on waitEventsTimeout(100ms)
                                                 |
  2. Input Frame Reset:     m_inputSystem->beginFrame() [Clears edge latches & resets deltas]
                                                 |
  3. Producer Phase:        m_backend->pumpEvents(m_eventStream) [OS Thread -> SPSC Ring Buffer]
                                                 |
  4. Consumer Phase:        drainEventStream() [Drains TLV packets from SPSC Ring Buffer]
                            |---> WindowEvent   -> m_mainWindow->onWindowEvent() [Shadow State]
                            |---> FocusLost     -> m_inputSystem->releaseAllInputs() [Anti-Stuck]
                            |---> DisplayEvent  -> m_backend->notifyDisplayEvent() [Topology Sync]
                            |---> Input Events  -> m_inputSystem->on*Event() [State Tables]
                            +---> Virtual Hooks -> onKeyboardEvent(), onMouseEvent(), etc.
                                                 |
  5. Timekeeping & Pacing:  timeStats = m_clock.tick() [QPC/TSC, Outlier Smoothing, Accumulator]
                                                 |
  6. Fixed Simulation:      for (0 .. stepCount) -> onFixedUpdate(fixedDelta) [Deterministic Hz]
                                                 |
  7. Variable Simulation:   onUpdate(timeStats) [Gameplay logic, animation, UI]
                                                 |
  8. Presentation / Render: if (visible) -> onRender(timeStats) [With interpolation alpha]
                                                 |
  9. Adaptive Pacing:       m_clock.paceFrame(targetFps) [Foreground vs. Background FPS target]
                                                 |
                                            (Repeat Loop)
```

### Subsystem ownership hierarchy

`Application` owns these core runtime primitives:

```text
gp::Application
  |-- m_desc:            ApplicationDesc (configuration, window dimensions, FPS targets)
  |-- m_backend:         gp::UniquePtr<hal::IApplicationBackend> (injected OS backend or fallback)
  |-- m_inputSystem:     gp::UniquePtr<hal::input::IInputSystem> (input coordinator & slots)
  |-- m_mainWindow:      gp::UniquePtr<hal::IWindow> (primary OS display surface)
  |-- m_eventStream:     gp::SPSCByteRingBuffer (lock-free cross-thread event queue)
  |-- m_clock:           gp::time::EngineClock (master hardware monotonic clock & accumulator)
  |-- m_lastPumpStats:   hal::EventPumpStats (telemetry counters for event shed/push volume)
  `-- m_isRunning:       gp::Atomic<bool> (thread-safe termination flag)
```

### Architectural invariants

1. **Sequential, deterministic frame phases:** The game loop in `Application::run()` executes in a
   non-reentrant, nine-phase order:
   1. *Power-saving check:* Blocks on `waitEventsTimeout()` when minimized to yield CPU cycles.
   2. *Input frame initialization:* `beginFrame()` clears the previous frame's edge latches and
      zeroes relative mouse/stick deltas ([ADR-0034](./ADR-0034.md)).
   3. *OS event ingestion:* Pushes raw OS messages into `m_eventStream` using two-tier backpressure
      ([ADR-0026](./ADR-0026.md)).
   4. *Stream draining and state sync:* Decodes TLV packets, updating window shadow state
      ([ADR-0027](./ADR-0027.md)), display topologies ([ADR-0028](./ADR-0028.md),
      [ADR-0029](./ADR-0029.md)), and input tables before game logic runs.
   5. *Clock accumulation:* Hardware tick updates smoothed deltas and computes discrete sub-steps
      ([ADR-0033](./ADR-0033.md)).
   6. *Fixed timestep simulation:* Executes `onFixedUpdate()` zero or more times with fixed
      $\Delta t$.
   7. *Variable update:* Executes `onUpdate()` for frame-rate-dependent gameplay.
   8. *Render presentation:* Invokes `onRender()` with interpolation factor $\alpha \in [0.0, 1.0)$.
   9. *Adaptive frame pacing:* Enforces foreground vs. background FPS limits via high-resolution
      timers ([ADR-0031](./ADR-0031.md)).

2. **Immutable input snapshot per tick:** Draining and dispatching all queued OS events at phase 4
   before `onUpdate()` runs gives gameplay code a consistent input snapshot across the entire
   frame, avoiding races from mid-tick hardware interrupts.

3. **Automatic stuck-key sanitization:** When `drainEventStream()` sees `WindowAction::FocusLost`,
   `WindowAction::Hidden`, or `WindowState::Minimized`, `Application` calls
   `m_inputSystem->releaseAllInputs()` ([ADR-0036](./ADR-0036.md)) so keys do not stay stuck after
   Alt-Tab.

4. **Zero-allocation steady-state loop:** `m_eventStream` pre-allocates its buffer during
   `Application::initializeInternal()`. `drainEventStream()` uses stack-allocated structs and
   direct pointer copies (`consumeFixedPayload`) with zero heap allocations per frame.

5. **Reverse-order teardown:** `shutdownInternal()` tears down subsystems in the reverse order of
   construction: input system resets, window closes, backend terminates, and event ring buffers
   release.

### Hook contracts for engine specialization

Downstream applications (such as `gp_editor` or game binaries) specialize `Application` via
protected virtual hooks:

<!-- markdownlint-disable MD013 -->
| Virtual hook | Frequency | Purpose |
| :--- | :--- | :--- |
| `onInitialize()` | Once on startup | Allocate systems, load config, init scene |
| `onFixedUpdate(fixedDelta)` | Fixed steps (60 Hz) | Physics, prediction, rigid-body dynamics |
| `onUpdate(timeStats)` | Once per frame | Variable-timestep gameplay, cameras, UI |
| `onRender(timeStats)` | Once per frame (visible) | Draw commands, `interpolationAlpha` |
| `onShutdown()` | Once on exit | Save state, release GPU/CPU resources |
| `onWindowEvent(ev)` | Event-driven | React to DPI, resizes, focus shifts |
| `onKeyboardEvent(ev)` | Event-driven | Low-level key checks (console hotkeys) |
| `onTextInputEvent(ev, text)` | Event-driven | UTF-8 typing and IME for editor fields |
| `onDropEvent(ev, path)` | Event-driven | Drag-and-drop file imports from desktop |
<!-- markdownlint-enable MD013 -->

## Alternatives Considered

### Option A: Decentralized / subsystem-driven ad-hoc loops

Allow individual subsystems (Input, Physics, Renderer, Audio) to maintain their own loops or poll
the platform backend directly whenever they need data.

**Why rejected:** Creates conflicting execution-order dependencies. If the renderer polls window
size while input polls cursor positions, spatial coordinates mismatch. Enforcing fixed-timestep
physics accumulation and render interpolation ($\alpha$) also fragments across files, breaking
deterministic replays.

### Option B: Monolithic god-class `Application`

Combine the application loop, graphics device initialization (RHI), audio device management, and
asset streaming into one `Application` class.

**Why rejected:** Violates single responsibility and our module separation rules
([ADR-0001](./ADR-0001.md), [ADR-0004](./ADR-0004.md)). A graphics device failure should not block
headless simulation testing. Keeping `gp::Application` scoped to lifecycle, platform orchestration,
time, and input lets the graphics pipeline stay an independent consumer
([ADR-0002](./ADR-0002.md)).

### Option C: Inversion of control via OS event callbacks (push architecture)

Let the OS drive the main loop directly via platform callbacks (similar to Emscripten's
`emscripten_set_main_loop` or `NSApplicationMain` run loops).

**Why rejected:** Push architectures take away explicit control over the frame budget. When the OS
invokes the render callback on compositor cadence, the engine cannot run fixed-rate physics
sub-stepping, insert hitch sleep intervals, or pace foreground vs. background frame rates. Desktop
engines need a pull-based `while (isRunning)` loop; on platforms that mandate push loops (such as
WebAssembly or iOS), the backend adapts to synthesize tick dispatches.

## Consequences

### Positive

- **Deterministic frame execution.** Separating fixed-rate physics ticks (`onFixedUpdate`) from
  variable-rate render frames (`onRender`) keeps simulation dynamics stable and visual
  interpolation smooth across refresh rates.
- **Input integrity.** Intra-frame input latching and focus-loss sanitization prevent dropped
  clicks, missed key releases, and stuck keys.
- **Energy efficiency.** Background throttling and sleep-when-minimized drop idle CPU usage toward
  0% when the window is hidden.
- **Decoupled and testable.** The application host depends only on `IApplicationBackend` and
  `IInputSystem`, allowing headless unit tests and CI runs without changes.
- **Readable frame loop.** Reading `Application.cpp` shows the full frame execution flow in one
  file.

### Negative

- **Rigid lifecycle structure.** Subsystems must fit the nine-phase execution order. Custom setups
  such as decoupled asynchronous render threads must be orchestrated inside `onRender` rather than
  ad-hoc thread spawning.
- **Virtual dispatch on hook invocations.** Specialization hooks (`onUpdate`, `onRender`) go
  through a vtable once per frame or once per fixed tick, adding a negligible nanosecond cost.
