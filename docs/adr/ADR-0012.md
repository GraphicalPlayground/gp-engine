# ADR-0012: Centralized Application Layer for Platform Lifecycle and Event Orchestration

> Defines the `gp::application::Application` class as the central manager that owns the injected
> backend, tracks active windows, and acts as the orchestrator between OS events and engine
> subsystems.

![Proposed][badge-proposed]

## Context

A production AAA game engine is not a passive library; it is an active real-time runtime that must
drive a deterministic execution loop at 60, 120, or 240 Hz. At the heart of this runtime lies the
orchestration problem: coordinating asynchronous, unpredictable operating system events (window
resizes, display DPI changes, hotplugged controllers, power suspensions) with synchronous, deterministic
engine subsystems (high-resolution clocks, fixed-frequency physics sub-stepping, variable gameplay updates,
and graphics presentation).

Naive engine designs commonly suffer from severe architectural dysfunctions in this layer:

- **Decentralized Polling & State Desynchronization:** Allowing individual subsystems (e.g., input,
  audio, physics, renderer) to poll the OS message queue independently causes race conditions, frame-order
  inconsistencies, and mid-frame state tearing. For instance, if an OS window resize event is processed
  midway through a render pass, swapchains invalidate while command buffers are being recorded,
  triggering GPU device lost errors.
- **The Monolithic "God-Class" Trap:** Historically, engines like early OGRE, Irrlicht, or simple
  frameworks collapsed windowing, OpenGL context creation, asset loading, scene graph ticking, and
  audio into a massive, tightly coupled `Application` class. This violates the Single Responsibility
  Principle (SRP), destroys compilation modularity, and renders unit testing impossible.
- **Inconsistent Frame Pacing and the "Spiral of Death":** Directly passing variable OS elapsed time
  into physics integrators leads to non-deterministic simulations and numerical explosions. Conversely,
  unbounded physics sub-stepping during CPU hitches causes the simulation to consume increasing frame
  time, locking the engine into a terminal freeze.
- **Runaway Background Resource Consumption:** Naive while-loops that spin continuously even when
  the engine window is minimized or hidden waste 100% of a CPU core, draining laptop batteries and
  throttling thermal budgets.
- **Peripheral Stuck-State Anomalies:** Losing OS window focus (`FocusLost`) midway through a user
  keypress causes the OS to swallow the subsequent key-up message, stranding the input system in a
  permanent "stuck key" state unless systematically sanitized by an application-level supervisor.

We require a centralized, highly disciplined application host that cleanly separates platform
plumbing from engine simulation, guarantees a strictly deterministic frame execution lifecycle,
provides lock-free OS-to-game event routing, and enforces graceful power management.

## Decision

We establish `gp::Application` (in `source/runtime/application/`) as the engine's central execution
host and subsystem orchestrator.

`Application` owns the lifecycle of the injected platform abstraction layer ([ADR-0011](./ADR-0011.md)),
manages the primary application window, provisions the lock-free Single-Producer Single-Consumer
(SPSC) byte ring buffer ([ADR-0013](./ADR-0013.md)), coordinates the master engine clock
([ADR-0030](./ADR-0030.md), [ADR-0031](./ADR-0031.md), [ADR-0032](./ADR-0032.md)), and drives the
canonical frame loop.

```text
+-------------------------------------------------------------------------------------------------+
|                                     gp::Application Host Loop                                   |
+-------------------------------------------------------------------------------------------------+
                                                 |
  1. OS Power-Saving Wait:  If minimized/suspended, sleep on waitEventsTimeout(100ms)
                                                 |
  2. Input Frame Reset:     m_inputSystem->beginFrame() [Clears edge latches & resets deltas]
                                                 |
  3. Producer Phase:        m_backend->pumpEvents(m_eventStream) [OS Thread -> SPSC Ring Buffer]
                                                 |
  4. Consumer Phase:        drainEventStream() [Drains TLV packets from SPSC Ring Buffer]
                            |---> WindowEvent   -> m_mainWindow->onWindowEvent() [Shadow State]
                            |---> FocusLost     -> m_inputSystem->releaseAllInputs() [Anti-Stuck]
                            |---> DisplayEvent  -> m_backend->notifyDisplayEvent() [Topology Sync]
                            |---> Input Events  -> m_inputSystem->on*Event() [State Tables]
                            +---> Virtual Hooks -> onKeyboardEvent(), onMouseEvent(), etc.
                                                 |
  5. Timekeeping & Pacing:  timeStats = m_clock.tick() [QPC/TSC, Outlier Smoothing, Accumulator]
                                                 |
  6. Fixed Simulation:      for (0 .. stepCount) -> onFixedUpdate(fixedDelta) [Deterministic Hz]
                                                 |
  7. Variable Simulation:   onUpdate(timeStats) [Gameplay logic, animation, UI]
                                                 |
  8. Presentation / Render: if (visible) -> onRender(timeStats) [With interpolation alpha α]
                                                 |
  9. Adaptive Pacing:       m_clock.paceFrame(targetFps) [Foreground vs. Background FPS target]
                                                 |
                                            (Repeat Loop)
```

### Subsystem Ownership Hierarchy

`Application` acts as the explicit owner of core runtime primitives:

```text
gp::Application
  |-- m_desc:            ApplicationDesc (configuration parameters, window dimensions, FPS targets)
  |-- m_backend:         gp::UniquePtr<hal::IApplicationBackend> (injected OS backend or generic fallback)
  |-- m_inputSystem:     gp::UniquePtr<hal::input::IInputSystem> (input coordinator & player slots)
  |-- m_mainWindow:      gp::UniquePtr<hal::IWindow> (primary OS display surface)
  |-- m_eventStream:     gp::SPSCByteRingBuffer (lock-free cross-thread event queue)
  |-- m_clock:           gp::time::EngineClock (master hardware monotonic clock & accumulator)
  |-- m_lastPumpStats:   hal::EventPumpStats (telemetry counters for event shed/push volume)
  `-- m_isRunning:       gp::Atomic<bool> (thread-safe termination flag)
```

### Architectural Invariants

1. **Strictly Sequential, Deterministic Frame Phases:** The game loop in `Application::run()`
   executes in a strictly non-reentrant, eight-phase order:
   1. *Power-Saving Check:* Blocks on `waitEventsTimeout()` when minimized to yield CPU cycles.
   2. *Input Frame Initialization:* `beginFrame()` clears the previous frame's transient edge latches
      and zeroes relative mouse/stick deltas ([ADR-0034](./ADR-0034.md)).
   3. *OS Event Ingestion:* Pushes raw OS messages into `m_eventStream` using two-tier backpressure
      ([ADR-0026](./ADR-0026.md)).
   4. *Stream Draining & State Synchronization:* Decodes TLV packets, updating window shadow state
      ([ADR-0027](./ADR-0027.md)), display topologies ([ADR-0028](./ADR-0028.md), [ADR-0029](./ADR-0029.md)),
      and input tables before any game logic executes.
   5. *Clock Accumulation:* Hardware tick updates smoothed deltas and computes discrete sub-steps
      ([ADR-0033](./ADR-0033.md)).
   6. *Fixed Timestep Simulation:* Executes `onFixedUpdate()` zero or more times with fixed $\Delta t$.
   7. *Variable Update:* Executes `onUpdate()` for frame-rate-dependent gameplay.
   8. *Render Presentation:* Invokes `onRender()` passing normalized interpolation factor $\alpha \in [0.0, 1.0)$.
   9. *Adaptive Frame Pacing:* Enforces foreground vs. background FPS limits via high-resolution timers
      ([ADR-0031](./ADR-0031.md)).

2. **Immutable Input Snapshot per Tick:** By completely draining and dispatching all queued OS events
   at phase 4 before `onUpdate()` executes, gameplay programmers interact with an internally
   consistent, immutable input state throughout the entire frame, eliminating race conditions caused
   by mid-tick hardware interrupts.

3. **Automatic Stuck-Key Sanitization:** When `drainEventStream()` encounters a `WindowAction::FocusLost`,
   `WindowAction::Hidden`, or `WindowState::Minimized` event, `Application` immediately calls
   `m_inputSystem->releaseAllInputs()` ([ADR-0036](./ADR-0036.md)), preventing sticky keys when the
   user Alt-Tabs away from the application.

4. **Zero-Allocation Steady-State Loop:** `m_eventStream` pre-allocates its storage during
   `Application::initializeInternal()`. Event consumption in `drainEventStream()` utilizes
   stack-allocated destination structs and direct pointer copies (`consumeFixedPayload`), guaranteeing
   zero heap allocations during steady-state frame ticks.

5. **Deterministic Reverse-Order Teardown:** `shutdownInternal()` cleanly dismantles subsystems in
   the exact inverse order of construction: input system resets, window closes, backend terminates,
   and event ring buffers release.

### Hook Contracts for Engine Specialization

Downstream applications (such as `gp_editor` or game binaries) specialize `Application` via protected
virtual hooks:

<!-- markdownlint-disable MD013 -->
| Virtual Hook | Execution Frequency | Primary Architectural Purpose |
| :--- | :--- | :--- |
| **`onInitialize()`** | Once on startup | Allocate game systems, load configuration, initialize scene resources. |
| **`onFixedUpdate(fixedDelta)`** | Discrete sub-steps (e.g. 60 Hz) | Deterministic physics simulation, network prediction, rigid body dynamics. |
| **`onUpdate(timeStats)`** | Once per frame | Variable-timestep gameplay logic, camera controllers, UI logic. |
| **`onRender(timeStats)`** | Once per frame (if visible) | Record draw commands, interpolate physics transforms via `timeStats.fixedStep.interpolationAlpha`. |
| **`onShutdown()`** | Once on exit | Serialize state, release game-specific GPU/CPU resources before HAL shutdown. |
| **`onWindowEvent(ev)`** | Event-driven (drained) | React to DPI changes, window resizes, focus shifts. |
| **`onKeyboardEvent(ev)`** | Event-driven (drained) | Low-level raw key interception (e.g., debug console hotkeys). |
| **`onTextInputEvent(ev, text)`**| Event-driven (drained) | Unicode UTF-8 text typing and IME composition for editor input fields. |
| **`onDropEvent(ev, path)`** | Event-driven (drained) | Drag-and-drop file imports from the desktop into the engine/editor. |

## Alternatives Considered

### Option A: Decentralized / Subsystem-Driven Ad-Hoc Loops

Allow individual subsystems (Input, Physics, Renderer, Audio) to maintain their own loops or poll
the platform backend directly whenever they need data.

**Why rejected:** This produces an unmaintainable tangle of execution order dependencies. If the
renderer polls the window size while the input system is polling cursor positions, spatial coordinate
mismatches occur. Furthermore, without a centralized coordinator, enforcing fixed-timestep physics
accumulation and render interpolation ($\alpha$) becomes fragmented across multiple files, making
deterministic replays impossible.

### Option B: Monolithic God-Class Application

Combine the application loop, graphics device initialization (RHI), audio device management, and
asset streaming into a single monolithic `Application` class (analogous to early game frameworks).

**Why rejected:** Violates the Single Responsibility Principle and our physical module separation
discipline ([ADR-0001](./ADR-0001.md), [ADR-0004](./ADR-0004.md)). A graphics device failure should
not prevent headless simulation testing. By restricting `gp::Application` strictly to lifecycle,
platform orchestration, time, and input, the graphics pipeline remains a completely independent
consumer ([ADR-0002](./ADR-0002.md)).

### Option C: Inversion of Control via OS Event Callbacks (Push Architecture)

Let the operating system drive the main loop directly via platform callbacks (analogous to the
Emscripten `emscripten_set_main_loop` or pure Cocoa `NSApplicationMain` run loops).

**Why rejected:** OS-driven push architectures strip the engine of explicit control over its frame
budget. In a push model, the OS invokes the render callback whenever the compositor dictates,
preventing the engine from executing fixed-rate physics sub-stepping, enforcing sleep intervals during
hitches, or pacing foreground vs. background frame rates. Desktop AAA engines require an explicit
pull-based `while (isRunning)` frame budget loop. Where platforms strictly require push loops (e.g.
WebAssembly/iOS), the platform backend must adapt to synthesize tick dispatches, preserving the
centralized `Application` structure.

## Consequences

### Positive

- **Deterministic, reproducible frame execution.** Clear separation between fixed-rate physics
  ticks (`onFixedUpdate`) and variable-rate render frames (`onRender`) guarantees stable simulation
  dynamics and smooth visual interpolation regardless of display refresh rate.
- **Robust input integrity.** Intra-frame input latching and automatic focus-loss sanitization
  completely eliminate dropped clicks, missed key releases, and stuck keys.
- **Superior energy efficiency.** Intelligent background throttling and sleep-when-minimized
  mechanisms drop idle CPU consumption to 0% when the window is not visible.
- **Decoupled and testable.** The application host operates on pure abstractions (`IApplicationBackend`,
  `IInputSystem`), permitting headless unit testing and automated CI execution without modification.
- **Clean architectural pedagogy.** Engine learners can read a single file (`Application.cpp`) to
  comprehend the complete, unbroken end-to-end execution flow of a production-grade AAA game engine loop.

### Negative

- **Rigid lifecycle structure.** Game logic and subsystems must conform to the prescribed eight-phase
  execution order. Custom execution models (e.g. completely decoupled asynchronous render threads)
  require explicit architecture within `onRender` rather than ad-hoc thread spawning.
- **Virtual dispatch on hook invocations.** Specialization hooks (`onUpdate`, `onRender`) incur
  virtual dispatch overhead. However, because these hooks are invoked exactly once per frame (or once
  per fixed tick), the nanosecond cost is completely unmeasurable against frame budgets.
