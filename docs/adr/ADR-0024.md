# ADR-0024: Strict Compile-Time Lock-Free Guarantees via Concept-Constrained Atomics

> The C++ standard library (`std::atomic<T>`) silently falls back to hidden OS software locks if
> `T` exceeds the hardware's native register size, silently destroying real-time thread scaling.
> The engine strictly forbids this by constraining `gp::Atomic<T>` with a `C++20` concept
> (`AtomicValue`). This guarantees that any atomic instantiation is strictly 1, 2, 4, or 8 bytes
> and trivially copyable, ensuring it always compiles 1:1 down to hardware-native lock-free
> instructions (e.g., `LOCK CMPXCHG`) or fails at compile-time.

![Proposed][badge-proposed]

## Context

The standard library `std::atomic<T>` template allows instantiation for any type `T` that is
trivially copyable:

```cpp
struct TransformData
{
    float matrix[16];
};

std::atomic<TransformData> g_worldTransform; // Compiles cleanly in standard C++
```

When `sizeof(T)` exceeds native register width (8 bytes on 64-bit CPU targets), standard library
implementations do not generate compile errors. Implementations such as GNU `libstdc++`, LLVM
`libc++`, and Microsoft MSVC CRT fall back to runtime support functions in `libatomic` (such as
`__atomic_load` and `__atomic_store`). These functions synchronize state using a global hash
table of spinlocks or operating system mutexes.

In a real-time game engine, this silent fallback introduces three failure modes:

1. **Lock Contention and False Serialization:** Multiple independent atomic objects hash to the
   same bucket in the global mutex table. Unrelated worker threads serialize behind the same lock,
   degrading throughput across CPU cores.
2. **Priority Inversion:** High-priority execution paths, such as the 48 kHz audio mixer thread
   or the primary render thread, can block on an OS mutex held by a low-priority background asset
   streaming worker. If the OS scheduler pre-empts the worker thread, real-time deadlines fail,
   causing dropped frames or audio buffer underruns.
3. **Late Runtime Discovery:** Developers cannot catch non-lock-free atomics through compiler
   diagnostics or static analysis. The lock fallback is discoverable only via runtime calls to
   `is_lock_free()`, thread sanitizers, or profiler traces during late production stages.

Engine concurrency primitives must guarantee hardware-native execution at compile time. Any type
that requires software locking must produce an immediate compilation failure.

## Decision

We introduce `gp::thread::Atomic<T>`, constrained by the `AtomicValue` C++20 concept:

```cpp
template <typename T>
concept AtomicValue = gp::concepts::IsTriviallyCopyable<T> &&
                      gp::concepts::IsSameAs<T, std::remove_cv_t<T>> &&
                      (sizeof(T) == 1u || sizeof(T) == 2u ||
                       sizeof(T) == 4u || sizeof(T) == 8u);
```

The concept enforces three mechanical properties:

- The type must be trivially copyable (`gp::concepts::IsTriviallyCopyable<T>`), ensuring its bit
  pattern can be transferred via direct memory copy.
- The type must have no top-level `const` or `volatile` qualifiers
  (`gp::concepts::IsSameAs<T, std::remove_cv_t<T>>`).
- The type size must equal exactly 1, 2, 4, or 8 bytes.

Any attempt to instantiate `gp::thread::Atomic<T>` with an unsupported type triggers a compiler
error detailing the unsatisfied concept constraints.

### Hardware Instruction Mapping

Every permitted size maps directly to target hardware registers and atomic CPU instructions:

- **1 Byte (8-bit):** Types such as `bool`, `char`, and `uint8_t` map to `LOCK CMPXCHG8` (or
  `CMPXCHGB`) on x86-64, and `LDREXB`/`STREXB` (or `LDXRB`/`STXRB`) on ARM64.
- **2 Bytes (16-bit):** Types such as `int16_t` and `uint16_t` map to `LOCK CMPXCHG16` (or
  `CMPXCHGW`) on x86-64, and `LDREXH`/`STREXH` (or `LDXRH`/`STXRH`) on ARM64.
- **4 Bytes (32-bit):** Types such as `int32_t`, `uint32_t`, and `float` map to `LOCK CMPXCHG32`
  and `LOCK XADD` on x86-64, and `LDREX`/`STREX` (or `LDXR`/`STXR`) on ARM64.
- **8 Bytes (64-bit):** Types such as `int64_t`, `uint64_t`, `double`, and object pointers (`T*`)
  map to `LOCK CMPXCHG64` on x86-64, and `LDREXD`/`STREXD` (or `LDXR`/`STXR`, `CAS`) on ARM64.

### Memory Ordering Abstraction

The engine provides `gp::memory::MemoryOrder`, an enumeration describing six memory ordering
models: `Relaxed`, `Consume`, `Acquire`, `Release`, `AcqRel`, and `SeqCst`. These map directly to
compiler intrinsics (`_Interlocked*` on MSVC, `__atomic_*` builtins on Clang and GCC) without
including `<atomic>`.

### Architectural Invariants

1. **Strict Compile-Time Sizing:** Every atomic payload must satisfy `AtomicValue`. The compiler
   rejects any type whose byte width is not 1, 2, 4, or 8 at the point of instantiation.
2. **Deterministic Hardware Mapping:** Every atomic operation compiles down to a native CPU
   instruction and register load or store, preventing any fallback to runtime mutex tables.
3. **Zero Standard Library Coupling:** The atomic subsystem never includes `<atomic>` or links
   against `libatomic`. Low-level synchronization relies on compiler intrinsics and engine
   platform headers.
4. **Natural Hardware Alignment:** Atomic storage enforces natural alignment via
   `alignas(sizeof(T))`. This avoids split cache-line memory accesses on x86-64 and unaligned
   access faults on ARM platforms.

## Alternatives Considered

### Option A: Standard `std::atomic<T>` with Runtime `is_lock_free()` Assertions

Use `std::atomic<T>` from `<atomic>` and place runtime assertions `assert(val.is_lock_free())` in
debug builds.

**Why rejected:** Runtime assertions execute only when control flow passes through specific code
paths. Code instantiating an oversized atomic can pass automated test suites on developer
workstations if those branches are not fully exercised. Furthermore, hardware architectures
differ: a 16-byte structure might be lock-free on an x86-64 CPU supporting `CMPXCHG16B` but fall
back to a software mutex on an ARM device. Compile-time constraints eliminate platform
discrepancy risks before code compiles.

### Option B: Static Assertions inside `std::atomic` Subclasses

Derive custom atomic classes from `std::atomic<T>` and embed `static_assert(sizeof(T) <= 8)`
within the class body.

**Why rejected:** Standard library atomic templates are not intended as base classes. They do not
provide virtual destructors, and their internal implementations rely on compiler-specific class
hierarchies. In addition, subclassing requires including `<atomic>`, which introduces standard
library template bloat into the engine's core compilation unit and creates ABI dependencies across
dynamic module boundaries.

### Option C: Supporting 16-Byte Atomics via `CMPXCHG16B`

Expand `AtomicValue` to permit 16-byte data types, using `LOCK CMPXCHG16B` on x86-64 and
`LDXP`/`STXP` on ARM64.

**Why rejected:** 16-byte atomic instructions introduce steep microarchitectural penalties. On AMD
Zen and Intel processors, 16-byte compare-and-swap instructions exhibit substantially higher cycle
latency than 64-bit atomics. Furthermore, 16-byte atomic operations require strict 16-byte address
alignment; misaligned accesses trigger a hardware general protection fault (`#GP`). Finally,
support across target architectures is uneven: older or embedded ARM and x86 chips lack 128-bit
atomic instructions or fall back to internal locks, breaking cross-platform determinism.

## Consequences

### Positive

- **Guaranteed lock-free execution at compile time.** The compiler verifies that every atomic
  variable maps directly to hardware registers, eliminating hidden software locks and mutex
  contention.
- **Protection against priority inversion.** Real-time audio and frame-critical render threads
  cannot block on low-priority worker threads through global runtime lock tables.
- **Elimination of standard library concurrency headers.** Custom intrinsics avoid `<atomic>`
  header bloat, cutting translation unit parse times and preserving ABI stability.
- **Immediate diagnostic feedback.** Developers who pass oversized or non-trivially copyable types
  receive explicit compile-time concept failures at the line of instantiation.

### Negative

- **Payload size restriction.** Structures exceeding 8 bytes cannot be stored directly in an
  atomic container; systems must use index handles or pointer indirection.
- **Platform intrinsic maintenance.** The engine must implement and maintain platform-specific
  atomic bindings across Windows, Linux, and macOS rather than relying on standard library
  vendors.
