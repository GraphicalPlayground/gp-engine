# ADR-0011: Dependency-Injected Application Backend Interface for Platform Agnosticism

> Establishes `IApplicationBackend` so engine logic stays independent of the OS/SDL3 layer, with the
> concrete backend injected at the executable level (e.g., inside `gp_editor`).

![Proposed][badge-proposed]

## Context

The application and windowing runtime sits between high-level engine orchestration (gameplay ticks,
frame pacing, rendering dispatch) and low-level OS mechanics (event polling, window surface
creation, display topology queries). Three common anti-patterns appear at this boundary:

1. **Direct link-time and header coupling:** The central application class `#include`s the platform
   library directly (`<windows.h>`, `<SDL3/SDL.h>`, or `<GLFW/glfw3.h>`). Every consumer,
   including test runners, headless servers, and offline asset compilers, must then link against OS
   windowing and graphics libraries.
2. **Hidden global state and service locators:** Exposing the backend through global singletons
   (`gEnv->pPlatform` or `Platform::Get()`) introduces unpredictable static initialization and
   destruction order, blocks parallel engine instances in tests, and hides subsystem dependencies.
3. **Compile-time `#ifdef` branching:** Hardcoding platform selection via preprocessor macros
   (`#ifdef _WIN32 ... #elif __APPLE__ ...`) prevents substituting mock or headless backends in
   tests, hurts modularity, and triggers wide recompiles on config changes.

`gp-engine` also runs automated tests in CI environments. Build agents and Linux containers often
lack monitors, X11 displays, Wayland compositors, and audio hardware. If `Application` were tied to
a concrete backend like SDL3, automated tests would crash or hang at startup trying to open a
display.

We need a pattern that keeps high-level engine logic platform-agnostic, isolates headers, and lets
us swap between windowed backends (SDL3) and zero-dependency headless backends with no steady-state
frame cost.

## Decision

We establish `gp::hal::IApplicationBackend` and use Composition Root Dependency Injection for
platform abstraction.

The engine runtime (`source/runtime/application/`) depends only on the abstract contracts in
`hal/base` and the platform-agnostic logic in `hal/generic`. It has zero link-time or compile-time
dependencies on concrete backends such as `hal/sdl3`. Concrete backends are instantiated at the
executable launch tier (`source/launch/editor/`, `source/launch/standalone/`) and passed into
`gp::Application` at construction.

```text
[Executable Layer: gp_editor] (Composition Root)
         |
         +---> Instantiates: gp::makeUnique<gp::hal::sdl3::ApplicationBackend>()
         |
         +---> Injects into: gp::Application(desc, std::move(backend))
                    |
                    V
         [source/runtime/application/]
                    |
       (links strictly to hal/base & hal/generic)
                    |
                    V
       +------------+------------+
       |                         |
       V                         V
 [IApplicationBackend]     [generic::ApplicationBackend]
  (Abstract Contract)       (Headless Fallback & Topology Math)
       ^
       | (implements)
       |
 [sdl3::ApplicationBackend]
  (Concrete Implementation)
  (links privately to SDL3)
```

### Architectural structure and invariants

1. **Abstract contract (`IApplicationBackend`):** The pure virtual interface
   `gp::hal::IApplicationBackend`
   (`source/runtime/hal/base/public/backend/IApplicationBackend.hpp`) defines the platform boundary:
   - **Lifecycle management:** `initialize(desc)` and `shutdown()`.
   - **Non-blocking OS event ingestion:** `pumpEvents(eventStream, outStats)`.
   - **Low-power throttling:** `waitEventsTimeout(timeoutMs)` and cross-thread `wakeEventLoop()`.
   - **Subsystem resource factories:** `createWindow(desc)` and `createInputSystem()`.
   - **Display topology and spatial resolution:** `getDisplayCount()`, `getPrimaryDisplay()`,
     `getDisplayForPoint(point)`, and `getDisplayForRect(rect)`.
   - **Platform services:** `getDialog()` ([ADR-0038](./ADR-0038.md)) and `getClipboard()`.

2. **Zero link-time dependency in `application`:** GPBT enforces dependency inversion:

   ```cmake
   # source/runtime/application/CMakeLists.txt
   gpStartModule(application)
     gpAddDependency(PUBLIC core)
     gpAddDependency(PUBLIC hal/base)
     gpAddDependency(PUBLIC hal/generic)
     # NOTE: hal/sdl3 is NEVER linked here!
   gpEndModule()
   ```

   The executable composition root introduces the concrete backend:

   ```cmake
   # source/launch/editor/CMakeLists.txt
   gpStartExecutable(editor)
     gpAddDependency(PUBLIC core)
     gpAddDependency(PUBLIC application)
     gpAddDependency(PUBLIC hal/sdl3)   # Composition Root brings both together
   gpEndExecutable()
   ```

3. **Deterministic headless fallback:** If an executable or unit test creates `gp::Application`
   without injecting a backend (`backend == nullptr`), `Application::initialize()` creates a
   `gp::hal::generic::ApplicationBackend`:

   ```cpp
   // source/runtime/application/private/Application.cpp
   if (!m_backend.isValid())
   {
       m_backend = gp::makeUnique<hal::generic::ApplicationBackend>();
   }
   ```

   `generic::ApplicationBackend` runs in memory with zero third-party dependencies, zero OS
   syscalls, and a virtual 1080p@60Hz display topology ([ADR-0029](./ADR-0029.md)), so unit tests
   and headless tools run on bare CI containers.

4. **Explicit unique ownership:** `Application` owns the backend via
   `gp::UniquePtr<hal::IApplicationBackend>`. Binding backend lifetime to `Application` gives a
   deterministic teardown order: windows close and input systems release before the backend
   terminates.

5. **Decoupled steady-state execution:** Setup, window creation, and event pumping use virtual
   dispatch, while the game loop drains events from `gp::SPSCByteRingBuffer` via non-virtual POD
   memory reads ([ADR-0013](./ADR-0013.md), [ADR-0020](./ADR-0020.md)). Virtual calls on
   `IApplicationBackend` stay at coarse, once-per-frame boundaries such as `pumpEvents()` on the OS
   thread, avoiding virtual overhead during simulation.

### Comparison of injection patterns

<!-- markdownlint-disable MD013 -->
| Dimension | Composition DI (Adopted) | Global (`gEnv`) | Static `#ifdef` | Dynamic DLL |
| :--- | :--- | :--- | :--- | :--- |
| Coupling | `application` ignores `sdl3` | Global leaks | `#ifdef _WIN32` | Symbol loading |
| Headless CI | Inject `generic` or mock | Global stubs | Full rebuild | Dummy shared libs |
| Lifetime | `Application` `UniquePtr` | Static order | Process exit | Manual `FreeLibrary` |
| Instances | Independent instances | Singleton clashes | Single config | Independent |
| Startup | Direct C++ instantiation | Pointer assign | Static binding | Disk I/O, lookup |

## Alternatives Considered

### Option A: Static compile-time binding via preprocessor macros

Compile platform-specific classes directly into the application module using OS guards (similar to
Unreal Engine's `ApplicationCore` compiling `FWindowsApplication` on Windows and `FCocoaApplication`
on macOS).

**Why rejected:** Forces `application` to depend directly on platform libraries, prevents headless
testing without recompiling the engine with different flags, and blocks swapping mock or null
backends inside one executable. It also breaks our module directory discipline
([ADR-0001](./ADR-0001.md)).

### Option B: Global service locator / singleton (`PlatformBackend::Get()`)

Keep a global singleton pointer to the active platform backend accessible everywhere (similar to
CryEngine's `gEnv->pSystem`).

**Why rejected:** Global singletons create hidden dependencies across subsystems, making coupling
harder to trace from headers. They also make multi-instance unit tests fragile, add races in
parallel test runners, and risk static-destruction-order crashes at shutdown.

### Option C: Dynamic plugin loading via shared libraries (`LoadLibrary` / `dlopen`)

Load the platform backend from a shared library at startup, matching our RHI architecture
([ADR-0002](./ADR-0002.md)).

**Why rejected:** Runtime loading makes sense for graphics backends where Vulkan vs. D3D12 depends
on GPU hardware and user config, whereas the windowing layer is the root host of the process.
Dynamic loading there adds filesystem searches before logging or error dialogs exist, symbol
lookups, and platform-specific DLL search paths. Constructor injection at the composition root
decouples the modules with compile-time type safety and no loader complexity.

## Consequences

### Positive

- **Platform-agnostic `application` module.** Core engine loops, frame timing, and event
  distribution compile without any OS windowing SDK.
- **Headless CI testing.** Tests create `Application` with `generic::ApplicationBackend` and run
  full lifecycle and input pipelines on displayless Linux servers without mocking OS APIs.
- **Deterministic initialization and destruction order.** Owning the backend via `UniquePtr` ensures
  windows, input hooks, and message pumps release before the platform library shuts down.
- **Swappable backends.** Future backends (such as GLFW, WebAssembly/Emscripten, or a
  record-and-replay mock) plug in without modifying `Application`.
- **Explicit composition root.** All concrete bindings sit in `launch/editor/private/Main.cpp`,
  making subsystem wiring easy to inspect.

### Negative

- **Virtual dispatch on coarse operations.** Platform calls (`pumpEvents`, `createWindow`) go
  through a vtable, costing under 2 ns per call and staying outside inner simulation and rendering
  loops.
- **Executable composition boilerplate.** Executables must `#include` and instantiate the concrete
  backend before passing it to `Application`. This keeps subsystem wiring explicit.
