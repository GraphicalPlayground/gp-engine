# ADR-0011: Dependency-Injected Application Backend Interface for Platform Agnosticism

> Establishes the `IApplicationBackend` pattern, ensuring the engine logic remains completely blind
> to the underlying OS/SDL3 layer, with the specific backend injected at the executable level
> (e.g., inside `gp_editor`).

![Proposed][badge-proposed]

## Context

In game engine architecture, the application and windowing runtime sits directly at the boundary
between high-level engine orchestration (gameplay ticks, frame pacing, rendering dispatch) and
low-level operating system mechanics (event polling, window surface creation, display topology
queries). Naive architectures frequently commit one of three architectural anti-patterns at this
boundary:

1. **Direct Link-Time and Header Coupling:** The central application class `#include`s the concrete
   platform library directly (e.g., `<windows.h>`, `<SDL3/SDL.h>`, or `<GLFW/glfw3.h>`). This forces
   every consumer of the application library, including automated test runners, headless dedicated
   servers, and offline asset compilers, to link against heavy OS windowing and graphics libraries.
2. **Hidden Global State & Service Locators:** Exposing the platform backend through global singleton
   pointers (e.g., `gEnv->pPlatform` or `Platform::Get()`) introduces unpredictable static
   initialization and destruction orders (the Static Initialization Order Fiasco), prevents running
   multiple engine instances in parallel test runners, and obscures the true dependencies of
   subsystems.
3. **Compile-Time `#ifdef` Branching:** Hardcoding platform selection via preprocessor macros inside
   the application layer (e.g., `#ifdef _WIN32 ... #elif __APPLE__ ...`) prevents substituting mock
   or headless backends during testing, destroys code modularity, and causes recompilation cascades
   whenever platform configuration changes.

Furthermore, Graphical Playground (`gp-engine`) requires robust automated testing in Continuous
Integration (CI) environments. Dedicated build agents and cloud Linux containers often lack physical
monitors, X11 displays, Wayland compositors, and audio hardware. If the core `Application` class is
hardwired to a concrete backend like SDL3, automated tests will crash or hang upon startup when
attempting to initialize non-existent OS display subsystems.

We require an architectural pattern that guarantees complete platform agnosticism for high-level
engine logic, enforces strict header isolation, and allows seamless substitution between concrete
windowed backends (SDL3) and zero-dependency headless backends without runtime penalty during steady-state
frame execution.

## Decision

We establish the `gp::hal::IApplicationBackend` interface and mandate the **Composition Root
Dependency Injection** pattern for platform abstraction.

The engine runtime (`source/runtime/application/`) depends strictly on the abstract contracts
defined in `hal/base` and the platform-agnostic business logic in `hal/generic`. It contains zero
link-time or compile-time dependencies on concrete backends such as `hal/sdl3`. Concrete backends
are instantiated exclusively at the executable launch tier (`source/launch/editor/`,
`source/launch/standalone/`) and injected into `gp::Application` at construction time.

```text
[Executable Layer: gp_editor] (Composition Root)
         |
         +---> Instantiates: gp::makeUnique<gp::hal::sdl3::ApplicationBackend>()
         |
         +---> Injects into: gp::Application(desc, std::move(backend))
                    |
                    V
         [source/runtime/application/]
                    |
       (links strictly to hal/base & hal/generic)
                    |
                    V
       +------------+------------+
       |                         |
       V                         V
 [IApplicationBackend]     [generic::ApplicationBackend]
  (Abstract Contract)       (Headless Fallback & Topology Math)
       ^
       | (implements)
       |
 [sdl3::ApplicationBackend]
  (Concrete Implementation)
  (links privately to SDL3)
```

### Architectural Structure & Invariants

1. **Abstract Contract Completeness (`IApplicationBackend`):** The pure virtual interface
   `gp::hal::IApplicationBackend` (in `source/runtime/hal/base/public/backend/IApplicationBackend.hpp`)
   defines the entire hardware platform capability boundary:
   - **Lifecycle Management:** `initialize(desc)` and `shutdown()`.
   - **Non-Blocking OS Event Ingestion:** `pumpEvents(eventStream, outStats)`.
   - **Low-Power Throttling:** `waitEventsTimeout(timeoutMs)` and cross-thread `wakeEventLoop()`.
   - **Subsystem Resource Factories:** `createWindow(desc)` and `createInputSystem()`.
   - **Display Topology & Spatial Resolution:** `getDisplayCount()`, `getPrimaryDisplay()`,
     `getDisplayForPoint(point)`, and `getDisplayForRect(rect)`.
   - **Platform Services:** `getDialog()` ([ADR-0038](./ADR-0038.md)) and `getClipboard()`.

2. **Zero Link-Time Dependency in `application`:** The build configuration enforces dependency
   inversion mechanically through GPBT:

   ```cmake
   # source/runtime/application/CMakeLists.txt
   gpStartModule(application)
     gpAddDependency(PUBLIC core)
     gpAddDependency(PUBLIC hal/base)
     gpAddDependency(PUBLIC hal/generic)
     # NOTE: hal/sdl3 is NEVER linked here!
   gpEndModule()
   ```

   The concrete backend is introduced strictly at the executable composition root:

   ```cmake
   # source/launch/editor/CMakeLists.txt
   gpStartExecutable(editor)
     gpAddDependency(PUBLIC core)
     gpAddDependency(PUBLIC application)
     gpAddDependency(PUBLIC hal/sdl3)   # Composition Root brings both together
   gpEndExecutable()
   ```

3. **Deterministic Headless Fallback:** If an executable or unit test instantiates `gp::Application`
   without injecting a backend (`backend == nullptr`), `Application::initialize()` automatically
   provisions a `gp::hal::generic::ApplicationBackend`:

   ```cpp
   // source/runtime/application/private/Application.cpp
   if (!m_backend.isValid())
   {
       m_backend = gp::makeUnique<hal::generic::ApplicationBackend>();
   }
   ```

   `generic::ApplicationBackend` operates entirely in-memory with zero third-party dependencies,
   zero OS syscalls, and automatically synthesizes a virtual 1080p@60Hz display topology
   ([ADR-0029](./ADR-0029.md)), allowing unit tests and headless tools to run flawlessly on bare CI
   containers.

4. **Explicit Unique Ownership:** The application host owns the backend via
   `gp::UniquePtr<hal::IApplicationBackend>`. The backend's lifetime is bound strictly to the
   `Application` instance, guaranteeing deterministic teardown ordering: windows are closed and input
   systems released before the platform backend terminates.

5. **Decoupled Steady-State Execution:** While setup, window creation, and event pumping utilize
   virtual dispatch, the high-frequency game loop drains events from `gp::SPSCByteRingBuffer` via
   direct, non-virtual POD memory reads ([ADR-0013](./ADR-0013.md), [ADR-0020](./ADR-0020.md)).
   Virtual calls on `IApplicationBackend` are restricted to coarse, once-per-frame boundaries (such
   as `pumpEvents()` on the OS thread), incurring zero cache-miss or virtual overhead during frame
   simulation.

## Alternatives Considered

### Option A: Static Compile-Time Binding via Preprocessor Macros

Compile platform-specific classes directly into the application module using OS guards
(analogous to Unreal Engine's `ApplicationCore` compiling `FWindowsApplication` on Windows and
`FCocoaApplication` on macOS).

**Why rejected:** This forces `application` to directly depend on platform libraries. It makes headless
unit testing impossible without recompiling the entire engine with a different macro flag, and prevents
running test suites with mock or null backends within the same executable. It also violates our
modular physical directory discipline ([ADR-0001](./ADR-0001.md)).

### Option B: Global Service Locator / Singleton (`PlatformBackend::Get()`)

Maintain a global singleton pointer to the active platform backend accessible anywhere in the engine
(analogous to CryEngine's `gEnv->pSystem` or legacy game toolkits).

**Why rejected:** Global singletons introduce hidden dependencies across subsystems, making it
impossible to reason about component coupling from class headers alone. Singletons make multi-instance
unit testing fragile, introduce race conditions in multithreaded test runners, and frequently cause
crashes during engine shutdown due to undefined static destruction order.

### Option C: Dynamic Plugin Loading via Shared Libraries (`LoadLibrary` / `dlopen`)

Dynamically load the platform backend from a shared library at startup, identical to our Rendering
Hardware Interface (RHI) architecture ([ADR-0002](./ADR-0002.md)).

**Why rejected:** While runtime dynamic loading is essential for graphics backends (where Vulkan vs.
Direct3D 12 is chosen based on GPU hardware and user configuration), the application and OS windowing
layer represents the root execution host of the process. Dynamically loading the windowing backend
introduces unnecessary complexity: searching filesystem paths before logging or error dialogs are
initialized, handling dynamic loader symbol lookups, and managing platform-specific DLL search paths.
Constructor dependency injection at the executable composition root achieves complete architectural
decoupling with compile-time type safety and zero loader complexity.

## Consequences

### Positive

- **Total decoupling of core engine logic from platform SDKs.** The `application` module remains
  100% platform-agnostic, enabling pure pedagogical focus on engine loops, frame timing, and event
  distribution.
- **Flawless automated testing on headless CI pipelines.** Tests instantiate `Application` with
  `generic::ApplicationBackend`, executing full engine lifecycle and input pipelines on displayless,
  headless Linux servers without mocking OS APIs.
- **Deterministic initialization and destruction order.** Owning the backend through `UniquePtr`
  guarantees that all window surfaces, input hooks, and message pumps are released before the
  platform library shuts down.
- **Extensible multi-backend architecture.** Enables effortless authoring of alternative platform
  backends in the future (e.g., a lightweight GLFW backend, a WebAssembly/Emscripten backend, or a
  deterministic record-and-replay mock backend) without modifying a single line of `Application` code.
- **Clean composition root.** All concrete technology binding decisions are centralized in the
  executable entry point (`launch/editor/private/Main.cpp`), making the engine's physical dependency
  wiring immediately legible to engineers.

### Negative

- **Minor virtual dispatch on coarse operations.** Platform operations (`pumpEvents`, `createWindow`)
  incur virtual table indirection. However, this cost is negligible ($< 2\text{ ns}$) and is never
  incurred on inner simulation or rendering loops.
- **Executable composition boilerplate.** Executables must explicitly `#include` the concrete backend
  header and instantiate the backend before passing it to `Application`. This minor boilerplate is
  an intentional pedagogical win, as it makes subsystem wiring explicit rather than magical.

cross-platform scalability while serving as an educational reference for clean, testable systems
