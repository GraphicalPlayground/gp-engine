# ADR-0057: Runtime Console Variable and Command Registry with Dual-Slot Render Sync

> Adopts a zero-allocation runtime console subsystem (`gp::console`) in `gp::core` that combines
> O3DE/id Tech intrusive static registration with Unreal-style dual Game/Render slots, priority
> tiers, and `gp::Delegate` notifications.

![Accepted][badge-accepted]

## Context

`gp-engine` needs a runtime console variable (CVar) and command registry for debug toggles, frame
budgets, render pass parameters, and command dispatch across `gp::core`, `gp::hal`, `gp::rhi`,
`gp::renderer`, and `gp::application`.

Using a naive `std::unordered_map` singleton, mutex-guarded variable reads, or heap-allocated
callbacks fails under engine constraints in four ways:

- Subsystems declare file-scope static CVars (`AutoConsoleVariable<T>`). Touching a singleton
  hash map or allocator during C++ static initialization triggers the Static Initialization Order
  Fiasco across translation units and shared libraries (`GP_IS_MONOLITHIC == 0`).
- The Game Thread and console commands write CVars while Render Thread or Render Dependency Graph
  (RDG) fibers extract the prior frame or build current command lists. Shared mutable variables
  race and tear across related graphics settings, and mutexes on hot CVar reads hurt scaling.
- Startup and runtime configuration arrive from defaults, scalability tiers, config files,
  `gp::CommandLine`, C++ code, and console input. Without source priority tracking, a lower-tier
  preset can overwrite a command-line flag.
- Placing CVar types above `gp::core` violates the upward dependency DAG ([ADR-0041](./ADR-0041.md))
  and prevents `gp::hal` or `gp::rhi` from declaring CVars. Heap-allocating `std::string` or
  `std::function` objects breaks our zero-allocation rule ([ADR-0042](./ADR-0042.md)).

`gp::core` therefore needs an STL-free, zero-allocation console registry with safe static init,
lock-free render-thread reads, override precedence, and decoupled callbacks.

## Decision

We add a non-allocating `gp::Delegate` / `gp::FixedMulticastDelegate` primitive in
`templates/Delegate.hpp` and the `gp::console` subsystem in `source/runtime/core/`.

### Physical file layout

Following the three-tier module layout ([ADR-0001](./ADR-0001.md)) and co-located tests
([ADR-0006](./ADR-0006.md)), declarations are split by role:

```text
source/runtime/core/
  public/
    templates/
      Delegate.hpp              <-- 32-byte SBO Delegate & FixedMulticastDelegate
    console/
      ConsoleForward.hpp        <-- Forward declarations for console interfaces & types
      ConsoleEnums.hpp          <-- ConsoleVarType, ConsoleVarFlags, SetBy, ConsoleResult
      ConsoleTypes.hpp          <-- ConsoleString, ConsoleCommandArgs, delegates, parsers
      ConsoleDesc.hpp           <-- ConsoleManagerDesc configuration descriptor
      IConsoleObject.hpp        <-- Shared variable/command object contract
      IConsoleVariable.hpp      <-- Game, Render, and AnyThread CVar contract
      IConsoleCommand.hpp       <-- Console command execution contract
      IConsoleManager.hpp       <-- Registry contract and singleton access
      ConsoleManager.hpp        <-- ConsoleManagerBase & templated BasicConsoleManager
      AutoConsoleVariable.hpp   <-- AutoConsoleVariable<T>, Ref, Sink, Command wrappers
      Console.hpp               <-- Umbrella public header
  private/
    console/
      ConsoleManager.cpp        <-- Hash table, deferred lists, CLI & built-in commands
  tests/
    templates/
      Delegate.tests.cpp        <-- Unit tests for Delegate, Handle, FixedMulticastDelegate
    console/
      ConsoleEnums.tests.cpp    <-- Flag bitmask, SetBy ordering, and string helper tests
      ConsoleTypes.tests.cpp    <-- Command line tokenizer and <charconv> parser tests
      ConsoleVariable.tests.cpp <-- Dual Game/Render reads, Ref, Sink, Command, Delegates
      ConsoleManager.tests.cpp  <-- Registry, SIOF deferral, CLI overrides, stress tests
```

### Intrusive registration and frame sync

```text
  [ Static C++ Init: AutoConsoleVariable<T> / Ref / Sink / Command ]
                                 |
        Pushes node to constinit .bss intrusive list (Zero heap allocs)
                                 |
                                 v
  [ IConsoleManager::get() / initialize() ]
        Drains intrusive list into Fnv1a64 open-addressed table
        Applies gp::CommandLine overrides (-cvar=val, +cvar val, -ExecCmds=...)
                                 |
         +-----------------------+-----------------------+
         |                                               |
  (Game Thread Write)                           (Render Thread Read)
         |                                               |
         v                                               v
  AutoConsoleVariable::set()                    getValueOnRenderThread()
    - Checks ReadOnly, Cheat, SetBy priority      - Lock-free Atomic::load(Acquire)
    - Writes m_gameScalar (or m_latchedScalar)      on m_renderScalar (or seqlock string)
    - Fires change delegates (locks released)     - Observes frame-coherent snapshot
    - Marks dirty for render sync                        ^
         |                                               |
         +-----> IConsoleManager::syncRenderThreadValues() (at frame handoff)
```

### Architectural invariants

1. Every console type avoids heap allocations. `AutoConsoleVariable<T>`, `AutoConsoleVariableRef`,
   `AutoConsoleVariableSink`, and `AutoConsoleCommand` store names, help strings, fixed-size
   255-byte `ConsoleString` values, and 32-byte SBO `gp::Delegate` callbacks inline. The global
   `IConsoleManager::get()` registry lives in `.bss` with an open-addressed hash table and fixed
   pools (`BasicConsoleManager`).
2. Static constructors push nodes onto a `constinit` zero-initialized intrusive list guarded by an
   `AtomicFlag` in `ConsoleManager.cpp`. Destructors unlink cleanly from either the deferred list
   or the owning manager hash table, so hot-reloaded modules and scoped test variables leave no
   dangling pointers.
3. Scalar `AutoConsoleVariable<T>` instances (`bool`, `Int32`, `UInt32`, `Float32`, `Float64`) keep
   separate `m_defaultScalar`, `Atomic<T> m_gameScalar`, `Atomic<T> m_renderScalar`, and
   `m_latchedScalar` slots. String CVars use fixed `char` buffers paired with `Atomic<UInt32>`
   seqlock counters and acquire/release fences for tear-free copies. Render-thread slots use
   `HardwareConstants::cacheLineSize` alignment to avoid false sharing with Game Thread writes, and
   the frame host calls `syncRenderThreadValues()` at the Game-to-Render boundary without coupling
   `gp::core` to any renderer command queue.
4. Every write carries a `ConsoleVarSetBy` priority (`Constructor < Scalability < GameSetting <
   ProjectSetting < SystemConfig < DeviceProfile < ConsoleVariables < CommandLine < Code <
   Console`). Writes from lower tiers return `ConsoleResult::PriorityTooLow` without replacing
   higher-priority overrides. Variables with `ConsoleVarFlags::Latched` stage writes until
   `flushLatchedVariables()`.
5. Render-thread and any-thread reads never acquire spinlocks. Before calling change delegates,
   `AutoConsoleCommand::execute()`, or `AutoConsoleVariableSink` callbacks, `ConsoleVariableBase`
   and `ConsoleManagerBase` copy callbacks onto the stack and release all internal locks, which
   prevents deadlocks when callbacks query or set other CVars.
6. `applyCommandLineOverrides()` reads `gp::CommandLine` ([ADR-0040](./ADR-0040.md)) for
   `-cvar=val`, `-cvar:val`, `+cvar val`, and `-ExecCmds="..."`. Console availability follows
   `GP_ALLOW_CONSOLE` from `BuildDefines.hpp`.

## Alternatives Considered

### Option B: Single atomic slot per CVar with explicit latch flags

Each variable stores one `gp::thread::Atomic<T>` (similar to O3DE `AZ_CVAR` and DOOM 3 BFG
`idCVar`) and updates it immediately on writes unless `ConsoleVarFlags::Latched` is set.

**Why rejected:** Mid-frame writes on non-latched CVars become visible immediately to concurrent
Render Extraction or RDG fibers, so one frame can read an inconsistent mix of old and new values
across related settings.

### Option C: Global double-buffered value arrays indexed by slot ID

Keep all CVar state inside two contiguous arrays inside `ConsoleManager`, storing only a compact
integer index inside each `AutoConsoleVariable<T>`.

**Why rejected:** External reference bindings (`AutoConsoleVariableRef`) point to caller-owned C++
variables that live outside the manager's arrays, and reading static CVars before manager startup
still needs local default storage.

## Consequences

### Positive

- **Frame-coherent lock-free render reads.** Render and RDG fibers call `getValueOnRenderThread()`
  via single atomic loads or seqlocks with no lock contention and no mid-frame tearing between sync
  barriers.
- **Zero-allocation registration and dispatch.** Static construction, case-insensitive `Fnv1a64`
  hash lookup, SBO delegate binding, and string snapshots run without heap allocations.
- **Safe DLL unload and isolated unit testing.** Intrusive destructors unlink on module unload or
  scope exit, and tests can instantiate local `ConsoleManager` instances separate from
  `IConsoleManager::get()`.
- **Engine-wide declarations without upward coupling.** Because `gp::console` resides in `gp::core`,
  lower layers such as `gp::hal` and `gp::rhi` can define CVars without circular dependencies.

### Negative

- **Larger inline footprint per CVar.** Each `AutoConsoleVariable<T>` carries default, Game,
  Render, latched, and callback fields inline, multiplying fixed-buffer space on string CVars.
- **Explicit frame sync requirement.** Subsystems that update render-facing CVars must call
  `syncRenderThreadValues()` on the frame boundary before Render Thread reads see the new value.
- **Bounded pools for imperative registrations.** Dynamic variables, commands, and sinks created
  via `IConsoleManager::registerConsoleVariable()` or `registerConsoleCommand()` draw from fixed
  capacities in `BasicConsoleManager`.
