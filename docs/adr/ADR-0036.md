# ADR-0036: Logical Player Slot Mapping and Focus-Loss Input Sanitization

> OS hardware instance IDs (`deviceId`) increment monotonically across USB/Bluetooth reconnects,
> breaking gameplay systems that index controllers by player number, while losing OS window focus
> (`WindowAction::FocusLost`) mid-keypress causes the OS to swallow the subsequent key-up message,
> leaving the engine in a permanent "stuck key" state. `InputSystem` maps dynamic hardware
> `deviceId` handles onto fixed-capacity logical player slots (`kMaxGamepads = 8`) with automatic
> reconnect rebinding, and forcefully synthesizes release transitions for all active keys and
> buttons upon window focus loss or application backgrounding.

![Proposed][badge-proposed]

## Context

Operating system input subsystems assign transient hardware identifiers to peripheral devices.
Under Microsoft Windows (RawInput, XInput, and Windows Gaming Input), Linux (`evdev`), macOS
(`IOHIDManager`), and cross-platform abstractions like SDL3, peripheral handles (`deviceId`)
increment monotonically every time a physical device connects, disconnects, or resumes from
a low-power wireless standby state.

When a player uses a wireless game controller (such as an Xbox Wireless Controller or a Sony
DualSense), brief signal dropouts, dead batteries, or USB cable disconnections cause the kernel
driver to tear down the device node. When the device reconnects seconds later, the operating
system registers it under a newly generated hardware instance ID (for example, incrementing
from device index 1 to device index 4).

If gameplay code references input devices directly through these volatile hardware identifiers,
or stores controllers in dynamic arrays that shift indices on removal, game state breaks:

- Local split-screen multiplayer loses player associations. Player 1 suddenly loses input
  authority, and their character stops responding to controller inputs.
- UI focus and viewport assignments become unlinked, requiring players to pause and rebind
  controllers manually through configuration menus.
- Dangling device pointers reference detached hardware contexts, causing invalid memory
  accesses or dropped input frames during gameplay ticks.

A separate input failure occurs when desktop applications lose window focus. Operating systems
route keyboard and mouse messages exclusively to the active window holding input focus. When a
player holds a movement key (such as `W` for forward movement) or a mouse button (such as primary
attack) and triggers a focus change (through Alt+Tab, pressing the Windows key, or clicking a
secondary monitor), the window manager sends a focus loss notification (`WM_KILLFOCUS` or
`SDL_EVENT_WINDOW_FOCUS_LOST`).

When the user releases the physical key or button outside the unfocused window, the operating
system sends the corresponding release message to the other active application or drops it.
The game never receives a `KeyState::Released` or `ButtonAction::Released` packet. When the user
restores focus, the input system still marks the key as `Held`. The character continues walking
into obstacles or expending ammunition indefinitely until the player presses and releases that
same control again.

`gp-engine` requires an input architecture that decouples volatile hardware instance IDs from
fixed gameplay player slots, preserves controller identity across reconnect cycles, and clears
active inputs upon window focus loss or backgrounding.

## Decision

We implement fixed-capacity logical player slot mapping and focus-loss input sanitization
within the HAL input subsystem and the runtime application layer.

### 1. Fixed-Capacity Logical Player Slot Table

The input system insulates gameplay systems from hardware instance IDs by defining a fixed
logical player enumeration (`GamepadSlot`) in `InputEnums.hpp`:

```cpp
enum class GamepadSlot : gp::UInt8
{
    Player1 = 0,
    Player2 = 1,
    Player3 = 2,
    Player4 = 3,
    Player5 = 4,
    Player6 = 5,
    Player7 = 6,
    Player8 = 7,
    Count   = 8,
    Any     = 0xFF
};

inline constexpr gp::UInt32 kMaxGamepads = static_cast<gp::UInt32>(GamepadSlot::Count);
```

`GenericInputSystem` maintains an inline array of controller slots (`m_gamepadTable[8]`).
Gameplay systems query gamepads exclusively through these logical player slots:

```cpp
[[nodiscard]] virtual IGamepad* getGamepad(
    GamepadSlot slot = GamepadSlot::Player1
) noexcept = 0;

[[nodiscard]] virtual bool isGamepadButtonDown(
    GamepadButton button, GamepadSlot slot = GamepadSlot::Player1
) const noexcept = 0;
```

Passing `GamepadSlot::Any` resolves to `m_mostRecentGamepadSlot`, which tracks the slot index
of the controller that generated the latest actuation exceeding analog deadzone thresholds.
Single-player games can poll `GamepadSlot::Player1` or `GamepadSlot::Any` without writing
hardware-detection code.

### 2. Automatic Slot Binding and Reconnect Rebinding

When a `GamepadEvent` or `DeviceChangeEvent` arrives from the platform message pump,
`GenericInputSystem::resolveOrAllocateSlotForDevice` resolves the hardware `deviceId` to a
logical slot index:

```cpp
[[nodiscard]] constexpr gp::UInt32 resolveOrAllocateSlotForDevice(InputDeviceId deviceId) noexcept
{
    if (deviceId == kInvalidInputDeviceId) [[unlikely]]
    {
        return kMaxGamepads;
    }

    // Step 1: Check if this hardware device is already bound to a slot
    for (gp::UInt32 i = 0u; i < kMaxGamepads; ++i)
    {
        if (m_gamepadTable[i] != nullptr && m_gamepadTable[i]->getDeviceId() == deviceId)
        {
            return i;
        }
    }

    // Step 2: Assign device to the lowest-numbered available slot
    for (gp::UInt32 i = 0u; i < kMaxGamepads; ++i)
    {
        if (m_gamepadTable[i] != nullptr && !m_gamepadTable[i]->isConnected())
        {
            m_gamepadTable[i]->attach(deviceId, static_cast<GamepadSlot>(i));
            return i;
        }
    }

    return kMaxGamepads;
}
```

When a controller disconnects (`DeviceAction::Disconnected`), `GenericGamepad::detach()` clears
the hardware handle, synthesizes release transitions for all held buttons, and marks the slot
disconnected:

```cpp
constexpr void detach() noexcept
{
    releaseAllInputs();
    m_isConnected = false;
}
```

The logical slot assignment remains intact. When the controller reconnects under a new hardware
`deviceId`, Step 2 assigns it to the lowest-numbered disconnected slot. In a single-player setup,
the reconnected gamepad reclaims `GamepadSlot::Player1`.

### 3. Focus-Loss Input Sanitization Protocol

To eliminate stuck-key defects during window focus transitions, `gp::application::Application`
intercepts window and application lifecycle actions in its event dispatcher:

```cpp
// source/runtime/application/private/Application.cpp
if (ev.action == ApplicationAction::WillEnterBackground ||
    ev.action == ApplicationAction::DidEnterBackground)
{
    m_isSuspended = true;
    m_inputSystem->releaseAllInputs();
}

if (ev.action == WindowAction::FocusLost || ev.action == WindowAction::Hidden ||
    (ev.action == WindowAction::StateChanged && ev.state == WindowState::Minimized))
{
    m_inputSystem->releaseAllInputs();
}
```

Calling `releaseAllInputs()` cascades across all active device categories:
`Keyboard`, `Mouse`, `SpatialDevice`, and every entry in `m_gamepadTable`:

```cpp
// GenericInputSystem.hpp
constexpr void releaseAllInputs() noexcept override
{
    m_keyboard.releaseAllInputs();
    m_mouse.releaseAllInputs();
    m_spatialDevice.releaseAllInputs();

    for (gp::UInt32 i = 0u; i < kMaxGamepads; ++i)
    {
        if (m_gamepadTable[i] != nullptr)
        {
            m_gamepadTable[i]->releaseAllInputs();
        }
    }
}
```

Within each device implementation (such as `GenericKeyboard.hpp` and `GenericGamepad.hpp`),
any control marked with `ButtonStateFlags::Held` has `Held` cleared and
`ButtonStateFlags::ReleasedThisFrame` set:

```cpp
if ((m_buttons[i] & ButtonStateFlags::Held) != ButtonStateFlags::None)
{
    m_buttons[i] = (m_buttons[i] & ~ButtonStateFlags::Held) |
                   ButtonStateFlags::ReleasedThisFrame;
}
```

Continuous analog stick positions, wheel deltas, and mouse relative deltas are zeroed.
Gameplay state machines observing edge latches (ADR-0034) observe an explicit release
transition, halting character velocity and weapon discharges before the next tick executes.

### Architectural Invariants

1. **Fixed Inline Allocation:** `GenericInputSystem` allocates `m_gamepadTable` as a fixed
   inline array of size `kMaxGamepads = 8`. Dynamic memory allocation during runtime gamepad
   connection, polling, or detachment is prohibited.
2. **Deterministic Lowest-Index Slot Assignment:** Dynamic device IDs bind to the lowest
   available unoccupied slot index (`Player1` through `Player8`). Disconnected slots retain
   their logical index until reclaimed, preserving stable bindings for multiplayer viewports.
3. **Symmetric Release Edge Synthesis:** Whenever `releaseAllInputs()` executes, any control
   carrying `ButtonStateFlags::Held` must clear `Held` and set
   `ButtonStateFlags::ReleasedThisFrame`. This preserves edge-triggered gameplay state machines
   without dropping release callbacks.
4. **Zero-Tolerance for Leaked Hardware IDs:** Gameplay code must never access peripherals
   through raw OS hardware handles (`InputDeviceId`). All gameplay queries must route through
   `GamepadSlot` or the default `GamepadSlot::Player1` and `GamepadSlot::Any` abstractions.

| :--- | :--- | :--- | :--- |
| **Split-Screen Stability** | Broken; reconnects append new slots or shift array indices | Unsupported; only one player permitted | Preserved; slots 1 through 8 remain stable across reconnects |
| **Reconnect Survival** | Failed; requires custom gameplay rebind logic per title | Fragile; driver ID changes can stall input polling | Automatic; disconnected slots rebind to lowest free player index |
| **Alt+Tab Stuck Keys** | Common; unhandled focus loss leaves `Held` flags set | Common; keys held during focus change remain pressed | Prevented; synthesizes `ReleasedThisFrame` on focus loss |

## Alternatives Considered

### Option A: Raw Hardware Device IDs in Gameplay Code (`getGamepadByHardwareId(id)`)

Expose raw platform `InputDeviceId` handles directly to gameplay systems and game scripting.

**Why rejected:** This shifts hardware lifecycle management into gameplay code. When a player's
controller disconnects due to a low battery and reconnects with an incremented hardware handle,
gameplay scripts lose track of the player's controller. Supporting hotplugging would force every
gameplay system to implement custom reconnection listeners and identity reconciliation logic.

### Option B: Querying OS Key State on Regaining Focus (`GetKeyboardState` / `GetAsyncKeyState`)

When the window receives `WindowAction::FocusGained`, query the operating system keyboard API
synchronously to update input states.

**Why rejected:** Win32 `GetAsyncKeyState` and `GetKeyboardState` query asynchronous hardware
state directly from the OS, bypassing the thread-safe ring buffer architecture established in
ADR-0013 and ADR-0020. This introduces platform-specific system calls into cross-platform
generic code, creates race conditions with the OS event pump thread, and fails to resolve mouse
buttons, touch contacts, or gamepad button releases that occurred while unfocused.

### Option C: Dynamic Vector of Gamepads (`std::vector<Gamepad>`)

Store connected gamepads in a dynamically resizing array, adding elements on connection and
removing them on disconnection.

**Why rejected:** Dynamic vectors require heap allocations on peripheral hotplug events,
violating the zero-allocation constraints of the HAL layer (ADR-0020). Vector reallocations
invalidate raw pointers and references held by gameplay entities across frames. Defective USB
hubs or erratic drivers reporting high-frequency connect and disconnect cycles can cause memory
churn and unpredictable frame stalls.

## Consequences

### Positive

- **Deterministic local multiplayer mapping.** Player slots 1 through 8 maintain stable indices
  regardless of peripheral hotplugging, cable snags, or battery disconnects.
- **Elimination of stuck-key bugs.** Window focus changes, minimization, and application
  suspension synthesize release transitions, preventing runaway character movement.
- **Zero runtime heap allocations.** Fixed inline storage for eight controllers eliminates
  allocator pressure and memory fragmentation in input paths.
- **Uniform cross-device sanitization.** Focus loss sanitization cascades through keyboards,
  mice, gamepads, and spatial devices through a single interface method (`releaseAllInputs`).
- **Ergonomic single-player querying.** `GamepadSlot::Any` allows single-player titles to
  consume input from any active controller without manual slot management.

### Negative

- **Fixed eight-controller ceiling.** Games requiring more than eight simultaneous local
  gamepads cannot allocate additional slots without modifying engine compile-time constants.
- **Synthetic release side-effects.** Tabbing away from the application while deliberately
  holding a button cancels the action immediately rather than resuming upon refocusing.
