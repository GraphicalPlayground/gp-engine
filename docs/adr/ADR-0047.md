# ADR-0047: Sharded Global Interned String Pool (`gp::Name`), Split Numeric Instance Suffixes, and `constexpr` Hash Literals

> Establishes `gp::container::Name` (`gp::Name`) as an 8-byte, trivially copyable, $O(1)$-comparable
> interned identifier combining a 32-bit `NameEntryId` handle into a 64-shard, cache-line-isolated
> global `NamePool` with an Unreal-inspired 32-bit split numeric instance suffix (`m_number`),
> paired with `constexpr` 64-bit FNV-1a `gp::NameHash` (`_nh`) compile-time string literals.

![Proposed][badge-proposed]

## Context

In [ADR-0046](./ADR-0046.md), `gp-engine` established the first three pillars of its string
architecture: non-owning views (`gp::StringView` — [ADR-0040](./ADR-0040.md)), bounded stack buffers
(`gp::FixedString<N>` — [ADR-0043](./ADR-0043.md)), and dynamic 24-byte SSO strings (`gp::String`).
However, using `gp::String` or `gp::StringView` as an **identifier key** in hot runtime loops—such
as skeletal bone/socket lookup (`"pelvis"`, `"hand_r"`), shader parameter binding
(`"RoughnessScale"`), input action routing (`"Jump"`), entity/component tags, and reflection
property tables—introduces four severe AAA performance hazards:

### 1. $O(N)$ Character Comparison and Cache-Line Scatter

Comparing two `gp::StringView` or `gp::String` instances requires dereferencing their character
pointers and scanning up to $N$ bytes (`memcmp` or case-folded byte loops). When an animation
pose evaluation or material parameter binder performs thousands of identifier lookups per frame,
chasing string pointers across disparate heap or read-only data pages pollutes the L1 data cache and
stalls execution pipelines. An engine-grade identifier must fit inside a single 64-bit CPU register
(`8 bytes`) and reduce equality (`==`, `!=`) and map/sort ordering (`<=>`) to a **single-cycle 64-bit
integer comparison**.

### 2. Global Lock Contention and Pointer Invalidation in Naïve Intern Pools

A naïve global string intern table (`Mutex` + `HashMap<String, uint32>`) serializes all worker
threads in a multi-threaded job system whenever assets stream in or gameplay systems resolve names
concurrently. Furthermore, if the intern pool stores characters inside a contiguous reallocating
array, growing the pool invalidates every previously returned `StringView` or `const char*` pointer,
causing catastrophic dangling-pointer races across worker threads reading existing names.

### 3. Numeric Instance Suffix Pool Pollution (`"Enemy_0"` .. `"Enemy_9999"`)

During gameplay, spawning thousands of actor or particle instances frequently generates numbered
identifiers (`"Goblin_0"`, `"Goblin_1"`, ..., `"Goblin_5000"`). If every numbered variant is
interned as a distinct string inside the permanent global string pool, the append-only pool leaks
megabytes of redundant character data over a long play session.

### 4. Unhashed Runtime Lookups vs. `switch` / Compile-Time Dispatch

In C++, `gp::Name` interning requires a runtime lookup into the global `NamePool` (because
`NameEntryId` slab offsets depend on registration order). However, low-level packet dispatchers,
shader permutation switches, and asset chunk loaders frequently need `constexpr` `switch (hash)`
dispatch on string literals at compile time with zero runtime table lookups.

## Decision

We introduce the **`gp::Name` Interned Identifier Subsystem** in `gp::core`
(`source/runtime/core/public/containers/strings/`), synthesizing **Unreal Engine 5's sharded
`FNamePool` + split numeric suffix** (`Engine/Source/Runtime/Core/Public/UObject/NameTypes.h`,
`UnrealNames.cpp`) with **Decima / Ubisoft Anvil's `constexpr` 64-bit FNV-1a `NameHash` literal
idiom**.

### 1. Exact 8-Byte Register Footprint (`sizeof(gp::Name) == 8`)

`gp::container::Name` (`gp::Name`) is an 8-byte, trivially copyable value type
(`IsRelocatable<gp::Name> == true`) consisting of two 32-bit fields:

```cpp
class Name
{
private:
    NameEntryId m_comparisonId{ kNameNoneId }; // 4 bytes: packed (shardIndex, slabIndex, byteOffset)
    gp::Int32   m_number{ kNameNoNumber };     // 4 bytes: 0 = no suffix, > 0 = (suffixValue + 1)
};
static_assert(sizeof(Name) == 8u, "gp::Name must be exactly 8 bytes.");
```

- **`m_comparisonId == 0` (`kNameNoneId`)** represents `Name()` (`"None"` / empty identifier) with
  **zero pool lookups** on default construction.
- **$O(1)$ Equality and Fast Ordering:** `lhs == rhs` compares
  `m_comparisonId == rhs.m_comparisonId && m_number == rhs.m_number` (which the compiler lowers to
  a single 64-bit register comparison). `operator<=>` orders by `(m_comparisonId, m_number)` in
  $O(1)$ time for fast binary search and sorted maps, while `compareLexicographical(other)` provides
  alphabetical string ordering when needed for UI display.

### 2. Unreal-Style Split Numeric Suffix (`Base_N`)

When constructing a `gp::Name` from a string view (e.g., `"Enemy_42"`):

1. The parser scans the trailing characters in $O(\text{digits})$ time.
2. If the string ends with `'_'` followed by a canonical non-negative 32-bit decimal integer with
   **no leading zeros** (i.e., `"_0"` or `"_[1-9][0-9]*"` fitting in `gp::Int32`, with at least one
   character preceding `'_'`), the string is split into:
   - **Base string:** `"Enemy"` (interned once in `NamePool`)
   - **Internal number:** `m_number = 42 + 1 = 43` (`kNameNoNumber = 0` means no suffix; `1` means
     `_0`; `N + 1` means `_N`).
3. Strings with leading zeros after the underscore (such as `"Agent_007"` or `"Shader_01"`) are
   **not** split, preserving their exact formatting as literal base strings so round-tripping via
   `toString()` is 100% lossless.
4. Callers may also construct numbered names explicitly in $O(1)$ from an existing `Name` via
   `Name(baseName, instanceNumber)` or `withNumber(instanceNumber)` without re-parsing strings.

### 3. 64-Shard Cache-Line-Isolated `NamePool` with Permanent 16 KiB Slabs

`gp::container::NamePool` eliminates global lock contention and pointer invalidation:

- **64 Independent Shards (`kShardCount = 64`):** The case-insensitive 64-bit FNV-1a hash of the
  base string selects `shardIdx = (hash >> 58u) & 63u`. Each shard is aligned to a 64-byte hardware
  cache line (`alignas(64)`) to prevent MESI false sharing ([ADR-0025](./ADR-0025.md)) and is
  protected by its own lightweight TTAS atomic spinlock (`gp::thread::AtomicFlag` with
  `gp::platform::Thread::spinWait()`).
- **Permanent 16 KiB Bump Slabs:** Each shard allocates `16 KiB` slab pages from `gp::memory::DefaultAllocator`
  and bump-allocates `NameEntryHeader` + null-terminated UTF-8 characters inside the active slab.
  Slabs are **never moved or reallocated** when the shard's open-addressed hash index grows.
- **Lock-Free $O(1)$ `baseView()` Resolution:** Because `NameEntryId` encodes
  `(validBit: 1 bit, shardIdx: 6 bits, slabIdx: 14 bits, alignedOffset: 11 bits)`, resolving
  `name.baseView()` or `name.baseCString()` indexes directly into the shard's atomic slab pointer
  array without acquiring the shard's hash-table probe lock!
- **Case-Insensitive Canonicalization:** Following Unreal Engine's default `FName` semantics,
  `NamePool` hashes and compares base strings using ASCII case-insensitive folding
  (`CharTraits<char>::hashIgnoreCase` / `equalsIgnoreCase`), while preserving the casing of the
  first-registered string in the slab for human-readable debugging and UI display.
- **Non-Polluting `NameFindMode::Find`:** Passing `NameFindMode::Find` queries the shard's probe
  table and returns `Name()` (`isNone() == true`) if the base string has not yet been registered,
  preventing untrusted network or console input from polluting the permanent `NamePool`.

### 4. Compile-Time `gp::NameHash` and `_nh` User-Defined Literal

For compile-time `switch` statements and zero-registration hash checks, `NameTypes.hpp` provides
`gp::container::NameHash` (`gp::NameHash`) and the `gp::literals::operator""_nh` literal:

```cpp
using namespace gp::literals;
switch ( gp::NameHash(shaderStageStr) )
{
    case "vertex"_nh:   /* ... */ break;
    case "fragment"_nh: /* ... */ break;
}
```

`NameHash` is `constexpr`-constructible from any `StringView` or `gp::Name` (computing the exact
same 64-bit case-insensitive FNV-1a hash stored in `NameEntryHeader::caseInsensitiveHash`).

## Alternatives Considered

### 1. Pure Compile-Time Hash Only (No String Storage in Shipping Builds)

- **Pros:** Zero pool memory overhead; fully `constexpr`.
- **Cons:** Cannot recover the string via `toString()` for serialization, console commands, shader
  reflection binding, or crash logs; vulnerable to 32-bit hash collisions and cannot split `_N`
  instance suffixes without re-hashing every spawned actor.
- **Verdict:** Rejected as the sole representation; retained as `gp::NameHash` (`_nh`) alongside
  `gp::Name`.

### 2. Single Global Mutex + `std::unordered_map<std::string, uint32_t>`

- **Pros:** Trivial to implement.
- **Cons:** Violates the Zero STL Allocations mandate; causes severe multi-threaded lock contention
  during parallel asset loading; incurs two heap allocations per interned name (node + string).
- **Verdict:** Rejected.

## Consequences

### Positive

- **$O(1)$ Single-Register Comparisons:** Comparing two `gp::Name` instances (`8 bytes`) compiles to
  a single 64-bit `cmp` instruction, regardless of identifier length.
- **Zero Pool Pollution for Numbered Instances:** `"Particle_0"` through `"Particle_99999"` share a
  single 8-byte `"Particle"` entry in `NamePool`.
- **Permanent Pointer Stability:** `name.baseView()` and `name.cString()` remain valid for the
  entire process lifetime without ref-counting or locks.
- **High Multi-Threaded Throughput:** 64 cache-line-aligned shards reduce lock contention by up to
  $64\times$ across job-system worker threads.

### Negative

- **Append-Only Memory Lifetime:** Interned base strings inside `NamePool` live for the duration of
  the process and are only freed on `NamePool` destruction at process exit. Dynamic transient text
  (such as chat messages or per-frame formatted UI strings) must use `gp::String` or
  `gp::ScratchString` ([ADR-0046](./ADR-0046.md)) rather than `gp::Name`.
