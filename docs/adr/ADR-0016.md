# ADR-0016: Explicit Separation of Physical ScanCodes and Logical KeyCodes

> Separates `ScanCode` (the physical hardware location of the key on the board, used for gameplay
> controls like WASD) from `KeyCode` (the localized OS character mapping, used for UI text typing).

![Proposed][badge-proposed]

## Context

Input architecture in interactive 3D game engines supports two distinct models of human-computer
interaction through a single peripheral: spatial motor control (driving avatars through 3D space)
and symbolic linguistic entry (typing text and issuing mnemonic menu commands).

When an engine conflates this distinction into a single key identifier, as in early GLFW, Win32
raw virtual keys (`VK_*`), or DirectInput, international keyboards break.

### 1. Hardware Matrix Scanning and the USB HID Standard

At the electrical level, a physical keyboard has no knowledge of human language, alphabets, or
typographical symbols. Beneath the keycaps lies a printed circuit grid made of intersecting row and
column strobe lines:

```text
       Column 0        Column 1        Column 2        Column 3
          │               │               │               │
Row 0 ────┼──────[ Esc ]──┼──────[ F1 ]───┼──────[ F2 ]───┼── ...
          │               │               │               │
Row 1 ────┼──────[  `  ]──┼──────[ 1  ]───┼──────[ 2  ]───┼── ...
          │               │               │               │
Row 2 ────┼──────[ Tab ]──┼──────[ Q  ]───┼──────[ W  ]───┼── ...  <-- Row 2, Col 2 switch
          │               │               │               │
Row 3 ────┼──────[Caps ]──┼──────[ A  ]───┼──────[ S  ]───┼── ...
```

The keyboard's embedded micro-controller continuously scans this grid by strobing output pins and
sampling input pins. When a mechanical switch closes, the micro-controller identifies the electrical
coordinates `(row, column)` and transmits an 8-bit or 16-bit packet defined by the **USB
Implementers Forum (USB-IF) HID Usage Tables (Page 0x07: Keyboard/Keypad)**.

USB HID codes identify hardware switch positions:
- HID Usage `0x1A` designates the switch at Row 2, Column 2. In the USB specification, it is named
  `"Keyboard w and W"` as a historical mnemonic.
- HID Usage `0x04` designates Row 3, Column 1 (historically named `"Keyboard a and A"`).
- HID Usage `0x14` designates Row 2, Column 1 (historically named `"Keyboard q and Q"`).
- HID Usage `0x1D` designates Row 4, Column 2 (historically named `"Keyboard z and Z"`).

### 2. The International Layout Problem

While the physical matrix layout is nearly identical across keyboards globally (conforming to ANSI
104-key or ISO 105-key physical dimensions), the legends printed on the plastic keycaps and the OS
driver translation tables differ across regions:

- **US / UK English (ANSI / ISO QWERTY):** The alphanumeric rows begin with `Q-W-E-R-T-Y`.
- **French / Belgian (ISO AZERTY):** The letters 'A' and 'Q' are swapped; the letters 'Z' and 'W'
  are swapped. The number row defaults to punctuation/accents, requiring `Shift` to type numbers.
- **German / Central European (ISO QWERTZ):** The letters 'Y' and 'Z' are swapped to accommodate
  the high frequency of 'Z' in German orthography.
- **Dvorak Simplified / Colemak:** Ergonomic layouts that shuffle almost all letters across the
  board to reduce finger travel distance and balance hand usage.
- **Cyrillic / Greek / Japanese Kana / Korean Hangul:** The Latin alphabet is replaced or
  supplemented by a secondary script, often mediated by OS Input Method Editors (IMEs).

```text
Standard ANSI US Layout (QWERTY):
┌─────┬─────┬─────┬─────┐
│  Q  │  W  │  E  │  R  │   Physical Inverted-T Cluster:
└─────┼─────┼─────┼─────┤      [ W ]       -> Forward
      │  A  │  S  │  D  │   [ A ][ S ][ D ] -> Left, Back, Right
      └─────┴─────┴─────┘

French ISO Layout (AZERTY):
┌─────┬─────┬─────┬─────┐
│  A  │  Z  │  E  │  R  │   Same Physical Inverted-T Cluster:
└─────┼─────┼─────┼─────┤      [ Z ]       -> Cap is 'Z', position is Forward
      │  Q  │  S  │  D  │   [ Q ][ S ][ D ] -> Caps are 'Q','S','D' (Left, Back, Right)
      └─────┴─────┴─────┘
```

### 3. Two Failure Modes of Conflation

When an engine provides only a single `Key` identifier, it picks one meaning and breaks the other:

#### Failure Mode 1: Conflating Physical Movement with Character Symbols ("The WASD Disaster")
In first-person, third-person, and vehicular games, navigation uses the physical inverted-T cluster:
- The forward motion key is the switch at Row 2, Column 2 (the middle key above the home row).
- The lateral and backward motion keys are the three switches directly beneath it (Row 3, Columns
  1, 2, and 3).

If a game engine queries logical characters (`if (input.isKeyDown('W'))`), an AZERTY player hits
two immediate problems:
- Pressing the physical key where their middle finger rests (Row 2, Column 2) emits character `'Z'`.
  The engine ignores it, so the avatar stands still.
- To move forward, the player must press the key labeled `'W'`, which sits on the bottom row next to
  the spacebar (Row 4, Column 2).
- The player must use an awkward hand position or manually remap every movement binding to `Z-Q-S-D`
  before the game is playable.

#### Failure Mode 2: Conflating Character Symbols with Physical Positions ("The UI Typing Disaster")
For user interface text input (typing a player's name, multiplayer chat, in-game developer console)
or mnemonic hotkeys (`Ctrl+S` for Save, `Ctrl+Z` for Undo, `Ctrl+O` for Open):
- The user looks at their keycaps or relies on typing muscle memory.
- When a French player wants to save, they press the keycap marked `'S'`.
- When typing text in chat, an AZERTY player pressing Row 2 Column 1 expects the character `'A'`.
- If the engine uses physical scancodes for UI typing, pressing the top-left key produces `'Q'`,
  emitting wrong characters in international text fields.
- The in-game developer console toggle also typically defaults to the grave accent / tilde key
  (`` ` `` / `~`). On US keyboards, this is Scancode `Grave` (Row 1, Column 0). On French
  keyboards, that physical switch is `²` (superscript two), while on German keyboards it is `^`
  (circumflex dead key).

### 4. Operating System Translation Mechanics

Modern operating systems implement an internal two-stage pipeline:
1. **Hardware Interrupt to Scancode:** The kernel driver receives the physical USB HID usage code
   (or legacy PS/2 scan set 1/2 translated by the motherboard 8042 controller).
2. **Scancode to Virtual Key / Unicode:** The OS passes the scancode through an active
   user-selected keyboard layout table:
   - On **Windows**: Handled via `MapVirtualKeyExW` and `ToUnicodeEx`.
   - On **Linux (X11 / Wayland)**: Handled via `libxkbcommon` state machines translating
     `xkb_keycode_t` into `xkb_keysym_t`.
   - On **macOS**: Handled via `UCKeyTranslate` and `NSEvent.charactersIgnoringModifiers`.

To support both gameplay and text entry, `gp-engine` exposes both layers with zero runtime
allocation and compile-time type safety.

## Decision

We enforce a type-safe separation within `source/runtime/hal/base/` between physical hardware
scancodes and logical localized keycodes. Neither concept implicitly converts to the other.

```text
source/runtime/hal/
  base/
    public/
      input/
        InputEnums.hpp      <-- enum class Scancode (UInt16) and Keycode (UInt32)
        InputTypes.hpp      <-- Capacity constants (kMaxScancodes=512, kMaxKeycodeSlots=768)
        IKeyboard.hpp       <-- Query interfaces for Scancodes and Keycodes
      event/
        input/
          KeyboardEvent.hpp <-- Dual-payload POD carrying Scancode and Keycode (16 bytes)
  generic/
    public/
      input/
        GenericKeyboard.hpp <-- O(1) dual state arrays, sub-frame edge latching (ADR-0034)
```

### 1. Type-Safe Enum Definitions (`InputEnums.hpp`)

We introduce two distinct strongly typed enums with explicit underlying integer representations:

```cpp
namespace gp::hal::input
{

/// @brief Physical key location on the keyboard (layout-independent).
/// @details Values follow the USB HID Usage Tables (Keyboard/Keypad Page 0x07).
///          These correspond 1:1 with the physical switch regardless of OS keyboard layout.
enum class Scancode : gp::UInt16
{
    Unknown = 0,

    /// Letters (HID 0x04-0x1D) - Hardware positions corresponding to standard US QWERTY letters
    A = 4,   // Row 3, Col 1 on ANSI (Q on AZERTY)
    B = 5,
    C = 6,
    D = 7,   // Row 3, Col 3 on ANSI (D on AZERTY)
    E = 8,
    F = 9,
    G = 10,
    H = 11,
    I = 12,
    J = 13,
    K = 14,
    L = 15,
    M = 16,
    N = 17,
    O = 18,
    P = 19,
    Q = 20,  // Row 2, Col 1 on ANSI (A on AZERTY)
    R = 21,
    S = 22,  // Row 3, Col 2 on ANSI (S on AZERTY)
    T = 23,
    U = 24,
    V = 25,
    W = 26,  // Row 2, Col 2 on ANSI (Z on AZERTY)
    X = 27,
    Y = 28,  // Row 2, Col 6 on ANSI (Z on QWERTZ)
    Z = 29,  // Row 4, Col 2 on ANSI (W on AZERTY)

    /// Number row (HID 0x1E-0x27)
    Num1 = 30,
    Num2 = 31,
    Num3 = 32,
    Num4 = 33,
    Num5 = 34,
    Num6 = 35,
    Num7 = 36,
    Num8 = 37,
    Num9 = 38,
    Num0 = 39,

    /// Control & Function Keys
    Return = 40,
    Escape = 41,
    Backspace = 42,
    Tab = 43,
    Space = 44,
    LeftCtrl = 224,
    LeftShift = 225,
    LeftAlt = 226,
    LeftGui = 227,

    /// Sentinel capacity value
    Count = 512
};

} // namespace gp::hal::input
```

For logical keys, we adopt a hybrid encoding modeled after SDL3:
- Printable ASCII characters occupy values `0` through `127` (`'a'` to `'z'`, `'0'` to `'9'`, space,
  punctuation), matching their Unicode/ASCII code points directly.
- Non-printable keys (function keys, navigation arrows, locks, numpad operations) derive from their
  scancode by setting bit 30 (`kScancodeMask = 0x40000000u`):

```cpp
namespace gp::hal::input
{

/// @brief Bitmask constant used to mark a keycode as scancode-derived.
inline constexpr gp::UInt32 kScancodeMask = 0x40000000u;

/// @brief Converts a Scancode into its corresponding Keycode value.
[[nodiscard]] inline constexpr gp::UInt32 scancodeToKeycode(Scancode scanCode)
{
    return static_cast<gp::UInt32>(scanCode) | kScancodeMask;
}

/// @brief Layout-dependent virtual key.
/// @details The low 16 bits encode the Scancode when bit 30 is set. Non-scancode
///          keycodes (printable ASCII) live in [0, 127] and map to ASCII code points.
enum class Keycode : gp::UInt32
{
    Unknown = 0,

    /// Printable ASCII range (layout-dependent)
    Return = '\r',
    Escape = 0x1B,
    Backspace = '\b',
    Tab = '\t',
    Space = ' ',
    A = 'a',
    B = 'b',
    C = 'c',
    D = 'd',
    S = 's',
    W = 'w',
    Z = 'z',

    /// Scancode-derived virtual keys
    CapsLock = scancodeToKeycode(Scancode::CapsLock),
    F1 = scancodeToKeycode(Scancode::F1),
    F12 = scancodeToKeycode(Scancode::F12),
    Right = scancodeToKeycode(Scancode::Right),
    Left = scancodeToKeycode(Scancode::Left),
    Down = scancodeToKeycode(Scancode::Down),
    Up = scancodeToKeycode(Scancode::Up),
};

} // namespace gp::hal::input
```

### 2. Physical vs. Logical Separation Matrix

The engine defines clear rules for when to use each primitive:

| Domain | Primitive | Example APIs | Behavior on AZERTY |
| :--- | :--- | :--- | :--- |
| Spatial Movement | `Scancode` | `isScancodeDown(Scancode::W)` | Top-middle ('Z') moves forward. |
| Action Triggers | `Scancode` | `wasScancodeJustPressed(...)` | Physical spacebar, any layout. |
| Hotbar Slots | `Scancode` | `isScancodeDown(Scancode::Num1)` | Top-row 1 without `Shift`. |
| UI Typing | `Keycode` | `ev.keycode == Keycode::A` | Cap labeled 'A' enters 'A'. |
| Mnemonic Keys | `Keycode` | `isKeyDown(Keycode::S)` | `Ctrl` + cap labeled 'S' saves. |
| Undo / Redo | `Keycode` | `isKeyDown(Keycode::Z)` | `Ctrl` + cap 'Z' (QWERTZ-safe). |

### 3. Dual-Payload Event Transport (`KeyboardEvent.hpp`)

Rather than requiring the gameplay thread to make synchronous round-trips to the OS windowing
backend to translate keys, every `KeyboardEvent` pushed through the cross-thread
`SPSCByteRingBuffer` ([ADR-0013](./ADR-0013.md), [ADR-0019](./ADR-0019.md)) carries both the
physical `Scancode` and the localized `Keycode` in a single 16-byte POD:

```cpp
namespace gp::hal::event
{

/// @brief Fixed-size POD payload for EventCategory::Keyboard (16 bytes, zero implicit padding).
/// @details Enforces ADR-0016 by transporting the physical hardware matrix location (scancode)
///          and the localized OS layout mapping (keycode) alongside active modifier flags.
struct KeyboardEvent
{
    gp::UInt32 windowId = 0u;                                  // Window holding focus (4 B)
    gp::hal::input::Keycode keycode =
        gp::hal::input::Keycode::Unknown;                      // Localized virtual key (4 B)
    gp::hal::input::Scancode scancode =
        gp::hal::input::Scancode::Unknown;                     // Physical USB HID scan code (2 B)
    gp::hal::input::KeyModifier modifiers =
        gp::hal::input::KeyModifier::None;                     // Active modifier bitmask (2 B)
    gp::hal::input::KeyState state =
        gp::hal::input::KeyState::Released;                    // Pressed or Released (1 B)
    gp::UInt8 isRepeat = 0u;                                   // Non-zero if OS auto-repeat (1 B)
    gp::UInt8 reserved[2] = { 0u, 0u };                        // Alignment padding (2 B)
};

static_assert(sizeof(KeyboardEvent) == 16, "KeyboardEvent size mismatch!");

} // namespace gp::hal::event
```

### 4. Keyboard State Architecture (`GenericKeyboard.hpp`)

In `gp::hal::input::generic::Keyboard`, both domains are tracked via contiguous flat arrays that
support $O(1)$ lookups and sub-frame edge latching ([ADR-0034](./ADR-0034.md)):

```cpp
class Keyboard : public IKeyboard
{
    // Flat O(1) state tables
    ButtonStateFlags m_scancodes[kMaxScancodes]{};   // 512 entries (512 bytes)
    ButtonStateFlags m_keycodes[kMaxKeycodeSlots]{}; // 256 ASCII + 512 Scancode-derived = 768 B
    OverflowKeyEntry m_overflowKeycodes[32]{};       // Fallback for exotic Unicode virtual keys
    KeyModifier      m_modifiers{ KeyModifier::None };
    ...
};
```

1. **Scancode Queries ($O(1)$ Array Index):**
   `getScancodeState(Scancode s)` directly indexes `m_scancodes[static_cast<UInt16>(s)]`.
2. **Keycode Queries ($O(1)$ Hashless Slot Mapping):**
   `mapKeycodeToSlot(Keycode k)` maps printable ASCII `[0..255]` directly to indices `[0..255]`,
   and scancode-derived keys (`raw & kScancodeMask`) to indices `[256..767]`, with no hash tables,
   heap allocations, or branching in the fast path.
3. **Sub-Frame Edge Latching:**
   Both arrays keep `ButtonStateFlags::PressedThisFrame`, `ReleasedThisFrame`, and `Held`
   independently so rapid sub-frame inputs are not lost across either abstraction.

## Alternatives Considered

### Option A: Unified Single Key Enumeration (Legacy GLFW / Win32 `VK_*` model)

Expose a single unified `enum class Key` representing virtual keys (e.g., `Key::W`, `Key::A`,
`Key::Space`), matching the legacy Win32 `WM_KEYDOWN` or early GLFW 2.x design.

```cpp
// Legacy anti-pattern:
if (input.isKeyDown(Key::W)) { player.moveForward(); }
```

**Why rejected:**
- This causes the "WASD disaster" on international keyboards. On an AZERTY layout, `Key::W` sits
  at the bottom-left of the keyboard next to the spacebar.
- Forcing gameplay code to handle layouts requires every game script to implement custom remapping
  tables or query platform-specific OS APIs (`GetKeyboardLayout`, `ToUnicodeEx`).
- It blurs the distinction between physical switches and linguistic symbols, causing bugs and
  player frustration.

### Option B: Pure String-Based Key Identifiers (`"KeyW"`, `"KeyA"`, `"Digit1"`)

Adopt the W3C DOM UI Events model directly, passing strings such as `"KeyW"` (for physical
location) and `"w"` (for logical character) throughout the engine.

```cpp
// String-based anti-pattern:
if (input.isCodeDown("KeyW")) { player.moveForward(); }
```

**Why rejected:**
- **Performance & Cache Penalties:** Checking input states during high-frequency gameplay ticks
  (60-240 Hz) would require string hashing, string interning, or dynamic pointer comparisons.
- **Dynamic Allocations:** String manipulation risks invoking dynamic heap allocations (`malloc`),
  violating the engine's zero-STL, zero-allocation runtime rules.
- **Cache-Line Overhead:** Flat array indexing (`m_scancodes[idx]`) fits key states within eight
  64-byte cache lines. String maps scatter memory across the heap, causing L1/L2 data cache misses
  on every input check.

### Option C: Scancode-Only Input (No KeyCode in Engine)

Expose only physical `Scancode` values in the engine and eliminate `Keycode`, requiring all
gameplay and UI subsystems to work with hardware switch positions.

**Why rejected:**
- **Breaks UI and Text Input:** Text fields, chat boxes, and the in-game developer console cannot
  function with physical scancodes alone. An AZERTY user pressing the physical switch at Row 2
  Column 1 would type `'Q'` instead of `'A'`.
- **Breaks Mnemonic Shortcuts:** Shortcuts like `Ctrl+S` (Save) or `Ctrl+Z` (Undo) depend on the
  printed keycap letter. On German QWERTZ keyboards, `Z` and `Y` are swapped; a scancode-only
  engine would force German users to press `Ctrl+Y` to undo.
- **Leaks Platform Plumbing:** Forcing the game or editor layer to resolve text characters by
  calling OS APIs directly violates the encapsulation of the Hardware Abstraction Layer
  ([ADR-0001](./ADR-0001.md), [ADR-0010](./ADR-0010.md)).

## Consequences

### Positive

- **Out-of-the-box international gameplay ergonomics.** Gameplay systems binding movement controls
  to `Scancode::W`, `Scancode::A`, `Scancode::S`, and `Scancode::D` work on QWERTY, AZERTY, QWERTZ,
  Dvorak, and Colemak keyboards without requiring the player to rebind keys.
- **Accurate UI and text editing.** Text entry widgets, in-game developer consoles, and mnemonic
  shortcuts (`Ctrl+S`, `Ctrl+Z`) use `Keycode`, matching the user's active OS keyboard layout.
- **Deterministic, zero-allocation O(1) input queries.** Key states live in fixed-size contiguous
  arrays indexed via arithmetic or bitmasking, keeping instruction budgets predictable with zero
  heap allocations.
- **Single-packet event delivery without game-thread OS translation.** The HAL event translator
  resolves both `Scancode` and `Keycode` once at event ingestion time, populating the 16-byte
  `KeyboardEvent` POD so consumer systems incur no layout conversion latency.
- **Decoupling of platform-specific keyboard drivers.** High-level gameplay and editor modules
  depend on engine-native enums, insulating the codebase from OS headers (`<windows.h>`,
  `<X11/Xlib.h>`).

### Negative

- **Dual API cognitive overhead for gameplay engineers.** Programmers must learn the difference
  between `isScancodeDown()` and `isKeyDown()`, requiring clear onboarding documentation.
- **Memory footprint of parallel keyboard state lookup tables.** Maintaining separate flat arrays
  for scancodes (512 bytes) and keycodes (768 bytes) uses roughly 1.3 KB per `Keyboard` instance,
  though this fits in L1 cache and is small compared to heap-based maps.
- **Handling edge-case layout changes at runtime.** When a user toggles their OS keyboard layout
  (e.g. `Alt+Shift` on Windows) while holding down a key, the engine must sanitize active `Keycode`
  hold states to prevent dangling stuck keys, as addressed in [ADR-0036](./ADR-0036.md).
