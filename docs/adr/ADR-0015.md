# ADR-0015: Strict Semantic Differentiation Between Point2D (Position) and Extent2D (Size)

> Establishes separate, type-safe POD structs for coordinate positions (`Point2D`) versus
> dimensional sizes (`Extent2D`) in window management, preventing logical bugs caused by passing a
> width/height into an x/y parameter.

![Proposed][badge-proposed]

## Context

In 2D graphics, window management, and hardware display abstraction, software systems repeatedly
encounter a ubiquitous and catastrophic class of defects: **semantic coordinate conflation**.

### The Anatomy of Semantic Conflation

At the hardware, operating system, and mathematical levels, two fundamentally distinct geometric
concepts describe screen space:

1. **Coordinate Position ($P \in \mathbb{A}^2$):** A discrete point designating a specific location
   within an affine coordinate frame (such as the virtual desktop coordinate system or a window's
   local client area). A position has no intrinsic area, volume, or physical extent; it is simply an
   address in space relative to an arbitrary reference origin $(0, 0)$.
2. **Physical Dimension or Size ($E \in \mathbb{N}_0^2$):** A non-negative physical span or measure
   designating extent along the Cartesian axes (such as width and height in pixels). An extent
   possesses physical magnitude and defines surface area ($w \times h$), but has no intrinsic
   spatial location until paired with a reference origin.

When an engine conflates these two concepts into a single generic type, such as `Vector2`,
`Vector2i`, a generic `Point` struct, or `std::pair<int, int>`, several severe engineering failure
modes emerge:

#### 1. Transposed Parameter Bugs (Silent Call-Site Inversion)

Consider classic windowing API signatures:

```cpp
// Flawed legacy approach: generic types or raw integers
void setWindowBounds(Int32 x, Int32 y, Int32 width, Int32 height);
void setWindowBounds(Vector2i position, Vector2i size);
```

When a programmer mistakenly writes:

```cpp
// BUG: Position and size arguments silently transposed!
setWindowBounds(size, position);
setWindowBounds(width, height, x, y);
```

Because both parameters share the identical underlying type (`Vector2i` or raw integer primitives),
the C++ compiler cannot detect the error. The code compiles cleanly with zero diagnostic warnings. At
runtime, the window is relocated to an unintended coordinate (often off-screen or onto an incorrect
monitor) while having its dimensions resized to match its former screen coordinates.

#### 2. Affine Geometry Semantic Violations

Affine geometry rigorously distinguishes between points and displacement vectors:

```text
       Point P0 (Position)                 Point P1 (Position)
            o ---------------------------------> o
             \               Vector Δ           /
              \           (Displacement)       /
               \                              /
                \                            /
                 \                          /
                  v                        v
              ===================================
               Reference Frame Origin (0, 0)
```

In valid affine mathematics:

- **$\text{Point} - \text{Point} = \text{Displacement Vector}$:** Subtracting one point from another
  yields the directional offset between them.
- **$\text{Point} + \text{Displacement} = \text{Point}$:** Translating a point by a vector yields a
  new point.
- **$\text{Point} + \text{Point} = \text{UNDEFINED}$:** Adding two positions is geometrically
  meaningless. (What does the sum of Paris and London represent?)
- **$\text{Extent} + \text{Extent} = \text{Extent}$:** Combining two extents along an axis yields a
  valid aggregated bounding dimension.
- **$\text{Extent} \times \text{Scalar} = \text{Extent}$:** Scaling a physical dimension (e.g.,
  $2 \times$ High-DPI scaling) scales the physical pixel area.
- **$\text{Point} \times \text{Scalar} = \text{UNDEFINED}$:** Multiplying a position by a scalar
  implicitly assumes an origin $(0, 0)$, yielding arbitrary results if the coordinate frame origin
  is translated.

When a codebase collapses positions and sizes into a general-purpose math vector (`Vector2i`), it
permits nonsensical operations such as `posA + posB` or `sizeA - posB`, leading to subtle spatial
rendering artifacts and broken UI layout engines.

#### 3. Signedness Invariants in Multi-Monitor Topologies

A critical physical invariant separates screen positions from dimensional extents:

- **Window/Display Positions are Signed ($\mathbb{Z}^2$):** In modern multi-monitor desktop
  environments, displays are arranged in an arbitrary 2D grid within the OS virtual desktop space.
  Monitors positioned to the left of or above the primary display (which defines $(0, 0)$) possess
  **negative coordinates**:

```text
  [-1920, 0]                     [0, 0]                     [1920, 0]
  +--------------------------+  +--------------------------+  +--------------------------+
  |  Secondary Display 1     |  |  Primary Display 0       |  |  Secondary Display 2     |
  |  Origin: (-1920, 0)      |  |  Origin: (0, 0)          |  |  Origin: (1920, 0)       |
  |  Extent: 1920 x 1080     |  |  Extent: 1920 x 1080     |  |  Extent: 1920 x 1080     |
  +--------------------------+  +--------------------------+  +--------------------------+
                                         ^
                                         | Virtual Desktop Origin (0, 0)
```

  A window placed on the secondary display can validly reside at position $(-1400, 200)$. Therefore,
  coordinate positions must strictly use signed 32-bit integers (`Int32`).

- **Physical Extents are Non-Negative ($\mathbb{N}_0^2$):** A physical window dimension or display
  resolution cannot be negative. An extent with negative width ($width = -100$) represents a
  physical impossibility and an invalid program state. Storing extents as signed integers allows
  negative dimensions to propagate undetected until they trigger buffer allocation underflows,
  memory corruption, or GPU driver crashes during swapchain initialization.

By enforcing unsigned 32-bit integers (`UInt32`) for dimensions, the type system makes negative
extents unrepresentable, turning boundary corruption into an explicit, compile-time impossible state.

## Decision

We establish two distinct, strongly-typed Plain Old Data (POD) structures in
`source/runtime/hal/base/public/window/WindowTypes.hpp`:

1. `gp::hal::Point2D`: Encapsulates a discrete, signed 2D coordinate position.
2. `gp::hal::Extent2D`: Encapsulates a non-negative, unsigned 2D dimensional size.

```text
source/runtime/hal/
  base/
    public/
      window/
        WindowTypes.hpp    <-- Point2D (Int32) and Extent2D (UInt32) definitions
        WindowDesc.hpp     <-- Point2D position, Extent2D size, minSize, maxSize
        IWindow.hpp        <-- setPosition(Point2D), setSize(Extent2D) contracts
      display/
        DisplayTypes.hpp   <-- DisplayRect: Point2D origin + Extent2D extent
      event/
        system/
          WindowEvent.hpp  <-- WindowEvent union: Point2D position / Extent2D extent
```

### 1. Structural Definitions in `WindowTypes.hpp`

Both structures are declared as trivially copyable, standard layout POD types:

```cpp
namespace gp::hal
{

/// @brief Represents a 2D discrete coordinate point in signed Cartesian screen space.
struct Point2D
{
public:
    Int32 x;
    Int32 y;

public:
    [[nodiscard]] constexpr Point2D() noexcept : x(0), y(0) {}
    [[nodiscard]] constexpr Point2D(const Int32 inX, const Int32 inY) noexcept : x(inX), y(inY) {}
    [[nodiscard]] constexpr explicit Point2D(const Int32* arr) noexcept : x(arr[0]), y(arr[1]) {}
    [[nodiscard]] constexpr explicit Point2D(const Int32 (&arr)[2]) noexcept : x(arr[0]), y(arr[1]) {}

    [[nodiscard]] constexpr Point2D(const Point2D& other) noexcept = default;
    [[nodiscard]] constexpr Point2D(Point2D&& other) noexcept = default;
    constexpr Point2D& operator=(const Point2D& other) noexcept = default;
    constexpr Point2D& operator=(Point2D&& other) noexcept = default;

    [[nodiscard]] constexpr bool operator==(const Point2D& other) const noexcept
    {
        return x == other.x && y == other.y;
    }

    [[nodiscard]] constexpr bool operator!=(const Point2D& other) const noexcept
    {
        return !(*this == other);
    }

    [[nodiscard]] constexpr Point2D operator-() const noexcept { return Point2D(-x, -y); }
    [[nodiscard]] constexpr Point2D operator+(const Point2D& other) const noexcept
    {
        return Point2D(x + other.x, y + other.y);
    }
    [[nodiscard]] constexpr Point2D operator-(const Point2D& other) const noexcept
    {
        return Point2D(x - other.x, y - other.y);
    }
};

/// @brief Represents a 2D physical dimensional extent in non-negative pixel units.
struct Extent2D
{
public:
    UInt32 width;
    UInt32 height;

public:
    [[nodiscard]] constexpr Extent2D() noexcept : width(0), height(0) {}
    [[nodiscard]] constexpr Extent2D(const UInt32 inWidth, const UInt32 inHeight) noexcept
        : width(inWidth), height(inHeight) {}
    [[nodiscard]] constexpr explicit Extent2D(const UInt32* arr) noexcept : width(arr[0]), height(arr[1]) {}
    [[nodiscard]] constexpr explicit Extent2D(const UInt32 (&arr)[2]) noexcept : width(arr[0]), height(arr[1]) {}

    [[nodiscard]] constexpr Extent2D(const Extent2D& other) noexcept = default;
    [[nodiscard]] constexpr Extent2D(Extent2D&& other) noexcept = default;
    constexpr Extent2D& operator=(const Extent2D& other) noexcept = default;
    constexpr Extent2D& operator=(Extent2D&& other) noexcept = default;

    [[nodiscard]] constexpr bool operator==(const Extent2D& other) const noexcept
    {
        return width == other.width && height == other.height;
    }

    [[nodiscard]] constexpr bool operator!=(const Extent2D& other) const noexcept
    {
        return !(*this == other);
    }
};

static_assert(sizeof(Point2D) == 8, "Point2D must be exactly 8 bytes (2 x Int32).");
static_assert(sizeof(Extent2D) == 8, "Extent2D must be exactly 8 bytes (2 x UInt32).");
static_assert(std::is_trivially_copyable_v<Point2D>, "Point2D must be trivially copyable.");
static_assert(std::is_trivially_copyable_v<Extent2D>, "Extent2D must be trivially copyable.");

} // namespace gp::hal
```

### 2. Architectural Comparison Matrix

| Property | `Point2D` | `Extent2D` |
| :--- | :--- | :--- |
| **Domain Semantics** | Spatial coordinate position | Physical dimensional extent / resolution |
| **Coordinate Space** | Virtual Desktop or Client Window $(\mathbb{Z}^2)$ | Pixel or Texel Space $(\mathbb{N}_0^2)$ |
| **Component Types** | `Int32 x`, `Int32 y` | `UInt32 width`, `UInt32 height` |
| **Negative Values** | **Valid:** Multi-monitor offsets (e.g., $x = -1920$) | **Invalid:** Enforced positive-definite by unsigned type |
| **Zero State $(0, 0)$** | Primary display origin | Degenerate / zero-area extent |
| **Affine Meaning** | Point in affine space ($P \in \mathbb{A}^2$) | Dimensional vector span ($E \in \mathbb{R}_{\ge 0}^2$) |
| **Memory Footprint** | 8 bytes (two 32-bit signed ints) | 8 bytes (two 32-bit unsigned ints) |
| **ABI Register Passing** | Single 64-bit register (`rcx`/`rdi`) | Single 64-bit register (`rcx`/`rdi`) |

### 3. Compiler-Enforced API Contracts in `WindowDesc` and `IWindow`

Because `Point2D` and `Extent2D` are distinct concrete types, the C++ compiler strictly forbids
passing an extent where a position is expected, and vice versa:

```cpp
// Window configuration descriptor (WindowDesc.hpp)
struct WindowDesc
{
    StringView title{ "Graphical Playground" };
    Point2D    position{ 100, 100 };       // Signed coordinates
    Extent2D   size{ 1280u, 720u };        // Non-negative pixel dimensions
    Extent2D   minimumSize{ 0u, 0u };      // Non-negative limits
    Extent2D   maximumSize{ 0u, 0u };
    // ...
};

// Window interface contract (IWindow.hpp)
class GP_HAL_BASE_API IWindow
{
public:
    [[nodiscard]] virtual Point2D  getPosition() const noexcept = 0;
    [[nodiscard]] virtual Extent2D getSize() const noexcept = 0;
    [[nodiscard]] virtual Extent2D getFramebufferSize() const noexcept = 0;

    virtual void setPosition(const Point2D& position) noexcept = 0;
    virtual void setPosition(Int32 x, Int32 y) noexcept = 0;

    virtual void setSize(const Extent2D& size) noexcept = 0;
    virtual void setSize(UInt32 width, UInt32 height) noexcept = 0;
};
```

#### Compilation Invariants

```cpp
Extent2D windowSize{ 1920u, 1080u };
Point2D  windowPos{ -1920, 0 };

// COMPILES: Correct type matches function signature
window->setPosition(windowPos);
window->setSize(windowSize);

// COMPILATION ERROR: Static type safety prevents argument inversion!
// error: no matching member function for call to 'setPosition'
// note: candidate function not viable: no known conversion from 'Extent2D' to 'const Point2D&'
window->setPosition(windowSize);

// COMPILATION ERROR: Static type safety prevents assigning position as size!
// error: no matching member function for call to 'setSize'
// note: candidate function not viable: no known conversion from 'Point2D' to 'const Extent2D&'
window->setSize(windowPos);
```

### 4. Composition in `DisplayRect` and `WindowEvent`

The decoupling between `Point2D` and `Extent2D` naturally composes into compound spatial
abstractions:

#### Spatial Bounds Composition (`DisplayRect`)

In `source/runtime/hal/base/public/display/DisplayTypes.hpp`, a rectangle is defined as an origin
`Point2D` combined with a dimensional `Extent2D`:

```cpp
struct DisplayRect
{
    Point2D  origin{ 0, 0 };
    Extent2D extent{ 0u, 0u };

    [[nodiscard]] constexpr DisplayRect() noexcept = default;
    [[nodiscard]] constexpr DisplayRect(const Point2D& inOrigin, const Extent2D& inExtent) noexcept
        : origin(inOrigin), extent(inExtent) {}
};
```

This makes bounding calculations mathematically unambiguous:

$$\text{Right} = \text{origin.x} + \text{static\_cast}<\text{Int32}>(\text{extent.width})$$
$$\text{Bottom} = \text{origin.y} + \text{static\_cast}<\text{Int32}>(\text{extent.height})$$

#### Zero-Padding Union Packing in Event Streaming (`WindowEvent`)

In `source/runtime/hal/base/public/event/system/WindowEvent.hpp` ([ADR-0020](./ADR-0020.md)), window
state transitions cross thread boundaries via a 16-byte POD event payload:

```cpp
struct WindowEvent
{
    UInt32       windowId = 0u;
    WindowAction action = WindowAction::None;
    WindowState  state = WindowState::Normal;
    WindowMode   mode = WindowMode::Windowed;
    UInt8        isHDREnabled = 0u;

    union
    {
        Point2D              position{};   // Signed screen coordinates (WindowAction::Moved)
        Extent2D             extent;       // Unsigned client dimensions (WindowAction::Resized)
        detail::DPIScale     dpi;
        detail::DisplayChange display;
    };
};

static_assert(sizeof(WindowEvent) == 16, "WindowEvent size mismatch!");
```

Because both `Point2D` and `Extent2D` are exactly 8 bytes with 4-byte alignment, they fit seamlessly
into the union without introducing implicit compiler padding bytes, preserving strict cache
locality and deterministic serialization across threads.

## Alternatives Considered

### Option A: Single Generic `Vector2i` / `Pair<int, int>` for Both Position and Size

Use a unified integer vector (e.g., `gp::math::Vector2<Int32>` or `std::pair<int, int>`) across all
windowing and display APIs.

**Why rejected:**

- **Zero Compile-Time Transposition Protection:** Eliminates compiler verification against argument
  swapping. A call to `setWindowBounds(size, pos)` compiles cleanly.
- **Conflates Signed and Unsigned Semantics:** Forces either dimensional sizes to be signed (allowing
  catastrophic negative dimensions such as $width = -500$), or positions to be unsigned (making
  multi-monitor coordinates to the left of the primary display impossible).
- **Affine Geometry Incoherence:** Permits nonsensical operations such as adding two positions
  (`posA + posB`), which violates fundamental spatial geometry.

### Option B: Type Aliases / Typedefs (`using Point2D = Vector2i; using Extent2D = Vector2i;`)

Define semantic names as type aliases wrapping an underlying signed integer vector:

```cpp
using Point2D = Vector2i;
using Extent2D = Vector2i;
```

**Why rejected:**

- **Pure Syntactic Illusion in C++:** In the C++ type system, `using` and `typedef` define type
  synonyms, not distinct strong types. The compiler treats `Point2D` and `Extent2D` as completely
  interchangeable. Passing an `Extent2D` to a function expecting `Point2D` triggers neither an error
  nor a warning.
- **Fails Signedness Guarantees:** Because both aliases must share the same underlying type, sizes
  remain signed, failing to prevent negative width/height bugs.

### Option C: Strong Typedef Wrapper Templates (e.g., `NamedType<Vector2i, struct PointTag>`)

Implement a generic phantom-type template wrapper (similar to `BOOST_STRONG_TYPEDEF` or
`foonathan::NamedType`) to generate distinct types from a shared vector base:

```cpp
template <typename T, typename Tag>
struct NamedType { T value; };
using Point2D = NamedType<Vector2i, struct PointTag>;
using Extent2D = NamedType<Vector2i, struct ExtentTag>;
```

**Why rejected:**

- **Template Bloat and Compilation Cost:** Generates extraneous template instantiations and symbol
  names across compilation units, increasing build times.
- **Obscures C-Style ABI Interoperability:** Wrappers complicate trivial binary mapping to native OS
  and graphics API structures (such as Win32 `POINT`, `SDL_Point`, `VkOffset2D`, and `VkExtent2D`).
- **Defeats Pedagogical Clarity:** Obscures basic engine primitives behind template metaprogramming
  layers, contrary to `gp-engine`'s deconstructive teaching mission. Direct, explicit POD structs
  are self-documenting, immediately readable, and debuggable in native IDE memory inspectors.

## Consequences

### Positive

- **Zero-overhead compile-time error detection.** Inverting position and size arguments at call-sites
  immediately halts compilation with a clear compiler diagnostic, eliminating an entire class of
  silent runtime spatial bugs.
- **Encoding domain invariants into the type system.** Using `Int32` for `Point2D` guarantees support
  for negative multi-monitor desktop offsets, while using `UInt32` for `Extent2D` mathematically
  precludes negative dimensions at the type boundary.
- **Strict affine geometry semantics.** Prevents mathematically invalid operations (such as adding
  two positions together) while preserving meaningful operations (subtracting points to yield
  offsets, scaling extents).
- **Direct binary compatibility with graphics and OS APIs.** Both structs are 8-byte trivially
  copyable PODs that directly match Vulkan (`VkOffset2D`, `VkExtent2D`), Win32 (`POINT`), and SDL3
  (`SDL_Point`), enabling zero-cost bitwise conversions and register-passable ABI efficiency.
- **Deconstructive pedagogical clarity.** Students and engine contributors can inspect
  `WindowTypes.hpp` and immediately understand the physical difference between spatial coordinates in
  virtual screen space versus pixel dimensions of a framebuffer.

### Negative

- **Explicit conversion boilerplate.** Code converting between a point and an extent (such as
  computing a bounding box or converting a cursor displacement into a window dimension) requires
  explicit constructor invocations rather than implicit assignment.
- **Additional struct definitions.** Introduces two separate types in `WindowTypes.hpp` rather than
  reusing a generic vector primitive from the math module.
- **Signed-to-unsigned static cast requirements.** Operations that calculate screen coordinates from
  extents (or vice-versa) require deliberate `static_cast` between `Int32` and `UInt32` to satisfy
  strict compiler sign-conversion warnings.
