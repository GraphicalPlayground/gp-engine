# ADR-0006: Co-Located Documentation, Tests, and Benchmarks per Module

> Rejects satellite test directories in favor of co-locating tests, benchmarks, and documentation
> inside each module so these assets move and refactor atomically with the code they describe.

![Accepted][badge-accepted]

## Context

In most large C++ projects, tests, benchmarks, and documentation sit in satellite directories
separated from the code they describe:

```text
project/
  src/          <-- code
  tests/        <-- tests for all of src/
  docs/         <-- documentation for all of src/
  benchmarks/   <-- benchmarks for all of src/
```

In this layout, documentation and tests tend to drift from the code they describe. When a module is
refactored, its satellite tests must move too; when a module is deleted, its tests must be hunted
down separately. Often they are missed, leaving orphan test files that reference deleted code.

A student opening any module should find everything needed to understand, test, and benchmark that
module in the same place as the code. A module is a self-contained unit of ownership: code, build
description, documentation, change history, tests, and benchmarks.

## Decision

Every module in the GP Engine ships its own documentation, tests, and benchmarks co-located within
the module directory. The canonical module anatomy is:

```text
<module_name>/
  public/           <-- exported headers (PUBLIC include path)
  private/          <-- .cpp sources + internal headers (PRIVATE)
  internal/         <-- restricted-share headers (PRIVATE-but-friend, optional)
  tests/            <-- test sources, opt-in via gpTargetSetTestsEnabled(TRUE)
  benchmarks/       <-- benchmark sources, opt-in via gpTargetSetBenchmarksEnabled(TRUE)
  docs/             <-- longer-form documentation, design notes, module-level ADRs
  README.md         <-- module overview (what, why, dependencies, API surface)
  CHANGELOG.md      <-- per-module change history (Keep a Changelog format)
  CMakeLists.txt    <-- GPBT module declaration
  .gitignore        <-- module-specific gitignore
```

### `README.md` contract

Every module's `README.md` answers four questions, in order:

1. What does this module do?
2. Why does it exist as a separate module (instead of being merged into `core` or `engine`)?
3. What are its declared dependencies?
4. What does it expose to consumers?

Code review checks this template. A README that skips question 2 is flagged, since that explains the
module's architectural boundary.

### `CHANGELOG.md` contract

Every module ships a `CHANGELOG.md` following the [Keep a Changelog](https://keepachangelog.com)
format with a per-module version stream independent of the engine's master `CHANGELOG.md`. SDK
consumers tracking ABI stability for a single module can subscribe to that module's changelog
without reading engine-wide release notes.

### Opt-in tests and benchmarks

Tests and benchmarks are excluded from the default build. Each module's `CMakeLists.txt` opts in:

```cmake
gpStartModule(audio)
  gpAddDependency(PUBLIC core)
  gpTargetSetTestsEnabled(TRUE)
  gpTargetSetBenchmarksEnabled(TRUE)
gpEndModule()
```

When enabled, GPBT creates `<module>_tests` and `<module>_benchmarks` CMake targets that link
against the module under test plus the engine's test framework and benchmarking harness. They are
built only when enabled via a CMake preset or flag.

The opt-in design prevents CI from building every module's tests on every change. CI selects which
modules' tests to run based on which files changed (path filtering in GPBT).

## Alternatives Considered

### Option A: Single top-level `tests/` directory (satellite pattern)

All test files live in a flat `tests/` at the repository root, mirroring the module structure.

**Why rejected:** Module refactoring breaks test paths. Module deletion requires manual cleanup of
the satellite directory. A student reading `source/runtime/audio/` must remember to look in
`tests/runtime/audio/` for the tests.

**Reference:** Godot uses this pattern (`tests/` at root), which creates friction when modules are
reorganized.

### Option B: In-source tests (test code mixed into `private/`)

Place test source files alongside implementation files in `private/`, guarded with
`#ifdef GP_BUILD_TESTS`.

**Why rejected:** Pollutes the module's implementation namespace with test symbols. Conditional
compilation for tests is a common source of subtle bugs where test-only code paths are never
compiled by production builds and vice versa.

### Option C: Separate `tests/` module per module (O3DE / Gem pattern)

O3DE places tests in a separate `Tests/` subdirectory within a Gem, treated as its own GPBT target.

**Why adopted partially:** We adopt the same co-location principle, but GPBT creates the test and
benchmark targets automatically via `gpTargetSetTestsEnabled` without a separate `CMakeLists.txt`
inside `tests/`. GPBT discovers the test sources by glob and creates the target, avoiding the
boilerplate of a second module.

### Option D: Central `docs/` repository (documentation-as-a-repo)

Move all documentation to a separate repository, linked as a Git submodule or managed by a docs
platform.

**Why rejected:** Decoupling docs from code accelerates doc rot. A PR that renames a public API
must also update the docs; if docs live in a separate repo, reviewers cannot see the omission.
Co-location keeps docs maintenance part of every PR.

## Consequences

### Positive

- **Refactoring is atomic.** Moving a module moves its tests, benchmarks, and documentation with
  it, with no satellite cleanup.
- **Deletion is clean.** `git rm -r source/runtime/audio/` removes the module and all of its
  associated files.
- **Per-module changelogs enable targeted ABI tracking.** SDK consumers can subscribe to
  `audio/CHANGELOG.md` and ignore the rest.
- **Everything in one place.** Navigating to any module shows the README, the API (`public/`),
  the implementation (`private/`), the tests, and the benchmarks together.
- **Benchmark proximity encourages profiling.** Running a benchmark for
  `core/memory/backends/Malloc` is one CMake target away, and the benchmark sits next to the source.

### Negative

- **Module directories contain more items.** A newcomer sees eight items in a module directory
  instead of two, which adds one-time orientation overhead.
- **Per-module CHANGELOG maintenance requires discipline.** Developers must update the module-level
  `CHANGELOG.md` on API-visible changes, which is enforced in code review rather than tooling.
- **`docs/` inside each module can overlap with the module README.** By convention, `README.md`
  gives a quick orientation and `docs/` holds longer design documents, decision records, and
  diagrams.

  `tests/`, `benchmarks/`, `docs/` are the next three.
- [ADR-0003](./ADR-0003.md): `gpTargetSetTestsEnabled` / `gpTargetSetBenchmarksEnabled` are the
  GPBT primitives that wire up co-located test/benchmark directories.
- [ADR-0004](./ADR-0004.md): Co-location applies to every lifecycle bucket: runtime, developer,
  and plugin modules all follow the same anatomy.

**Canonical references:**

- O3DE Gems: each Gem is a self-contained unit with code, assets, tests, and a manifest.
- Bevy crates: each crate has its own `Cargo.toml`, `README.md`, and test module.
