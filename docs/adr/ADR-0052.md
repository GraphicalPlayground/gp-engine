## Context

Matrices in a AAA graphical engine are foundational mathematical primitives spanning multiple rendering
and spatial-computation domains, each with distinct dimensional, storage, and computational requirements:

1. **2D Linear Transformations `(gp::Matrix2x2)`**: Rotation, scaling, shearing, and linear transformations
    in two-dimensional space, including UI geometry, texture operations, and specialized mathematical computations.

2. **3D Linear Transformations `(gp::Matrix3x3)`**: Rotation, scaling, orientation, normal transformations,
    and basis transformations used throughout 3D spatial mathematics, rendering, and physics integration.

3. **3D Affine Transformations `(gp::Matrix3x4)`**: Translation, rotation, and scaling represented
    through a compact affine transformation matrix, commonly used for object transforms,
    skeletal animation, bone hierarchies, and scene graph propagation.

4. **4D Homogeneous Transformations `(gp::Matrix4x4)`**: Model, view, projection, and combined
    transformation matrices used throughout the rendering pipeline, including perspective projection,
    camera transformations, and homogeneous coordinate operations.

The Implementionn of the foundational matrix layer must satisfy its Biggest issue, speed and
computational optimzitation. Matrices are fundamental to almost all graphical calculation, with its
limiting factor being not calculation but data fetching and computing. THankfully, this optimization
already exists, it is called **SIMD** or **Single instruction, multiple data**. SIMD describes computers
with multiple processing elements that perform the same operation on multiple data points simultaneously.

The issue now being that these optimizations are both hardware (CPU's register portfolio) as well as
software (individual SIMD solution). This demands individual/unique solutions based on SIMD
implemtation.

The goal is to determine then create a Matrix architecture that can utilize SIMD on the majority of
Pc's that wish to run our program.



## Decision
we implemented a ***Column major column***, ***direct abstraction*** aproach of 2 opposing SIMD types,
as well as a scalar fallback incase backend of given pc is unidentifiable.
these types are:

+=============+============================+
| **Backend** | **Coverage**               |
+=============+============================+
| SSE2	      |  Older and baseline x86-64 |
+=============+============================+
| NEON	      |  ARM / Apple Silicon       |
+=============+============================+

these should cover over 80-90% of cpu used on the market today,
for those that still dont fit in that criteria, there is a final fallback of a generic
Scalar cpp implemented of the matrix


### 1. Architecture layout

```text
┌──────────────────────────────────────────────┐
│  Public API       gp::math::Matrix<R,C>      │  storage, semantics
|operators                                     |
│                   MatrixOps (det, inverse)   │
├──────────────────────────────────────────────┤
│  SIMD abstraction gp::math::Vec4             │  one 4-lane register + 10
| operations                                   |
├──────────────────────────────────────────────┤
│  Backends         SSE | NEON | Scalar        │  exactly one compiled in
└──────────────────────────────────────────────┘
```


### 2. abstraction methodolgy 

Every backend must provide the same operations:

| Operation                 | Meaning                                               |
|---------------------------|-------------------------------------------------------|
| `Vec4()`, `zero()`        | All lanes zero                                        |
| `Vec4(x,y,z,w)`           | Construct from four values                            |
| `splat(s)`                | Fill all lanes with `s`                               |
| `load(p)` / `store(p)`    | Unaligned load/store of 4 floats                      |
| `broadcast<I>()`          | Copy lane `I` (compile-time constant) to all lanes    |
| `+`, `-`, `*`             | Component-wise arithmetic                             |
| unary `-`                 | Component-wise negation                               |



## Alternatives Considered

### Option A: runtime dispatch vs compile-time selection

**Runtime dispatch** (`gp::MatrixRuntime` + function-pointer table) compiles every
backend (SSE2, SSE4.1, AVX2, NEON, SVE) into the binary, detects the CPU at startup
and picks one.

**Compile-time selection (chosen)** compiles only the one backend needed for the
target, chosen by the preprocessor, with a scalar fallback.

**Why runtime dispatch was rejected:**
- A call through a function pointer cannot be inlined. For a 4x4 multiply (16 multiplies,
  12 adds) the call overhead can exceed the work itself.
- It adds CPUID detection, per-file compiler flags and a test matrix across backends,
  which is more maintenance than this problem warrants.
- Our data is 4 floats wide, so wider instruction sets would not make a single
  matrix operation faster.

It would be justified if the workload were large batches (vertex buffers, skinning).
It can be added later as a separate layer without changing the `Matrix` API.

### Option B: row-major vs column-major

**Column-major was chosen.** Each column is padded to 4 floats and held in one SIMD
register. Matrix multiplication is then a sum of columns scaled by a number, which
works the same for every matrix size.

It also matches the layout OpenGL, Vulkan and GLSL expect, so data can be uploaded to
the GPU without transposing.

**Why row-major was rejected:** it is not impossible on SIMD (rows could be used the
same way), but it would mean transposing for every GPU upload, or using a
row-vector convention that conflicts with the rest of the graphics stack.

### Option C: SIMD backends

+=============+=============================+
| **Backend** |     **CPU architecture**    |
+=============+=============================+
| SSE2        | x86 / x86-64	            |
+=============+=============================+
| AVX2 + FMA  | Intel / AMD x86-64	        |
+=============+=============================+
| NEON	      | ARM / AArch64               |
+=============+=============================+
| SVE / SVE2  | Compatible ARM CPUs         |
+=============+=============================+
| AVX-512     | Selected Intel / AMD CPUs   |
+=============+=============================+
Plus a plain scalar fallback for any other platform.

**Why:** SSE2 and NEON are guaranteed on every x86-64 and AArch64 CPU, so no runtime
detection is needed. Both are 4 lanes wide, which matches one matrix column. Any
CPU with AVX2 also has SSE2, so nothing is lost on newer hardware.

AVX-512 and SVE are only available on some CPUs, so they would need runtime
detection and separate code paths.

**Revisit:** if profiling shows batch operations (vertex transforms, skinning) are a
bottleneck, add an AVX2 layer for those operations only.

## Consequences

### Positive

- **Single implementation for all matrix sizes.** 2x2, 3x3, 3x4 and 4x4 share one
  class template and one multiply, so there is no per-size SIMD code to maintain.
- **Matrix code is backend-agnostic.** `Matrix` only uses the small `MatrixVec4` interface.
  Adding or changing a backend (SSE, NEON, scalar) does not touch matrix logic.
- **Zero-overhead abstraction.** Everything resolves at compile time and inlines, so
  small fixed-size operations avoid function-pointer calls. Loops over R and C unroll,
  and a 2x2 multiply compiles down to a handful of instructions.
- **No runtime detection needed.** SSE2 (x86-64) and NEON (AArch64) are guaranteed
  baselines, so there is no CPUID code, no per-file compiler flags, and no risk of
  executing unsupported instructions.
- **Compile-time dimension safety.** Invalid operations such as `Matrix3x4 * Matrix3x3`
  fail to compile instead of producing wrong results.
- **Guaranteed scalar fallback.** The scalar backend can be forced with a macro, so it
  can be tested on any machine and compared against the SIMD backends.
- **Data is GPU-ready.** Column-major storage with a fixed 16-byte column stride can
  be uploaded directly, and aligned loads are always valid.
- **Small surface to verify.** The backend contract is about ten operations, which is
  easy to unit test per backend.
- **Leaves room to grow.** A runtime-dispatched layer (e.g. AVX2) can be added later,
  for batch operations only, without changing the `Matrix` API.

### Negative

- **Memory overhead from padding.** Every column occupies 16 bytes. A 3x3 uses 48
  bytes instead of 36, and a 2x2 uses 32 instead of 16. Negligible for engine math,
  but relevant if matrices are stored in very large arrays.
- **Wasted lanes on small matrices.** 2x2 and 3-row matrices leave 1 to 2 lanes of
  each register carrying zeros. Not a correctness issue, but not full SIMD efficiency.
- **Padding invariant must be maintained.** Padding lanes must stay zero. This is
  enforced by encapsulation (private column setter, bounds-limited element access),
  so future code that bypasses it can silently break results.
- **No benefit from wider ISAs on single operations.** The design is fixed at 4 lanes.
  AVX2/AVX-512/SVE cannot speed up one 4x4 multiply, only batch work, which would
  need the separate dispatch layer.
- **Backend is chosen at compile time.** One binary targets one baseline. Shipping
  builds optimized for different CPU levels from the same binary is not possible.
- **Hard limit of 4x4.** A column must fit one register, so the scheme does not extend
  to 5x5 or larger matrices. These would need a different implementation.
- **Floating-point results may differ across backends.** Operation order and FMA use
  can change rounding in the last bits, so tests must compare with a tolerance rather
  than for exact equality.
- **Generic determinant/inverse is not optimal.** The cofactor implementation is
  correct for all sizes but slower than hand-tuned 3x3/4x4 versions. Specializing
  them is deferred until profiling justifies it.
- **Template-heavy code.** More header-only code means longer compile times,
  harder-to-read error messages, and a cost to incremental builds as more files
  include it.
- **Debug builds are slow.** The abstraction depends on inlining. Unoptimized builds
  will not inline the wrappers and will be noticeably slower.
- **Each backend must be verified on its own platform.** NEON code only compiles and
  runs on ARM, so it needs CI coverage there.
- **Floating-point type is fixed** (if you drop the template parameter on `MatrixVec4`).
  `double` matrices would need a separate path. If you keep `MatrixVec4<T>`, you take on
  the specialization work described earlier.\
