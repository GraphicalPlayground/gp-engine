# ADR-0040: Zero-Allocation `.bss` Arena and Tokenized `StringView` Command-Line Parser

> Establishes a globally accessible, zero-heap-allocation command-line subsystem in `gp::core`
> backed by a fixed-capacity `.bss` character arena (`8 KiB`) and a contiguous `gp::StringView`
> token array (`128` slots), providing non-dangling lifetime guarantees, last-wins override
> semantics, `-no-<flag>` boolean negation, and `<charconv>` typed value extraction before dynamic
> memory allocators initialize.

![Proposed][badge-proposed]

## Context

Game engine command-line parsers operate under a strict bootstrapping paradox: they must be
initialized and queried at the earliest stage of process startup—before custom memory allocators,
thread pools, crash handlers, or windowing backends are constructed. Indeed, those foundational
subsystems depend on command-line flags (such as `-headless`, `-page_allocator`, `-rhi=vulkan`, or
`-threads=8`) to configure their own initialization.

If the command-line parser relies on dynamic heap allocations (e.g.,
`gp::Map<gp::String, gp::String>` or `gp::Vector<gp::String>`), it triggers a chicken-and-egg
failure with the engine's memory tracking subsystem and violates `gp-engine`'s zero-STL-allocation
invariant. Conversely, if the parser merely wraps raw OS `char** argv` pointers or temporary stack
strings inside `gp::StringView` instances without copying the underlying characters, any arguments
injected from temporary configuration buffers, response files, or Win32 `GetCommandLineA()`
conversions will immediately dangle once the initialization scope exits.

Furthermore, a production AAA command-line utility must resolve several ergonomic and
cross-platform ambiguities:

1. **OS Entry Signature Divergence:** POSIX platforms pass pre-tokenized `argc`/`argv` arrays to
   `main()`, whereas Windows GUI applications (`WinMain`) provide a single unparsed command-line
   string requiring quote-aware tokenization.
2. **Syntax Heterogeneousness:** Developers and build scripts pass arguments using space-separated
   (`-map Level01`), equals-separated (`-map=Level01`), and colon-separated (`-map:Level01`)
   conventions, alongside single (`-f`) and double (`--fullscreen`) dash prefixes.
3. **Negative Number vs. Flag Ambiguity:** A naive parser that treats any token beginning with
   `'-'` as a flag misinterprets negative numeric values in space-separated pairs (e.g.,
   `-offset -42` or `-exposure -1.25`) as separate flags.
4. **Override Hierarchy:** Automated test harnesses and developer launch scripts frequently
   append override arguments to the end of a base command line (e.g., `-rhi=dx12 -rhi=vulkan` or
   `-vsync --no-vsync`), requiring deterministic "last-wins" evaluation.

## Decision

We introduce `gp::CommandLine` inside `gp::core` (`source/runtime/core/public/miscellaneous/CommandLine.hpp`)
as a static, zero-allocation subsystem backed entirely by fixed-size buffers in the executable's
`.bss` data segment.

### 1. Physical Module Placement

```text
source/runtime/core/
├── public/
│   └── miscellaneous/
│       └── CommandLine.hpp
├── private/
│   └── miscellaneous/
│       └── CommandLine.cpp
└── tests/
    └── miscellaneous/
        └── CommandLine.tests.cpp

```

### 2. Memory Layout & Storage Architecture

All state resides in translation-unit-local `.bss` arrays inside `CommandLine.cpp`:

* **`s_arena[8192]` (`kMaxBufferBytes`):** Contiguous character arena storing null-terminated
  copies of every parsed token with outer quotes stripped.
* **`s_reconstructedBuffer[8192]`:** Contiguous character buffer storing the reconstructed
  command-line string (excluding `argv[0]`) for crash logs and telemetry.
* **`s_args[128]` (`kMaxArguments`):** Flat array of `gp::StringView` slices pointing exclusively
  into `s_arena`.

<!-- markdownlint-disable MD013 -->
| Architectural Dimension         | Chosen Mechanism                                  | Hardware / Runtime Guarantee                                 |
|---------------------------------|---------------------------------------------------|--------------------------------------------------------------|
| **Heap Allocations**            | `0 bytes` (`.bss` static arena)                   | Safe to call prior to memory subsystem boot.                 |
| **Token Lookup Complexity**     | $O(N)$ over contiguous `StringView[128]`          | Fits in 32 cache lines (2 KiB); zero pointer-chasing.        |
| **Lifetime Safety**             | Deep copy into `s_arena` on `init`/`append`       | Returned `gp::StringView` slices never dangle.               |
| **Override Resolution**         | Reverse scan (`s_argCount - 1` $\rightarrow$ `1`) | Appended CLI flags deterministically override earlier flags. |
| **String-to-Number Conversion** | C++23 `std::from_chars` (`<charconv>`)            | Locale-independent, non-allocating, non-throwing parsing.    |
<!-- markdownlint-enable MD013 -->

### 3. API & Usage Pattern

```cpp
// Initialization inside gp::launch entry point:
gp::CommandLine::init(argc, argv);
gp::CommandLine::append("-threads=16 --no-vsync");

// Zero-allocation typed queries anywhere in gp::core, gp::hal, or gp::application:
const bool isHeadless = gp::CommandLine::hasArgument("-headless");
const bool useVsync   = gp::CommandLine::getBool("-vsync", true);     // Returns false (--no-vsync won)
const gp::UInt32 jobs = gp::CommandLine::getUInt32("-threads", 4u);   // Returns 16u
const gp::Float32 fov = gp::CommandLine::getFloat32("-fov", 90.0f);
const gp::StringView mapName = gp::CommandLine::getValue("-map", "DefaultLobby");

if (const gp::Optional<gp::UInt64> seed = gp::CommandLine::tryGet<gp::UInt64>("-seed"))
{
     initializeRng(*seed);
}

```

### 4. Architectural Invariants

1. **Zero Dynamic Memory Allocation:** `gp::CommandLine` must never invoke `new`, `malloc`, or any
   engine heap allocator. Excess tokens beyond `kMaxArguments` (`128`) or `kMaxBufferBytes`
   (`8192`) are safely truncated.
2. **Non-Dangling `StringView` Guarantee:** Both `init(argc, argv)` and `init(StringView)` copy
   source characters into `s_arena`. Callers may freely destroy their input buffers immediately
   after `init()` or `append()`.
3. **Prefix & Separator Normalization:** Leading dashes (`-` or `--`) are stripped during key
   comparison, and inline values separated by `=` or `:` are split automatically.
4. **Negative Literal Disambiguation:** A token starting with `'-'` followed by an ASCII digit
   (`0`–`9`) or `'.'` + digit is classified as a numeric value rather than a flag, allowing
   `-offset -42` and `-exposure -1.25` to parse without ambiguity.
5. **Double-Dash (`--`) Termination:** Any token appearing after a standalone `--` delimiter is
   excluded from flag queries and treated strictly as a positional argument.
6. **Last-Wins Single Value / Forward Multi-Value:** Single-value queries (`tryGetString`,
   `tryGet<T>`, `tryGetBool`) scan backwards from the end of the token list so later flags
   override earlier ones, whereas `getValues()` scans forward to preserve list ordering (e.g.,
   `-plugin=A -plugin=B`).

## Alternatives Considered

### Option A: Global Raw String Scanner (Unreal Engine `FCommandLine` / `FParse` Style)

Store the entire command line as a single flat `char` array and perform substring searches
(`strstr` / `FParse::Value`) on every query.
**Why rejected:** Scanning a raw un-tokenized character buffer on every query requires repeatedly
handling quote escaping, whitespace boundaries, and prefix collisions (where searching for `-map`
accidentally matches `-map_dir`) at query time rather than once during `init()`. Tokenizing once
into `s_args[128]` makes subsequent queries simpler, faster, and immune to substring false positives.

### Option B: Pre-Parsed Dynamic Hash Map (`gp::Map<String, String>`)

Parse all arguments into a heap-allocated hash table during `init()` for $O(1)$ lookup.
**Why rejected:** Allocates heap memory before the engine's memory allocators are configured,
exhibits poor cache locality for small token counts ($N \le 128$) due to bucket hashing overhead,
and complicates preserving positional arguments and repeatable flags (`-plugin=A -plugin=B`).

### Option C: Zero-Copy `argv` Pointer Wrapping

Store `gp::StringView` slices pointing directly into the OS `char** argv` array without a
backing `.bss` character arena.

**Why rejected:** Fails to support single-string command lines (`WinMain` `lpCmdLine` or
`append("-extra=1")`) without mutating caller memory or risking dangling pointers when temporary
string buffers go out of scope.

## Consequences

### Positive

* **Pre-Heap Bootstrapping Safety.** Memory allocators, crash handlers, and logging subsystems can
  query command-line flags at the very first instruction of `main()`/`WinMain()`.
* **Deterministic Override Workflow.** Developers and CI pipelines can append flags via
  `CommandLine::append()` or trailing CLI arguments knowing that last-wins semantics will
  reliably override earlier defaults, including `-no-<flag>` boolean negations.
* **Type-Safe Extraction without Exceptions.** `<charconv>` (`std::from_chars`) paired with
  `gp::Optional<T>` provides strict bounds-checked parsing for `bool`, `Int8`..`Int64`,
  `UInt8`..`UInt64` (including `0x` hex and `0b` binary), and `Float32`/`Float64` with zero
  exceptions or locale overhead.

### Negative

* **Fixed `.bss` Footprint (~18.5 KiB).** Reserving `s_arena` (`8 KiB`), `s_reconstructedBuffer`
  (`8 KiB`), and `s_args` (`2 KiB`) increases static `.bss` memory usage by ~18.5 KiB regardless
  of how many arguments are passed.
* **Hard Compile-Time Capacity Limits.** Command lines exceeding `128` discrete tokens or `8192`
  total characters will drop trailing tokens (though standard game launch commands rarely
  exceed 20–30 tokens).
