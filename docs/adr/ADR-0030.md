# ADR-0030: 64-Bit Integer Nanoseconds and Rational Frame Rates as Canonical Time Units

> Storing accumulated engine time in 32-bit `float` degrades precision past 1 millisecond after
> just 4.5 hours of uptime, while storing frame rates as floating-point seconds
> (`1.0f / 60.0f = 0.016666668f`) introduces cumulative rounding drift during long cutscenes and
> deterministic replays. The engine mandates 64-bit integer nanoseconds (`gp::Int64` for
> `Duration`, `gp::UInt64` for `Timestamp`) as the canonical internal representation ($\pm 292$
> years range at $1\text{ ns}$ resolution) alongside rational `FrameRate`
> (`numerator` / `denominator`) for exact frame intervals. Floating-point deltaTime
> (`Float32` / `Float64`) is strictly a read-only leaf view generated for shader and physics
> integrators.

![Proposed][badge-proposed]

## Context

In real-time simulation engines, time values drive numerical integration, state interpolation,
physics steps, animation timelines, and network packet synchronization. Historically, game
engines stored accumulated uptime and frame step sizes as 32-bit single-precision IEEE 754
floating-point values (`float totalTime`).

### The Floating-Point Time Catastrophe

A standard 32-bit float allocates 1 sign bit, 8 exponent bits, and 23 explicit mantissa bits,
providing 24 bits of effective significand precision (roughly 7.22 decimal digits). Because the
exponent scales the distance between consecutive representable numbers, the resolution (Unit
in the Last Place, or ULP) degrades as accumulated time grows:

- At $t = 100\text{ s}$, the ULP is $2^{-17}\text{ s} \approx 7.63\ \mu\text{s}$. Individual
  frame deltas near 16.6 ms retain microsecond fidelity.
- At $t = 16,384\text{ s}$ ($\approx 4.55\text{ hours}$), the exponent increases such that
  $\text{ULP} = 2^{-10}\text{ s} \approx 0.976\text{ ms} \approx 1\text{ ms}$. At this point,
  accumulating a 60 FPS frame delta ($16.66\text{ ms}$) truncates roughly 1 millisecond of
  resolution on every addition.
- At $t = 131,072\text{ s}$ ($\approx 36.4\text{ hours}$), $\text{ULP} = 2^{-7}\text{ s} \approx
  7.81\text{ ms}$. Adding a 16.66 ms frame step incurs nearly 50% quantization error.
- At $t = 16,777,216\text{ s}$ ($\approx 194.18\text{ days}$), $\text{ULP} = 1.0\text{ s}$.
  Fractional frame steps below 1.0 second cannot be represented. Any addition of $dt < 0.5\text{ s}$
  rounds down to zero, freezing engine time completely.

Dedicated game servers frequently run continuously for days or weeks without restarting. As
mantissa exhaustion sets in, numerical integration produces non-uniform time steps, velocity
calculations jitter, collision detection breaks down, and rigid bodies clip through geometry.

### The Rational Frame Rate Dilemma

Standard video and monitor refresh rates cannot be represented accurately in binary
floating-point:

- 60.0 FPS: $1.0 / 60.0 = 0.01666666666... \to 0.016666668\text{ s}$ in 32-bit float.
- NTSC 59.94 FPS: $1001.0 / 60000.0 = 0.01668333333...$
- Cinema 23.976 FPS: $1001.0 / 24000.0 = 0.04170833333...$

When an engine stores frame intervals or target step durations as floating-point seconds, every
frame accumulates truncation error. Over thousands of frames, this error causes visible drift
between audio playback and video animation tracks, desynchronizes cutscene subtitles, and
creates discrepancies in deterministic network rollback buffers where two peers accumulate
slightly different elapsed times.

## Decision

We establish 64-bit integer nanoseconds as the canonical internal representation for all
temporal measurements across `gp-engine`, paired with rational integer pairs for display and
tick rates. Time calculations never accumulate in floating-point types.

```cpp
namespace gp::time {

struct Duration
{
    Int64 nanoseconds = 0; // +/- 292.47 years at 1 ns precision

    [[nodiscard]] constexpr Float32 asFloatSeconds() const noexcept
    {
        return static_cast<Float32>(static_cast<Float64>(nanoseconds) * 1e-9);
    }

    [[nodiscard]] constexpr Float64 asDoubleSeconds() const noexcept
    {
        return static_cast<Float64>(nanoseconds) * 1e-9;
    }
};

struct Timestamp
{
    UInt64 nanoseconds = 0; // Monotonic or epoch timestamp
};

struct FrameRate
{
    UInt32 numerator = 60;
    UInt32 denominator = 1;

    [[nodiscard]] constexpr Duration getFrameDuration() const noexcept
    {
        return Duration{ static_cast<Int64>((1'000'000'000ULL * denominator) / numerator) };
    }
};

} // namespace gp::time
```

### Mathematical Range and Precision

Signed 64-bit integer nanoseconds (`gp::Int64`) span $-2^{63}$ to $2^{63} - 1$ nanoseconds,
corresponding to approximately $\pm 292.47$ years ($\approx \pm 9.22 \times 10^{18}\text{ ns}$).
The resolution remains exactly 1 nanosecond throughout the entire duration. Unsigned 64-bit
nanoseconds (`gp::UInt64`) provide a monotonic timestamp range of approximately $584.94$ years.

### Architectural Invariants

1. **Canonical Integer Representation:** Core clock state, event timestamps, timer queues, and
   fixed-step accumulators store and update time exclusively using 64-bit integer nanoseconds
   (`gp::Int64` for `Duration`, `gp::UInt64` for `Timestamp`) and rational `FrameRate`.
2. **Non-Owning Leaf Views:** Conversions to floating-point (`Float32` and `Float64` seconds via
   `asFloatSeconds()` and `asDoubleSeconds()`) are strictly non-owning leaf views. Physics
   integrators (such as `pos += vel * dt.asFloatSeconds()`) or shader uniforms consume these
   values at callsites, but floating-point values never write back into clock accumulators.
3. **Exact Rational Frame Durations:** Display refresh cycles, fixed simulation steps, and media
   timelines are defined as rational integer pairs (`numerator` and `denominator`). Frame
   advancement calculates intervals via integer ratios, preventing fractional truncation drift
   across long running sequences.
4. **Monotonic Two's-Complement Delta Arithmetic:** Time differences between timestamps use
   signed two's-complement arithmetic to compute durations. Duration arithmetic clamps or
   asserts against integer overflow to prevent silent sign wrapping.

## Alternatives Considered

### Option A: Single-Precision 32-Bit Float Seconds (`float time`)

Store accumulated engine time and delta seconds as standard 32-bit IEEE 754 floats.

**Why rejected:** Suffers catastrophic mantissa exhaustion after 4.5 hours of uptime. Dedicated
multiplayer servers running for days or weeks experience simulation freezing, physics
breakdowns, and animation stuttering.

### Option B: Double-Precision 64-Bit Float Seconds (`double time`)

Store accumulated engine time and delta seconds as 64-bit IEEE 754 floats.

**Why rejected:** While 53 mantissa bits extend precision to days of uptime, rational frame rates
(such as 59.94 Hz and 23.976 Hz) cannot be expressed cleanly in binary floating-point. Cumulative
fractional drift persists over long playback sessions. Floating-point addition is also
non-associative (`(a + b) + c != a + (b + c)`), breaking cross-platform deterministic replay
verification across varying compiler optimization flags and target architectures.

### Option C: Millisecond-Integer Time (`UInt64 ms`)

Store time in 64-bit integers with millisecond granularity.

**Why rejected:** Millisecond resolution is too coarse for modern engine requirements. High-polling
input devices (such as gaming mice running at 1000 Hz or 8000 Hz) generate events every 1 ms or 125
microseconds. VR head-tracking pose prediction, audio buffer scheduling (48 kHz samples occur every
20.83 microseconds), and sub-frame physics interpolation all require sub-millisecond precision.

## Consequences

### Positive

- **Uptime-invariant temporal precision.** Signed 64-bit nanoseconds preserve uniform 1 ns
  resolution for over 292 years, preventing mantissa degradation and simulation stutter on
  long-running dedicated servers.
- **Bit-identical simulation determinism.** Integer arithmetic and rational frame rates guarantee
  identical time step accumulation across different CPU architectures and compiler flags,
  supporting lockstep networking and replay validation.
- **Drift-free media and display synchronization.** Rational frame rates (`numerator` /
  `denominator`) eliminate cumulative rounding drift for non-integer broadcast and display
  standards such as 59.94 Hz NTSC and 23.976 Hz cinema cutscenes.
- **Low-latency hardware execution.** 64-bit integer operations execute in single-cycle ALU
  instructions on modern processors without consuming floating-point execution ports or
  triggering FPU rounding mode differences.

### Negative

- **Leaf conversion overhead.** Converting integer nanoseconds to floating-point seconds requires
  an integer-to-float cast and multiplication by $10^{-9}$ when feeding graphics shaders or
  physics solvers.
- **Intermediate overflow in multiplication.** Compounding operations on large nanosecond values
  (such as scaling durations by high multipliers) can exceed `Int64` limits, requiring careful
  ordering, 128-bit intermediate arithmetic, or explicit bounds checks.
