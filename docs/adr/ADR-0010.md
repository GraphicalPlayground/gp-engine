# ADR-0010: Adoption of SDL3 as the Primary Platform Abstraction Backend

> Selects SDL3 to handle OS windowing, input polling, and device discovery as the concrete
> implementation behind the engine's generic HAL.

![Proposed][badge-proposed]

## Context

Operating systems (Windows, Linux, macOS, Android, iOS) expose divergent windowing and hardware
interfaces. A cross-platform engine must abstract these differences without losing execution
determinism, memory locality, or compile speed:

- **Windowing and message loop divergence:** Windows uses the Win32 message pump (`PeekMessageW`,
  `DispatchMessageW`, `WNDCLASSEX`) with re-entrant WinProc callbacks during modal drag/resize
  events. macOS runs an Objective-C runtime hosting `NSApplication`, `NSWindow`, and `NSEvent` on
  the main thread (`thread 0`). Linux splits between X11 (`Xlib`/`XCB`) and Wayland
  (`wayland-client`), which uses client-driven surface commit handshakes, asynchronous `xdg_shell`
  events, and no global screen coordinates. Mobile platforms (Android NDK `ANativeActivity` and iOS
  UIKit) add asynchronous lifecycle suspensions and touch-event queues.
- **Peripheral discovery and calibration:** Gamepads vary across DirectInput, XInput, and
  Windows.Gaming.Input on Windows, `GCController` on macOS, and `evdev`/`hidraw` on Linux. Raw
  controllers ship with inconsistent axis directions, trigger thresholds, deadzones, and
  vendor-specific HID reports. Handling USB and Bluetooth hotplugging, handle recycling, and
  reconnection across thousands of controllers is a large maintenance burden.
- **Header pollution and namespace poisoning:** Native platform headers pollute C++ builds:
  - `<windows.h>` injects thousands of preprocessor macros (`min`, `max`, `near`, `far`,
    `DrawText`, `CreateWindow`, `GetMessage`), colliding with standard library functions and engine
    identifiers.
  - `<X11/Xlib.h>` defines macros such as `None`, `Success`, `Always`, and `Bool`, breaking C++
    `enum class` scoping and concept definitions.
  - Cocoa headers require Objective-C++ compilation units (`.mm`), slowing builds.
- **High-polling event saturation:** Modern gaming peripherals poll up to 8,000 Hz (esports mice
  and IMU sensors). Handling those messages directly in synchronous UI loops stalls the render
  thread and thrashes CPU caches.

Implementing every OS backend from scratch would consume hundreds of hours on platform glue and
compositor bugs instead of rendering and core engine architecture. Exposing a third-party library's
types across the engine would violate our zero-STL, ABI, and encapsulation rules
([ADR-0001](./ADR-0001.md)).

## Decision

We adopt Simple DirectMedia Layer 3 (SDL3) as the primary platform abstraction backend for
`gp-engine`, encapsulated behind an injected Hardware Abstraction Layer (HAL).

SDL3 is a private, low-level implementation detail hidden behind the abstract interfaces of
`source/runtime/hal/base/` and the reusable logic of `source/runtime/hal/generic/`. Consumers see
zero SDL3 symbols or headers.

```text
source/runtime/hal/
  base/       <-- Abstract contracts (IApplicationBackend, IWindow, IInputSystem, ...)
    public/   <-- Public API seen by consumers: zero third-party headers
    private/
  generic/    <-- Reusable platform-agnostic logic
    public/   <-- GenericWindow shadow state, display topology tables, input mapping
    private/
  sdl3/       <-- Concrete SDL3 backend
    public/   <-- Backend declaration (SDL3ApplicationBackend.hpp, SDL3Window.hpp)
              <-- Opaque forward declarations only: struct SDL_Window; struct SDL_Cursor;
    private/  <-- Only place <SDL3/SDL.h> is included; translates OS events to PODs
```

### Architectural invariants

1. **Private encapsulation and header hygiene:** `<SDL3/SDL.h>` is forbidden in public headers.
   `hal/sdl3/public/` forward-declares opaque types (`struct SDL_Window;`, `struct SDL_Cursor;`).
   All SDL3 API calls, event translations, and property queries live in `hal/sdl3/private/`,
   enforced by private linkage:

   ```cmake
   # source/runtime/hal/sdl3/CMakeLists.txt
   gpStartModule(hal/sdl3)
     gpAddDependency(PUBLIC core)
     gpAddDependency(PUBLIC hal/base)
     gpAddDependency(PUBLIC hal/generic)
     gpAddDependency(PRIVATE gp::thirdparty::sdl3)
   gpEndModule()
   ```

2. **Dependency injection:** Per [ADR-0007](./ADR-0007.md) and [ADR-0011](./ADR-0011.md), engine
   consumers (`engine`, `renderer`, `editor`) depend only on `hal/base` and `hal/generic`. The
   concrete `gp::hal::sdl3::ApplicationBackend` is instantiated at the executable entry point
   (`gp_editor`, `gp_runtime`) and injected via `IApplicationBackend`.

3. **POD event translation into lock-free SPSC streams:** Per [ADR-0013](./ADR-0013.md),
   [ADR-0019](./ADR-0019.md), and [ADR-0020](./ADR-0020.md), raw `SDL_Event` unions are polled on
   the OS message thread via `SDL_PollEvent()`, translated into trivially copyable, standard-layout
   POD structs (`WindowEvent`, `KeyboardEvent`, `MouseEvent`, `GamepadEvent`, `DisplayEvent`), and
   written to a lock-free `gp::SPSCByteRingBuffer`. No `SDL_Event` or heap allocation reaches the
   Game Thread.

4. **Two-tier backpressure and critical reserve admission:** The SDL3 event pump enforces
   [ADR-0026](./ADR-0026.md). Continuous motion packets (mouse movement, gamepad axis, sensor
   updates) are dropped if free space in the ring buffer falls below `criticalReserveBytes`, so
   discrete lifecycle events (`WindowAction::CloseRequested`, `KeyState::Released`) survive Game
   Thread hitches.

5. **Native window handle extraction via properties:** The RHI needs native OS surface pointers
   (`HWND`, `NSWindow*`, `wl_surface*`, `Window`) to create swapchains ([ADR-0002](./ADR-0002.md)).
   `gp::hal::sdl3::Window` queries `SDL_GetWindowProperties` and fills a `NativeWindowHandle` tagged
   union ([ADR-0014](./ADR-0014.md)):

   <!-- markdownlint-disable MD013 -->
   | Platform | SDL3 property key | Extracted engine handle |
   | :--- | :--- | :--- |
   | Win32 | `SDL_PROP_WINDOW_CREATE_WIN32_HWND_POINTER` | `NativeWindowHandle::win32.hwnd` |
   | Cocoa | `SDL_PROP_WINDOW_CREATE_COCOA_WINDOW_POINTER` | `NativeWindowHandle::cocoa.nsWindow` |
   | Wayland | `SDL_PROP_WINDOW_CREATE_WAYLAND_WL_SURFACE_POINTER` | `wayland.surface` |
   | X11 | `SDL_PROP_WINDOW_CREATE_X11_WINDOW_NUMBER` | `NativeWindowHandle::x11.window` |
   | Android | `SDL_PROP_WINDOW_ANDROID_WINDOW_POINTER` | `NativeWindowHandle::android.window` |
   | UIKit | `SDL_PROP_WINDOW_UIKIT_WINDOW_POINTER` | `NativeWindowHandle::uikit.uiWindow` |
   | KMSDRM | `SDL_PROP_WINDOW_KMSDRM_GBM_DEVICE_POINTER` | `NativeWindowHandle::kmsdrm.gbmDevice` |
   <!-- markdownlint-enable MD013 -->

6. **Zero steady-state heap allocation:** Display mode tables, monitor topologies, clipboard
   buffers, and input states live in pre-allocated or fixed-capacity structures inside
   `GenericApplicationBackend` and `GenericDisplay` ([ADR-0028](./ADR-0028.md),
   [ADR-0029](./ADR-0029.md)). The per-frame SDL3 message loop makes zero dynamic allocations.

### Platform abstraction comparison

<!-- markdownlint-disable MD013 -->
| Dimension | SDL3 + HAL (Adopted) | Native OS | GLFW | Qt / CEF |
| :--- | :--- | :--- | :--- | :--- |
| Headers | Private to `hal/sdl3` | Leaks OS headers | Exposes C pointers | Macros, MOC |
| Platforms | Win32, Cocoa, Linux, mobile, KMSDRM | ~40k LOC per OS | Desktop only | Desktop only |
| Input | `SDL_Gamepad` DB + gyro | Custom HID | Generic joysticks | Limited |
| Display | DPI v2, HDR, Wayland scaling | Custom EDID | Basic scaling | Widget-oriented |
| Memory | Zero-alloc SPSC stream | Zero-alloc | Internal heap | Heap, exceptions |
| Maint. | Upstream (Valve, Epic) | High in-house | Smaller backing | Heavy ABI coupling |

## Alternatives Considered

### Option A: Bespoke in-house platform backends (Win32, Cocoa, Wayland, X11)

Implement platform abstraction directly against native SDKs (similar to Unreal Engine's
`FWindowsApplication`, `FCocoaApplication`, `FLinuxApplication`).

**Why rejected:** Maintaining tens of thousands of lines of OS glue is expensive. Modern Linux
requires separate X11 and Wayland client protocols, sub-surface synchronization, `xdg-shell` state
handling, and fractional DPI scaling. Custom gamepad support requires hundreds of hardware PID/VID
tables and USB/Bluetooth hotplugging edge cases, with no runtime performance advantage over SDL3.

### Option B: Lightweight windowing abstraction via GLFW 3.x

Use GLFW as the underlying windowing and input library.

**Why rejected:** GLFW works well for single-window demos, but lacks three capabilities needed by a
full engine:

1. **Limited hardware device support:** No built-in gamepad mapping database like `SDL_GamepadDB`,
   and no first-class haptics, IMU sensors (gyroscope/accelerometer), or pen/tablet pressure.
2. **Missing OS primitives:** No native message box dialogs ([ADR-0038](./ADR-0038.md)), system
   cursor management across topologies, or MIME-based clipboard abstractions.
3. **Wayland and multi-monitor gaps:** GLFW's Wayland backend lags on fractional scaling and
   multi-window docking needed for editors.

### Option C: Legacy SDL2 backend

Use SDL2.

**Why rejected:** SDL2 carries legacy design choices that conflict with our engine rules:

1. **No unified property system:** SDL2 uses `SDL_syswm.h` to extract native window handles, pulling
   in `<windows.h>` and `<X11/Xlib.h>`. SDL3 replaces this with `SDL_GetWindowProperties()`.
2. **Coordinate and DPI conflation:** SDL2 mixes window coordinates with pixel viewports on high-DPI
   and fractional-scaled displays. SDL3 separates window coordinates from physical pixel buffers.
3. **Missing dialog primitives:** SDL2 lacks built-in native file dialogs and modal message boxes,
   requiring third-party libraries such as `tinyfiledialogs`.

## Consequences

### Positive

- **Reduced platform maintenance.** OS windowing, compositor sync, and display edge cases are
  delegated to an actively maintained library.
- **Clean header hygiene.** Keeping SDL3 headers inside `hal/sdl3/private/` and using forward
  declarations in public headers keeps OS macros (`min`, `max`, `near`, `far`, `None`, `Success`)
  out of engine compilation units.
- **Out-of-the-box gamepad and peripheral support.** The engine gets mapping tables for DirectInput,
  XInput, DualSense, Xbox, and Nintendo Switch controllers, plus rumble, haptics, and IMU sensors.
- **Modern protocol support.** SDL3 handles Wayland `xdg_shell`, macOS Cocoa run loops, and Win32
  Per-Monitor DPI Awareness v2.
- **Deterministic, zero-allocation Game Thread.** Translating `SDL_Event` into POD events on the OS
  thread keeps the Game Thread lock-free and allocation-free ([ADR-0013](./ADR-0013.md),
  [ADR-0020](./ADR-0020.md)).
- **Property-based RHI handles.** `SDL_GetWindowProperties` lets the RHI ([ADR-0002](./ADR-0002.md))
  build Vulkan, D3D12, or Metal swapchains without platform `#ifdef` blocks in consumer code.

### Negative

- **External third-party build dependency.** The engine depends on `gp::thirdparty::sdl3`, requiring
  pre-compiled binaries or CMake submodule orchestration.
- **Boundary translation cost.** Events are copied from SDL's queue, translated to POD structs, and
  written to `SPSCByteRingBuffer`. This adds under 15 ns per event on the OS polling thread, which
  is small compared to OS syscalls.
- **Upstream sync cadence.** Fixes for OS-level quirks depend on upstream SDL3 releases or local
  vendor patches.
