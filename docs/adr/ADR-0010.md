# ADR-0010: Adoption of SDL3 as the Primary Platform Abstraction Backend

> Defines the choice of SDL3 to handle the chaotic realities of OS windowing, input polling, and
> device discovery, acting as the concrete implementation behind the engine’s generic HAL.

![Proposed][badge-proposed]

## Context

Operating systems (Windows, Linux, macOS, Android, iOS) expose radically divergent, historically
convoluted, and asynchronous windowing and hardware interfaces. Writing a cross-platform AAA engine
requires abstracting these chaotic platform realities without compromising execution determinism,
memory locality, or compilation performance:

- **Windowing and Message Loop Divergence:** Windows uses the Win32 message pump (`PeekMessageW`,
  `DispatchMessageW`, `WNDCLASSEX`) coupled with re-entrant WinProc callbacks during modal drag/resize
  events. macOS demands an Objective-C runtime hosting `NSApplication`, `NSWindow`, and `NSEvent`
  bound strictly to the OS process main thread (`thread 0`). Linux is fractured between the legacy
  asynchronous X11 protocol (`Xlib`/`XCB`) and modern Wayland compositors (`wayland-client`), which
  rely on client-driven surface commit handshakes, asynchronous `xdg_shell` configuration events,
  and lack global screen coordinates. Mobile platforms (Android NDK `ANativeActivity` and iOS UIKit)
  introduce asynchronous lifecycle suspensions and touch-event queuing.
- **Peripheral Discovery and Calibration Chaos:** The peripheral hardware ecosystem is rife with
  non-standard devices. Gamepads vary across DirectInput, XInput, and Windows.Gaming.Input on Windows,
  `GCController` on macOS, and `evdev`/`hidraw` on Linux. Raw controller hardware features inconsistent
  axis directions, divergent trigger thresholds, broken deadzones, and vendor-specific HID reports.
  Managing physical USB and Bluetooth hotplugging, handle recycling, and hardware reconnection across
  thousands of controllers is an enormous maintenance burden.
- **Header Pollution and Namespace Poisoning:** Native platform headers are notoriously toxic in C++:
  - `<windows.h>` injects thousands of preprocessor macros (`min`, `max`, `near`, `far`, `DrawText`,
    `CreateWindow`, `GetMessage`), trampling standard library functions and engine identifiers.
  - `<X11/Xlib.h>` defines pervasive macros such as `None`, `Success`, `Always`, and `Bool`,
    violating modern C++ enum class scoping and concept definitions.
  - Cocoa headers require Objective-C++ compilation units (`.mm`), contaminating compilation units
    and degrading compile times.
- **High-Polling Event Saturation:** Modern gaming peripherals poll at extreme rates (up to 8,000 Hz
  for esports mice and high-frequency IMU sensors). Directly handling these messages in naive
  synchronous UI loops stalls the rendering thread and exhausts CPU cache lines.

If every OS backend were implemented from scratch within the engine, hundreds of engineering hours
would be consumed maintaining platform-specific boilerplate and tracking OS compositor bugs rather
than advancing graphics engineering, pedagogical deconstruction, and core rendering architecture.
Conversely, exposing a third-party library's types throughout the engine would violate our zero-STL,
strict ABI, and physical encapsulation principles ([ADR-0001](./ADR-0001.md)).

## Decision

We adopt **Simple DirectMedia Layer 3 (SDL3)** as the primary concrete platform abstraction backend
for `gp-engine`, fully encapsulated behind an injected Hardware Abstraction Layer (HAL).

SDL3 serves exclusively as a private, low-level plumbing implementation. It is hidden behind the
abstract interfaces of `source/runtime/hal/base/` and the reusable logic of
`source/runtime/hal/generic/`. The engine and its consumers remain completely blind to SDL3 symbols
and headers.

```text
source/runtime/hal/
  base/                       <-- Pure abstract contracts (IApplicationBackend, IWindow, IInputSystem, ...)
    public/                   <-- Public API seen by consumers: zero third-party headers
    private/
  generic/                    <-- Reusable platform-agnostic business logic
    public/                   <-- GenericWindow shadow state, display topology tables, input mapping
    private/
  sdl3/                       <-- Concrete SDL3 implementation backend
    public/                   <-- Backend declaration (SDL3ApplicationBackend.hpp, SDL3Window.hpp)
                              <-- Opaque forward declarations only: struct SDL_Window; struct SDL_Cursor;
    private/                  <-- Only place <SDL3/SDL.h> is included; translates OS events to engine PODs
```

### Architectural Invariants

1. **Strict Private Encapsulation & Header Hygiene:** SDL3 headers (`<SDL3/SDL.h>`) are **strictly
   forbidden** in public headers. `hal/sdl3/public/` forward-declares opaque types (`struct SDL_Window;`,
   `struct SDL_Cursor;`). All SDL3 API calls, event translations, and property queries reside
   exclusively within `hal/sdl3/private/` compilation units. The build system enforces this via
   private linkage:

   ```cmake
   # source/runtime/hal/sdl3/CMakeLists.txt
   gpStartModule(hal/sdl3)
     gpAddDependency(PUBLIC core)
     gpAddDependency(PUBLIC hal/base)
     gpAddDependency(PUBLIC hal/generic)
     gpAddDependency(PRIVATE gp::thirdparty::sdl3)
   gpEndModule()
   ```

2. **Decoupled Architecture via Dependency Injection:** In accordance with [ADR-0007](./ADR-0007.md)
   and [ADR-0011](./ADR-0011.md), engine consumers (`engine`, `renderer`, `editor`) depend solely on
   `hal/base` and `hal/generic`. The concrete `gp::hal::sdl3::ApplicationBackend` is instantiated at
   the application entry point (`gp_editor`, `gp_runtime`) and injected into the engine runtime via
   `IApplicationBackend`.

3. **POD Event Translation into Lock-Free SPSC Streams:** As mandated by [ADR-0013](./ADR-0013.md),
   [ADR-0019](./ADR-0019.md), and [ADR-0020](./ADR-0020.md), raw `SDL_Event` unions are polled on the
   dedicated OS message thread via `SDL_PollEvent()`, immediately translated into trivially copyable,
   standard-layout engine POD structures (`WindowEvent`, `KeyboardEvent`, `MouseEvent`,
   `GamepadEvent`, `DisplayEvent`), and committed to a lock-free `gp::SPSCByteRingBuffer`. No `SDL_Event`
   or dynamic heap allocation ever crosses into the Game Thread.

4. **Two-Tier Backpressure and Critical Reserve Admission:** The SDL3 event pump enforces
   [ADR-0026](./ADR-0026.md). High-frequency continuous motion packets (mouse movement, gamepad axis,
   sensor updates) are shed if free space in the ring buffer falls below `criticalReserveBytes`,
   guaranteeing that discrete lifecycle events (`WindowAction::CloseRequested`, `KeyState::Released`)
   are never dropped even during heavy Game Thread hitches.

5. **Type-Safe Native Window Handle Extraction via Properties:** The Rendering Hardware Interface
   (RHI) requires native OS surface pointers (`HWND`, `NSWindow*`, `wl_surface*`, `Window`) to create
   graphics swapchains ([ADR-0002](./ADR-0002.md)). Rather than relying on fragile platform-specific
   SDL hacks, `gp::hal::sdl3::Window` queries SDL3's unified property system
   (`SDL_GetWindowProperties`) and populates a type-safe `NativeWindowHandle` tagged union
   ([ADR-0014](./ADR-0014.md)):

   <!-- markdownlint-disable MD013 -->
   | Platform | SDL3 Property Key | Extracted Engine Handle |
   | :--- | :--- | :--- |
   | **Win32** | `SDL_PROP_WINDOW_CREATE_WIN32_HWND_POINTER` | `NativeWindowHandle::win32.hwnd` |
   | **Cocoa** | `SDL_PROP_WINDOW_CREATE_COCOA_WINDOW_POINTER` | `NativeWindowHandle::cocoa.nsWindow` |
   | **Wayland** | `SDL_PROP_WINDOW_CREATE_WAYLAND_WL_SURFACE_POINTER` | `NativeWindowHandle::wayland.surface` |
   | **X11** | `SDL_PROP_WINDOW_CREATE_X11_WINDOW_NUMBER` | `NativeWindowHandle::x11.window` |
   | **Android**| `SDL_PROP_WINDOW_ANDROID_WINDOW_POINTER` | `NativeWindowHandle::android.window` |
   | **UIKit** | `SDL_PROP_WINDOW_UIKIT_WINDOW_POINTER` | `NativeWindowHandle::uikit.uiWindow` |
   | **KMSDRM** | `SDL_PROP_WINDOW_KMSDRM_GBM_DEVICE_POINTER` | `NativeWindowHandle::kmsdrm.gbmDevice` |
   <!-- markdownlint-enable MD013 -->

6. **Zero Steady-State Heap Allocation:** Display mode tables, monitor topologies, clipboard buffers,
   and input states are pre-allocated or cached within fixed-capacity structures inside
   `GenericApplicationBackend` and `GenericDisplay` ([ADR-0028](./ADR-0028.md), [ADR-0029](./ADR-0029.md)).
   The per-frame SDL3 message pumping loop executes with zero dynamic allocations.

## Alternatives Considered

### Option A: Bespoke In-House Platform Backends (Win32, Cocoa, Wayland, X11)

Implement platform abstraction directly against native platform SDKs from scratch (analogous to
Unreal Engine's `FWindowsApplication`, `FCocoaApplication`, `FLinuxApplication`).

**Why rejected:** Building bespoke platform backends from scratch forces the engine team to maintain
tens of thousands of lines of fragile OS glue. In particular, supporting modern Linux requires
authoring independent X11 and Wayland client protocols, handling sub-surface synchronization,
negotiating xdg-shell surface states, and implementing custom fractional DPI scaling. Furthermore,
writing custom gamepad drivers requires maintaining hundreds of hardware PID/VID mapping tables
and dealing with USB/Bluetooth hotplugging edge cases. This massive maintenance burden distracts
from the engine's primary pedagogical and graphics rendering goals without providing runtime
performance advantages over SDL3.

### Option B: Lightweight Windowing Abstraction via GLFW 3.x

Use GLFW as the underlying windowing and input library.

**Why rejected:** While GLFW provides a clean C API for simple single-window OpenGL/Vulkan demos, it
falls short for a full-scale game engine:
1. **Limited Hardware Device Support:** GLFW lacks an integrated, community-maintained gamepad
   mapping database comparable to `SDL_GamepadDB`. It provides no first-class abstractions for
   controller haptics, sensor/IMU feeds (gyroscope/accelerometer), or pen/tablet pressure input.
2. **Missing OS Primitives:** GLFW does not provide native message box dialogs ([ADR-0038](./ADR-0038.md)),
   system cursor management across complex topologies, or MIME-based clipboard abstractions.
3. **Wayland and Multi-Monitor Maturation:** GLFW's Wayland backend historically lags behind modern
   fractional scaling and multi-window docking requirements needed by modern game editors.

### Option C: Legacy SDL2 Backend

Use the battle-tested SDL2 library.

**Why rejected:** SDL2 carries twenty years of legacy design choices that conflict with modern AAA
engine patterns:
1. **Lack of Unified Property System:** SDL2 relies on platform-specific query headers
   (`SDL_syswm.h`) to extract native window handles, dragging in `<windows.h>` and `<X11/Xlib.h>`
   and destroying header hygiene. SDL3 replaces this with `SDL_GetWindowProperties()` and opaque
   dictionary queries.
2. **Legacy Coordinate and DPI Handling:** SDL2 conflates window coordinates with pixel viewports on
   high-DPI and fractional-scaled displays. SDL3 separates floating-point window coordinates from
   physical pixel framebuffers.
3. **Single-Window Audio and Dialog Deficiencies:** SDL2 lacks built-in native file dialogs and modal
   message box abstractions, requiring third-party libraries (e.g., `tinyfiledialogs`).

## Consequences

### Positive

- **Drastic reduction in non-differentiating platform maintenance.** The engine delegates the
  fragile, vendor-specific edge cases of OS windowing, compositor synchronization, and display
  management to an actively maintained, battle-tested library backed by the video game industry.
- **Flawless header hygiene and zero namespace contamination.** By restricting SDL3 headers to
  `hal/sdl3/private/` and using forward declarations in public headers, engine consumers compile
  with zero exposure to toxic OS macros (`min`, `max`, `near`, `far`, `None`, `Success`).
- **Comprehensive out-of-the-box gamepad and peripheral support.** The engine instantly gains
  precise mapping tables for thousands of DirectInput, XInput, DualSense, Xbox, and Nintendo Switch
  controllers, including rumble, haptics, and IMU motion sensors.
- **Native Wayland, Cocoa, and Win32 modern protocol support.** SDL3 provides battle-tested support
  for Wayland `xdg_shell` protocols, macOS Cocoa run loops, and Win32 Per-Monitor DPI Awareness v2.
- **Deterministic, zero-allocation Game Thread execution.** Converting `SDL_Event` instances into
  trivially copyable POD events on the OS thread preserves lock-free, allocation-free execution on
  the Game Thread ([ADR-0013](./ADR-0013.md), [ADR-0020](./ADR-0020.md)).
- **Seamless RHI swapchain integration via property-based handles.** Extracting native OS handles
  via `SDL_GetWindowProperties` allows the RHI layer ([ADR-0002](./ADR-0002.md)) to construct Vulkan,
  D3D12, or Metal swapchains without platform-specific preprocessor spaghetti.

### Negative

- **External third-party build dependency.** The engine depends on an external C library
  (`gp::thirdparty::sdl3`), requiring pre-compiled binaries or CMake submodule orchestration.
- **Translation overhead across the boundary.** Events must be copied from SDL's internal event queue,
  translated into engine POD structures, and committed to the `SPSCByteRingBuffer`. However, this
  overhead is negligible ($< 15\text{ ns}$ per event) compared to OS syscalls and is masked by the
  dedicated OS polling thread.
- **Upstream dependency synchronization cadence.** Bug fixes in OS-level handling may depend on
  upstream SDL3 releases or custom engine vendor patches.

## Rationale and Cross-References

with the engine's architectural principles: total memory control, modular decomposition, and
deconstructive pedagogy. Students and developers can inspect `source/runtime/hal/sdl3/` to understand
how real-world OS events are sanitized and mapped into lock-free engine streams without being overwhelmed
by raw Win32 or Wayland protocol complexities.
