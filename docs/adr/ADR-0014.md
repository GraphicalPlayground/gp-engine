# ADR-0014: Type-Safe Native Handles Using Tagged Unions over Opaque Void Pointers

> Rejects a generic `void*` for OS window handles (HWND, Wayland surface, etc.) in favor of a
> tagged union (Struct + Enum) to enforce type safety and backend identification at compile time
> and runtime.

![Proposed][badge-proposed]

## Context

In `gp-engine`, the Hardware Abstraction Layer (`HAL`, `source/runtime/hal/`) and the Rendering
Hardware Interface (`RHI`, `source/runtime/rhi/`) sit on opposite sides of a platform boundary. The
HAL manages OS window creation, event dispatch, compositor negotiation, and monitor topology; the
RHI manages graphics devices, pipeline state objects, command queues, and swapchain backbuffers.

To present rendered frames, the RHI swapchain must obtain native window handles from the HAL
window:

- **Direct3D 11 and Direct3D 12:** Require a Win32 window handle (`HWND`) passed to
  `IDXGIFactory2::CreateSwapChainForHwnd`.
- **Metal:** Requires an `NSWindow*` / `CAMetalLayer` pointer on macOS Cocoa, or a `UIWindow*` /
  `MTKView` pointer on iOS UIKit.
- **Vulkan:** Requires different handle combinations depending on the OS and window server:
  - Win32: `VkWin32SurfaceCreateInfoKHR` requires `HWND` and `HINSTANCE`.
  - Wayland (Linux): `VkWaylandSurfaceCreateInfoKHR` requires both `wl_display*` and `wl_surface*`.
  - X11 (Linux): `VkXlibSurfaceCreateInfoKHR` requires `Display*` and `Window`, or
    `VkXcbSurfaceCreateInfoKHR` requires `xcb_connection_t*` and `xcb_window_t`.
  - Android: `VkAndroidSurfaceCreateInfoKHR` requires `ANativeWindow*` and `EGLSurface`.
  - KMS/DRM (headless Linux / embedded consoles): Requires `gbm_device*`, `gbm_surface*`, and a
    DRM file descriptor (`drmFd`).
  - Vivante (embedded automotive / IoT): Requires `EGLNativeDisplayType`, `EGLNativeWindowType`,
    and `EGLSurface`.

### Failure modes of raw `void*`

Many windowing libraries (such as GLFW `glfwGetWin32Window()`, or legacy SDL user pointers) expose
a single untyped pointer:

```cpp
// ANTI-PATTERN: Opaque void* pointer
virtual void* getNativeHandle() const noexcept = 0;
```

This creates four failure modes:

1. **No compile-time or runtime type safety:** Because `void*` is untyped, the compiler cannot catch
   cross-backend mismatches. Passing an X11 `Display*` into a Wayland swapchain constructor or an
   `HWND` into a Cocoa Metal backend compiles without a warning and causes memory corruption or GPU
   driver crashes at startup.
2. **No backend discrimination at runtime:** On Linux, sessions may use native Wayland, XWayland,
   X11, or DRM/KMS. Given a bare `void*`, a Vulkan RHI swapchain cannot tell which windowing
   protocol produced the handle without blind type punning or global state queries.
3. **No composite multi-handle support without heap allocation:** Wayland needs two pointers
   (`wl_display*`, `wl_surface*`), and KMS/DRM needs two pointers and two integers (`gbm_device*`,
   `gbm_surface*`, `drmFd`, `deviceIndex`). A single 64-bit `void*` cannot hold composite handles,
   forcing callers to heap-allocate temporary structs (`new WaylandWindowHandles`), which violates
   our zero-allocation policy ([ADR-0020](./ADR-0020.md)), risks dangling pointers, and causes
   cache misses.
4. **Header pollution and namespace poisoning:** Including `<windows.h>`, `<X11/Xlib.h>`,
   `<wayland-client.h>`, or `<Cocoa/Cocoa.h>` directly in handle headers leaks global macros (`min`,
   `max`, `near`, `far`, `None`, `Success`, `Always`, `Bool`) into every downstream translation unit
   and slows compilation.

## Decision

We introduce `gp::hal::NativeWindowHandle` (in
`source/runtime/hal/base/public/window/NativeWindow.hpp`) as a discriminator-tagged union of
plain-old-data (POD) handle structs.

```text
source/runtime/hal/
  base/
    public/
      window/
        NativeWindow.hpp         <-- Tagged union definition & POD handles
        IWindow.hpp              <-- getNativeHandle() returning NativeWindowHandle
  sdl3/
    private/
      window/
        SDL3Window.cpp           <-- Caches and populates NativeWindowHandle
```

### Physical memory layout

`NativeWindowHandle` pairs a 1-byte enum discriminator (`NativeWindowBackend`) with a union of
platform POD structs backed by `void* _storage[4]`:

```text
+-------------------------------------------------------------------------------------------------+
|                                       NativeWindowHandle                                        |
+-------------------+---------------------+-------------------------------------------------------+
| Offset 0x00       | Offset 0x01 - 0x07  | Offset 0x08 - 0x27 (32 Bytes Backing Union)           |
+-------------------+---------------------+-------------------------------------------------------+
| backend (UInt8)   | Padding (7 Bytes)   | Active Platform POD Storage (_storage[4])             |
|                   | [Alignment Pad]     |                                                       |
|                   |                     | Win32:   [hwnd: 8B]    [hinstance: 8B]   [Pad: 16B]   |
|                   |                     | Cocoa:   [nsWindow: 8B]                  [Pad: 24B]   |
|                   |                     | UIKit:   [uiWindow: 8B] [metalTag: 8B]   [Pad: 16B]   |
|                   |                     | Wayland: [display: 8B]  [surface: 8B]    [Pad: 16B]   |
|                   |                     | X11:     [display: 8B]  [window XID: 8B] [Pad: 16B]   |
|                   |                     | Android: [window: 8B]   [surface: 8B]    [Pad: 16B]   |
|                   |                     | KMSDRM:  [gbmDev: 8B]   [gbmSurf: 8B]    [fd|idx: 8B] |
|                   |                     | Vivante: [display: 8B]  [window: 8B]     [surface: 8B]|
+-------------------+---------------------+-------------------------------------------------------+
| Total Size: 40 Bytes (64-bit Architecture) | Alignment: 8 Bytes | Trivially Copyable POD        |
+-------------------------------------------------------------------------------------------------+
```

### C++ type definitions

```cpp
namespace gp::hal
{

/// @brief Supported native window backends and platform capabilities.
enum class NativeWindowBackend : gp::UInt8
{
    Unknown,
    Win32,     // Windows Desktop
    Cocoa,     // macOS
    UIKit,     // iOS / tvOS
    Wayland,   // Linux (Modern Compositor)
    X11,       // Linux (Legacy X11 Server)
    Android,   // Android NDK
    KMSDRM,    // Linux Console / Embedded Direct-to-Display
    Vivante    // Embedded Linux Vivante Driver
};

namespace detail
{

struct Win32WindowHandles final
{
    void* hwnd;        // HWND
    void* hinstance;   // HINSTANCE
};

struct CocoaWindowHandles final
{
    void* nsWindow;    // NSWindow*
};

struct UIKitWindowHandles final
{
    void* uiWindow;             // UIWindow*
    gp::UIntPtr metalViewTag;   // MTKView Tag queried from SDL3 on iOS
};

struct WaylandWindowHandles final
{
    void* display;   // wl_display*
    void* surface;   // wl_surface*
};

struct X11WindowHandles final
{
    void* display;        // Display*
    gp::UIntPtr window;   // Window (XID integer)
};

struct AndroidWindowHandles final
{
    void* window;    // ANativeWindow*
    void* surface;   // EGLSurface
};

struct KMSDRMWindowHandles final
{
    void* gbmDevice;          // gbm_device*
    void* gbmSurface;         // gbm_surface*
    gp::Int32 drmFd;          // DRM kernel file descriptor
    gp::UInt32 deviceIndex;   // Physical device index
};

struct VivanteWindowHandles final
{
    void* display;   // EGLNativeDisplayType
    void* window;    // EGLNativeWindowType
    void* surface;   // EGLSurface
};

} // namespace detail

struct NativeWindowHandle final
{
public:
    NativeWindowBackend backend{ NativeWindowBackend::Unknown };

    union
    {
        detail::Win32WindowHandles win32;
        detail::CocoaWindowHandles cocoa;
        detail::UIKitWindowHandles uikit;
        detail::WaylandWindowHandles wayland;
        detail::X11WindowHandles x11;
        detail::AndroidWindowHandles android;
        detail::KMSDRMWindowHandles kmsdrm;
        detail::VivanteWindowHandles vivante;
        void* _storage[4];
    };

public:
    constexpr NativeWindowHandle(
        NativeWindowBackend backend = NativeWindowBackend::Unknown) noexcept
        : backend(backend)
        , _storage{}
    {}
};

} // namespace gp::hal
```

### Architectural invariants

1. **Discriminator check before field access:** Every consumer (such as an RHI swapchain
   constructor) must check `backend` before reading union members. Reading an inactive union member
   is undefined behavior in C++ and forbidden by engine rules.

   ```cpp
   // RHI Vulkan Swapchain Initialization for Wayland
   GP_ASSERT(handle.backend == NativeWindowBackend::Wayland);
   VkWaylandSurfaceCreateInfoKHR surfaceInfo{};
   surfaceInfo.sType = VK_STRUCTURE_TYPE_WAYLAND_SURFACE_CREATE_INFO_KHR;
   surfaceInfo.display = static_cast<wl_display*>(handle.wayland.display);
   surfaceInfo.surface = static_cast<wl_surface*>(handle.wayland.surface);
   ```

2. **Zero OS header pollution:** All members in `detail::*WindowHandles` use `void*` or standard
   engine integers (`gp::UIntPtr`, `gp::Int32`, `gp::UInt32`). `NativeWindow.hpp` never includes
   `<windows.h>`, `<X11/Xlib.h>`, or `<wayland-client.h>`. Casts to native OS types live inside
   platform-private `.cpp` files.

3. **Composite handles without heap allocation:** Descriptors up to four 64-bit words (32 bytes)
   fit inline inside `_storage[4]`. Passing handles between HAL, Application, and RHI makes zero
   heap allocations (`new`/`delete`).

4. **Trivially copyable standard-layout POD:** `NativeWindowHandle` satisfies
   `std::is_trivially_copyable_v` and `std::is_standard_layout_v` via `static_assert`. It can be
   passed by value, copied with `memcpy`, and placed inside lock-free event buffers
   ([ADR-0013](./ADR-0013.md), [ADR-0020](./ADR-0020.md)).

## Alternatives Considered

### Option A: Single opaque `void*` pointer (`void* getNativeHandle()`)

Expose a single untyped pointer from `IWindow`, as used in GLFW (`glfwGetWin32Window`) and older
engines.

**Why rejected:** No type safety. A single `void*` cannot tell an X11 window from a Wayland surface
or an `HWND`. Linux Wayland (`wl_display*` + `wl_surface*`) and KMS/DRM (`gbm_device*`,
`gbm_surface*`, `drmFd`) also need multiple handles, forcing heap allocation (`new WaylandData`) on
every query and violating [ADR-0020](./ADR-0020.md).

### Option B: C++ polymorphic class hierarchy (`INativeWindowHandle` with virtual getters)

Define a base interface `INativeWindowHandle` with subclasses (`Win32NativeWindowHandle`,
`WaylandNativeWindowHandle`) using virtual functions:

```cpp
// REJECTED OOP PATTERN
class INativeWindowHandle {
public:
    virtual ~INativeWindowHandle() = default;
    virtual NativeWindowBackend getBackend() const noexcept = 0;
};
```

**Why rejected:** Adds virtual dispatch and forces heap allocations
(`std::unique_ptr<INativeWindowHandle>`), hurting cache locality and frame determinism. Downcasting
to concrete types also requires RTTI (`dynamic_cast`), which is disabled globally in `gp-engine`
(`-fno-rtti` / `/GR-`).

### Option C: Opaque 64-bit integer handle (`uint64_t` / `gp::UInt64`)

Expose an integer identifier (similar to an X11 XID or an OS file descriptor).

**Why rejected:** A 64-bit integer holds only one pointer or scalar. It cannot carry composite
handles where two or three pointers are needed together (Wayland, KMS/DRM) without an auxiliary
lookup table and dynamic registration.

## Consequences

### Positive

- **Type safety and backend discrimination at the HAL-RHI boundary.** Graphics backends check
  `handle.backend` and read named fields (`win32.hwnd`, `wayland.surface`) instead of guessing
  memory layouts.
- **Zero header pollution.** Consumers of `NativeWindow.hpp` never parse `<windows.h>` or
  `<X11/Xlib.h>`, keeping OS macros (`min`, `max`, `None`, `Success`) out of compilation units and
  keeping incremental builds fast.
- **Zero heap allocations for composite handles.** Wayland's display and surface, or KMS/DRM's
  device, surface, and file descriptor, fit inline inside the 32-byte union.
- **Trivially copyable POD semantics.** The handle passes by value and embeds directly in event
  queues without destructor overhead.
- **Multi-backend support on Linux.** A single binary can distinguish Wayland, X11, and KMS/DRM at
  runtime without `#ifdef` branching in consumer code.

### Negative

- **Manual union discipline and assertions.** C++ unions let callers read an inactive member if
  they skip checking `handle.backend`; `GP_ASSERT` catches mismatches in debug builds.
- **Fixed 40-byte size on single-handle platforms.** Platforms needing one pointer (such as Cocoa at
  8 bytes) carry 24 bytes of unused union padding. Because window handles are passed only during
  swapchain creation and resizing, this fixed size is small compared to heap allocation.
- **Casts required at leaf OS/RHI files.** Storing handles as `void*` means concrete `.cpp` files
  (`SDL3Window.cpp`, `VulkanSwapchain.cpp`) must cast back to native types (`static_cast<HWND>`,
  `reinterpret_cast<wl_display*>`).
