# ADR-0014: Type-Safe Native Handles Using Tagged Unions over Opaque Void Pointers

> Rejects the use of a generic `void*` for OS window handles (HWND, Wayland surface, etc.) in favor
> of a tagged union (Struct + Enum) to enforce type-safety and exact backend identification at
> compile/runtime.

![Proposed][badge-proposed]

## Context

In modern modular game engine architecture, the Hardware Abstraction Layer (`HAL`, located in
`source/runtime/hal/`) and the Rendering Hardware Interface (`RHI`, located in
`source/runtime/rhi/`) operate across a critical architectural fault line. The HAL manages operating
system window creation, event dispatching, desktop compositor negotiation, and monitor topology.
The RHI manages graphics device contexts, pipeline state objects, command queues, and swapchain
presentation backbuffers.

To present rendered graphics to a display, the RHI presentation swapchain must obtain low-level
native window handles from the HAL window:

- **Direct3D 11 & Direct3D 12:** Require a Win32 window handle (`HWND`) passed to
  `IDXGIFactory2::CreateSwapChainForHwnd`.
- **Metal:** Requires an `NSWindow*` / `CAMetalLayer` pointer on macOS Cocoa, or a `UIWindow*` /
  `MTKView` pointer on iOS UIKit.
- **Vulkan:** Requires distinct native handle combinations depending on the operating system and
  window server protocol:
  - Win32: `VkWin32SurfaceCreateInfoKHR` requires an `HWND` and its module `HINSTANCE`.
  - Wayland (modern Linux): `VkWaylandSurfaceCreateInfoKHR` requires both a display connection
    `wl_display*` and a compositor surface `wl_surface*`.
  - X11 (legacy Linux): `VkXlibSurfaceCreateInfoKHR` requires a connection pointer `Display*` and an
    integer XID `Window`, or `VkXcbSurfaceCreateInfoKHR` requires `xcb_connection_t*` and
    `xcb_window_t`.
  - Android: `VkAndroidSurfaceCreateInfoKHR` requires an `ANativeWindow*` and an `EGLSurface`.
  - KMS/DRM (headless Linux / direct-to-display embedded consoles): Direct-to-framebuffer
    presentation requires a `gbm_device*`, a `gbm_surface*`, and an open DRM file descriptor
    (`drmFd`).
  - Vivante (embedded automotive / IoT): Requires an `EGLNativeDisplayType`, `EGLNativeWindowType`,
    and `EGLSurface`.

### Common Industry Failure Modes with Raw `void*`

A common pattern across historical game engines and lightweight windowing libraries (e.g., GLFW
`glfwGetWin32Window()`, or legacy SDL querying `void*` user pointers) is to expose a single generic
opaque pointer signature:

```cpp
// ANTI-PATTERN: Opaque void* pointer
virtual void* getNativeHandle() const noexcept = 0;
```

This naive approach introduces four catastrophic engineering failure modes in a production AAA
codebase:

1. **Complete Loss of Compile-Time and Runtime Type Safety:**
   Because `void*` is completely untyped, the compiler cannot diagnose cross-backend mismatches. An
   engineer working on a multi-backend Linux build can accidentally pass an X11 `Display*` into a
   Wayland swapchain constructor or an `HWND` into a Cocoa Metal backend without generating a
   single warning. Such errors manifest as silent memory corruption or GPU driver kernel panics
   during presentation initialization.

2. **Absence of Backend Discrimination in Dynamic Environments:**
   On platforms such as Linux, modern compositors seamlessly transition between native Wayland,
   XWayland compatibility layers, legacy X11 servers, and direct DRM/KMS consoles. A receiving
   Vulkan RHI swapchain given an untyped pointer cannot programmatically query which windowing
   protocol created the underlying handle. Without an explicit discriminator, the RHI must resort to
   blind type punning or ambient global state queries.

3. **Inability to Represent Composite Multi-Handle Platforms without Heap Allocations:**
   Wayland requires *two* distinct pointers (`wl_display*` and `wl_surface*`). KMS/DRM requires *two
   pointers and two integers* (`gbm_device*`, `gbm_surface*`, `drmFd`, `deviceIndex`). A single 64-bit
   `void*` physically cannot represent composite handle topologies. Engines relying on `void*` are
   forced to allocate a temporary heap structure (`new WaylandWindowHandles`), returning a pointer to
   it. This violates our zero-allocation engine philosophy ([ADR-0020](./ADR-0020.md)), creates
   dangling pointer hazards, and triggers cache misses during frame initialization.

4. **Header Pollution and Namespace Poisoning:**
   If a native handle abstraction directly includes `<windows.h>`, `<X11/Xlib.h>`,
   `<wayland-client.h>`, or `<Cocoa/Cocoa.h>`, it pollutes every downstream compilation unit with
   toxic global macros (`min`, `max`, `near`, `far`, `None`, `Success`, `Always`, `Bool`) and
   drastically degrades compile times across the engine.

## Decision

We introduce `gp::hal::NativeWindowHandle` (defined in
`source/runtime/hal/base/public/window/NativeWindow.hpp`) as a discriminator-tagged union of
concrete, plain-old-data (POD) handle structures.

```text
source/runtime/hal/
  base/
    public/
      window/
        NativeWindow.hpp         <-- Tagged union definition & POD handles
        IWindow.hpp              <-- getNativeHandle() returning NativeWindowHandle
  sdl3/
    private/
      window/
        SDL3Window.cpp           <-- Caches and populates NativeWindowHandle
```

### Physical Memory Layout

`NativeWindowHandle` couples a 1-byte enumeration discriminator (`NativeWindowBackend`) with an
overlapping union of platform-specific POD structs backed by a fixed `void* _storage[4]` array:

```text
+-----------------------------------------------------------------------------------------------+
|                                      NativeWindowHandle                                       |
+-------------------+-----------------------+---------------------------------------------------+
|  Offset 0x00      |  Offset 0x01 - 0x07   |  Offset 0x08 - 0x27 (32 Bytes Backing Union)      |
+-------------------+-----------------------+---------------------------------------------------+
|  backend (UInt8)  |  Padding (7 Bytes)    |  Active Platform POD Storage (_storage[4])        |
|                   |  [Alignment Pad]      |                                                   |
|                   |                       |  Win32:   [hwnd: 8B]    [hinstance: 8B]   [Unused: 16B]
|                   |                       |  Cocoa:   [nsWindow: 8B]                  [Unused: 24B]
|                   |                       |  UIKit:   [uiWindow: 8B] [metalTag: 8B]   [Unused: 16B]
|                   |                       |  Wayland: [display: 8B]  [surface: 8B]    [Unused: 16B]
|                   |                       |  X11:     [display: 8B]  [window XID: 8B] [Unused: 16B]
|                   |                       |  Android: [window: 8B]   [surface: 8B]    [Unused: 16B]
|                   |                       |  KMSDRM:  [gbmDev: 8B]   [gbmSurf: 8B]    [drmFd|idx: 8B]
|                   |                       |  Vivante: [display: 8B]  [window: 8B]     [surface: 8B]
+-------------------+-----------------------+---------------------------------------------------+
| Total Size: 40 Bytes (64-bit Architecture) | Alignment: 8 Bytes | Trivially Copyable POD      |
+-----------------------------------------------------------------------------------------------+
```

### C++ Type Definitions

```cpp
namespace gp::hal
{

/// @brief Supported native window backends and platform capabilities.
enum class NativeWindowBackend : gp::UInt8
{
    Unknown,
    Win32,     // Windows Desktop
    Cocoa,     // macOS
    UIKit,     // iOS / tvOS
    Wayland,   // Linux (Modern Compositor)
    X11,       // Linux (Legacy X11 Server)
    Android,   // Android NDK
    KMSDRM,    // Linux Console / Embedded Direct-to-Display
    Vivante    // Embedded Linux Vivante Driver
};

namespace detail
{

struct Win32WindowHandles final
{
    void* hwnd;        // HWND
    void* hinstance;   // HINSTANCE
};

struct CocoaWindowHandles final
{
    void* nsWindow;    // NSWindow*
};

struct UIKitWindowHandles final
{
    void* uiWindow;             // UIWindow*
    gp::UIntPtr metalViewTag;   // MTKView Tag queried from SDL3 on iOS
};

struct WaylandWindowHandles final
{
    void* display;   // wl_display*
    void* surface;   // wl_surface*
};

struct X11WindowHandles final
{
    void* display;        // Display*
    gp::UIntPtr window;   // Window (XID integer)
};

struct AndroidWindowHandles final
{
    void* window;    // ANativeWindow*
    void* surface;   // EGLSurface
};

struct KMSDRMWindowHandles final
{
    void* gbmDevice;          // gbm_device*
    void* gbmSurface;         // gbm_surface*
    gp::Int32 drmFd;          // DRM kernel file descriptor
    gp::UInt32 deviceIndex;   // Physical device index
};

struct VivanteWindowHandles final
{
    void* display;   // EGLNativeDisplayType
    void* window;    // EGLNativeWindowType
    void* surface;   // EGLSurface
};

} // namespace detail

struct NativeWindowHandle final
{
public:
    NativeWindowBackend backend{ NativeWindowBackend::Unknown };

    union
    {
        detail::Win32WindowHandles win32;
        detail::CocoaWindowHandles cocoa;
        detail::UIKitWindowHandles uikit;
        detail::WaylandWindowHandles wayland;
        detail::X11WindowHandles x11;
        detail::AndroidWindowHandles android;
        detail::KMSDRMWindowHandles kmsdrm;
        detail::VivanteWindowHandles vivante;
        void* _storage[4];
    };

public:
    constexpr NativeWindowHandle(
        NativeWindowBackend backend = NativeWindowBackend::Unknown) noexcept
        : backend(backend)
        , _storage{}
    {}
};

} // namespace gp::hal
```

### Architectural Invariants

1. **Strict Discriminator Verification before Field Access:**
   Every consumer of `NativeWindowHandle` (such as an RHI swapchain constructor) must assert or
   validate the `backend` tag before dereferencing union members. Accessing union fields without
   verifying `backend` is undefined behavior in C++ and strictly forbidden by engine guidelines.
   ```cpp
   // RHI Vulkan Swapchain Initialization for Wayland
   GP_ASSERT(handle.backend == NativeWindowBackend::Wayland);
   VkWaylandSurfaceCreateInfoKHR surfaceInfo{};
   surfaceInfo.sType = VK_STRUCTURE_TYPE_WAYLAND_SURFACE_CREATE_INFO_KHR;
   surfaceInfo.display = static_cast<wl_display*>(handle.wayland.display);
   surfaceInfo.surface = static_cast<wl_surface*>(handle.wayland.surface);
   ```

2. **Absolute Zero OS Header Pollution:**
   All native handles stored inside `detail::*WindowHandles` use generic `void*` or standard engine
   integer types (`gp::UIntPtr`, `gp::Int32`, `gp::UInt32`). No OS header (`<windows.h>`,
   `<X11/Xlib.h>`, `<wayland-client.h>`, etc.) is ever included by `NativeWindow.hpp`. Type casts to
   concrete OS types occur strictly inside platform-private `.cpp` implementation files.

3. **Multi-Handle Completeness without Dynamic Memory Allocation:**
   Composite descriptors requiring up to four 64-bit words (32 bytes) are held inline within the
   union storage `_storage[4]`. Passing native handles between HAL, Application, and RHI requires
   zero heap allocations (`new`/`delete`), eliminating memory fragmentation and cache stalls.

4. **Trivially Copyable Standard-Layout POD:**
   `NativeWindowHandle` is verified by static assertions to satisfy `std::is_trivially_copyable_v`
   and `std::is_standard_layout_v`. It can be passed by value, copied via `memcpy`, stored inside
   lock-free event buffers ([ADR-0013](./ADR-0013.md), [ADR-0020](./ADR-0020.md)), and discarded
   with zero destructor overhead.

## Alternatives Considered

### Option A: Single Opaque `void*` Pointer (`void* getNativeHandle()`)

Expose a single untyped pointer from `IWindow`, as used in GLFW (`glfwGetWin32Window`) and early
cross-platform engines.

**Why rejected:** Utter breakdown of type safety. A single `void*` provides zero runtime
identification of whether the pointer represents an X11 window, a Wayland surface, or an HWND.
Furthermore, modern graphics APIs on Linux (Wayland requires `wl_display*` and `wl_surface*`) and
embedded displays (KMS/DRM requires `gbm_device*`, `gbm_surface*`, and `drmFd`) require multiple
handles. A single `void*` cannot express composite handles without forcing the HAL to dynamically
allocate heap memory (`new WaylandData`) on every query, violating [ADR-0020](./ADR-0020.md).

### Option B: C++ Polymorphic Class Hierarchy (`INativeWindowHandle` with Virtual Getters)

Define an abstract base interface `INativeWindowHandle` with concrete subclasses
(`Win32NativeWindowHandle`, `WaylandNativeWindowHandle`) using virtual functions:

```cpp
// REJECTED OOP PATTERN
class INativeWindowHandle {
public:
    virtual ~INativeWindowHandle() = default;
    virtual NativeWindowBackend getBackend() const noexcept = 0;
};
```

**Why rejected:** Introduces unnecessary virtual dispatch overhead and forces heap allocations
(`std::unique_ptr<INativeWindowHandle>`). The HAL window would have to allocate dynamic memory on the
heap, destroying CPU data cache locality and violating deterministic frame budgets. Furthermore,
downcasting from the base interface to concrete types requires RTTI (`dynamic_cast`), which is
disabled globally in `gp-engine` (`-fno-rtti` / `/GR-`).

### Option C: Opaque 64-Bit Integer Handle (`uint64_t` / `gp::UInt64`)

Expose an integer identifier (similar to an X11 XID or an OS file descriptor).

**Why rejected:** On 64-bit architectures, a 64-bit integer can only hold a single pointer or a
single scalar handle. It is completely incompatible with composite multi-handle platforms where two
or three distinct 64-bit pointers must be provided simultaneously (such as Wayland and KMS/DRM).
Packing multiple 64-bit pointers into an integer is physically impossible without an auxiliary
lookup table and dynamic registration overhead.

## Consequences

### Positive

- **Strict type safety and backend discrimination at the HAL-RHI boundary.** Graphics backends can
  programmatically query `handle.backend` and access named, semantic fields (`win32.hwnd`,
  `wayland.surface`) rather than guessing untyped memory offsets.
- **Zero header pollution and fast compilation across all translation units.** Consumers of
  `NativeWindow.hpp` never parse `<windows.h>` or `<X11/Xlib.h>`, preventing namespace poisoning
  from toxic macros (`min`, `max`, `None`, `Success`) and minimizing incremental compile times.
- **Guaranteed zero heap allocations for composite multi-handle descriptors.** Composite native
  handles (such as Wayland's display and surface, or KMS/DRM's device, surface, and file descriptor)
  are accommodated inline within fixed 32-byte union storage without invoking `malloc` or `new`.
- **Trivially copyable standard-layout POD ergonomics.** The handle conforms to standard layout rules,
  enabling pass-by-value, memory copying, and trivial embedding within event queues and thread
  boundaries without destructor execution overhead.
- **Seamless multi-backend adaptability for modern Linux compositors.** The RHI can cleanly distinguish
  between Wayland, legacy X11, and direct-to-display KMS/DRM within a single unified executable,
  enabling robust fallback chains without conditional compilation branching.

### Negative

- **Manual union field discipline and active discriminator assertions required.** C++ unions allow
  accessing inactive member structs if an engineer fails to check `handle.backend`; runtime assertions
  (`GP_ASSERT`) are necessary to enforce invariant correctness in debug builds.
- **Fixed storage footprint overhead on single-handle platforms.** On platforms that only require a
  single pointer (e.g. Cocoa with 8 bytes), the 40-byte handle carries 24 bytes of unused union
  padding. However, because window handles are passed infrequently (e.g., during swapchain creation
  and resizing), this fixed cost is negligible compared to heap allocation overhead.
- **Internal `reinterpret_cast` required at leaf OS/RHI translation units.** Because handle members
  are stored as `void*` to prevent header contamination, the concrete platform files (e.g.
  `SDL3Window.cpp` or `VulkanSwapchain.cpp`) must explicitly cast `void*` back to native types (e.g.
  `static_cast<HWND>` or `reinterpret_cast<wl_display*>`).
