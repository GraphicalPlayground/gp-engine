# ADR-0035: Scaled Radial 2D Thumbstick Deadzones and Hysteresis-Gated Active Device Switching

> Applying independent 1D axial deadzones to analog thumbsticks creates a cardinal
> "cross-snapping" artifact that degrades 360-degree character and camera movement, while raw
> analog potentiometer noise causes UI prompts to flicker between Keyboard/Mouse and Gamepad icons.
> The input system enforces 2D Scaled Radial Deadzones
> ($\vec{v}_{\text{out}} = \hat{v} \cdot \text{remap}(\Vert{}\vec{v}\Vert{}, dz_{\text{in}}, dz_{\text{out}})$)
> on dual-axis thumbsticks, 1D axial deadzones on triggers, and requires analog inputs to exceed
> an intentional actuation threshold before switching the active `InputDeviceType`.
<!-- markdownlint-enable MD013 -->

![Proposed][badge-proposed]

## Context

Analog thumbsticks and triggers translate physical mechanical displacement into electrical
signals. On modern gamepads, thumbsticks use two potentiometers or Hall effect sensors
oriented at 90 degrees around a central gimbal, while triggers use single potentiometers
or Hall sensors along an independent linear axis. Physical springs pull the thumbstick back
toward its geometric center when released.

Mechanical springs and gimbal housings exhibit physical wear, manufacturing tolerances,
and mechanical hysteresis. As a result, released thumbsticks rarely return to absolute zero
electrical resistance. Standard gamepads exhibit resting sensor drift between 5% and 15%
deflection. Without deadzone filtering, an untouched controller lying on a desk continuously
emits non-zero coordinate pairs, causing characters to creep across the ground or cameras
to rotate uncontrollably.

### Failure Modes of 1D Axial Deadzones on 2D Sticks

A common naive approach applies independent 1D scalar deadzones to the X and Y axes:

```cpp
if (std::abs(rawX) < deadzone) rawX = 0.0f;
if (std::abs(rawY) < deadzone) rawY = 0.0f;
```

While simple to implement, independent 1D axial filtering introduces three severe geometric
distortions in dual-axis stick coordinates:

1. **Cardinal Cross-Snapping:** Independent axial clamping zeroes whichever coordinate falls
   below the deadzone threshold while leaving the orthogonal coordinate unmodified. If a
   player deflects a thumbstick to `(0.08, 0.50)` with a deadzone of `0.12`, the input angle
   is $80.9^\circ$. The axial filter clamps `rawX` to `0.0`, snapping the output vector to
   `(0.0, 0.50)` at an angle of $90.0^\circ$. Near cardinal axes (north, south, east, west),
   fine diagonal deflections snap artificially to pure horizontal or pure vertical lines.
   This destroys subtle aiming adjustments for shooter cameras and introduces jagged
   steering steps into vehicular or character locomotion.

2. **Cross-Shaped Deadzone Geometry:** Independent axial filtering creates a non-responsive
   region shaped like a cross. Along cardinal directions, stick motion registers once
   deflection exceeds `deadzone`. Along a 45-degree diagonal, both axes must simultaneously
   exceed `deadzone`, requiring a physical stick displacement magnitude of
   $\sqrt{dz^2 + dz^2} = dz\sqrt{2} \approx 1.414 \cdot dz$. Diagonal activation requires
   roughly 41.4% more mechanical force and displacement than cardinal activation.

3. **Corner Over-Magnitude:** In an axial square space, diagonal corners reach coordinates
   `(+1.0, +1.0)`, producing a vector magnitude of $\sqrt{1^2 + 1^2} \approx 1.414$. Unless
   explicitly clipped or normalized to a unit circle, characters moving diagonally travel
   approximately 41.4% faster than characters moving in cardinal directions.

### Potentiometer Jitter and Active Device Flickering

Modern games present dynamic UI button prompts that update to reflect the player's active
input peripheral (for example, displaying `[E] Interact` when using a keyboard and mouse, or
`[(X)] Interact` when holding a gamepad). The engine coordinates this by tracking an active
`InputDeviceType`.

Analog potentiometers on a resting controller continually fluctuate by minute increments
due to thermal variations and electrical sensor noise. If any non-zero analog coordinate
immediately changes the active device to `InputDeviceType::Gamepad`, resting stick jitter
continually overrides keyboard or mouse input. When a player attempts to aim with the mouse
or navigate a menu with a keyboard, background noise from an attached controller flips the
active device back to gamepad, causing UI glyphs to flicker between keyboard and gamepad
icons on every frame.

## Decision

We introduce 2D Scaled Radial Deadzones for dual-axis thumbsticks, 1D axial deadzones for
analog triggers, and hysteresis-gated active device switching within the Hardware Abstraction
Layer (`gp::hal::input`).

### 2D Scaled Radial Deadzone Algorithm

Dual-axis thumbsticks (left stick, right stick) are evaluated as unified 2D vectors rather
than isolated scalar axes. The filtering algorithm (`filterRadial` in `GenericGamepad.hpp`)
operates in four mathematical stages:

1. **Squared Magnitude Rejection:** Given raw coordinates $(x, y)$, calculate squared
   magnitude $m^2 = x^2 + y^2$. If $m^2 \le \text{innerDeadzone}^2$, return $(0, 0)$
   immediately. This rejects resting hardware drift without computing a square root.

2. **Constexpr Square Root:** If $m^2 > \text{innerDeadzone}^2$, calculate vector magnitude
   $m = \text{fastSqrt}(m^2)$. The engine computes this using an IEEE-754 bit-cast initial
   seed approximation followed by three iterations of Newton-Raphson refinement:

   $$x_{n+1} = \frac{1}{2}\left(x_n + \frac{S}{x_n}\right)$$

   This provides a fast, `constexpr` floating-point square root that complies with our
   STL-free compilation directives and avoids linking external runtime math libraries.

3. **Radial Range Remapping:** Remap vector magnitude linearly from the active range
   $[\text{innerDeadzone}, \text{outerDeadzone}]$ onto the normalized interval $[0.0, 1.0]$:

   <!-- markdownlint-disable MD013 -->
   $$
   \text{norm} = \min\left(1.0f, \frac{m - \text{innerDeadzone}}{\text{outerDeadzone} - \text{innerDeadzone}}\right)
   $$
   <!-- markdownlint-enable MD013 -->

   The outer deadzone threshold (default `0.95f`) ensures that mechanical stick travel
   reaches full saturation $(1.0)$ even if controller shell tolerances prevent the gimbal
   from reaching physical extremity across all 360 degrees.

4. **Angle-Preserving Rescaling:** Scale the original raw vector by the normalized scalar
   ratio without altering its angular orientation:

   <!-- markdownlint-disable MD013 -->
   $$
   \vec{v}_{\text{out}} = \frac{\text{norm}}{m} \vec{v} =
   \begin{pmatrix} \frac{\text{norm}}{m} x \\ \frac{\text{norm}}{m} y \end{pmatrix}
   $$

   Because both coordinates share the uniform scalar multiplier $\frac{\text{norm}}{m}$,
   the direction angle $\theta = \operatorname{atan2}(y, x)$ remains strictly identical
   before and after filtering:

   $$
   \theta_{\text{out}} = \operatorname{atan2}\left(\frac{\text{norm}}{m} y, \frac{\text{norm}}{m} x\right)
   = \operatorname{atan2}(y, x) = \theta_{\text{in}}
   $$
   <!-- markdownlint-enable MD013 -->

### 1D Axial Deadzone for Analog Triggers

Gamepad triggers (`LeftTrigger`, `RightTrigger`) represent single-axis potentiometers with
readings between $0.0$ and $1.0$. Because triggers possess no orthogonal axis, they do not
suffer from cross-snapping or angular distortion.

Triggers use 1D axial deadzones (`filterAxial` in `GenericGamepad.hpp`) with default
parameters `innerDeadzone = 0.05f` and `outerDeadzone = 0.98f`:

<!-- markdownlint-disable MD013 -->
$$
\text{val}_{\text{out}} = \text{sign} \cdot \min\left(
  1.0f,
  \frac{|\text{raw}| - \text{innerDeadzone}}{\text{outerDeadzone} - \text{innerDeadzone}}
\right)
$$
<!-- markdownlint-enable MD013 -->

Inputs below `0.05f` are clamped to `0.0f` to prevent unintended firing or braking when
resting fingers touch the triggers. Inputs at or above `0.98f` saturate to `1.0f`, ensuring
full actuation before physical bottom-out.

### Hysteresis-Gated Active Device Switching

To eliminate UI icon flickering caused by potentiometer drift or resting vibrations,
`GenericInputSystem` segregates device transitions into discrete and continuous pathways:

- **Discrete Events (Immediate Switching):** Keyboard key presses (`KeyState::Pressed`),
  mouse button clicks (`MouseButton::Pressed`), mouse wheel scrolling, gamepad button
  presses (`GamepadAction::ButtonChanged`), and D-pad hat switches switch `m_activeDeviceType`
  immediately upon arrival.

- **Continuous Analog Stick Events (Gated by Actuation Threshold):** Incoming
  `GamepadAction::AxisMoved` events switch `m_activeDeviceType` to `Gamepad` only if
  either thumbstick exceeds the actuation threshold:

  <!-- markdownlint-disable MD013 -->
  $$
  \Vert\vec{v}_{\text{left}}\Vert^2 \ge kDeviceSwitchStickThreshold^2
  \quad\text{or}\quad
  \Vert\vec{v}_{\text{right}}\Vert^2 \ge kDeviceSwitchStickThreshold^2
  $$
  <!-- markdownlint-enable MD013 -->

  where `kDeviceSwitchStickThreshold = 0.25f` (squared threshold `0.0625f`), or if an analog
  trigger reading meets or exceeds `0.25f`.

- **Continuous Mouse Motion Events (Gated by Distance Threshold):** Mouse displacement
  packets (`MouseAction::Moved`) switch `m_activeDeviceType` to `Mouse` only if squared
  pixel movement meets or exceeds `kDeviceSwitchMouseThresholdSq = 4.0f` pixels
  ($\Delta x^2 + \Delta y^2 \ge 4.0$). Micro-vibrations from desk bumps are discarded.

### Implementation Mechanics

<!-- markdownlint-disable MD013 -->
```cpp
[[nodiscard]] GP_FORCEINLINE_HINT static constexpr gp::Float32 fastSqrt(gp::Float32 val) noexcept
{
    if (val <= 0.0f) [[unlikely]]
    {
        return 0.0f;
    }
    gp::UInt32 bits = __builtin_bit_cast(gp::UInt32, val);
    bits = (bits >> 1u) + 0x1FC00000u;
    gp::Float32 guess = __builtin_bit_cast(gp::Float32, bits);
    guess = 0.5f * (guess + (val / guess));
    guess = 0.5f * (guess + (val / guess));
    guess = 0.5f * (guess + (val / guess));
    return guess;
}

[[nodiscard]] static constexpr Stick2D
    filterRadial(gp::Float32 rawX, gp::Float32 rawY, const AnalogDeadzoneConfig& cfg) noexcept
{
    if (cfg.mode == DeadzoneMode::None)
    {
        return Stick2D(rawX, rawY);
    }
    if (cfg.mode == DeadzoneMode::Axial)
    {
        return Stick2D(filterAxial(rawX, cfg), filterAxial(rawY, cfg));
    }

    const gp::Float32 magSq = (rawX * rawX) + (rawY * rawY);
    if (magSq <= (cfg.innerDeadzone * cfg.innerDeadzone))
    {
        return Stick2D(0.0f, 0.0f);
    }

    const gp::Float32 mag = fastSqrt(magSq);
    if (mag <= 1e-6f) [[unlikely]]
    {
        return Stick2D(0.0f, 0.0f);
    }

    const gp::Float32 range = cfg.outerDeadzone - cfg.innerDeadzone;
    gp::Float32 norm = (range > 1e-5f) ? ((mag - cfg.innerDeadzone) / range) : 1.0f;
    if (norm > 1.0f)
    {
        norm = 1.0f;
    }
    const gp::Float32 scale = norm / mag;
    return Stick2D(rawX * scale, rawY * scale);
}
```
<!-- markdownlint-enable MD013 -->

### Architectural Invariants

1. **Radial Direction Invariance:** Thumbstick deadzone filtering scales vector magnitude while
   preserving angular orientation. The output vector angle $\theta = \operatorname{atan2}(y, x)$
   matches the physical input angle across all 360 degrees.
2. **Boundary Continuity and Clamping:** Output magnitude is continuous at the deadzone
   boundary, smoothly scaling from $0.0f$ at `innerDeadzone` to $1.0f$ at `outerDeadzone`.
   Maximum vector length never exceeds $1.0f$, eliminating diagonal over-speed artifacts.
3. **Axis-Specific Geometry Decoupling:** Dual-axis thumbsticks enforce 2D scaled radial
   filtering, while single-axis triggers enforce 1D axial filtering. Subsystems configure
   deadzones independently through `AnalogDeadzoneConfig`.
4. **Hysteresis-Gated Device Switching:** Discrete input transitions trigger immediate active
   device type changes, while continuous analog streams (stick axes, mouse motion) switch the
   active device only when magnitude exceeds intentional physical thresholds.

### Architecture Comparison Matrix

<!-- markdownlint-disable MD013 -->
| Property | 1D Axial Deadzone | Simple Radial Deadzone | 2D Scaled Radial Deadzone |
| :--- | :--- | :--- | :--- |
| **Angle Preservation** | Distorts angles near cardinals | Preserves true stick angle | Preserves true stick angle |
| **Cardinal Cross-Snapping** | Severe (one axis clamped to 0) | None (radial boundary) | None (radial boundary) |
| **Boundary Continuity** | Discontinuous jump at threshold | Discontinuous jump at threshold | Smooth gradient starting at 0.0 |
| **Diagonal Magnitude** | Unbounded up to $\sqrt{2} \approx 1.414$ | Clamped to unit radius (1.0) | Clamped to unit radius (1.0) |
| **Deadzone Geometry** | Square or cross | True circle ($r = dz_{\text{in}}$) | True circle ($r = dz_{\text{in}}$) |
| **Outer Saturation Zone** | Corner clipping required | Abrupt saturation at perimeter | Smooth remapping to 1.0 at $dz_{\text{out}}$ |

## Alternatives Considered

### Option A: Simple 1D Axial Deadzone (`filterAxial` on X and Y)

Evaluate each axis independently using scalar thresholds.

**Why rejected:** Causes cardinal cross-snapping, where inputs near the horizontal or
vertical axis snap artificially to pure cardinal directions. Creates a cross-shaped
deadzone requiring 41.4% higher displacement along diagonals, and allows diagonal vector
magnitudes up to 1.414 unless secondary clipping is applied.

### Option B: Unscaled Radial Deadzone (Zeroing Below Radial Threshold)

Zero the 2D vector when $\Vert\vec{v}\Vert < dz_{\text{in}}$, but pass the raw vector
unmodified when above the threshold.

**Why rejected:** Introduces a velocity step discontinuity at the deadzone boundary. As soon
as the stick crosses `innerDeadzone` (for example, `0.12f`), output velocity jumps instantly
from `0.0f` to `0.12f`. This sudden jerk prevents fine-grained slow-speed locomotion, such as
stealth crouching or gentle camera micro-adjustments.

### Option C: Immediate Device Switching on Any Non-Zero Analog Value

Switch `m_activeDeviceType` to `Gamepad` or `Mouse` whenever any axis or delta is non-zero.

**Why rejected:** Potentiometer noise on resting gamepads and minute vibrations transmitted
through desks cause continuous device ping-ponging. UI button prompts flicker repeatedly
between keyboard/mouse and gamepad icons, creating visual distraction and redundant UI
rebuilding on every frame.

## Consequences

### Positive

- **Preserves 360-degree directional fidelity.** Radial vector scaling maintains the true
  physical angle of the stick, eliminating unnatural snapping along cardinal axes and
  enabling smooth omnidirectional movement and aiming.
- **Continuous velocity response curves.** Remapping the active range from zero at the inner
  deadzone to unity at the outer deadzone prevents abrupt velocity jumps, giving players fine
  control over subtle inputs.
- **Stable active device prompt resolution.** Gating continuous analog transitions behind
  hysteresis thresholds prevents UI glyph flickering caused by electrical noise and resting
  controller drift.
- **Zero dynamic memory allocation.** Mathematical filtering and active device state checks
  execute entirely in register memory using inline `constexpr` arithmetic without allocating
  heap storage or invoking OS calls.

### Negative

- **Marginally higher computational cost.** Computing radial magnitude requires a squared
  magnitude check and a Newton-Raphson square root for active deflections, which is more
  expensive than two independent scalar floating-point comparisons.
- **Device-specific calibration needs.** Controllers with non-standard mechanical stops or
  unusually worn potentiometers may require custom inner and outer thresholds to achieve
  optimal response.
