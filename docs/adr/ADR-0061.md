# ADR-0061: Hybrid Static/Dynamic Module Manager and Per-Module Shadow Malloc Binding

> Establishes `gp::modules` (`IModule`, `ModuleManager`, `GP_IMPLEMENT_MODULE`) inside `gp::core`
> to orchestrate dynamic (`.dll`/`.so`/`.dylib`) and monolithic static engine modules. It enforces
> an entry-point ABI handshake (`gpInitializeModule`) that synchronizes each shared library's
> image-local `g_localShadowMalloc` pointer prior to module allocation, injects per-DLL
> `operator new`/`delete` overrides, and executes lock-free-loader, reverse-LIFO teardown
> (amending [ADR-0041](./ADR-0041.md)).

![Accepted][badge-accepted]

## Context

[ADR-0002](./ADR-0002.md) and [ADR-0007](./ADR-0007.md) mandate that pluralistic engine subsystems
(`rhi/`, `audio/`, `physics/`, `parser/`) compile their concrete implementations (`rhi/d3d12`,
`rhi/vulkan`, `audio/openal`, etc.) as independent shared libraries linked via
`gpAddDependency(DYNAMIC ...)`. While `gp::platform::SharedLibrary` provides low-level OS library
handles (`LoadLibraryW` / `dlopen`) and symbol resolution (`GetProcAddress` / `dlsym`), raw OS
dynamic loading fails to solve five architectural challenges in a C++23 game engine:

1. **Image-Local Shadow Allocator Isolation Across DLL Boundaries:**
   [ADR-0042](./ADR-0042.md) defines `gp::memory::detail::g_localShadowMalloc` in
   `GlobalMemory.hpp` (`#if !GP_IS_MONOLITHIC`) so `getInlineMalloc()` and `HeapAllocator` can
   allocate memory without traversing the Windows PE Import Address Table (IAT) or ELF PLT/GOT on
   every call. Because `g_localShadowMalloc` has hidden per-image linkage (`-fvisibility=hidden` on
   ELF/Mach-O and unexported COMDAT on Windows PE), each compiled `.dll`/`.so`/`.dylib` contains its
   own distinct `.bss` copy of `g_localShadowMalloc`. Writing to `g_localShadowMalloc` from code
   compiled inside `gp-core` only updates `gp-core`'s copy, leaving `g_localShadowMalloc == nullptr`
   inside `gp-rhi-d3d12.dll` or `gp-audio-openal.dll`.
2. **Cross-DLL CRT Heap Mismatch (`operator new` / `operator delete`):**
   On Windows and modular POSIX builds, each shared library links its own local `operator new` and
   `operator delete` unless explicitly overridden inside that binary. If an object is allocated via
   `new` inside a backend DLL and destroyed via `delete` in the host module (or vice versa) without
   per-module operator overrides wired to `gp::memory::Malloc`, the deallocation hits the wrong
   heap and corrupts memory.
3. **Upward Dependency DAG Violation ([ADR-0041](./ADR-0041.md) Amendment):**
   [ADR-0041](./ADR-0041.md) informally listed `ModuleManager` under `gp::application`. However,
   pluralistic `base/` modules (`rhi/base`, `audio/base`) and their backends depend exclusively on
   `gp::core` and never on `gp::application`. If `IModule` and `ModuleManager` lived in
   `gp::application`, `rhi/base` and `audio/base` could not load their dynamic backends without
   creating a circular dependency (`gp::rhi` $\leftrightarrow$ `gp::application`).
4. **Monolithic vs. Modular Build Divergence (`GP_IS_MONOLITHIC`):**
   In development builds (`GP_IS_MONOLITHIC == 0`), modules compile to `.dll`/`.so`/`.dylib` files
   loaded at runtime. In monolithic shipping builds (`GP_IS_MONOLITHIC == 1`), GPBT compiles all
   modules as static libraries linked into one executable. Subsystem factories must use one unified
   `ModuleManager::loadModule()` call across both build modes without `#if GP_IS_MONOLITHIC`
   branches in consumer code.
5. **OS Loader-Lock Deadlocks, Recursive Loads, and Teardown Order:**
   Holding an internal registry mutex across `SharedLibrary::getHandle()` or `onStartupModule()`
   causes AB-BA deadlocks with the OS loader lock (`LdrpLoaderLock`) and prevents a module's
   `onStartupModule()` from loading a dependent module. At engine exit, unloading modules in
   arbitrary hash-table order destroys dependencies while higher-level modules still reference them.

## Decision

We introduce the `gp::modules` subsystem inside `gp::core` (`source/runtime/core/public/modules/`),
amending [ADR-0041](./ADR-0041.md)'s responsibility table so every engine tier (`gp::core`,
`gp::hal`, `gp::rhi`, `gp::audio`, `gp::application`) can implement `IModule` and load backend
modules without upward coupling.

### 1. Physical Module & Header Granularity Layout

Following [ADR-0001](./ADR-0001.md), [ADR-0006](./ADR-0006.md), and the **Header Granularity Law**,
the module subsystem is decomposed by architectural role:

```text
source/runtime/core/
├── public/
│   ├── memory/
│   │   ├── GlobalMemory.hpp        • setupLocalShadowMalloc(), resetLocalShadowMalloc(),
│   │   │                             isLocalShadowMallocInitialized(), getActiveMalloc()
│   │   └── MemoryOverrides.hpp     • Routes operator new/delete via getActiveMalloc()
│   └── modules/
│       ├── ModuleForward.hpp       • Forward declarations for gp::modules types
│       ├── ModuleEnums.hpp         • ModuleLoadResult, ModuleUnloadResult, ModuleState,
│       │                             ModuleFlags, ModuleChangeReason, ModuleShutdownPhase
│       ├── ModuleTypes.hpp         • ABI constants, ModuleInitContext, ModuleInitHandshake,
│       │                             entry-point function pointers, observer delegates
│       ├── ModuleDesc.hpp          • ModuleDesc and ModuleStatusView POD descriptors
│       ├── IModule.hpp             • Pure abstract IModule contract & DefaultModuleImpl
│       ├── ModuleBoilerplate.hpp   • Inlined shadow-Malloc handshake, static registrant
│       │                             list, and GP_PER_MODULE_MEMORY_BOILERPLATE
│       ├── ModuleMacros.hpp        • GP_IMPLEMENT_MODULE, GP_IMPLEMENT_GAME_MODULE,
│       │                             GP_IMPLEMENT_DEFAULT_MODULE, GP_REGISTER_STATIC_MODULE
│       ├── ModuleManager.hpp       • Fixed-capacity .bss ModuleManager registry
│       └── Modules.hpp             • Umbrella public convenience header
├── private/
│   ├── memory/
│   │   └── GlobalMemory.cpp        • Synchronizes gp-core shadow Malloc on init
│   └── modules/
│       └── ModuleManager.cpp       • Dynamic/static loading, cycle checks, LIFO teardown
└── tests/
    └── modules/
        └── ModuleManager.tests.cpp • GTest suite for ABI handshake, shadow Malloc, cycles,
                                      hot-reload, LIFO teardown, and thread concurrency
```

### 2. Entry-Point ABI Handshake and Local Shadow `Malloc` Synchronization

```text
  [ ModuleManager::loadModule("rhi/d3d12") ]  (Inside gp-core)
                        |
  1. Normalizes "rhi/d3d12" -> canonical gp::Name("rhi-d3d12")
     Formats GPBT library name -> "gp-rhi-d3d12" (.dll / .so / .dylib)
  2. Marks slot ModuleState::Loading (records calling ThreadId) & RELEASES lock
  3. Calls SharedLibrary::getHandle("gp-rhi-d3d12") & getExport("gpInitializeModule")
  4. Populates ModuleInitContext { kModuleAbiMagic, kModuleAbiVersion,
                                   buildFlags, gp::memory::getGlobalMalloc() }
                        |
                        v  (Crosses C ABI boundary into target DLL's .text segment)
  [ extern "C" GP_DLLEXPORT gpInitializeModule(ctx, outHandshake) ]  (Inside target DLL)
                        |
  5. Verifies ctx->abiMagic, ctx->abiVersion, and ctx->buildFlags
  6. Calls GP_FORCEINLINE setupLocalShadowMalloc(ctx->globalMalloc):
       -> Writes directly to target DLL's own .bss detail::g_localShadowMalloc!
  7. Allocates & constructs ModuleClass via bound shadow Malloc
  8. Returns ModuleInitHandshake { moduleInstance, boundShadowMalloc }
                        |
                        v  (Returns to ModuleManager in gp-core)
  9. Invokes moduleInstance->onStartupModule() outside registry lock
 10. Acquires lock, transitions slot to ModuleState::Loaded, assigns monotonic
     loadOrder, releases lock, and broadcasts ModuleChangeReason::Loaded
```

### 3. Architectural Invariants

1. **In-Module Shadow `Malloc` Binding Before Any Module Heap Allocation:**
   `gp::memory::setupLocalShadowMalloc(Malloc* hostMalloc)` in `GlobalMemory.hpp` is marked
   `GP_FORCEINLINE_HINT`. When invoked inside `executeModuleEntryHandshake<InModuleClass>()` (which
   is instantiated inside the target module's `.cpp` via `GP_IMPLEMENT_MODULE`), the assignment
   `detail::g_localShadowMalloc = resolved;` compiles against the target DLL's own `.bss` segment.
   The handshake binds `g_localShadowMalloc` *before* allocating `InModuleClass` or running
   `onStartupModule()`, and `executeModuleExitTeardown<InModuleClass>()` destroys the instance via
   the module's `gpDestroyModule` export and calls `resetLocalShadowMalloc()` prior to
   `SharedLibrary::freeHandle()`.
2. **Per-Module `operator new` / `operator delete` Injection (`GP_PER_MODULE_MEMORY_BOILERPLATE`):**
   In modular builds (`!GP_IS_MONOLITHIC`), `GP_IMPLEMENT_MODULE` injects
   `GP_OVERLOAD_OPERATOR_NEW_AND_DELETE` into every non-`core` module (`!defined(GP_CORE_EXPORTS)`).
   `MemoryOverrides.hpp` routes all 24 C++23 `operator new` and `operator delete` overloads through
   `gp::memory::getActiveMalloc()`, which checks `getInlineMalloc()` (`g_localShadowMalloc`) first
   with `[[likely]]` and falls back to `getGlobalMalloc()` for pre-entry static constructors.
3. **Compile-Time & Build-Configuration ABI Verification:**
   `ModuleInitContext` embeds `kModuleAbiMagic` (`0x47504D4F44554C45ULL`), `kModuleAbiVersion`
   (`1`), and `buildFlags` (encoding `Debug`/`Development`/`Profile`/`Shipping` and
   `GP_IS_MONOLITHIC`). If a stale DLL compiled under a mismatched configuration or ABI version is
   loaded, `gpInitializeModule` rejects it with `ModuleLoadResult::AbiVersionMismatch` before
   touching the heap or invoking virtual methods.
4. **Seamless Modular and Monolithic Parity (`GP_IS_MONOLITHIC`):**
   In modular builds (`GP_IS_MONOLITHIC == 0`), `GP_IMPLEMENT_MODULE(ModuleClass, Name)` exports
   `gpInitializeModule` and `gpDestroyModule`. In monolithic builds (`GP_IS_MONOLITHIC == 1`), it
   expands to `GP_REGISTER_STATIC_MODULE(ModuleClass, Name)`, linking a zero-allocation
   `StaticModuleRegistrantNode` into a `.bss` intrusive list drained by `ModuleManager`. In both
   modes, `ModuleManager::loadModule("rhi/d3d12")` normalizes `"rhi/d3d12"`, `"rhi_d3d12"`,
   `"rhi-d3d12"`, and `"gp-rhi-d3d12"` to the same canonical identifier (`"rhi-d3d12"`).
5. **Lock-Free OS Loader Execution & Deterministic Cycle Detection:**
   `ModuleManager` never holds its `CacheAlignedSharedMutex` across `SharedLibrary::getHandle()`,
   `SharedLibrary::freeHandle()`, `gpInitializeModule()`, `onStartupModule()`,
   `onShutdownModule()`, or `onModuleChanged` delegate broadcasts. While a slot is in
   `ModuleState::Loading`, its `loadingThreadId` is recorded; if a nested `loadModule()` on the
   same thread targets a module already in `ModuleState::Loading`, `ModuleManager` immediately
   returns `ModuleLoadResult::CircularDependency`.
6. **Strict Reverse-LIFO Shutdown Ordering & `gp::Application` Lifecycle Wiring:**
   Every successfully loaded module receives a post-order monotonic `loadOrder` ticket after
   `onStartupModule()` completes. `gp::Application` loads `ApplicationDesc::startupModules` (and
   CLI `-load-module` / `-modules` overrides) before `onInitialize()`, and calls
   `ModuleManager::unloadAllModules()` during `shutdownInternal()` *after* `JobSystem` workers and
   named-thread queues drain, but *before* frame arenas, HAL, logging, and VFS shut down.

## Alternatives Considered

### Option A: Pure C99 Function-Pointer `ApiRegistry` Table (Our Machinery / BitSquid)

Replace C++ `IModule` interfaces with a central hash table mapping `(apiName, version)` to plain C
structs of function pointers populated via `gpLoadPlugin(ApiRegistry*, bool load)`.

**Why rejected:** [ADR-0002](./ADR-0002.md), [ADR-0007](./ADR-0007.md), [ADR-0011](./ADR-0011.md),
and [ADR-0045](./ADR-0045.md) establish C++23 pure abstract interfaces (`IRHIDevice`,
`IApplicationBackend`, `IConsoleManager`) and `IntrusiveRefCounted` objects as `gp-engine`'s
subsystem boundary. Wrapping every C++ interface method inside parallel C function-pointer tables
duplicates API surfaces and degrades pedagogical clarity.

### Option B: Global System Environment Table Injection (`SSystemGlobalEnvironment* gEnv`)

Follow CryEngine by passing a monolithic `SystemGlobalEnvironment` struct containing pointers to
every engine subsystem (`Malloc*`, `IRHIDevice*`, `IAudioDevice*`, `IConsoleManager*`) into each
DLL's `ModuleInitISystem()` entry point.

**Why rejected:** Coupling `gp::core` to a global environment table that forward-declares upper
subsystems violates [ADR-0001](./ADR-0001.md) and [ADR-0041](./ADR-0041.md)'s upward DAG and turns
explicit module dependencies into hidden global state.

### Option C: Source-Style `CreateInterface(const char* versionName, int* outCode)` Export Only

Export a stateless factory function from each DLL without a central `ModuleManager` lifecycle
registry or bundled memory handshake.

**Why rejected:** A bare factory symbol lacks centralized tracking of loaded module lifetimes,
reverse-LIFO teardown ordering, circular dependency detection, and atomic binding of
`g_localShadowMalloc` prior to module object construction.

## Consequences

### Positive

- **Zero-IAT Local Shadow `Malloc` Across Dynamic Modules.** Every DLL loaded through
  `ModuleManager` binds its image-local `g_localShadowMalloc` inside `gpInitializeModule` before
  constructing its `IModule` instance, enabling single-instruction `getInlineMalloc()` reads across
  all allocations in that DLL.
- **Cross-DLL `new`/`delete` Heap Safety.** `GP_IMPLEMENT_MODULE` automatically injects
  `GP_OVERLOAD_OPERATOR_NEW_AND_DELETE` wired to `getActiveMalloc()`, guaranteeing that objects
  allocated in one DLL and freed in another use the same `gp::memory::Malloc` backend.
- **100% Monolithic and Modular Source Compatibility.** Subsystems (`rhi/base`, `audio/base`,
  `application`) invoke the exact same `ModuleManager::get().loadModule(...)` API whether compiled
  as dynamic plugins (`GP_IS_MONOLITHIC == 0`) or a single static binary (`GP_IS_MONOLITHIC == 1`).
- **Deadlock-Free Recursive Module Loading.** Releasing the registry mutex during OS library
  loading and `onStartupModule()` prevents `LdrpLoaderLock` inversions and catches recursive cycles
  deterministically via `ModuleLoadResult::CircularDependency`.

### Negative

- **Mandatory Entry-Point Macro per Module.** Every dynamic or static engine module must include
  one `GP_IMPLEMENT_MODULE(ModuleClass, "module/name")` invocation in a private `.cpp` file.
- **Fixed-Capacity Registry Table.** `ModuleManager` pre-allocates `kMaxRegisteredModules = 128`
  slots in `.bss` to guarantee zero internal container allocations at runtime.
