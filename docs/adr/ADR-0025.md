# ADR-0025: MESI Cache-Line Isolation and Shadow Indexing in Lock-Free Structures

> To prevent "False Sharing" (cache-line ping-ponging) from bottlenecking cross-core throughput,
> all lock-free communication primitives (e.g., `SPSCRingBuffer`) must explicitly align and pad
> their internal state to hardware cache-line boundaries (64 bytes), separating Read-Only,
> Producer-Modified, and Consumer-Modified zones. Furthermore, cross-thread atomic reads must be
> minimized using local "Shadow Index Caching," restricting interconnect bus traffic to only when
> a buffer is completely full or completely empty.

![Proposed][badge-proposed]

## Context

Modern symmetric multiprocessing (SMP) systems use multi-level cache hierarchies to hide
main memory latency. Each CPU core maintains private L1 and L2 caches, while L3 cache is
typically shared across cores on a silicon die or compute complex. Hardware cache
coherence protocols, such as MESI (Modified, Exclusive, Shared, Invalid) and MOESI, ensure
that cores observe a consistent view of shared memory across inter-core interconnects
such as Intel Ultra Path Interconnect (UPI) or AMD Infinity Fabric.

The fundamental unit of hardware memory coherence is the 64-byte cache line. Coherence
state tracking operates exclusively at this 64-byte granularity. When Core A attempts to
write to any byte within a cache line currently held in the Shared (S) state by Core B, Core A
must broadcast a Request For Ownership (RFO) across the interconnect. Core B invalidates
its local copy (transitioning the line to the Invalid state, I). When Core B subsequently
reads its own independent variable within that same 64-byte address range, it suffers a
cache miss. Core B stalls its instruction pipeline while re-fetching the updated line from
L3 cache or main memory.

Lock-free communication channels exhibit two primary hardware failure modes when memory
layout is left unmanaged:

### 1. False Sharing (Cache-Line Ping-Ponging)

In a naive Single-Producer Single-Consumer (SPSC) ring buffer, the write cursor (`m_head`)
and the read cursor (`m_tail`) often sit adjacent in memory within the same contiguous
struct. Because each variable occupies 8 bytes on 64-bit architectures, both cursors fit
easily inside a single 64-byte cache line:

- When the producer pushes an element, it modifies `m_head`. This invalidates Core B's L1
  cache line containing `m_tail`.
- When the consumer pops an element, it modifies `m_tail`. This invalidates Core A's L1
  cache line containing `m_head`.

Under heavy workloads, this mutual invalidation loop forces the 64-byte line to bounce
continually between cores. Hardware performance counters record extreme rates of L1 data
cache misses and RFO stall cycles. Empirical measurements on modern x86-64 hardware
demonstrate that false sharing degrades raw lock-free throughput by a factor of 10x to 50x
relative to cache-isolated designs.

### 2. Interconnect Bus Contention via Eager Atomic Polling

Even when `m_head` and `m_tail` reside on separate cache lines, naive implementations query
the remote cursor atomically on every operation to check available capacity. On every push,
the producer loads `m_tail` to verify that the buffer is not full. On every pop, the consumer
loads `m_head` to verify that the buffer is not empty.

Although separate cache lines prevent false sharing writes, loading an atomic variable
written by another core requires cache-coherence snooping across the CPU interconnect.
During sustained bursts of high-frequency events (such as raw mouse reports at 1000 Hz or
8000 Hz), eager cross-thread atomic reads saturate memory bus queues and trigger pipeline
stalls, even when the queue contains hundreds of available slots.

## Decision

We enforce a strict 3-Zone Cache-Line Isolation layout combined with Shadow Index Caching
across all lock-free single-producer single-consumer queues in `gp-engine`, including
`gp::container::SPSCRingBuffer<T>` and `gp::container::SPSCByteRingBuffer`.

### 1. Three-Zone Cache-Line Memory Layout

The internal memory of the ring buffer is separated into three distinct 64-byte zones.
Each zone is assigned strict alignment via `alignas(kCacheLineSize)` to guarantee that
read-only metadata, producer-owned variables, and consumer-owned variables never reside on
the same physical cache line:

<!-- markdownlint-disable MD013 -->
```text
+-------------------------------------------------------------------------------------------------+
| Cache Line 0 (64 Bytes) - Read-Only Zone (MESI State: Shared [S])                               |
| m_buffer (8B) | m_capacity (8B) | m_mask (8B) | m_allocator (8B) | m_ownsMemory (1B) | Pad (31B)|
+-------------------------------------------------------------------------------------------------+
                                                 |
                   Concurrent read-only access by both Producer and Consumer cores
                   Zero cache line invalidations during steady-state execution
                                                 |
                                                 v
+-------------------------------------------------------------------------------------------------+
| Cache Line 1 (64 Bytes) - Producer-Modified Zone (MESI State: Modified [M] on Producer Core)    |
| m_head (8B Atomic) | m_cachedTail (8B Shadow) | Padding (48B)                                   |
+-------------------------------------------------------------------------------------------------+
                         ^                                                 |
   Mutated solely by     |                                                 | Read by Consumer ONLY
   Producer (Core A)     |                                                 | when queue seems empty
                         |                                                 v
+-------------------------------------------------------------------------------------------------+
| Cache Line 2 (64 Bytes) - Consumer-Modified Zone (MESI State: Modified [M] on Consumer Core)    |
| m_tail (8B Atomic) | m_cachedHead (8B Shadow) | Padding (48B)                                   |
+-------------------------------------------------------------------------------------------------+
                                                 ^                                 |
                                                 | Mutated solely by               | Read by Producer ONLY
                                                 | Consumer (Core B)               | when queue seems full
```
<!-- markdownlint-enable MD013 -->

In C++23, the data members are declared as follows:

```cpp
// Zone 1: Read-Only metadata (Shared across all cores, never mutated after init)
alignas(kCacheLineSize) T* m_buffer = nullptr;
USize m_capacity = 0;
USize m_mask = 0;
memory::Malloc* m_allocator = nullptr;
bool m_ownsMemory = false;

// Zone 2: Producer-Modified state (Exclusive to Producer Core)
alignas(kCacheLineSize) Atomic<USize> m_head{0};
USize m_cachedTail = 0; // Shadow index: read locally by producer without bus traffic

// Zone 3: Consumer-Modified state (Exclusive to Consumer Core)
alignas(kCacheLineSize) Atomic<USize> m_tail{0};
USize m_cachedHead = 0; // Shadow index: read locally by consumer without bus traffic
```

### 2. Shadow Index Caching Mechanism

To eliminate cross-core atomic traffic during continuous data transfer, both endpoints
maintain thread-local shadow copies of the opposing cursor:

- **Producer Write Path (`tryPush` / `tryEmplace`):**
  1. The producer reads its local `m_head` with `MemoryOrder::Relaxed`.
  2. The producer evaluates available capacity against `m_cachedTail` (a local 8-byte
     integer residing on Cache Line 1).
  3. If `(m_head - m_cachedTail) < m_capacity`, remaining capacity is guaranteed. The
     producer writes the element directly to `m_buffer` and publishes the new `m_head`
     with `MemoryOrder::Release`. This path performs zero cross-thread memory reads.
  4. Only when `(m_head - m_cachedTail) == m_capacity` does the producer issue a
     cross-thread read: it executes `m_tail.load(MemoryOrder::Acquire)` to refresh
     `m_cachedTail`. If space is still unavailable, the queue is genuinely full.

- **Consumer Read Path (`tryPop` / `peek`):**
  1. The consumer reads its local `m_tail` with `MemoryOrder::Relaxed`.
  2. The consumer evaluates available items against `m_cachedHead` (a local 8-byte integer
     residing on Cache Line 2).
  3. If `m_tail != m_cachedHead`, unread items are guaranteed. The consumer moves the
     element from `m_buffer` and publishes the new `m_tail` with `MemoryOrder::Release`.
     This path performs zero cross-thread memory reads.
  4. Only when `m_tail == m_cachedHead` does the consumer issue a cross-thread read: it
     executes `m_head.load(MemoryOrder::Acquire)` to refresh `m_cachedHead`. If indices are
     still equal, the queue is genuinely empty.

### 3. Architectural Invariants

1. **Strict 64-Byte Cache-Line Alignment:** Every zone begins on an explicit 64-byte
   boundary (`kCacheLineSize`). The compiler enforces this layout via `alignas`,
   guaranteeing that adjacent member variables cannot share a cache line.
2. **Unidirectional Cache-Line Mutation:** Zone 1 remains immutable throughout steady-state
   streaming. Zone 2 is written exclusively by the producer thread. Zone 3 is written
   exclusively by the consumer thread. No single cache line is ever mutated by more than one
   core.
3. **Amortized Interconnect Traffic:** Cross-core atomic loads occur strictly at boundary
   conditions (when the queue appears full to the producer or empty to the consumer).
   During sustained throughput, push and pop operations execute entirely within the local
   L1 cache of the respective core.
4. **Acquire-Release Memory Ordering:** Cross-thread index synchronization uses
   `MemoryOrder::Release` for publishing and `MemoryOrder::Acquire` for shadow refreshes.
   Sequential consistency (`MemoryOrder::SeqCst`) is prohibited on queue fast paths to avoid
   issuing full hardware memory fences.

### 4. Architecture Comparison Matrix

| Metric | Naive Lock-Free Queue | Padded Queue (No Shadow) | Padded + Shadow-Indexed Queue |
| :--- | :--- | :--- | :--- |
| **False Sharing Risk** | High (Head/Tail on 1 line) | None (Lines isolated) | None (Lines isolated) |
| **Interconnect Traffic** | Bus broadcast on every write | Atomic load on every op | Snooping only on empty/full |
| **Enqueue / Dequeue Latency** | 50ns to 150ns (RFO stalls) | 15ns to 30ns (cross-L1 load) | 2ns to 5ns (local L1 hit) |

## Alternatives Considered

### Option A: Unpadded Contiguous Struct Layout

Store `m_head`, `m_tail`, and buffer metadata sequentially in a single standard C++ struct
without explicit alignment or padding attributes.

**Why rejected:** Guarantees false sharing. Because `m_head` and `m_tail` sit within the same
64-byte line, every enqueue by the OS message thread invalidates the consumer cache line on
the Game thread, and every dequeue by the Game thread invalidates the producer cache line on
the OS thread. This ping-pong effect stalls the CPU execution pipelines and causes frame
micro-stutters during high input rates, such as 1000 Hz or 8000 Hz gaming peripherals.

### Option B: Full Atomic Query per Operation without Shadow Caching

Separate `m_head` and `m_tail` onto distinct 64-byte cache lines, but query the remote
atomic cursor directly on every push and pop operation.

**Why rejected:** Floods the CPU interconnect bus with atomic cache-coherence queries. Even
with thousands of available slots in the buffer, each push forces an acquire-load across the
interconnect to inspect `m_tail`, and each pop forces an acquire-load to inspect `m_head`.
This creates unnecessary memory bus contention and increases per-operation queue latency
from 3 nanoseconds to over 20 nanoseconds.

### Option C: Mutex or Spinlock Guarded Circular Queue

Synchronize access to a standard circular buffer using an OS mutual exclusion primitive
(`gp::platform::Mutex`) or a user-space atomic spinlock.

**Why rejected:** Introduces OS syscall context switches and thread descheduling under
contention. If the producer holds a lock while interrupted by the OS scheduler, the
consumer stalls completely. Active spinlocks avoid context switches but consume CPU cycles
wastefully and risk priority inversion. Real-time engine threads require deterministic,
wait-free forward progress guarantees.

## Consequences

### Positive

- **Eliminates cross-core false sharing.** Hardware cache lines for write cursors remain in
  Modified or Exclusive state on their respective cores, preventing invalidation broadcasts
  during concurrent push and pop operations.
- **Minimizes CPU interconnect bus traffic.** Shadow index caching reduces cross-core atomic
  reads to boundary cases, allowing the majority of push and pop operations to complete
  entirely within the local L1 data cache.
- **Guarantees deterministic wait-free execution.** Neither the producer nor the consumer
  blocks or yields to the operating system scheduler, maintaining microsecond-level latency
  for real-time threads.
- **Zero dynamic memory allocation during streaming.** Ring buffer storage is pre-allocated
  during initialization, ensuring zero steady-state heap operations on high-frequency paths.

### Negative

- **Memory padding overhead.** Explicit 64-byte alignment and padding increases the struct
  footprint from approximately 32 bytes to 192 bytes (three full cache lines). In exchange,
  the queue gains cache isolation.
- **Single-Producer Single-Consumer topology constraint.** The layout supports strictly one
  producer thread and one consumer thread. Multiple producers or multiple consumers require
  external synchronization or multi-producer queue algorithms.
