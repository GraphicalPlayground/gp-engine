# ADR-0020: Strict Data-Oriented Design (PODs) at the Hardware-to-Engine Boundary

> Mandates that all events crossing from the OS thread to the Game thread must be Trivially
> Copyable, Standard Layout Plain Old Data (POD) structs. Explicitly forbids the use of C++
> inheritance, virtual tables, RTTI, and heap allocations (`new`/`delete`) at the HAL level to
> prevent heap fragmentation and lock contention.

![Proposed][badge-proposed]

## Context

Operating system message pumps process hundreds to thousands of peripheral signals every second.
Input devices (such as 8000 Hz esports mice, mechanical keyboards, and high-frequency gamepad IMUs),
desktop window managers, and monitors generate a continuous stream of state transitions. The engine
must transfer these hardware signals across the thread boundary from the platform message pump
thread to the Game Thread without stalling either execution context.

Traditional object-oriented event hierarchies introduce severe performance bottlenecks when handling
cross-thread hardware event streams:

- Virtual method dispatch introduces overhead. Polymorphic event hierarchies (such as `class
  WindowResizeEvent : public Event`) append an 8-byte virtual table pointer (`vptr`) to every
  instance. For small event payloads that contain between 4 and 16 bytes of useful data, an 8-byte
  `vptr` adds 50% to 200% memory bloat. Dispatching these events through virtual functions requires
  indirect function calls through the virtual method table, incurring branch mispredictions and
  instruction cache misses when processing high-volume queues.
- Dynamic memory allocation triggers allocator lock contention. Event classes that own
  variable-length data (such as file paths or IME text strings) often use heap-allocating members
  like `std::string` or `std::vector`. Enqueuing and dequeuing these objects across threads requires
  invoking general-purpose heap allocators (`malloc`, `free`, `new`, `delete`). Concurrent allocator
  invocations trigger operating system thread synchronization locks, cache-line contention on
  central memory pools, and runtime heap fragmentation.
- Memory layout opacity prevents block copying. Classes with virtual base classes, private
  non-static data members distributed across different inheritance tiers, or user-defined copy
  constructors prevent bitwise memory copying. Pushing such objects through a lock-free byte ring
  buffer requires invoking piecewise copy constructors rather than performing a direct block memory
  copy (`memcpy`), preventing the use of high-throughput raw byte streams.

Under the ISO C++ standard, Plain Old Data (POD) types are defined by two formal compile-time
properties:

1. Trivially Copyable (`std::is_trivially_copyable_v<T>`): The type has no user-defined copy
   constructors, move constructors, copy assignment operators, move assignment operators, or
   destructors. Its object representation can be copied byte-for-byte using `std::memcpy` or
   `std::memmove`. Copying the bytes produces an exact, fully valid duplicate of the original object
   state.
2. Standard Layout (`std::is_standard_layout_v<T>`): The type has no virtual functions, no virtual
   base classes, identical access control across all non-static data members, and all non-static
   members are defined in the same class in the inheritance hierarchy. The compiler guarantees
   predictable member offsets matching the physical layout of equivalent C structs, ensuring full C
   ABI interoperability.

Constraining event transport strictly to Trivially Copyable, Standard Layout types guarantees that
event data can be serialized, copied, and deserialized through contiguous memory channels with zero
allocator overhead and predictable CPU memory access patterns.

## Decision

We mandate that every event data structure crossing the hardware-to-engine boundary within
`source/runtime/hal/base/` must be a strict Plain Old Data (POD) struct satisfying both
`std::is_trivially_copyable_v` and `std::is_standard_layout_v`.

We explicitly prohibit virtual functions, inheritance hierarchies, run-time type information (RTTI),
user-defined constructors or destructors, and dynamic heap allocations (`new`, `delete`, `malloc`,
`free`) in all HAL event declarations.

### Structural Requirements for HAL Events

Every event struct declared under `source/runtime/hal/base/public/event/` must satisfy four
structural requirements:

1. Trivially copyable semantics: Structs must rely exclusively on default-generated copy and move
   operations. Enqueuing an event into a ring buffer or copying it to local stack variables must
   execute as a single bitwise memory copy without prologue or epilogue code.
2. Standard layout memory arrangement: All non-static data members must share the same access
   control specifier (`public`). Structs must contain zero virtual functions, zero virtual tables,
   and zero base classes.
3. Natural member ordering and explicit alignment: Data members must be arranged in descending order
   of size (64-bit fields first, followed by 32-bit, 16-bit, and 8-bit fields). Implicit compiler
   padding is eliminated by defining explicit reserved byte arrays (such as `gp::UInt8 reserved[2]`)
   that align structs to 4-byte or 8-byte boundaries.
4. Compile-time concept enforcement: Every event header must validate its struct definitions using
   compile-time static assertions:

```cpp
static_assert(std::is_trivially_copyable_v<WindowEvent>, "WindowEvent must be trivially copyable.");
static_assert(std::is_standard_layout_v<WindowEvent>, "WindowEvent must have standard layout.");
```

### Event Taxonomy

All HAL event structures are organized into clear domain subdirectories under
`source/runtime/hal/base/public/event/`:

```text
source/runtime/hal/base/public/event/
  EventCategory.hpp
  EventHeader.hpp
  system/
    ApplicationEvent.hpp
    DisplayEvent.hpp
    WindowEvent.hpp
  input/
    GamepadEvent.hpp
    KeyboardEvent.hpp
    MouseEvent.hpp
    PenEvent.hpp
    SensorEvent.hpp
    TouchEvent.hpp
  device/
    DeviceChangeEvent.hpp
  data/
    ClipboardEvent.hpp
    DropEvent.hpp
    TextInputEvent.hpp
```

Each event category corresponds to an entry in `EventCategory.hpp`. Events are preceded in the ring
buffer by a 4-byte `EventHeader` containing a 16-bit category identifier and a 16-bit payload
length:

```cpp
struct EventHeader
{
    EventCategory category;
    gp::UInt16 payloadSize;
};
static_assert(sizeof(EventHeader) == 4, "EventHeader must be exactly 4 bytes.");
```

### Zero Allocation Guarantee

All events pass through the single-producer single-consumer lock-free byte ring buffer
(`gp::container::SPSCByteRingBuffer`) established in [ADR-0013](./ADR-0013.md) and
[ADR-0019](./ADR-0019.md).

Operating system callbacks running on the platform thread serialize events into contiguous byte
segments by copying the fixed `EventHeader` followed by the POD struct bytes. For variable-length
data payloads (such as UTF-8 text in `TextInputEvent` or file paths in `DropEvent`), the trailing
characters are appended as contiguous raw bytes directly behind the fixed struct within the ring
buffer storage.

Draining the ring buffer on the Game Thread requires zero dynamic heap allocations:

1. The consumer reads the 4-byte `EventHeader` to determine the event category and total payload
   size.
2. The consumer casts the payload pointer directly to a const reference of the expected POD struct
   (`const WindowEvent& ev = *reinterpret_cast<const WindowEvent*>(bufferPtr);`).
3. For variable-length events, trailing data is referenced as a non-allocating string view
   (`gp::StringView(bufferPtr + sizeof(TextInputEvent), ev.byteLength)`).
4. Ring buffer read cursors advance by `sizeof(EventHeader) + payloadSize`.

Neither enqueuing nor dequeuing requires invoking heap management functions. Stack-allocated or
ring-buffer-resident bytes represent the entire memory footprint of the event subsystem.

## Alternatives Considered

### Option A: Classical Polymorphic Event Hierarchy (`class IEvent` with Virtual Dispatch)

Define a base class `IEvent` with virtual member functions (such as `virtual void
dispatch(IEventHandler& handler) = 0`) and derive specific event classes from it.

**Why rejected:** Every polymorphic instance contains a hidden 8-byte virtual pointer (`vptr`),
which inflates memory usage by 50% to 200% on small input packets. Polymorphic dispatch requires
indirect branch addressing through the virtual method table, which stalls CPU instruction pipelines
and degrades instruction cache locality during high-frequency input bursts. Furthermore, classes
containing virtual pointers cannot be copied bitwise with `memcpy` into raw contiguous byte buffers,
requiring per-event heap allocation or custom object pools.

### Option B: STL Standard Container Events (`std::string`, `std::variant`, `std::vector`)

Represent event unions with `std::variant` and store variable-length payloads (such as file paths
and text composition buffers) in `std::string` or `std::vector`.

**Why rejected:** Standard library containers allocate memory on the process heap. Copying these
objects between threads invokes global heap allocators, creating thread contention and latency
spikes on real-time render loops. Furthermore, standard library templates introduce dynamic memory
management that violates the engine-wide zero-STL architecture defined in [ADR-0021](./ADR-0021.md)
and exposes compiler-dependent ABI layouts across dynamic link boundaries.

### Option C: Raw Unstructured Byte Buffers with Manual Pointer Offsets

Transmit unstructured byte arrays across threads and calculate variable offsets manually without
formal POD struct declarations.

**Why rejected:** Manual pointer arithmetic without formal struct types removes compile-time type
verification. Developers must calculate offsets by hand, which introduces risks of memory
corruption, reading past buffer bounds, and unaligned hardware access faults on architectures that
penalize or fault on unaligned loads. Declaring strongly-typed POD structs verified with
compile-time assertions provides type safety while retaining the performance of raw byte transfers.

## Consequences

### Positive

- **Deterministic zero-allocation event routing.** Enqueuing and draining events across threads
  requires zero calls to `malloc`, `new`, or `delete`, eliminating memory fragmentation and lock
  contention on the heap.
- **Efficient cache-line memory utilization.** Packing event fields into 4-byte, 8-byte, 16-byte,
  32-byte, or 48-byte structs without virtual pointers maximizes data density, allowing multiple
  events to reside within a single 64-byte L1 cache line.
- **Mechanical compile-time verification.** Static assertions guarantee that any inadvertent
  addition of non-trivial members, virtual methods, or compiler padding fails compilation before
  code can be committed.
- **Binary layout stability across boundaries.** Standard layout types guarantee a deterministic
  C-compatible memory layout that remains consistent across dynamic link libraries and compiler
  versions.
- **High-throughput bitwise serialization.** Trivially copyable types permit direct `memcpy`
  operations and in-place cursor reinterpretations within the lock-free single-producer
  single-consumer ring buffer.

### Negative

- **Manual padding and field ordering maintenance.** Struct authors must manually order data members
  by descending size and add explicit reserved byte arrays to prevent compiler-inserted padding.
- **Absence of dynamic object-oriented dispatch.** Consumer code cannot use polymorphic dispatch
  patterns and must process events through explicit `switch` statements over the `EventCategory` and
  action enums.
- **Auxiliary length tracking for variable payloads.** Variable-length events like file drops and
  text inputs must coordinate trailing byte lengths through explicit struct fields and contiguous
  memory slices.
