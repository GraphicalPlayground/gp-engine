# ADR-0038: Synchronous Modal Message Boxes and Asynchronous Native File Dialogs with Headless Auto-Resolution

> Native OS file and folder pickers execute on asynchronous desktop compositor loops that stall
> swapchain presentation or deadlock the window manager if blocked synchronously on the Game
> Thread. Conversely, fatal assertion and crash message boxes must block synchronously and
> function even before the graphics/window backend is initialized or after it has crashed.
> Furthermore, spawning interactive OS modal dialogs on headless CI runners or dedicated servers
> hangs automated pipelines indefinitely. The HAL `IDialog` subsystem separates synchronous modal
> alerts (`showAlert`, `showMessageBox`, capable of pre-initialization panic execution and custom
> button/theme layouts) from non-blocking, callback-driven native file/folder pickers
> (`showOpenFileDialog`, `showSaveFileDialog`, `showOpenFolderDialog`), while `generic::Dialog`
> enforces deterministic headless auto-resolution (returning the designated default button or
> immediate cancellation without blocking).

![Proposed][badge-proposed]

## Context

Game engines and editor tools interact with operating system dialogs under two opposing
operational requirements: non-blocking asset navigation during live frame execution, and
synchronous failure isolation during unrecoverable engine panics. These modes present
divergent constraints regarding the desktop compositor loop, the engine lifecycle, and
unattended automated pipelines.

### Desktop Compositor Loops and Synchronous Modal Deadlocks

Modern operating systems execute native file and folder pickers through external desktop
compositor loops or isolated helper processes. On Windows, Common Item Dialogs (`IFileDialog`)
run via COM and the Desktop Window Manager. On macOS, Cocoa panels (`NSOpenPanel`, `NSSavePanel`)
rely on asynchronous sheet presentations and dispatch queues. On modern Linux desktop
environments, Flatpak, Snap, and native Wayland applications access host filesystems through
out-of-process XDG Desktop Portals (`org.freedesktop.portal.FileChooser`) via D-Bus IPC.

Blocking the engine Game Thread synchronously waiting for a file picker return creates several
severe runtime failure modes:

1. **Swapchain Presentation Stalls:** Halting the Game Thread freezes swapchain presentation,
   halting viewport rendering, animation playback, audio processing, background asset streaming,
   and editor user interface updates.
2. **Window Manager Deadlocks:** On Wayland and macOS, child modal dialogs require reciprocal
   event processing by the parent window. If the calling thread blocks and stops pumping its
   native OS event queue, the compositor handshake stalls, causing window manager deadlocks
   or triggering operating system watchdog terminations ("Application Not Responding").
3. **Editor Tooling Interruption:** Content creation tools require active scene rendering,
   camera movement, and inspector scrubbing while open file or save asset dialogs remain
   active on screen.

### Fatal Assertion and Panic Crash Isolation

Fatal assertion failures (`GP_ASSERT`), out-of-memory errors, and graphics device loss
(`DXGI_ERROR_DEVICE_REMOVED`, `VK_ERROR_DEVICE_LOST`) require the opposite execution paradigm.
When an engine panic occurs, continued simulation corrupts game state, risks data loss, and
generates cascading faults. Execution must halt immediately and block the thread while
notifying the developer or user.

Furthermore, fatal crashes frequently occur at the extremes of the engine lifecycle:

- **Pre-Initialization Boot Failures:** Missing asset directories, unsupported GPU hardware
  features, or configuration parse errors trigger assertions before the windowing backend
  (`IApplicationBackend`) or any `IWindow` instance exists.
- **Post-Crash Device Teardown:** A GPU driver crash or graphics device lost event can destroy
  the swapchain and rendering context. Any alert system relying on an operational graphics
  pipeline or an active window event loop will crash during the panic handling sequence.

Diagnostic message boxes must therefore function in isolation without requiring a valid parent
window handle (`parentWindow == nullptr`), an active message pump, or an initialized graphics
device.

### Headless Execution and Automated Pipeline Freezes

Continuous integration environments (such as GitHub Actions and Docker containers) and
dedicated multiplayer game servers run without attached displays or human operators.
If unit tests, integration suites, or headless server binaries trigger a GUI message box or
file picker:

- The process spawns an interactive modal prompt awaiting human keyboard or mouse input.
- Because no user is present to dismiss the dialog, the test process hangs indefinitely until
  the CI pipeline reaches its global timeout (often 30 to 60 minutes), failing the build.
- Headless execution requires deterministic, automated resolution of all dialog queries
  without interactive UI prompts or thread stalls.

## Decision

We introduce `gp::hal::IDialog`, a platform-agnostic interface that decomposes modal OS
communication into two distinct execution paradigms: synchronous modal message boxes for
diagnostics and crash alerts, and asynchronous callback-driven dialogs for filesystem picking.
Headless environments automatically resolve dialogs through `gp::hal::generic::Dialog`.

### Synchronous Modal Message Boxes (`showAlert`, `showMessageBox`)

For fatal assertions, diagnostic errors, and synchronous user queries, `IDialog` provides two
blocking entry points:

1. **`showAlert()`:** Displays standardized alerts using standard button presets
   (`DialogButtonPreset::Ok`, `OkCancel`, `YesNo`, `YesNoCancel`, `RetryCancel`,
   `AbortRetryIgnore`). Returns a strongly-typed `DialogButtonId`.
2. **`showMessageBox()`:** Configures custom dialogs through `MessageBoxDesc`, supporting up to
   `kMaxDialogButtons = 8u` buttons, custom integer IDs, keyboard shortcut associations
   (`DialogButtonFlags::ReturnKeyDefault`, `DialogButtonFlags::EscapeKeyDefault`), right-to-left
   button ordering, and an optional 24-bit RGB palette (`DialogColorScheme`).

Both methods accept `parentWindow = nullptr`. In pre-initialization panic situations or post-crash
teardown, passing a null window pointer instructs the platform backend (e.g. `SDL3Dialog`) to
display a system-level modal message box (`SDL_ShowMessageBox` or `SDL_ShowSimpleMessageBox`).
The underlying operating system spawns a self-contained dialog window that pumps its own modal
event loop independently of the engine graphics pipeline.

### Asynchronous Native File and Folder Pickers

For file selection, `IDialog` provides non-blocking entry points:

- `showOpenFileDialog(const FileDialogDesc& desc)`
- `showSaveFileDialog(const FileDialogDesc& desc)`
- `showOpenFolderDialog(const FileDialogDesc& desc)`

These methods return a boolean immediately upon dispatching the request to the operating
system. Results return asynchronously through a C-style function pointer callback:

```cpp
using FileDialogCallback = void (*)(void* userData, const FileDialogResult& result) noexcept;
```

The `FileDialogResult` structure delivers result data back to the caller:

- `paths`: Pointer to an array of `StringView` slices referencing selected UTF-8 filesystem
  paths (supporting up to `kMaxDialogSelectedFiles = 64u`).
- `pathCount`: Number of valid path entries.
- `selectedFilterIndex`: Index of the filter chosen by the user in `FileDialogDesc::filters`.
- `errorMessage`: Diagnostic error string populated if the operation fails.
- `status`: Completion enum (`DialogFileStatus::Accepted`, `Cancelled`, or `Error`).

### Zero-Allocation Context Pooling

To adhere to the engine zero-allocation runtime constraint, `SDL3Dialog.cpp` avoids dynamic heap
allocations when dispatching asynchronous file dialogs. Staging extension filters and callback
pointers across the asynchronous OS transition relies on a fixed-capacity static slot pool:

```cpp
constexpr gp::UInt32 kMaxConcurrentFileDialogs = 4u;
AsyncFileDialogContext s_fileDialogContexts[kMaxConcurrentFileDialogs]{};
```

Each `AsyncFileDialogContext` contains inline character arrays for filter names and extension
patterns (`kMaxFilterStringBytes = 128u`), fixed SDL filter structures, and the user callback
pointer. Slot reservation uses lock-free atomic compare-and-swap:

```cpp
AsyncFileDialogContext* acquireFileDialogContext() noexcept
{
    for (gp::UInt32 i = 0u; i < kMaxConcurrentFileDialogs; ++i)
    {
        bool expected = false;
        if (s_fileDialogContexts[i].inUse.compareExchangeStrong(
                expected, true, gp::MemoryOrder::Acquire, gp::MemoryOrder::Relaxed))
        {
            return &s_fileDialogContexts[i];
        }
    }
    return nullptr;
}
```

Upon completion, the SDL callback formats `FileDialogResult`, executes the user callback, clears
context pointers, and releases the slot via `inUse.store(false, gp::MemoryOrder::Release)`. If
requests exceed `kMaxConcurrentFileDialogs`, the backend invokes the callback with
`DialogFileStatus::Error` and an informative error message without blocking or crashing.

### Deterministic Headless Auto-Resolution (`generic::Dialog`)

The generic HAL dialog implementation (`gp::hal::generic::Dialog`) acts as the base class for
all platform backends and serves as the active dialog handler in headless mode. It eliminates
blocking modal prompts in CI pipelines through deterministic rules:

1. **`showAlert()` Auto-Resolution:** Automatically returns the designated primary button
   corresponding to the requested preset:
   - `Ok` for `DialogButtonPreset::Ok` and `DialogButtonPreset::OkCancel`.
   - `Yes` for `DialogButtonPreset::YesNo` and `DialogButtonPreset::YesNoCancel`.
   - `Cancel` for `DialogButtonPreset::RetryCancel`.
   - `Abort` for `DialogButtonPreset::AbortRetryIgnore`.
2. **`showMessageBox()` Auto-Resolution:** Iterates through `desc.buttons` and returns the ID
   of the button marked with `DialogButtonFlags::ReturnKeyDefault`. If no button carries the
   flag, it returns `desc.buttons[0].id`. If `desc.buttonCount == 0`, it returns `-1`.
3. **File Dialog Immediate Cancellation:** `showOpenFileDialog()`, `showSaveFileDialog()`, and
   `showOpenFolderDialog()` immediately invoke `desc.callback(desc.userData, result)` with
   `result.status = DialogFileStatus::Cancelled`, returning `false`.

Automated unit tests and headless servers execute dialog paths without UI stalls, maintaining
complete pipeline determinism.

### Architectural Invariants

1. **Strict Temporal Separation of Alerts and File Pickers:** Diagnostic message boxes and crash
   alerts execute synchronously to halt state corruption during panics. File and folder pickers
   execute asynchronously via non-blocking callbacks to preserve swapchain presentation and
   compositor message pumps.
2. **Deterministic Headless Auto-Resolution:** In headless environments or fallback mode,
   `generic::Dialog` resolves message boxes by selecting the designated default button and
   cancels file dialogs immediately via callback invocation. No interactive modal prompt blocks
   execution.
3. **Zero-Allocation Slot-Pooled File Dialog Dispatch:** Asynchronous file dialog contexts,
   extension filter arrays, and path slices are backed by a fixed-capacity slot pool
   (`kMaxConcurrentFileDialogs = 4u`) managed through lock-free atomic CAS. No dynamic memory
   allocations occur on the heap during dialog creation or result processing.
4. **Pre-Initialization and Post-Crash Panic Readiness:** Synchronous modal message boxes accept
   a null parent window pointer (`parentWindow = nullptr`), allowing fatal error reporting
   before the windowing subsystem initializes or after the graphics swapchain has crashed.

## Alternatives Considered

### Option A: Pure Synchronous File Dialogs (`std::string OpenFileDialog()`)

Implement blocking file dialog functions that halt thread execution and return selected paths
directly as strings.

**Why rejected:** Synchronously blocking the calling thread freezes the engine swapchain,
interrupting rendering, scene updates, and background tasks. On Wayland and macOS, synchronous
child dialogs that halt parent message pump processing cause compositor handshakes to deadlock
and trigger OS watchdog kills. Modern Linux desktop portals (`org.freedesktop.portal.FileChooser`)
are architecturally asynchronous and rely on D-Bus IPC callbacks, making synchronous APIs an
impedance mismatch.

### Option B: Exclusively In-Engine Immediate GUI (e.g., ImGui File Picker)

Render file selection windows entirely within the engine viewport using immediate-mode UI
widgets, bypassing native operating system dialogs completely.

**Why rejected:** In-engine dialogs lack integration with native desktop features, including
pinned bookmarks, recent file history, cloud drives (OneDrive, iCloud, Google Drive), network
shares, and platform sandboxing permissions. Furthermore, in-engine dialogs require an
operational graphics swapchain, rendering backend, and font engine, making them incapable of
displaying crash alerts when an assertion fails during early boot or following a GPU device
loss crash.

### Option C: Dynamic Heap Allocation per File Dialog Context (`new AsyncContext`)

Allocate asynchronous context structures, filter strings, and result arrays dynamically on the
heap with `new` or `malloc` whenever a file dialog opens.

**Why rejected:** Violates the engine's zero-allocation invariant for runtime hardware and OS
abstractions. Heap allocations introduce memory fragmentation and risk leaks if an application
abruptly terminates while a dialog is displayed. Staging filters in a fixed static pool of four
concurrent slots satisfies typical desktop and editor usage patterns with zero heap allocations.

## Consequences

### Positive

- **Uninterrupted swapchain presentation during file browsing.** Asynchronous file dialogs allow
  the Game Thread and Render Thread to maintain continuous frame ticks, viewport rendering, and
  asset streaming while the user navigates the filesystem.
- **Reliable panic reporting across the engine lifecycle.** Synchronous message boxes function
  without an active window or graphics device, enabling readable fatal crash alerts during early
  engine boot and post-GPU-crash panics.
- **Deterministic headless test execution.** Automated CI runners and dedicated servers resolve
  alerts and cancel file pickers instantly, preventing pipeline timeouts and test hangs.
- **Zero-allocation dispatch and result handling.** Static slot pooling with atomic CAS guarantees
  predictable memory overhead and eliminates heap fragmentation at the platform boundary.
- **Native operating system shell integration.** Leverages platform-native dialogs (Windows Common
  Item Dialogs, macOS Cocoa panels, Linux XDG portals), providing native shortcuts, cloud storage
  links, network shares, and OS access permissions.

### Negative

- **Asynchronous callback state management.** Callers opening file dialogs must manage object
  lifetimes and user data contexts across asynchronous callbacks instead of receiving a
  synchronous return value directly.
- **Fixed concurrent file dialog limit.** The slot pool caps simultaneous open file dialogs to
  `kMaxConcurrentFileDialogs = 4u`, rejecting surplus requests with an error status if exceeded.
- **Platform-dependent color theming.** While `DialogColorScheme` permits custom palettes on
  platforms that support themed message boxes, certain operating systems (such as Win32
  TaskDialogs) enforce native desktop themes and ignore custom color palettes.
