# ADR-0017: Domain-Specific Input State Abstractions for Keyboard, Mouse, and Gamepad

> Defines localized, independent classes (`Keyboard`, `Mouse`, `Gamepad`) that maintain their own
> previous and current state arrays, providing ergonomic polling APIs (e.g., `isKeyPressed`) for
> gameplay programmers.

![Proposed][badge-proposed]

## Context

Interactive game engines must bridge two conflicting execution models: asynchronous,
interrupt-driven operating system peripheral events, and synchronous, frame-budgeted gameplay
simulation loops.

### 1. Asynchronous OS Delivery Versus Discrete Frame Polling

Operating system windowing subsystems (Win32 message loops, Cocoa run loops, Wayland display
servers, and SDL3 event queues) dispatch input notifications unpredictably within a frame. A USB
mouse running at 1000 Hz to 8000 Hz delivers interrupts every 125 to 1000 microseconds. Keyboards
emit make and break electrical switch signals whenever keys are physically pressed or released.

Gameplay code does not operate on an asynchronous interrupt clock. Simulation systems, including
player character locomotion, weapon triggers, camera controllers, and vehicle dynamics, evaluate
state inside synchronous, fixed or variable time-step loops (`onUpdate(deltaTime)`). Within these
loops, gameplay code queries instantaneous questions:

- Is the movement key held down right now?
- Did the player pull the fire trigger during this specific frame?
- What was the relative mouse cursor displacement since the previous simulation step?

Bridging these two models requires a state-retaining translation layer that accumulates incoming
peripheral events and presents an instantaneous, immutable snapshot to simulation systems for the
duration of the frame.

### 2. Failure Modes of Pure Event-Driven Callback Models

A naive approach to input management exposes only event listeners or delegate subscriptions. Under
this model, individual game actors (such as player controllers, UI dialogs, or camera rigs)
register callbacks with an event dispatcher to receive push notifications when buttons are pressed
or axes move:

```text
OS Interrupt -> Event Dispatcher -> [Listener 1 Callback] -> [Listener 2 Callback] -> ...
```

This pattern exhibits critical engineering failure modes in production game architectures:

1. **Heap Allocation of Delegate Objects:** Registering dynamic callback delegates, lambda
   closures, or polymorphic listener interfaces requires heap allocations or large pre-allocated
   delegate buffers for every listening actor.
2. **Indeterminate Callback Ordering:** Multiple actors subscribed to the same physical key (such
   as `Space` for both jumping and menu selection) execute in arbitrary registration order unless
   complex priority sorting is executed on every subscription change.
3. **Pervasive State Caching Boilerplate:** Continuous locomotion logic (such as walking forward
   while holding `W`) cannot act on an instantaneous event notification alone. Each actor must
   declare internal boolean member variables, subscribe to both key-down and key-up events, toggle
   its internal booleans, and guard against missed release events.
4. **Dangling Listener Lifetimes:** Actors destroyed mid-frame or during level transitions leave
   dangling function pointers in the dispatcher unless strict, error-prone unregistration
   discipline is maintained across all systems.

### 3. Failure Modes of Monolithic Input God-Classes

To avoid callback proliferation, legacy engines frequently combined all peripheral inputs into a
single centralized class or singleton (such as `Input::IsKeyDown(k)` and `Input::GetMouseDelta()`):

```text
┌────────────────────────────────────────────────────────────────────────┐
│                        Monolithic "Input" Class                        │
│                                                                        │
│  m_scancodes[512]        m_mouseButtons[8]        m_gamepads[8][16]    │
│  m_keycodes[768]         m_cursorX, m_cursorY     m_gamepadAxes[8][6]  │
│  m_modifiers             m_deltaX, m_deltaY       m_gamepadIMU[8]      │
│  m_mouseWheel            m_haptics[8]                                  │
└────────────────────────────────────────────────────────────────────────┘
```

Grouping every peripheral into a single monolithic structure creates severe physical hardware and
software maintenance bottlenecks:

1. **L1 Data Cache Invalidation and False Sharing:** A monolithic struct aggregating 512
   scancodes, 768 keycodes, mouse coordinates, and up to eight gamepads exceeds 4 KB in memory.
   High-frequency mouse packets (arriving thousands of times per second) write coordinates into
   the same memory region or adjacent cache lines containing keyboard and controller data. This
   invalidates CPU L1/L2 data cache lines across cores and causes unnecessary cache line bounces.
2. **Interface Bloat and Coupling:** A subsystem that only requires mouse cursor coordinates (such
   as a canvas cursor renderer) must depend on a header that declares keyboard lookup tables,
   gamepad trigger thresholds, haptic motor structures, and multi-controller slot mappings.
3. **Multi-Player Slot Indirection:** Monolithic APIs either cater strictly to a single player or
   force every query to pass an explicit player index (`Input::IsButtonDown(playerIndex, button)`).
   This clutters single-player systems with redundant parameters and lacks localized encapsulation
   for split-screen or multi-device gameplay setups.

### 4. Divergent Physical Semantics Across Peripherals

Input hardware devices have distinct physical operating characteristics and data representations:

- **Keyboards:** Maintain hundreds of discrete switch positions (512 USB HID scancodes, 768
  logical keycodes). Values are binary, with discrete transition edges (Pressed, Released,
  Repeated).
- **Mice:** Combine discrete micro-switches with continuous planar motion. Position is an absolute
  sub-pixel coordinate within window bounds (`Stick2D`), while movement is a frame-relative
  displacement delta (`Stick2D`). Position persists across frames, whereas displacement deltas
  must be cleared to zero on every frame transition.
- **Gamepads:** Combine 16 discrete membrane or mechanical buttons with six continuous analog axes
  (`Stick2D` thumbsticks and 1D triggers). Analog axes produce raw hardware potentiometer or
  Hall-effect values in `[-1.0f, 1.0f]` or `[0.0f, 1.0f]` that require 2D scaled radial deadzone
  filtering (ADR-0035), hat switch decoders, IMU gyro and accelerometer snapshots, and haptic
  actuator feedback. Each gamepad is assigned to an independent logical player slot (`Player1`
  through `Player8`, ADR-0036).

Because these hardware profiles share almost no common data representations, forcing them into a
generic key-value abstraction or a monolithic structure compromises type safety, cache efficiency,
and API ergonomics.

## Decision

We establish domain-specific, localized input state abstractions within the Hardware Abstraction
Layer. Peripherals are decomposed into dedicated interfaces in
`source/runtime/hal/base/public/input/` and implemented with zero-allocation, flat-array state
tables in `source/runtime/hal/generic/public/input/`.

### 1. Architectural Layout and Directory Taxonomy

```text

│   └── public/
```

### 2. Domain Abstraction Responsibilities

#### `IKeyboard` / `generic::Keyboard`

Manages keyboard hardware switch states, localized OS virtual key states, and modifier bitmasks:

- Maintains flat arrays of `ButtonStateFlags` for physical scancodes (`kMaxScancodes = 512`) and
  virtual keycodes (`kMaxKeycodeSlots = 768`), plus an overflow list for high-unicode code points.
- Implements sub-frame edge latching (ADR-0034) using `ButtonStateFlags` bitmasks (`Held`,
  `PressedThisFrame`, `ReleasedThisFrame`, `RepeatedThisFrame`).
- Tracks active modifier states via `KeyModifier` (`Shift`, `Control`, `Alt`, `Gui`, `CapsLock`).
- Exposes explicit dual-path queries: `isScancodeDown()` for spatial navigation (WASD) and
  `isKeyDown()` for symbolic UI interactions (ADR-0016).

#### `IMouse` / `generic::Mouse`

Manages pointer coordinates, relative motion deltas, scroll wheel detents, and mouse button states:

- Tracks discrete button transitions for up to eight mouse buttons (`kMaxMouseButtons = 8`) and
  maintains a click counter array for double-click detection.
- Stores current cursor window coordinates as a sub-pixel `Stick2D` position vector.
- Stores accumulated relative motion displacement for the current frame as a `Stick2D` delta
  vector.
- Stores accumulated horizontal and vertical scroll wheel displacement as a `Stick2D` wheel delta
  vector.
- Tracks active window focus ID to handle multi-window cursor routing.
- Automatically zeroes relative motion and scroll deltas during `beginFrame()`, while preserving
  absolute cursor coordinates.

#### `IGamepad` / `generic::Gamepad`

Manages an individual game controller assigned to a specific logical player slot (`Player1`
through `Player8`):

- Composes three distinct capability interfaces: `IInputDevice` (buttons and axes), `IHapticDevice`
  (rumble motors, trigger actuators, LED lighting), and `ISpatialDevice` (IMU accelerometer and
  gyroscope data), adhering to ADR-0018.
- Maintains flat arrays for 16 controller buttons (`kMaxGamepadButtons = 16`) with edge latching.
- Maintains raw hardware axis values (`m_rawAxes`) and filtered axis values (`m_filteredAxes`) for
  six analog axes (`LeftX`, `LeftY`, `RightX`, `RightY`, `TriggerLeft`, `TriggerRight`).
- Evaluates 2D scaled radial deadzones on dual thumbsticks (`Stick2D`) and 1D axial deadzones on
  triggers (ADR-0035).
- Manages 8-way directional hat switch bitmasks, battery percentage telemetry, and integrated
  touchpad coordinates.
- Encapsulates physical attachment and detachment lifecycles (`attach()`, `detach()`) without
  altering pointer addresses used by gameplay code.

#### `IInputSystem` / `generic::InputSystem`

Coordinates all domain devices and manages frame lifecycles:

- Owns primary instances of `generic::Keyboard`, `generic::Mouse`, and `generic::SpatialDevice`.
- Owns an array of eight pre-allocated `generic::Gamepad` instances mapped to `GamepadSlot::Player1`
  through `GamepadSlot::Player8`.
- Dispatches `beginFrame()` across all connected devices to clear transient frame edges and reset
  relative deltas before incoming OS events are drained.
- Synthesizes release transitions across all devices on application focus loss via
  `releaseAllInputs()` (ADR-0036).
- Implements hysteresis-gated active device detection (`getActiveDeviceType()`), tracking whether
  the player is currently using Keyboard, Mouse, or Gamepad based on intentional movement
  thresholds (ADR-0035).
- Routes incoming event packets from the lock-free Single-Producer/Single-Consumer (SPSC) ring
  buffer (ADR-0013, ADR-0019) to the corresponding device instance.
- Provides direct accessor methods (`getKeyboard()`, `getMouse()`, `getGamepad(slot)`) alongside
  flattened convenience query helpers (`isScancodeDown()`, `isMouseButtonDown()`,
  `isGamepadButtonDown()`).

### 3. Memory Layout and Direct Array Indexing Model

Every domain class stores input states in contiguous flat arrays indexed directly by their
corresponding strongly typed enums. No associative maps, hashing algorithms, or pointer
indirections are permitted in the query path.

```text
Keyboard State (~1.6 KB):
┌──────────────────────────────────────────┬──────────────────────────────────────────┐
│ m_scancodes: ButtonStateFlags[512]       │ m_keycodes: ButtonStateFlags[768]        │
└──────────────────────────────────────────┴──────────────────────────────────────────┘

Mouse State (64 Bytes = Exactly 1 Cache Line):
┌──────────────┬──────────────┬──────────────┬──────────────┬───────────┬─────────────┐
│ m_buttons[8] │ m_clicks[8]  │ m_position   │ m_delta      │ m_wheel   │ m_windowId  │
│ 8 Bytes      │ 8 Bytes      │ 8 Bytes      │ 8 Bytes      │ 8 Bytes   │ 4 Bytes     │
└──────────────┴──────────────┴──────────────┴──────────────┴───────────┴─────────────┘

Gamepad State (~384 Bytes per Slot):
┌───────────────┬───────────────┬───────────────────┬──────────────────────┬──────────┐
│ m_buttons[16] │ m_rawAxes[6]  │ m_filteredAxes[6] │ m_left / m_rightStick│ Deadzones│
│ 16 Bytes      │ 24 Bytes      │ 24 Bytes          │ 16 Bytes             │ 36 Bytes │
├───────────────┴───────────────┴───────────────────┴──────────────────────┴──────────┤
│ IMU Sensors (Accel / Gyro) & Touchpad State (~160 Bytes)                            │
│ Slot, Battery, Name Buffer, Telemetry (~100 Bytes)                                  │
└─────────────────────────────────────────────────────────────────────────────────────┘
```

#### Memory Footprint and Cache Alignment

- **Mouse State:** Occupies exactly 64 bytes. Fits entirely within a single L1 data cache line.
  Updates to mouse coordinates never touch or invalidate memory lines belonging to the keyboard or
  gamepads.
- **Keyboard State:** Flat arrays consume 512 bytes for scancodes and 768 bytes for keycodes,
  totaling approximately 1.6 KB with overflow storage. This fits within a fraction of a modern
  32 KB L1 data cache.
- **Gamepad State:** Consumes approximately 384 bytes per controller slot. The eight slots total
  approximately 3 KB of contiguous memory.

#### Direct O(1) Indexing Calculation

Querying an input state executes as a single base address plus scaled offset instruction:

```cpp
// Direct O(1) lookup without branching or hashing:
ButtonStateFlags state = m_scancodes[static_cast<gp::UInt32>(scancode)];
bool isDown = (state & ButtonStateFlags::Held) != ButtonStateFlags::None;
```

This guarantees:

- Zero dynamic heap allocations during steady-state polling.
- Zero CPU branch mispredictions from hash table collision checks.
- Constant-time $O(1)$ query overhead requiring 1 to 2 CPU cycles when cache-resident.

## Alternatives Considered

### Option A: Pure Event-Driven Observer System (Callback Listeners Only)

Under this model, the engine provides no polling state tables. Any gameplay system requiring input
must implement an observer interface or register function callbacks with an event bus.

**Why rejected:**

- **Pervasive Delegate Heap Allocations:** Subscription mechanisms rely on dynamic delegates or
  heap-allocated callback wrappers, violating the engine's zero-allocation steady-state rule.
- **Unpredictable Invocation Order:** When multiple gameplay systems register for the same input
  signal, execution order depends on subscription order, introducing frame-rate-dependent or
  initialization-order-dependent bugs.
- **State Caching Boilerplate in Gameplay Code:** Gameplay actors performing continuous actions
  (such as walking forward or rotating a turret) must cache input states internally in local
  boolean variables, duplicating state storage across dozens of scripts.
- **Lifecycle Management Hazards:** Actors destroyed mid-frame risk receiving callbacks with
  invalid `this` pointers unless elaborate unregistration guards are authored for every component.

### Option B: Monolithic Centralized Input God-Class (`Input::Get()`)

This design maintains a single static singleton or global class containing all hardware states in
one large structure. Every query is routed through global methods like `Input::Get().isKeyDown()`
or `Input::Get().getAxis(player, axis)`.

**Why rejected:**

- **Cache Line False Sharing and Invalidation:** Grouping keyboard, mouse, and multi-gamepad
  tables into one memory structure causes high-frequency mouse updates (1000 to 8000 Hz) to dirty
  cache lines adjacent to keyboard or controller memory, degrading cache performance across
  threads.
- **Interface Pollution:** Gameplay modules that only query mouse coordinates are forced to include
  monolithic headers exposing gamepad rumble descriptors, IMU sensors, battery monitors, and
  keyboard tables.
- **Impedance Mismatch with Multi-Player Architectures:** Forcing an explicit `playerIndex` argument
  onto every query pollutes single-player systems, while omitting it complicates split-screen
  controller assignment.
- **Impaired Unit Testability:** Global singletons prevent instantiating isolated test fixtures or
  mocking a single peripheral in automated GoogleTest suites without bringing up the entire engine
  HAL.

### Option C: Dynamic Associative Key-Value Map (`HashMap<InputId, ButtonStateFlags>`)

Under this model, input state is stored in a hash map associating an input identifier with its
current state flags, allocating entries only for keys or buttons that have been pressed.

**Why rejected:**

- **Non-Deterministic Hash Lookup Latency:** Computing key hashes, resolving bucket collisions,
  and traversing linked nodes introduces variable latency and CPU branch mispredictions into
  critical gameplay frame budgets.
- **Dynamic Memory Allocation:** Associative containers require dynamic rehashing and memory bucket
  allocations, violating the engine's deterministic memory rules.
- **Pointer Indirection Overhead:** A direct array lookup resolves in a single cycle
  (`*(base + index)`). In contrast, hash map lookups involve multiple memory dereferences and
  pointer traversals that regularly incur CPU cache misses.

## Consequences

### Positive

- **Strict cache-line isolation between independent peripherals.** Grouping state variables into
  localized classes ensures that high-frequency mouse pointer updates (operating at 1000 Hz to
  8000 Hz) dirty only the 64-byte `Mouse` cache line, preventing false sharing and cache
  invalidation across keyboard and gamepad lookup tables.
- **Predictable, zero-allocation O(1) query performance.** States are stored in contiguous,
  fixed-capacity arrays indexed via direct enum integer arithmetic, eliminating hash table
  overhead, pointer indirection, and dynamic heap allocations during frame execution.
- **Ergonomic, domain-specific polling APIs for gameplay engineers.** Locomotion systems query
  `isScancodeDown()`, camera controllers query `mouse.getDelta()`, and vehicle systems query
  `gamepad.getLeftStick()` without unnatural parameter passing or generic polymorphic casts.
- **Encapsulated multi-controller player slot architecture.** Each `IGamepad` instance encapsulates
  a single logical player slot (`Player1` through `Player8`), providing a clean boundary for
  split-screen setups and isolating device hotplugging logic from actor simulation code.
- **Modular unit testability and hardware mocking.** Domain interfaces (`IKeyboard`, `IMouse`,
  `IGamepad`) can be mocked independently in automated test suites, allowing character locomotion
  or menu logic to be verified without initializing native OS display servers or hardware
  peripherals.

### Negative

- **Increased class and interface surface area.** Maintaining dedicated interfaces (`IKeyboard`,
  `IMouse`, `IGamepad`, `IInputSystem`) and their generic implementations requires more initial
  boilerplate and header files than a single monolithic structure.
- **Per-frame coordination dispatch overhead.** The master `GenericInputSystem` must iterate
  through all connected devices to invoke `beginFrame()` and `releaseAllInputs()`, introducing a
  small loop dispatch cost at the start of each frame.
- **Dual access path cognitive burden.** Gameplay programmers can query inputs either via the master
  `IInputSystem` convenience helpers or through direct device accessors
  (`getKeyboard().isScancodeDown()`), requiring clear codebase conventions to ensure consistent
  usage across gameplay modules.
