# ADR-0023: Zero-Allocation Thread Handoff via Suspended Creation and OS Synchronization

> To prevent heap allocations and dangling pointers during OS thread creation, the engine mandates
> a synchronized handoff protocol where threads are spawned in a suspended state
> (`CREATE_SUSPENDED`). Startup parameters (including string names and context pointers) are passed
> via a parent-stack-allocated payload, and the parent thread blocks on an OS event until the child
> securely copies the data to its own local stack.

![Proposed][badge-proposed]

## Context

Spawning an operating system thread requires passing startup arguments from the calling thread
(the parent) to the newly created thread (the child). At a minimum, the child requires an entry
function pointer and an opaque context pointer. In an engine runtime, threads also require a
human-readable name for CPU profilers (such as Tracy, Superluminal, and PIX), a target stack size,
and hardware scheduling attributes like core affinity and priority.

In C++, passing startup parameters across a newly spawned thread boundary exposes a classic
lifetime dilemma:

1. Heap allocation (`new ThreadStartPayload`): Allocating the context packet on the heap grants it
   an independent lifetime, allowing the parent thread to continue immediately. However, dynamic
   memory allocation violates the engine zero-allocation runtime rule. Invoking general-purpose
   heap allocators during thread creation risks memory fragmentation, triggers heap lock
   contention, and creates cleanup hazards if thread creation fails midway.
2. Unsynchronized stack references: Allocating the parameter packet on the parent thread stack and
   passing its pointer to the child thread without synchronization introduces a fatal race
   condition. The parent thread may return from its spawning function and unwind its stack frame
   before the OS scheduler ever dispatches the child thread. When the child thread finally runs,
   reading from that address triggers a use-after-free crash on corrupted stack memory.
3. Global or static storage: Using static pre-allocated memory buffers eliminates heap allocations
   but destroys reentrancy. Spawning multiple worker threads concurrently during engine boot or
   task pool initialization results in concurrent data races on the static buffer.

Standard library implementations such as `std::thread` and `boost::thread` resolve this dilemma by
allocating a shared heap control block (such as `new std::__thread_execute`) that manages the
lifetime of arguments through smart pointers and internal condition variables.

In a deterministic game engine, thread spawning during engine startup, worker pool initialization,
or subsystem bootstrapping must remain free of dynamic heap allocations and free of race conditions.
The engine requires a mechanical pattern that guarantees argument lifetime safety using only stack
memory and operating system primitives.

## Decision

We mandate a synchronized handoff protocol that combines suspended thread creation with operating
system kernel events. The parent thread allocates the startup payload on its local stack, spawns the
child thread in a suspended state (`CREATE_SUSPENDED`), and blocks on a kernel event until the child
copies all parameters to its own stack.

### Handoff Protocol Sequence

The handoff protocol proceeds across six explicit phases:

1. Stack-Allocated Context: The parent thread defines a `ThreadStartPayload` instance directly on
   its stack frame, populating the function pointer, user context pointer, and copying the UTF-8
   thread name into a fixed 64-byte character array.
2. Creation in Suspended State: The parent creates a Win32 manual-reset event via `CreateEventW`
   and spawns the thread using `_beginthreadex` with the `CREATE_SUSPENDED` flag. The operating
   system allocates the kernel thread object, Thread Environment Block (TEB), and execution stack,
   but halts execution before running the entry trampoline.
3. Pre-Execution Configuration: While the child remains suspended, the parent applies OS-level CPU
   core affinity (`SetThreadAffinityMask`) and scheduling priority (`SetThreadPriority`). If
   configuration fails and the caller set `failOnConfigError`, the parent terminates the suspended
   thread immediately before it ever begins executing.
4. Resumption and Dual-Wait: The parent calls `ResumeThread` and immediately enters a kernel wait
   via `WaitForMultipleObjects`, listening to both the handoff event and the child thread handle.
   Waiting on both handles prevents the parent from deadlocking if the child crashes or terminates
   prematurely before signaling.
5. Child Stack Copy and Signaling: The child begins executing inside `threadTrampoline`. It copies
   the entry pointer, user data pointer, and thread name into local stack variables, registers the
   thread name with the debugger via `SetThreadDescription`, and signals the manual-reset event
   via `SetEvent`.
6. Parent Unblock and Stack Teardown: The signaled event unblocks the parent. The parent closes the
   kernel event handle and returns from `Thread::start()`. The parent stack frame unwinds safely
   because the child operates entirely on its own stack copy.

### Architectural Invariants

1. **Zero Dynamic Memory Allocation:** Spawning a thread must never invoke general-purpose heap
   allocators (`malloc`, `free`, `new`, `delete`). All handoff data structures must reside on the
   parent thread stack and be copied to the child thread stack.
2. **Synchronous Handoff Boundary:** The parent thread must not return from `Thread::start()` until
   the child thread has fully ingested all parameters and signaled completion. Asynchronous
   fire-and-forget thread spawning is forbidden.
3. **Atomic Pre-Execution Configuration:** Thread affinity and scheduling priorities must be
   applied while the child thread is suspended, preventing transient scheduling on incorrect CPU
   cores.
4. **Failure Isolation:** The parent must never wait on a single naked synchronization primitive
   without accounting for child process failure. It must monitor both the handoff completion event
   and the thread handle to guard against premature termination.

### Implementation Pattern

The following excerpt from `WindowsThread.cpp` demonstrates the stack-allocated payload, suspended
creation, and dual-handle synchronization:

```cpp
namespace gp::platform::windows::detail
{

constexpr gp::UInt32 kMaxThreadNameBytes = 64u;

struct ThreadStartPayload
{
    ThreadEntryFunction entry = nullptr;
    void* userData = nullptr;
    HANDLE handoffEvent = nullptr;
    char name[kMaxThreadNameBytes] = {};
};

gp::UInt32 __stdcall threadTrampoline(void* rawPayload) noexcept
{
    auto* payload = static_cast<ThreadStartPayload*>(rawPayload);

    // Deep copy parameters onto child thread stack
    const ThreadEntryFunction entry = payload->entry;
    void* const userData = payload->userData;
    setCurrentThreadDebuggerName(payload->name);

    // Release parent from stack wait
    ::SetEvent(payload->handoffEvent);

    return entry(userData);
}

} // namespace gp::platform::windows::detail

ThreadResult Thread::start(const ThreadDesc& desc) noexcept
{
    const HANDLE handoffEvent = ::CreateEventW(nullptr, TRUE, FALSE, nullptr);
    if (handoffEvent == nullptr)
    {
        return ThreadResult::CreationFailed;
    }

    detail::ThreadStartPayload payload{};
    payload.entry = desc.entry;
    payload.userData = desc.userData;
    payload.handoffEvent = handoffEvent;
    detail::copyThreadName(payload.name, desc.name);

    gp::UInt32 winThreadId = 0u;
    const uintptr_t rawHandle = ::_beginthreadex(
        nullptr,
        static_cast<gp::UInt32>(desc.stackSize),
        &detail::threadTrampoline,
        &payload,
        CREATE_SUSPENDED,
        &winThreadId
    );

    if (rawHandle == 0u)
    {
        ::CloseHandle(handoffEvent);
        return ThreadResult::CreationFailed;
    }

    m_handle = reinterpret_cast<NativeHandle>(rawHandle);
    m_threadId = static_cast<ThreadId>(winThreadId);

    // Configure thread prior to scheduling
    if (desc.affinityMask != kNoAffinityMask)
    {
        (void)setAffinity(desc.affinityMask);
    }
    if (desc.priority != ThreadPriority::Normal)
    {
        (void)setPriority(desc.priority);
    }

    if (::ResumeThread(static_cast<HANDLE>(m_handle)) == static_cast<DWORD>(-1))
    {
        ::TerminateThread(static_cast<HANDLE>(m_handle), 0);
        ::CloseHandle(static_cast<HANDLE>(m_handle));
        ::CloseHandle(handoffEvent);
        return ThreadResult::ResumeFailed;
    }

    // Wait for handoff completion or early termination
    HANDLE waitHandles[2] = { handoffEvent, static_cast<HANDLE>(m_handle) };
    const DWORD waitStatus = ::WaitForMultipleObjects(2, waitHandles, FALSE, INFINITE);
    ::CloseHandle(handoffEvent);

    if (waitStatus != WAIT_OBJECT_0 && waitStatus != (WAIT_OBJECT_0 + 1))
    {
        return ThreadResult::WaitFailed;
    }

    return ThreadResult::Success;
}
```

## Alternatives Considered

### Option A: Heap Allocation of Startup Context (`new ThreadStartPayload`)

Allocate a parameter block on the dynamic heap using `malloc` or `operator new`, passing the raw
heap pointer to the OS thread entry point. The child thread assumes ownership and frees the block
upon completion or after copying.

**Why rejected:** Dynamic heap allocation violates the engine zero-allocation guarantee for runtime
code. General-purpose heap allocators introduce unpredictable latency and heap fragmentation. In
addition, if the OS fails to create the thread or the thread terminates unexpectedly before
executing the trampoline, the allocated block leaks unless tracked by recovery logic.

### Option B: Fire-and-Forget Asynchronous Creation without Wait

Allocate the startup structure on the parent stack and spawn the thread without blocking on a kernel
event, assuming the child will read the values before the parent function exits.

**Why rejected:** This pattern guarantees memory corruption and race conditions. Modern operating
system schedulers offer no timing guarantees regarding when a new thread will be scheduled relative
to its parent. In multicore systems, the parent thread will routinely return and unwind its stack
frame before the child thread executes its first instruction. The child thread subsequently reads
invalid memory, causing crashes or silent memory corruption.

### Option C: Static or Thread-Local Pre-Allocated Buffer

Allocate a fixed global buffer or use thread-local storage (`thread_local`) to hold startup
parameters during thread handoff.

**Why rejected:** Global static buffers break reentrancy. When multiple systems spawn threads
concurrently (such as during parallel engine initialization or dynamic job worker scaling), threads
corrupt each other's parameters unless protected by global mutexes. Thread-local storage avoids
cross-thread contention but increases thread control block memory overhead and complicates lifecycle
management across dynamic module boundaries.

## Consequences

### Positive

- **Zero dynamic heap allocations:** Thread creation uses stack memory exclusively, preventing heap
  fragmentation and eliminating allocation lock contention during engine startup.
- **Elimination of dangling pointer races:** The synchronous kernel event wait guarantees that the
  parent stack frame remains valid until the child finishes copying all startup parameters.
- **Atomic pre-execution configuration:** Spawning the thread in a suspended state allows thread
  affinity and priority to be established before the thread executes any code, preventing transient
  scheduling on unintended CPU cores.
- **Resilience against child crashes:** Waiting on both the handoff event and the thread handle
  prevents the parent thread from deadlocking if the child thread fails or terminates prematurely.

### Negative

- **Synchronous parent thread latency:** The parent thread blocks until the OS scheduler wakes the
  child thread and the child signals the event, introducing a brief context switch stall.
- **Kernel handle allocation overhead:** Creating and destroying a Win32 event (`CreateEventW` and
  `CloseHandle`) consumes OS kernel handles and incurs user-to-kernel transition costs.
- **Fixed-capacity thread naming:** Thread names are constrained to a fixed 64-byte stack
  buffer, truncating longer names.
