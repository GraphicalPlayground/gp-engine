# ADR-0026: Two-Tier Backpressure and Critical Reserve Admission in Lock-Free Event Queues

> High-polling-rate peripherals (8000 Hz mice, controller IMUs) can saturate a fixed-capacity
> lock-free ring buffer during temporary Game Thread stalls, causing critical discrete state
> transitions (such as `KeyState::Released` or `WindowAction::CloseRequested`) to be dropped and
> leaving the engine in a desynchronized "stuck key" state. To prevent this while maintaining a
> non-blocking OS message pump, the event producer enforces a two-tier admission policy:
> high-frequency continuous events (`Mouse::Moved`, `Gamepad::AxisMoved`, `Sensor`,
> `Touch::Motion`) are shed once free ring buffer capacity drops below a reserved threshold
> (`criticalReserveBytes`), preserving dedicated headroom strictly for discrete lifecycle and
> button-state transitions.

![Proposed][badge-proposed]

## Context

Modern gaming peripherals poll at high frequencies: 1000 Hz, 4000 Hz, and 8000 Hz USB mice,
along with high-frequency inertial measurement units (IMU gyro and accelerometers) on modern
gamepads. An 8000 Hz mouse emits raw motion packets every 125 microseconds. Under normal
execution, the Game Thread drains the single-producer single-consumer (SPSC) event ring
buffer once per frame.

Frame hitches on the Game Thread can pause event consumption for 50 ms to 200 ms. These
pauses stem from synchronous pipeline state object (PSO) compilation, heavy asset streaming,
garbage collection, or scene transitions. During a 100 ms stall, an 8000 Hz mouse produces
800 motion packets. In a fixed-capacity SPSC ring buffer (such as 64 KB or 256 KB), this flood
of continuous updates quickly fills available capacity.

### The Uniform Drop Failure Mode

When a naive ring buffer fills up, it either drops incoming packets at the tail or overwrites
unread packets at the head. Treating all packets uniformly causes severe gameplay bugs:

- **Continuous motion events** (`Mouse::Moved`, `Mouse::Wheel`, `Gamepad::AxisMoved`, `Sensor`,
  `Touch::Motion`) represent transient samples. Dropping an intermediate motion packet
  causes a brief jump in cursor delta, but subsequent packets supply the latest coordinates.
  Application state remains valid.
- **Discrete state transitions** (`Key::Pressed`, `Key::Released`, `MouseButton::Pressed`,
  `MouseButton::Released`, `WindowAction::CloseRequested`, `WindowAction::Resized`,
  `DisplayEvent`, `ApplicationEvent`) represent state changes that the engine must process.

If a player releases a movement key or fire button while the queue is full of mouse packets,
a uniform drop policy discards the `Key::Released` or `MouseButton::Released` event. The Game
Thread never learns that the key was released. The engine remains in an unintended continuous
walk or continuous firing state until the user presses and releases the same button again.
Dropping window lifecycle events such as `WindowAction::CloseRequested` or
`WindowAction::Resized` breaks window manager synchronization, leaving orphaned windows or
mismatched render targets.

### The Blocking Anti-Pattern

An alternative approach forces the producer to block (using a mutex, condition variable, or
spin loop) when the queue is full until the Game Thread frees space. This approach fails on
desktop platforms.

The event producer runs inside the OS message pump on the main platform thread (such as Win32
`PeekMessage`/`DispatchMessage` or SDL3 `SDL_PumpEvents`). If the OS thread blocks waiting for
the Game Thread during a hitch, the message pump halts. On Windows, a thread that stops
pumping messages for several seconds causes the Desktop Window Manager (DWM) to mark the
window as unresponsive. The OS replaces the client area with a ghost window bitmap and shows a
process termination dialog to the user. The OS message pump must never block.

## Decision

We implement a two-tier admission policy with a configurable critical reserve threshold
(`criticalReserveBytes`) in `gp::hal::ApplicationBackendDesc` and enforce it in
`SDL3ApplicationBackend`.

### Two-Tier Admission Policy

Event admission splits into two tiers based on semantic criticality:

1. **Tier 1: Continuous and Ephemeral Events**
   - Applies to: `Mouse::Moved`, `Mouse::Wheel`, `Gamepad::AxisMoved`, `Sensor`,
     `Touch::Motion`.
   - Admission Condition: `freeCapacityBytes > criticalReserveBytes + eventSize`.
   - Behavior: When free capacity falls to or below `criticalReserveBytes`, the producer sheds
     continuous packets immediately. The producer increments telemetry counters
     (`shedContinuousCount`) and returns without blocking the OS message loop.

2. **Tier 2: Discrete and Critical State Events**
   - Applies to: `Key::Pressed`, `Key::Released`, `MouseButton::Pressed`,
     `MouseButton::Released`, `WindowAction::*`, `DisplayEvent`, `ApplicationEvent`,
     `DeviceChange`.
   - Admission Condition: `freeCapacityBytes >= eventSize`.
   - Guarantee: Because Tier 1 events halt once free space hits `criticalReserveBytes`, the
     queue retains dedicated reserve capacity strictly for discrete state changes. Even
     during extended Game Thread hitches, discrete button releases and lifecycle events
     succeed.

### Subsystem Structure

The two-tier policy spans configuration in the HAL base module and admission logic in the
SDL3 platform backend:

```text
source/runtime/hal/
  base/
    public/
      backend/
        ApplicationBackendDesc.hpp  <-- criticalReserveBytes configuration
  sdl3/
    private/
      backend/
        SDL3ApplicationBackend.cpp  <-- commitFixedEvent & two-tier admission logic
```

In `SDL3ApplicationBackend.cpp`, `commitFixedEvent` verifies remaining buffer capacity against
the critical reserve before writing:

```cpp
template <typename PayloadT>
GP_FORCEINLINE_HINT void ApplicationBackend::commitFixedEvent(
    gp::SPSCByteRingBuffer& stream,
    gp::hal::event::EventCategory category,
    const PayloadT& payload,
    bool isContinuous,
    EventPumpStats& stats
) const noexcept
{
    constexpr gp::USize kTotalPacketBytes =
        sizeof(gp::hal::event::EventHeader) + sizeof(PayloadT);

    // Tier 1: Shed high-frequency continuous motion if free space falls into reserve
    if (isContinuous &&
        !stream.canWrite(kTotalPacketBytes + m_config.criticalReserveBytes)) [[unlikely]]
    {
        ++stats.shedContinuousCount;
        return;
    }

    const gp::hal::event::EventHeader header{
        .category = category,
        .payloadSize = static_cast<gp::UInt16>(sizeof(PayloadT))
    };

    if (stream.tryWritePacket(header, &payload, sizeof(PayloadT))) [[likely]]
    {
        ++stats.pushedCount;
        stats.bytesWritten += kTotalPacketBytes;
    }
    else
    {
        ++stats.droppedCriticalCount;
    }
}
```

### Architectural Invariants

1. **Non-Blocking Producer Execution:** The event producer never yields, sleeps, or spins on
   synchronization primitives when the queue is saturated. Execution returns immediately after
   shedding or enqueuing.
2. **Dedicated Headroom Preservation:** Continuous events are rejected when available capacity
   is less than or equal to `criticalReserveBytes + packetSize`. Discrete events retain
   exclusive access to the remaining `criticalReserveBytes`.
3. **Hardware Arrival Monotonicity:** Admitted events are written in exact hardware arrival
   order via the SPSC lock-free byte stream. Discarding continuous events does not reorder
   surrounding discrete transitions.
4. **Deterministic Telemetry Accounting:** Shed continuous events increment
   `shedContinuousCount`, and unadmitted discrete events increment `droppedCriticalCount`.
   The backend surfaces these counters without dynamic memory allocation.

### Architecture Comparison Matrix

<!-- markdownlint-disable MD013 -->
| Strategy | Stuck Key Prevention | OS Pump Responsiveness | Ephemeral Shedding Support | Implementation Complexity |
| :--- | :--- | :--- | :--- | :--- |
| **Naive Drop-Tail** | Fails (drops release events) | Maintained (non-blocking) | No (uniform drop) | Minimal |
| **Head-Overwrite (Drop-Head)** | Fails (overwrites release events) | Maintained (non-blocking) | No (corrupts TLV framing) | High |
| **Producer-Blocking** | Maintained (blocks until drained) | Fails (triggers OS ghosting) | No (forces waiting) | Moderate |
| **Two-Tier Critical Reserve** | Maintained (reserved headroom) | Maintained (non-blocking) | Yes (selective shedding) | Low |

## Alternatives Considered

### Option A: Dynamic Queue Growth (Reallocating Ring Buffer)

Reallocate a larger backing buffer on the producer thread when the ring buffer approaches
capacity.

**Why rejected:** Dynamic memory allocation on the time-critical OS message thread introduces
variable latency and heap contention. Reallocating the backing array during concurrent reads
requires coordinating cursor updates with the Game Thread, which invalidates wait-free SPSC
invariants and necessitates complex synchronization such as epoch-based reclamation.

### Option B: Producer Blocking (Condition Variable or Spinlock)

Suspend the OS message pump using a condition variable or spinlock until the Game Thread
drains queued events and restores capacity.

**Why rejected:** Blocking the OS message pump during game hitches causes operating system
window managers to flag the process as unresponsive. On Windows, failing to service the
Win32 message loop triggers desktop window manager ghosting and prompts users to terminate
the process. The OS message pump must process messages without blocking.

### Option C: Overwriting Oldest Packets (Drop-Head Ring Buffer)

Overwrite the oldest unread packets at the head of the circular buffer when capacity is
exhausted.

**Why rejected:** Discards earlier discrete transitions that the Game Thread has not yet
processed. If a user presses and releases a button, incoming mouse movements could overwrite
the unread release packet, causing the Game Thread to observe only the press event.
Overwriting also breaks variable-length TLV byte stream parsing: overwriting an unread packet
header corrupts length markers and causes deserialization failures on the consumer thread.

## Consequences

### Positive

- **Prevents desynchronized stuck keys.** Reserving dedicated buffer capacity guarantees that
  key release and mouse button release events survive temporary Game Thread stalls, avoiding
  infinite movement or firing states.
- **Preserves OS message pump responsiveness.** The platform event loop never blocks or spins
  during queue saturation, avoiding desktop window manager unresponsive warnings.
- **Zero dynamic memory allocation.** Shedding continuous packets executes as an integer
  comparison against available bytes without allocating memory or calling kernel APIs.
- **Clear diagnostic telemetry.** Dedicated telemetry counters track shed continuous packets
  and dropped discrete packets, simplifying performance profiling during engine hitches.

### Negative

- **Reduced spatial resolution during severe stalls.** When the Game Thread stalls for several
  hundred milliseconds, mouse movement packets during the stall are shed, causing an observable
  cursor jump once processing resumes.
- **Reserve capacity tuning requirements.** If `criticalReserveBytes` is configured too small,
  bursts of discrete events can exhaust the reserve; if set too large, usable capacity for
  continuous events is unnecessarily restricted.
