# ADR-0008: GPBT Extracted to an Independent, Versioned Repository

> Extracts the GPBT build tool into a standalone, version-controlled repository linked as a Git
> submodule, decoupling its release cadence from the main engine.

![Accepted][badge-accepted]

## Context

[ADR-0003](./ADR-0003.md) established the Graphical Playground Build Tool (GPBT) as a CMake
orchestration layer inside the engine's `cmake/` directory. Keeping the build tool in the same
repository simplified early iteration and avoided version-coordination overhead.

As the engine matured, two problems emerged:

1. **GPBT has value beyond the GP Engine.** Its declarative module system, two-pass dependency
   resolution, and `public/private/internal` enforcement apply to any C++ monorepo. Embedding it
   inside the engine repository prevents other projects from using it without forking the engine.
2. **GPBT's release cadence diverges from the engine's.** A bug fix in GPBT's scanner should not
   require an engine release to propagate, and an engine API change should not force a GPBT version
   bump.

## Decision

GPBT is extracted to its own repository at
[`GraphicalPlayground/gp-build-tool`](https://github.com/GraphicalPlayground/gp-build-tool) and is
no longer committed directly into the GP Engine source tree.

The GP Engine's `cmake/` directory holds a pinned Git submodule pointing to a tagged release of
GPBT. The engine's `CMakeLists.txt` includes GPBT via:

```cmake
include(cmake/gp-build-tool/gp-build-tool.cmake)
```

The submodule pin keeps builds reproducible: every contributor, CI run, and release uses the exact
same version of GPBT. Updating the pin is a deliberate PR when the engine adopts a new GPBT release.

### What changes

<!-- markdownlint-disable MD013 -->
| Before | After |
| --- | --- |
| `cmake/gp-build-tool/` committed in engine repo | Git submodule at a tagged GPBT release |
| GPBT version = engine version | GPBT has its own independent semver |
| Fixes require an engine commit | Fixes release in GPBT; engine updates pin |
| No external users of GPBT | Any CMake C++ project can adopt GPBT |
<!-- markdownlint-enable MD013 -->

### What does not change

- The `cmake/` directory structure is identical from the engine's perspective.
- All GPBT macros (`gpStartModule`, `gpAddDependency`, `gpStartPlugin`, etc.) keep the same
  semantics.
- GPBT applies the same `public/internal/` split to its own repository: `gp-build-tool.cmake` is
  the single public entry point, internal helpers live under `internals/`, and tests live under
  `tests/`.

### Submodule initialization

New contributors initialize the submodule with:

```sh
git clone --recurse-submodules https://github.com/GraphicalPlayground/gp-engine.git
```

Or, for an already-cloned repository:

```sh
git submodule update --init --recursive
```

The `.devcontainer/` setup (see [ADR-0005](./ADR-0005.md)) runs this automatically.

## Alternatives Considered

### Option A: Keep GPBT embedded in the engine repository (status quo)

No extraction; GPBT continues to live in `cmake/` as committed source files.

**Why rejected:** Prevents other projects from adopting GPBT without forking the engine, couples
GPBT's release cadence to the engine's, and forces GPBT contributors to work inside the full engine
repository.

### Option B: Publish GPBT as a CMake package (`find_package`)

Extract GPBT and publish it to a CMake package registry (vcpkg, Conan, or the CMake Package
Registry). Consumers find it via `find_package(GPBT)`.

**Why rejected:** CMake package management for build-system tooling (as opposed to runtime
libraries) is fragmented across platforms. A Git submodule records the exact commit in `.gitmodules`
and Git history without external package infrastructure.

### Option C: Copy GPBT into consuming projects (vendoring without submodule)

Distribute GPBT as a tarball or zip that consuming projects copy into their `cmake/` directories.

**Why rejected:** No update mechanism; bug fixes require manually re-copying files, and GPBT's Git
history is lost inside the consuming project. A submodule keeps reproducible offline builds while
preserving history and updates.

### Option D: Extract to a separate directory in the same monorepo

Keep GPBT in the engine's monorepo in a separate root-level directory (e.g., `gp-build-tool/`)
treated as a logically distinct project.

**Why rejected:** Solves neither release-cadence decoupling nor external reuse. GPBT remains
visible only to those who clone the engine repository, and its version stays tied to the engine.

## Consequences

### Positive

- **GPBT is reusable by other C++ projects.** Any project that wants declarative CMake module
  management with `public/private/internal` enforcement can adopt GPBT independently.
- **Release cadence is decoupled.** A GPBT patch release does not require a GP Engine release.
- **The engine's build is reproducible.** The submodule pin guarantees that a checked-out commit of
  the engine builds with the exact same GPBT version.
- **GPBT contributions are scoped.** A contributor fixing a GPBT bug works in the GPBT repository
  without touching the engine repository, keeping PRs small.
- **GPBT has its own changelog, issues, and release notes.**

### Negative

- **Submodule UX is easy to trip over.** Forgetting `--recurse-submodules` on clone, or forgetting
  `git submodule update` after a `git pull` that bumps the GPBT pin, breaks builds. The
  `.devcontainer/` setup and `CONTRIBUTING.md` document this.
- **Two repositories to maintain.** GPBT bug reports, PRs, and releases live in a separate GitHub
  repository.
- **Submodule pin updates require a PR.** Adopting a GPBT bug fix requires opening a PR in the
  engine repository to bump the submodule pin. Explicit PRs make adoption reviewable, at the cost of
  extra latency.
