# ADR-0019: Type-Length-Value (TLV) Byte-Stream for Cross-Thread Event Routing

> Rejects fixed-size Tagged Unions and polymorphic event objects in favor of a contiguous raw byte
> stream (`EventHeader` + payload). This eliminates the "Largest Payload Problem," natively
> supports variable-length data (like file drop paths or UTF-8 text input), and maximizes CPU
> cache efficiency.

![Proposed][badge-proposed]

## Context

Production game engines process input and operating system notifications across an asynchronous
thread boundary. An operating system message pump (such as SDL3, Win32 `GetMessage`, or Cocoa
`nextEventMatchingMask`) polls events on an OS thread, while the engine simulation updates state on
the Game Thread. Transporting events across this boundary requires a lock-free queue that avoids OS
mutexes, prevents dynamic memory allocations, and provides temporal ordering.

Engine architectures typically evaluate two common designs for cross-thread event queues:
fixed-size tagged unions and polymorphic heap objects. Both introduce severe physical memory and
performance failure modes.

### 1. The Largest Payload Problem of Tagged Unions

A tagged union represents events as an enumeration tag coupled with a C++ union containing all
possible event payload structs:

```cpp
struct Event
{
    EventCategory category;
    union
    {
        MouseEvent mouse;
        KeyboardEvent keyboard;
        WindowEvent window;
        TextInputEvent textInput;
        DropEvent drop;
    };
};
```

In C++, the memory footprint of a `union` is determined by its largest member, rounded up to the
strictest alignment requirement among its members.

Discrete peripheral events have compact payloads:

- A `MouseEvent` requires 16 to 32 bytes (window identifier, coordinates, relative deltas, button
  states).
- A `KeyboardEvent` requires 16 bytes (window identifier, keycode, scancode, modifiers, state).
- A `WindowEvent` requires 16 bytes (window identifier, action enum, union of position or extent
  coordinates).

However, desktop operating systems also generate events containing variable-length string data:

- Drag-and-drop file paths (`DropEvent`), where users drop external files onto an engine window. On
  Windows, file paths can reach `MAX_PATH` (260 bytes) or extended NT path lengths up to 32,767
  bytes.
  A practical static inline buffer for dropped paths requires 1024 or 2048 bytes.
- Text input and Input Method Editor (IME) composition (`TextInputEvent`), where committed UTF-8
  text
  or active composition strings (such as Japanese Kanji or Korean Hangul) can span dozens to
  hundreds
  of bytes.

If `DropEvent` allocates an inline buffer of 2048 bytes to store dropped file paths, `sizeof(Event)`
becomes 2056 bytes (2048-byte buffer + 2-byte enum tag + 6 bytes alignment padding). Consequently,
every single event placed into the circular ring buffer consumes 2056 bytes of physical memory, even
when the event is a 16-byte key press or a relative mouse movement packet. Over 99 percent of the
allocated queue space for that packet consists of unused trailing slack bytes.

```text
Tagged Union Queue Slot Memory Waste (Union Size = 2056 Bytes):

+------------------------------------------------------------------------------------+
| Tag (2B) | Pad (6B) | MouseEvent Payload (16B) | Unused Slack Space (2032 Bytes)   |
+------------------------------------------------------------------------------------+
|<------------------------------ Total Slot: 2056 Bytes ---------------------------->|
```

### 2. Queue Exhaustion Under High-Frequency Polling

The memory bloat of tagged unions creates a direct reliability failure under modern gaming
peripherals. In a 64 KB (65,536 bytes) ring buffer, allocating 2056 bytes per entry yields at most
31
usable slots (reserving one slot to differentiate full and empty queue states):

$$\text{Usable Slots} = \left\lfloor \frac{65536}{2056} \right\rfloor - 1 = 31 \text{ slots}$$

High-performance gaming mice poll at rates of 1000 Hz, 4000 Hz, or 8000 Hz. At 8000 Hz, the
operating
system receives a hardware motion event every 125 microseconds (0.125 ms). A 31-slot queue fills
completely in:

$$31 \times 0.125\text{ ms} = 3.875\text{ ms}$$

If the Game Thread experiences a transient 4-millisecond hitch (caused by shader compilation, an
asynchronous asset streaming page fault, or OS thread preemption), the 31-slot queue exhausts its
capacity in less than 4 milliseconds. The message pump must either drop subsequent input packets or
block the OS thread. Dropped packets cause missed button releases, stuck key states, and dropped
gestures.

### 3. Allocation and Cache Penalties of Polymorphic Objects

An alternative approach allocates individual event objects on the heap and routes them through a
pointer queue:

```cpp
gp::SPSCRingBuffer<gp::UniquePtr<IEvent>> m_eventQueue;
```

This strategy avoids the Largest Payload Problem by sizing each allocation to its concrete type.
However, it violates engine real-time execution guarantees:

- **Allocator Contention:** Invoking `new` or `malloc` on the OS message pump thread enters the
  global
  heap allocator, acquiring internal memory manager locks and contending with worker threads.
- **Heap Fragmentation:** Allocating and freeing thousands of small event objects every second
  across
  millions of frames fragments the process heap.
- **Cache-Line Invalidation via Pointer Chasing:** When the Game Thread drains the queue, it reads
  an
  array of pointers referencing disparate memory addresses across the heap. Each event dispatch
  incurs an L1/L2 cache miss, serializing execution around memory fetch latency.

The engine requires an event transport mechanism that achieves high packing density, supports
variable-length payloads, eliminates heap allocations, and preserves strict chronological ordering.

## Decision

The engine adopts a contiguous Type-Length-Value (TLV) framing protocol over the lock-free
single-producer
single-consumer byte stream, `gp::SPSCByteRingBuffer` (`SPSCRingBuffer<gp::UInt8>`).

Instead of storing uniform-sized struct slots, the ring buffer stores a packed stream of raw bytes.
Every event packet consists of an exact 4-byte framing header (`EventHeader`) followed immediately
by its raw payload bytes.

```text
Contiguous Type-Length-Value (TLV) Stream Layout:

+-------------------+--------------------+-------------------+--------------------+
| EventHeader (4B)  | Event Payload (NB) | EventHeader (4B)  | Event Payload (MB) | ...
| Category | Length | Raw Event Bytes    | Category | Length | Raw Event Bytes    |
+-------------------+--------------------+-------------------+--------------------+
```

### 1. Header Layout and Framing Invariants

The packet header is defined in `source/runtime/hal/base/public/event/EventHeader.hpp`:

```cpp
namespace gp::hal::event
{

/// @brief Represents the framing header of an event, containing its category and payload size.
/// @details Stored as two 16-bit integers to produce an exact 4-byte framing header without padding.
struct EventHeader
{
    EventCategory category;   // 2 bytes (16-bit routing category enum)
    gp::UInt16 payloadSize;   // 2 bytes (0 to 65535 payload bytes)
};

static_assert(sizeof(EventHeader) == 4, "EventHeader must occupy exactly 4 bytes.");

}   // namespace gp::hal::event
```

Framing invariants:

1. `EventCategory` is explicitly typed as `gp::UInt16`.
2. `payloadSize` is an unsigned 16-bit integer representing the exact byte count of the payload
   following the header.
3. The struct contains zero compiler padding bytes (`sizeof(EventHeader) == 4`).
4. Alignment matches 2-byte and 4-byte boundaries without padding overhead.

### 2. Fixed-Size Event Packing

For discrete events with fixed structures, the payload size equals `sizeof(PayloadT)`. The total
number of bytes written to the ring buffer is:

$$\text{Total Packet Bytes} = \text{sizeof}(\text{EventHeader}) + \text{sizeof}(\text{PayloadT})$$

Examples of fixed packet sizes in the engine:

- `KeyboardEvent` (16 bytes payload) + `EventHeader` (4 bytes) = 20 bytes total.
- `MouseEvent` (16 bytes payload) + `EventHeader` (4 bytes) = 20 bytes total.
  (Extended 32-byte `MouseEvent` + `EventHeader` = 36 bytes total).
- `WindowEvent` (16 bytes payload) + `EventHeader` (4 bytes) = 20 bytes total.
  (Extended 24-byte display geometry payload + `EventHeader` = 28 bytes total).

```text
Fixed-Size Event Layout in Byte-Stream:

KeyboardEvent (20 Bytes Total):
+-----------------------------------+-----------------------------------------+
| Category: Keyboard (2B) | Len: 16 (2B) | KeyboardEvent POD Struct (16 Bytes)     |
+-----------------------------------+-----------------------------------------+

MouseEvent (20 Bytes Total):
+-----------------------------------+-----------------------------------------+
| Category: Mouse (2B)    | Len: 16 (2B) | MouseEvent POD Struct (16 Bytes)        |
+-----------------------------------+-----------------------------------------+
```

### 3. Variable-Size Event Packing

For events containing variable-length strings (`TextInputEvent`, `DropEvent`), the payload consists
of a fixed-size descriptor struct followed immediately by the raw UTF-8 string bytes. The descriptor
records the length of the string in its `byteLength` field:

$$\text{payloadSize} = \text{sizeof}(\text{DescriptorT}) + \text{trailingBytes}$$

$$\text{Total Packet Bytes} = \text{sizeof}(\text{EventHeader}) + \text{payloadSize}$$

For example, when a user types the 8-character string `"Gameplay"`, the message pump emits:

- `EventHeader`: `category = EventCategory::TextInput`, `payloadSize = 16 + 8 = 24`.
- `TextInputEvent`: 16-byte descriptor with `byteLength = 8`.
- Trailing Data: 8 raw UTF-8 bytes (`"Gameplay"`), with no trailing null terminator or padding in
  the stream.
- Total packet size: 4 + 16 + 8 = 28 bytes.

When a user drops a file path (`"C:/Assets/Textures/diffuse.png"`, 31 bytes):

- `EventHeader`: `category = EventCategory::Drop`, `payloadSize = 16 + 31 = 47`.
- `DropEvent`: 16-byte descriptor with `byteLength = 31`.
- Trailing Data: 31 raw UTF-8 bytes.
- Total packet size: 4 + 16 + 31 = 51 bytes.

```text
Variable-Size Event Layout in Byte-Stream:

TextInputEvent ("Gameplay", 28 Bytes Total):
+-----------------------+--------------------+-------------------------+--------------------+
| Category: Text (2B)   | Len: 24 (2B)       | TextInput POD (16B)     | "Gameplay" (8B)    |
+-----------------------+--------------------+-------------------------+--------------------+

DropEvent ("C:/Assets/Textures/diffuse.png", 51 Bytes Total):
+-----------------------+--------------------+-------------------------+--------------------+
| Category: Drop (2B)   | Len: 47 (2B)       | DropEvent POD (16B)     | Path Bytes (31B)   |
+-----------------------+--------------------+-------------------------+--------------------+
```

### 4. Packing Density and Hitch Resilience Comparison

Comparing storage density between a fixed 2056-byte tagged union queue and the TLV byte stream in a
64 KB ($65,536$ bytes) buffer:

<!-- markdownlint-disable MD013 -->
| Metric | Fixed-Size Tagged Union (2 KB Slots) | Contiguous TLV Byte-Stream (20B Mouse Packets) | Contiguous TLV Byte-Stream (36B Mouse Packets) |
| :--- | :--- | :--- | :--- |
| **Slot / Packet Size** | 2056 bytes | 20 bytes | 36 bytes |
| **Usable Queue Capacity** | 31 events | 3,276 events | 1,820 events |
| **Capacity Multiplier** | Baseline ($1\times$) | $105.6\times$ | $58.7\times$ |
| **Memory Utilization (Mouse)** | 0.78% (99.22% wasted slack) | 100% packed | 100% packed |
| **Hitch Buffer @ 1000 Hz** | 31.0 milliseconds | 3,276 milliseconds | 1,820 milliseconds |
| **Hitch Buffer @ 8000 Hz** | 3.875 milliseconds | 409.5 milliseconds | 227.5 milliseconds |
<!-- markdownlint-enable MD013 -->

Under an 8000 Hz peripheral polling rate, the TLV stream expands the queue's hitch absorption buffer
from 3.8 milliseconds to over 400 milliseconds. The Game Thread can stall for multiple frames
without
dropping input events.

```text
Memory Packing Density Comparison in 64 KB Ring Buffer:

Fixed Tagged Union (Max 31 events, 99% slack space):
+-----------------------------------------------------------------------------------------+
| Slot 0 (20B valid, 2028B slack) | Slot 1 (20B valid, 2028B slack) | ... | Slot 30       |
+-----------------------------------------------------------------------------------------+
[Exhausts in 3.8 ms at 8000 Hz]

Contiguous TLV Byte-Stream (3,276 events, 0% slack space):
+-----------------------------------------------------------------------------------------+
| Evt 0 (20B) | Evt 1 (20B) | Evt 2 (28B) | Evt 3 (20B) | Evt 4 (51B) | Evt 5 (20B) | ... |
+-----------------------------------------------------------------------------------------+
[Absorbs 409.5 ms of hitches at 8000 Hz]
```

### 5. Producer Implementation: Atomic Multi-Byte Writes

In `source/runtime/hal/sdl3/private/backend/SDL3ApplicationBackend.cpp`, the backend writes packets
using `commitFixedEvent` and `commitVariableEvent`:

```cpp
template <typename PayloadT>
GP_FORCEINLINE_HINT void ApplicationBackend::commitFixedEvent(
    gp::SPSCByteRingBuffer& stream,
    gp::hal::event::EventCategory category,
    const PayloadT& payload,
    bool isContinuous,
    EventPumpStats& stats
) const noexcept
{
    constexpr gp::USize kTotalPacketBytes = sizeof(gp::hal::event::EventHeader) + sizeof(PayloadT);

    // Tier 1 Backpressure: Shed high-frequency continuous motion events
    // if free space enters the critical reserve
    if (isContinuous && !stream.canWrite(kTotalPacketBytes + m_config.criticalReserveBytes)) [[unlikely]]
    {
        ++stats.shedContinuousCount;
        return;
    }

    const gp::hal::event::EventHeader header{
        .category = category,
        .payloadSize = static_cast<gp::UInt16>(sizeof(PayloadT))
    };

    if (stream.tryWritePacket(header, &payload, sizeof(PayloadT))) [[likely]]
    {
        ++stats.pushedCount;
        stats.bytesWritten += kTotalPacketBytes;
    }
    else
    {
        ++stats.droppedCriticalCount;
    }
}
```

For variable-length events, the descriptor and trailing string bytes are assembled in a small local
stack buffer before being written through `tryWritePacket`. This guarantees that the header,
descriptor, and trailing bytes are committed in a single atomic memory release store:

```cpp
template <typename DescriptorT>
GP_FORCEINLINE_HINT void ApplicationBackend::commitVariableEvent(
    gp::SPSCByteRingBuffer& stream,
    gp::hal::event::EventCategory category,
    const DescriptorT& descriptor,
    const void* trailingData,
    gp::UInt16 trailingBytes,
    EventPumpStats& stats
) const noexcept
{
    const gp::UInt16 totalPayloadSize = static_cast<gp::UInt16>(sizeof(DescriptorT) + trailingBytes);
    const gp::USize totalPacketBytes = sizeof(gp::hal::event::EventHeader) + totalPayloadSize;

    if (!stream.canWrite(totalPacketBytes)) [[unlikely]]
    {
        ++stats.droppedCriticalCount;
        return;
    }

    // Stack-pack descriptor and trailing UTF-8 string so tryWritePacket
    // commits in a single atomic release store
    alignas(8) gp::UInt8 combinedPayload[sizeof(DescriptorT) + kMaxVariablePayloadBytes];
    gp::memory::copyMemory(combinedPayload, &descriptor, sizeof(DescriptorT));

    if (trailingBytes > 0u && trailingData != nullptr) [[likely]]
    {
        gp::memory::copyMemory(combinedPayload + sizeof(DescriptorT), trailingData, trailingBytes);
    }

    const gp::hal::event::EventHeader header{
        .category = category,
        .payloadSize = totalPayloadSize
    };

    if (stream.tryWritePacket(header, combinedPayload, totalPayloadSize)) [[likely]]
    {
        ++stats.pushedCount;
        stats.bytesWritten += totalPacketBytes;
    }
    else
    {
        ++stats.droppedCriticalCount;
    }
}
```

### 6. Consumer Implementation: Framing Verification and Draining

In `source/runtime/application/private/Application.cpp`, `Application::drainEventStream()` drains
the
queue at the start of each frame tick:

```cpp
void Application::drainEventStream() noexcept
{
    using namespace gp::hal;
    using namespace gp::hal::event;

    while (!m_eventStream.isEmptyApprox())
    {
        EventHeader header{};
        if (!m_eventStream.tryPeekAt(0u, &header, sizeof(EventHeader))) [[unlikely]]
        {
            break;
        }

        const gp::USize totalPacketBytes = sizeof(EventHeader) + header.payloadSize;
        if (!m_eventStream.canRead(totalPacketBytes)) [[unlikely]]
        {
            break;
        }

        switch (header.category)
        {
        case EventCategory::Keyboard:
        {
            KeyboardEvent ev{};
            if (gp::detail::consumeFixedPayload(m_eventStream, ev))
            {
                m_inputSystem->onKeyboardEvent(ev);
                onKeyboardEvent(ev);
            }
            break;
        }

        case EventCategory::Mouse:
        {
            MouseEvent ev{};
            if (gp::detail::consumeFixedPayload(m_eventStream, ev))
            {
                m_inputSystem->onMouseEvent(ev);
                onMouseEvent(ev);
            }
            break;
        }

        case EventCategory::TextInput:
        {
            TextInputEvent desc{};
            if (header.payloadSize >= sizeof(TextInputEvent) &&
                m_eventStream.tryPeekAt(sizeof(EventHeader), &desc, sizeof(TextInputEvent)))
            {
                char textBuffer[gp::detail::kMaxDecodedStringBytes + 1u]{};
                const gp::UInt16 copyLen = (desc.byteLength <= gp::detail::kMaxDecodedStringBytes)
                                               ? desc.byteLength
                                               : static_cast<gp::UInt16>(gp::detail::kMaxDecodedStringBytes);

                if (copyLen > 0u)
                {
                    (void)m_eventStream.tryPeekAt(
                        sizeof(EventHeader) + sizeof(TextInputEvent),
                        textBuffer,
                        copyLen
                    );
                }
                textBuffer[copyLen] = '\0';
                m_eventStream.advanceConsumer(totalPacketBytes);

                onTextInputEvent(desc, StringView(textBuffer, copyLen));
            }
            else
            {
                m_eventStream.advanceConsumer(totalPacketBytes);
            }
            break;
        }

        default:
            m_eventStream.advanceConsumer(totalPacketBytes);
            break;
        }
    }
}
```

The decoding helper `consumeFixedPayload` peeks the payload directly into stack memory and advances
the consumer cursor in a single step:

```cpp
template <typename PayloadT>
[[nodiscard]] GP_FORCEINLINE_HINT bool
    consumeFixedPayload(gp::SPSCByteRingBuffer& stream, PayloadT& outPayload) noexcept
{
    if (!stream.tryPeekAt(sizeof(hal::event::EventHeader), &outPayload, sizeof(PayloadT))) [[unlikely]]
    {
        return false;
    }
    stream.advanceConsumer(sizeof(hal::event::EventHeader) + sizeof(PayloadT));
    return true;
}
```

## Alternatives Considered

### Option A: Fixed-Size Tagged Union Queue (`union EventData` in circular array)

Allocate a circular ring buffer storing uniform `Event` structs containing a category enum and a
tagged union of all possible event types.

**Why rejected:** Suffers from the Largest Payload Problem. If any event variant (such as
`DropEvent`
or `TextInputEvent`) includes an inline buffer for filesystem paths or localized text strings (1024
or
2048 bytes), every event in the queue occupies 2048+ bytes. In a 64 KB ring buffer, capacity is
limited
to 31 usable entries. An 8000 Hz mouse saturates this queue in 3.8 milliseconds, causing immediate
overflow and dropped inputs during minor frame hitches. Over 99 percent of ring buffer memory is
wasted as uninitialized slack bytes.

### Option B: Heap-Allocated Polymorphic Objects (`UniquePtr<IEvent>`)

Represent events as an inheritance hierarchy derived from an abstract base class `IEvent`,
allocating
each event dynamically on the heap (`gp::makeUnique<MouseEvent>()`) and storing pointers in an
`SPSCRingBuffer<UniquePtr<IEvent>>`.

**Why rejected:** Dynamic heap allocations on the OS message pump thread introduce cross-thread lock
contention within the memory manager, defeating the purpose of lock-free queueing. Allocating and
freeing thousands of event objects per second fragments virtual memory. Furthermore, pointer
indirection during queue draining destroys CPU data cache locality: reading each event requires
dereferencing a pointer to a distinct heap address, incurring repeated cache misses.

### Option C: Multiple Dedicated Queues per Event Type (MouseQueue, KeyQueue, WindowQueue)

Provide independent, type-specific ring buffers for each event category (for example,
`SPSCRingBuffer<MouseEvent>` and `SPSCRingBuffer<KeyboardEvent>`), sizing each queue to its specific
element type.

**Why rejected:** Destroys chronological event interleaving. If mouse button transitions and
keyboard
key presses are isolated in separate ring buffers, the Game Thread cannot reconstruct the exact
order
in which user actions occurred without attaching high-resolution hardware timestamps and performing
multi-way merge sorts across queues every frame tick. Additionally, managing multiple ring buffers
multiplies atomic cache-line synchronization overhead (each SPSC queue requires three 64-byte cache
lines) and complicates buffer sizing.

## Consequences

### Positive

- **Eliminates slack memory waste from the Largest Payload Problem.** Framing events with an
  explicit
  4-byte header and a payload matching only its required size allows mouse and keyboard packets to
  consume 20 bytes instead of 2056 bytes, reducing per-event memory overhead by over 99 percent.
- **Expands hitch resilience under high-frequency peripheral polling.** In a 64 KB ring buffer,
  20-byte
  mouse packets provide storage for 3,276 queued events rather than 31 entries in a 2048-byte tagged
  union queue. At an 8000 Hz polling rate, queue absorption headroom increases from 3.8 milliseconds
  to
  over 400 milliseconds, preventing dropped inputs during multi-frame hitches.
- **Transports variable-length text and drag-and-drop payloads without heap allocations.** Strings
  from
  OS IME text composition and file drop paths serialize directly into contiguous bytes in the ring
  buffer immediately following their fixed descriptor struct, eliminating dynamic memory allocations
  on both producer and consumer threads.
- **Maximizes CPU data cache locality during queue draining.** Packing consecutive events
  contiguously
  without alignment gaps allows the Game Thread to process dozens of events per 64-byte L1 data
  cache
  line, avoiding pointer indirection and memory latency.
- **Preserves strict chronological ordering across diverse event categories.** Routing all events
  through a single unified byte stream guarantees that input sequences (such as mouse clicks,
  modifier
  key transitions, and window focus changes) are drained and processed in the exact order emitted by
  the operating system.

### Negative

- **Requires framing headers and length validation on consumer reads.** Because events have
  non-uniform
  sizes, consumer threads cannot index entries using constant stride arithmetic (`buffer[index]`).
  Draining requires a two-step peek of the 4-byte header to determine packet length followed by
  length
  validation before decoding.
- **Complex ring-boundary wrap handling for multi-byte payloads.** When a multi-byte packet crosses
  the physical end of the circular buffer, read and write operations must split into two contiguous
  memory copy operations. The underlying `SPSCByteRingBuffer` handles two-chunk wrapping, adding
  minor
  branching compared to single-element indexing.
- **Requires stack buffers for consumer string decoding.** Variable-length payloads such as dropped
  file paths cannot be referenced by a persistent direct pointer inside the ring buffer once the
  consumer cursor advances. The consumer must copy the string into a temporary stack buffer or
  expose
  a scoped `gp::StringView` during the dispatch callback.
