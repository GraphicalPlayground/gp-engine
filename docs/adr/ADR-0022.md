# ADR-0022: Functional, Stateless Thread Execution over Object-Oriented Payloads

> Rejects object-oriented thread interfaces (e.g., `IRunnable`) and `std::thread` in favor of
> stateless, C-style function pointers with `void*` context payloads, eliminating virtual dispatch
> overhead and forced heap allocations to perfectly mirror low-level OS APIs and support
> data-oriented Job Systems.

![Proposed][badge-proposed]

## Context

Operating systems manage concurrent execution by dispatching hardware threads onto available
CPU cores. High-performance game engines require tight control over thread lifecycles, memory
layouts, and execution overhead to meet hard 16.6 ms or 8.3 ms frame deadlines.

Traditional threading abstractions introduce performance liabilities:

- **Polymorphic Object Overhead (`IRunnable`):** Object-oriented models derived from Java or
  early C++ frameworks require worker tasks to inherit from an interface (such as `IRunnable`
  or `Thread::Run()`). Each polymorphic object embeds a virtual table pointer (`vptr`). Passing
  an `IRunnable` across thread boundaries requires dynamic heap allocation
  (`new RunnableSubclass`) to preserve polymorphic lifetime across threads. Invoking the worker
  requires an indirect call through a virtual method table, creating instruction cache misses
  and branch target buffer pipeline stalls.
- **Hidden Allocations in `std::thread`:** The C++ standard library abstraction (`std::thread`)
  accepts arbitrary invocables and parameter packs through templated type erasure. Under MSVC,
  libc++, and libstdc++, the `std::thread` constructor dynamically allocates a state block
  (`std::tuple<DecayedArgs...>`) on the process heap via `::operator new` to transport decayed
  arguments into the platform entry trampoline. This dynamic heap allocation violates engine
  zero-allocation constraints during startup and runtime worker spawning.
- **Mismatch with Operating System Primitives:** Native OS threading APIs do not expose object
  hierarchies or type-erased closures. The Win32 kernel API (`CreateThread`, `_beginthreadex`)
  expects a raw function pointer `unsigned int (__stdcall*)(void*)`. The POSIX standard
  (`pthread_create`) expects `void* (*)(void*)`. Object-oriented wrappers add layers of
  glue code and synthetic indirection around straightforward OS interfaces.
- **Job System Data-Oriented Requirements:** Modern game architectures divide per-frame
  workloads into thousands of fine-grained jobs managed by task schedulers and fiber pools.
  These jobs consist of plain-old-data (POD) payloads processed by stateless routines.
  Forcing an object model onto worker threads complicates payload storage, causes false sharing
  across cache lines, and fragments memory lifetimes.

## Decision

We adopt a functional, stateless thread execution model for `gp-engine`. All hardware threads
execute through a C-style function pointer signature that accepts an opaque pointer to caller
data:

```cpp
using ThreadEntryFunction = gp::UInt32 (*)(void* userData);
```

Thread configuration and launch parameters are encapsulated within the plain-old-data (POD)
descriptor `ThreadDesc`:

```cpp
struct ThreadDesc
{
    const char* name = "gp::Worker";
    gp::USize stackSizeBytes = 0; // 0 uses OS default
    ThreadPriority priority = ThreadPriority::Normal;
    ThreadEntryFunction entryPoint = nullptr;
    void* userData = nullptr;
};
```

Platform-specific implementations map `ThreadEntryFunction` directly to host OS entry points:

- **Windows (`WindowsThread`):** The thread trampoline passes `ThreadEntryFunction` and
  `userData` to `_beginthreadex` via `unsigned int (__stdcall*)(void*)`.
- **POSIX (`LinuxThread`, `MacOSThread`):** The thread trampoline passes `ThreadEntryFunction`
  and `userData` to `pthread_create` via `void* (*)(void*)`.

### Architectural Invariants

1. **Stateless Function Pointer Contract:** Thread routines are defined strictly through the
   C-style function pointer `using ThreadEntryFunction = gp::UInt32 (*)(void* userData);`.
   Polymorphic base classes, virtual methods, and C++ closures with implicit heap state are
   forbidden at the thread boundary.
2. **Plain-Old-Data Execution Context:** Any payload passed to an OS thread is encapsulated in
   a single pointer (`void* userData`) pointing to contiguous, trivially copyable or
   caller-managed data.
3. **Zero Dynamic Allocation at Creation:** The threading layer performs zero calls to dynamic
   memory allocators during thread construction, launch, or termination. All runtime parameters
   travel via stack handoff or user-provided buffers.
4. **Direct Operating System ABI Mapping:** The entry point signature maps 1:1 to platform
   primitives (`LPTHREAD_START_ROUTINE` on Windows via `_beginthreadex`, `void* (*)(void*)` on
   POSIX `pthread_create`) through trivial, zero-cost trampolines without intermediate type
   erasure objects.

### Architectural Model Comparison

The functional model eliminates heap allocation and virtual dispatch while aligning with native
OS interfaces and job systems:

<!-- markdownlint-disable MD013 -->
| Architectural Metric | `IRunnable` OOP Model | `std::thread` Lambda Model | `gp::Thread` Function Pointer |
| :--- | :--- | :--- | :--- |
| **Allocation Count** | 1+ heap allocations (`new Runnable`) | 1 heap allocation (`std::tuple` state) | 0 heap allocations (stack handoff) |
| **Virtual Dispatch Cost** | Yes (vptr dereference + indirect call) | Optional (inlined or erased via function ptr) | None (direct function pointer call) |
| **Memory Footprint** | Object size + 8-byte `vptr` + heap overhead | Callable size + capture tuple + heap header | 0 extra bytes beyond user POD payload |
| **Compatibility with OS APIs** | Poor (requires bridging adapter object) | Poor (requires runtime decay trampoline) | Native (direct 1:1 match to OS callback ABI) |
| **Job System Friendliness** | Low (object lifetime bound to thread) | Low (hidden captures prevent pooling) | High (POD payloads fit fiber/job queues) |

## Alternatives Considered

### Option A: Classical OOP Polymorphism (`IRunnable` / `IThreadRunnable`)

Define an abstract base interface containing a virtual execution method:

```cpp
class IRunnable
{
public:
    virtual ~IRunnable() = default;
    virtual gp::UInt32 run() = 0;
};
```

**Why rejected:** Every polymorphic instance contains a hidden 8-byte virtual method table
pointer (`vptr`). Passing an `IRunnable` instance across a thread boundary requires dynamic
heap allocation to ensure object lifetime survives the spawning scope. Virtual method dispatch
incurs an indirect call via the virtual method table, creating branch target buffer misses and
instruction cache stalls on cold thread startups. Furthermore, binding execution to class
inheritance couples thread management to object hierarchies, violating data-oriented design
principles.

### Option B: Templated Type-Erased Closures (`std::function` or Templated Invocables)

Accept arbitrary callables, lambdas, or `std::function` objects:

```cpp
template <typename Invocable>
void spawn(Invocable&& callable);
```

**Why rejected:** Storing arbitrary callables requires type erasure. When lambda capture sizes
exceed small buffer optimization limits, closures invoke dynamic heap allocations. Even when
closures fit inline buffers, templating thread creation on arbitrary invocable types causes
template code bloat across translation units. Generating separate trampoline instantiations for
every unique lambda signature fragments binary symbols and prevents uniform ABI boundaries
across platform modules.

### Option C: Bound Member Function Pointers (`&MyClass::memberFunc`, `this`)

Allow callers to register class member functions directly with an instance pointer:

```cpp
template <typename T>
void spawn(T* instance, gp::UInt32 (T::*memberFunc)());
```

**Why rejected:** Member function pointers in C++ do not have a uniform representation.
Under MSVC, member function pointers require 8 bytes for single inheritance, 16 bytes for
multiple inheritance, and up to 24 bytes for virtual inheritance to account for `this`-pointer
adjustments and virtual base offsets. The C++ standard forbids casting member function pointers
to `void*` or standard function pointers. Supporting member functions would require allocating
an auxiliary adapter wrapper on the heap, introducing the memory overhead of Option A and
Option B while coupling thread management to class hierarchies.

## Consequences

### Positive

- **Zero dynamic heap allocations.** Thread creation and launch operate entirely without
  allocating memory from the process heap, eliminating lock contention and allocator
  fragmentation during worker startup.
- **Minimal instruction cache latency.** Direct invocation of a C-style function pointer avoids
  virtual method table dereferencing and branch prediction stalls on cold thread wakeups.
- **Seamless integration with job and fiber systems.** Decoupling functions from payloads allows
  worker threads to execute homogeneous loops over heterogeneous job queues, matching
  data-oriented task schedulers.
- **Deterministic binary ABI stability.** Using primitive function pointers and standard layout
  structs ensures identical calling conventions across dynamic link libraries and compiler
  versions without C++ template mangling disparities.
- **Direct alignment with OS kernel primitives.** Eliminating intermediary adapter wrappers
  simplifies debugging, crash dumps, and stack traces in native tools such as PIX, Tracy,
  and Visual Studio.

### Negative

- **Loss of compile-time parameter pack type safety.** Passing execution context through
  `void* userData` requires explicit static casting within the entry function, leaving type
  safety verification to programmer discipline.
- **Manual context lifetime management.** Callers must guarantee that data referenced by
  `void* userData` remains valid for the duration of thread execution, requiring explicit
  lifetime synchronization.
- **Boilerplate for member function execution.** Invoking a member function on a specific class
  instance requires writing a static member or free function trampoline that unpacks the
  instance pointer from `userData`.
