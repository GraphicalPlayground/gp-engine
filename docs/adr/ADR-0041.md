# ADR-0041: Three-Tier Engine Bootstrapping Topology (`gp::core`, `gp::application`, `gp::launch`)

> Enforces a strict upward Directed Acyclic Graph (DAG) separating foundational OS primitives
> (`gp::core`), the hot-reloadable runtime orchestrator (`gp::application`), and the static
> executable entry-point shell (`gp::launch`) so low-level subsystems can query boot parameters
> without circular module dependencies.

![Proposed][badge-proposed]

## Context

As `gp-engine` expands to include command-line parsing, OS directory resolution, dynamic library
loading (`.dll`/`.so`/`.dylib`), hardware crash handling, and the cross-platform OS entry point
(`main` / `WinMain` / `android_main`), placing all startup infrastructure inside `gp::application`
creates two critical architectural defects:

1. **Circular Module Dependencies:** Low-level modules (`gp::core`, `gp::hal`, and future RHI/Audio
   backends) require access to command-line flags (`gp::CommandLine`), standardized OS paths
   (`gp::platform::Paths`), and dynamic library loaders (`gp::platform::SharedLibrary`). If
   these utilities live inside `gp::application`, lower-level modules cannot use them without
   creating a cyclic dependency (`gp::core` $\leftrightarrow$ `gp::application`).
2. **Linker & Hot-Reloading Restrictions on OS Entry Points:** Operating system loaders require
   the native process entry point (`main` or `WinMain`) to reside in the final executable
   binary's `.text` segment. If the entry point is compiled inside `gp::application` and
   `gp::application` is built as a shared library (`.dll` / `.so`) to support editor/gameplay
   C++ hot-reloading, the linker fails to resolve the executable entry point.

## Decision

We partition engine bootstrapping and lifecycle management across three strictly ordered module
tiers: **`gp::core`** (Foundation), **`gp::application`** (Orchestrator), and **`gp::launch`**
(Static Bootstrapper Shell).

### 1. Module Dependency DAG & Responsibility Matrix

```text
   [ Game / Sandbox Executable ]
                 │
                 ▼  (Links STATICALLY)
        ┌─────────────────┐
        │   gp::launch    │  • EntryPoint (main / WinMain / GP_DECLARE_APPLICATION)
        └────────┬────────┘  • CrashHandler (SEH __try/__except & POSIX sigaction)
                 │
                 ▼  (Links Static or Shared)
        ┌─────────────────┐
        │ gp::application │  • Application & EngineLoop (Tick, FixedUpdate, FramePacing)
        └────────┬────────┘  • ModuleManager (Plugin lifecycle & hot-reload orchestration)
                 │
                 ▼  (Links Static or Shared)
        ┌─────────────────┐
        │    gp::hal      │  • IApplicationBackend, IWindow, IInputSystem, IDialog, IClipboard
        └────────┬────────┘
                 │
                 ▼  (Links Static or Shared)
        ┌─────────────────┐
        │    gp::core     │  • CommandLine, Paths, Environment, SharedLibrary, Thread, Memory
        └─────────────────┘

```

<!-- markdownlint-disable MD013 -->
| Subsystem | Target Module | Linkage Type | Architectural Justification |
| --- | --- | --- | --- |
| **`gp::CommandLine`** | `gp::core` | Static / Shared | Must be readable by `gp::core` allocators and `gp::hal` backends before `Application` exists. |
| **`gp::platform::Paths` & `Environment**` | `gp::core` | Static / Shared | Fundamental OS queries (`ExecutableDir`, `UserDataDir`, CPU/RAM telemetry) needed by all layers. |
| **`gp::platform::SharedLibrary`** | `gp::core` | Static / Shared | Low-level RAII OS handle (`LoadLibraryW` / `dlopen`) independent of engine plugin interfaces. |
| **`Application` & `ModuleManager**` | `gp::application` | Static / Shared | High-level runtime orchestrator and `IModule` registry; can be compiled as a `.dll`/`.so`. |
| **`EntryPoint` & `CrashHandler**` | `gp::launch` | **Strictly Static** | Must stamp `main`/`WinMain` and top-level SEH/signal guards directly into the host executable. |
<!-- markdownlint-enable MD013 -->

### 2. Architectural Invariants

1. **Strict Upward Dependency Rule:** `gp::core` must never include headers from or link against
   `gp::hal`, `gp::application`, or `gp::launch`. `gp::application` must never link against `gp::launch`.
2. **Static Linkage of `gp::launch`:** `gp::launch` is compiled strictly as a static library
   linked into final executable targets so `WinMain`/`main` is always visible to the OS loader.
3. **Top-Level Guarded Initialization:** `gp::launch` initializes `gp::crash::CrashHandler`
   and `gp::CommandLine::init()` prior to constructing the user's `gp::Application` subclass.

## Alternatives Considered

### Option A: Monolithic `gp::application` Module (Delete `gp::launch`)

Merge `EntryPoint`, `CrashHandler`, `CommandLine`, and `Paths` directly into `gp::application`.

**Why rejected:** Forces `gp::application` to be compiled as a static library so the linker can
find `WinMain`, preventing dynamic reloading of the application layer, and prevents `gp::core`
or `gp::hal` from reading command-line flags or OS paths.

### Option B: Header-Only Macro Entry Point (`#define GP_DECLARE_APPLICATION`)

Inline the entire OS entry point, SEH crash handler, and command-line setup inside a public header
macro without a `gp::launch` static library.

**Why rejected:** Requires including `<Windows.h>`, `<dbghelp.h>`, or `<signal.h>` inside a public
header included by user game code, polluting the global namespace and increasing compile times.

## Consequences

### Positive

* **Zero Circular Dependencies.** Every module in the engine can safely query `gp::CommandLine` and
  `gp::platform::Paths` from `gp::core`.
* **Hot-Reloading & Shared Library Readiness.** Keeping `gp::launch` as a lightweight static shell
  allows `gp::application` and gameplay modules to be compiled as dynamic libraries (`.dll`/`.so`).
* **Clean Platform Isolation.** OS-specific entry points (`WinMain`) and crash dump APIs
  (`MiniDumpWriteDump`, `sigaction`) remain encapsulated inside `gp::launch`'s private
  implementation files.

### Negative

* **Additional Build Target.** Maintaining `gp::launch` alongside `gp::application` and `gp::core`
  requires one extra target definition in the build scripts.
